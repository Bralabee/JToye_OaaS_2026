## Decisions Made

- **EXEMPT_TABLES contains 4 entries, not 2.** The plan-text mentioned `flyway_schema_history` and `processed_stripe_events`. During the first test run, the schema-walk caught two more tables that legitimately have no tenant column: `tenants` (the registry itself — V2 explicitly comments "you may manage tenants via privileged admin connection") and `revinfo` (Hibernate Envers' global revision metadata; tenant filtering happens in `*_aud` child tables, not on revinfo). Both were added with written justification, exactly per the LOCKED rule "if a table is intentionally not tenant-scoped, add it with a comment justifying."
- **SUPERUSER drop via SET LOCAL ROLE.** When the spam/mismatch/null-email tests were first wired up, the INSERTs SUCCEEDED instead of being blocked. Diagnostic probe revealed that the Testcontainers postgres:15 default user is `SUPERUSER` (with `rolbypassrls=false` after V2's NOBYPASSRLS pass). Postgres treats SUPERUSER as bypass-all-checks regardless of NOBYPASSRLS — so RLS WITH CHECK clauses never fire. Fix: provision a `rls_test_role` (NOSUPERUSER NOBYPASSRLS LOGIN) once via an idempotent DO block, then `SET LOCAL ROLE rls_test_role` for the duration of each test transaction. This is the canonical Testcontainers-RLS pattern and is documented inline.
- **`hasStackTraceContaining` over `hasMessageContaining`.** Spring's `BadSqlGrammarException` wrapper hides the root `PSQLException`'s "ERROR: new row violates row-level security policy" message. The plan's literal acceptance text said `hasMessageContaining("row-level security")`; replaced with `hasStackTraceContaining("row-level security")` so the matcher actually finds the diagnostic text in the wrapped chain. Documented inline.
- **`ddl-auto: none` override.** application-test.yml hardcodes `ddl-auto: create-drop`, which Spring Boot honours even when Flyway is enabled. Hibernate then recreates the schema AFTER Flyway runs and wipes all RLS state — which the first test run correctly diagnosed as "customers missing RLS." Override `spring.jpa.hibernate.ddl-auto = none` in `@DynamicPropertySource` so the Flyway-managed schema is the sole source of truth.
- **`queryForObject` over `update` for `set_config`.** `set_config(...)` is a SELECT statement that returns a row. `JdbcTemplate.update` rejects this with "A result was returned when none was expected." Inline `queryForObject(..., String.class)` was used to consume the result.
- **Helper bypass for `app.customer_email`.** `TenantSetLocalAspect`'s `@Before` advice on JdbcTemplate.* would reset `app.current_tenant_id` to TenantContext's value before any JdbcTemplate call. To set `app.customer_email` (which the aspect doesn't manage) without triggering aspect interference, the test uses `entityManager.unwrap(Session.class).doWork(c -> ...)` directly — same pattern as `PublicStorefrontService.getCustomerOrders` line 238.
- **Storefront wiring: NO change required.** Per 16.1-CONTEXT.md Item 4 verification ask, I confirmed that the production review-submit path (`ReviewService.createReview`) sets `TenantContext` to the resolved shop's tenant; `TenantSetLocalAspect` then issues `set_config('app.current_tenant_id', ?, true)` on the connection before the JPA INSERT. This fires the **app branch** of V35's policy. The customer-email branch is not currently exercised by any production code path — it exists for defense-in-depth (any future anonymous direct-INSERT path). The test exercises both branches to lock in the contract.

## Deviations from Plan

The plan's task skeletons were respected with these adaptations (none change behaviour, all maintain or improve test fidelity — none meet the criteria for Rule 1/2/3 deviations):

- **EXEMPT_TABLES expanded from 2 → 4** (added `tenants` and `revinfo`). Justified above. Each carries a written code-comment justification, exactly per the LOCKED rule.
- **`SET LOCAL ROLE rls_test_role` added** to each ReviewsRlsPolicyIntegrationTest method. Without this, the test cannot exercise RLS denial (SUPERUSER bypasses). Documented inline.
- **AssertJ matcher swapped** from `hasMessageContaining` to `hasStackTraceContaining`. The plan's literal text would have failed because Spring wraps the PSQLException. Documented inline.
- **`ddl-auto: none` added** to `@DynamicPropertySource`. Without this, Hibernate's create-drop wipes the Flyway-installed RLS state. Necessary for any Testcontainers test that asserts RLS state.
- **Helper `setCustomerEmailGuc(...)` uses Session.doWork** instead of JdbcTemplate so the `TenantSetLocalAspect` doesn't reset `app.current_tenant_id` between my GUC manipulation and the INSERT.

These are all test-infrastructure adjustments necessary to make the LOCKED design intent actually exercise the policy. Auto-fix Rule 3 (blocking issue: test infrastructure prevents the test from working) applies to the SUPERUSER fix and the matcher swap; both stayed inside the test class's scope.

## Issues Encountered

1. **Initial RlsContractTest run reported `customers` missing RLS.** Cause: application-test.yml's `ddl-auto: create-drop` recreated the schema after Flyway. Fixed by adding `spring.jpa.hibernate.ddl-auto = none` to the test's `@DynamicPropertySource`. Resolved on the second run.
2. **Initial ReviewsRlsPolicyIntegrationTest seed failed with "A result was returned when none was expected."** Cause: `JdbcTemplate.update("SELECT set_config(...)")` — `set_config` is a SELECT and `update()` doesn't accept rows. Fixed by switching to `queryForObject(..., String.class, ...)`.
3. **Then seed failed on `delivery_fee_pennies` NOT NULL.** V26 dropped the default. Fixed by supplying `0` explicitly in the seedShop INSERT.
4. **Then seed failed on `subtotal_pennies` NOT NULL.** V23 dropped the default. Fixed by supplying explicit values for `subtotal_pennies`, `vat_rate`, `vat_amount_pennies` in seedOrder.
5. **Then 3 of 5 RLS-denial tests reported INSERT succeeded when it should have been blocked.** Cause: the Testcontainers `test` PG user is SUPERUSER, and SUPERUSER bypasses ALL RLS regardless of NOBYPASSRLS / FORCE (as confirmed by a probe showing `rolsuper=true rolbypassrls=false`). Fixed by provisioning `rls_test_role` (NOSUPERUSER NOBYPASSRLS LOGIN) and using `SET LOCAL ROLE rls_test_role` in each RLS-sensitive test method.
6. **Then matcher failed: `BadSqlGrammarException` does not contain "row-level security" in its top-level message.** Cause: Spring wraps the PSQLException; the diagnostic lives on the cause. Fixed by switching the AssertJ matcher from `hasMessageContaining(...)` to `hasStackTraceContaining(...)`.

All 6 issues were detection-then-fix during normal test development — none required architectural changes (Rule 4) or escalation to a checkpoint.
