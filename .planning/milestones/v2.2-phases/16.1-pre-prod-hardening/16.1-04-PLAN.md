**Implementation note (TOCTOU-safe path):** CONTEXT.md `<decisions>` Item 3 LOCKED `INSERT ... ON CONFLICT DO NOTHING RETURNING event_id` via `JdbcTemplate`. The remediation/01 doc proposed an `existsByEventId` + `saveAndFlush` JPA pair which is NOT atomic — under concurrent webhook delivery there is a TOCTOU window between the `exists` check and the `save`. We pick the LOCKED path (single SQL statement, atomic in Postgres, no JPA entity needed for the guard).
</plan_header>

<objective>
Make `PaymentService.handleWebhookEvent` idempotent against Stripe retries (AUDIT-W0-03). Today every retry of `payment_intent.succeeded` re-runs `handlePaymentIntentSucceeded`, which double-writes `financial_transactions`, double-publishes the order state-change event, and double-fires the payment-succeeded event. Stripe retries successful webhooks if our handler is slow or returns 5xx, and retries failed webhooks for up to 72h, so this is a routine production path.

Fix: at the top of `handleWebhookEvent` (after signature verification, before the type switch), execute a single TOCTOU-safe `INSERT ... ON CONFLICT (event_id) DO NOTHING` against `processed_stripe_events`. If 0 rows affected, the event is a retry — log INFO and return.

Output:
- Modified `PaymentService.java` with a `JdbcTemplate` dependency (constructor-inject; no new entity/repo needed).
- New Testcontainers-backed integration test `StripeWebhookIdempotencyIntegrationTest`.
- No new entity, no new JPA repository — JdbcTemplate keeps the guard a single atomic SQL.
</objective>

    ```java
    @Transactional
    public void handleWebhookEvent(String payload, String sigHeader) {
        Event event;
        try {
            event = Webhook.constructEvent(payload, sigHeader, stripeProperties.getWebhookSecret());
        } catch (SignatureVerificationException e) {
            log.warn("Stripe webhook signature verification failed: {}", e.getMessage());
            throw new IllegalArgumentException("Invalid Stripe signature");
        } catch (Exception e) {
            log.error("Failed to parse Stripe webhook event", e);
            throw new IllegalArgumentException("Invalid webhook payload");
        }

        // AUDIT-W0-03 — TOCTOU-safe idempotency guard.
        // Single SQL statement: INSERT ... ON CONFLICT DO NOTHING is atomic in Postgres.
        // 1 row affected ⇒ first delivery, proceed.
        // 0 rows affected ⇒ duplicate retry, return early so side effects fire exactly once.
        // Runs INSIDE the @Transactional boundary so a downstream rollback ALSO rolls back
        // the dedup row — a subsequent retry will get a fresh shot at processing. This is
        // the desired semantic: dedup is "successfully processed at least once", not
        // "we saw this event-id once".
        int inserted = jdbcTemplate.update(
                "INSERT INTO processed_stripe_events (event_id) VALUES (?) ON CONFLICT (event_id) DO NOTHING",
                event.getId());
        if (inserted == 0) {
            log.info("Stripe event {} ({}) already processed — skipping", event.getId(), event.getType());
            return;
        }

        log.info("Received Stripe event: {} ({})", event.getType(), event.getId());

        switch (event.getType()) {
            case "payment_intent.succeeded" -> handlePaymentIntentSucceeded(event);
            case "payment_intent.payment_failed" -> handlePaymentIntentFailed(event);
            default -> log.debug("Unhandled Stripe event type: {}", event.getType());
        }
    }
    ```
