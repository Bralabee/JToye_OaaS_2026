**Made the `verify` order-number param mandatory on `GET /public/orders`, removed the dead opt-in branch so `trackOrder` runs unconditionally as proof-of-ownership, and locked the contract with 4 MockMvc regression tests — closing the trivial email-based order-enumeration vulnerability flagged by the 2026-04-27 council audit.**

## Accomplishments

- Closed AUDIT-W0-02: anonymous callers can no longer enumerate the order history of any known email via `GET /public/orders?email=victim@example.com`. Now requires both `email` AND a recent `verify` order-number; mismatch → 404 before any order data is returned.
- Two complementary 400-rejection paths consolidated under a single client surface: `@RequestParam(name="verify")` (no `required=false`) catches the absent case via Spring's `MissingServletRequestParameterException`; an explicit `isBlank()` guard throwing `ResponseStatusException(400)` catches the present-but-blank case (`?verify=`). Both return the same RFC 7807 ProblemDetail status to the client.
- Deleted the dead opt-in `if (verifyOrderNumber != null && !verifyOrderNumber.isBlank())` block entirely. `trackOrder(verify, email)` is now unconditional — the IDOR cannot be reintroduced via an "optional verify" code path because there isn't one.
- Updated the OpenAPI `@Operation` description to explicitly state that `verify` is mandatory.
- Locked the four required behaviours with `PublicStorefrontControllerIdorTest` (4 tests, ~140ms total): missing → 400, blank → 400, wrong verify → 404 (existing trackOrder ResourceNotFoundException flow), valid verify → 200 with the customer's orders.
- 11 pre-existing `PublicStorefrontControllerTest` cases continue to pass — no regression on `/public/shops/*`, `/public/orders/{orderNumber}`, or any other storefront endpoint.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug + Rule 2 - Missing critical functionality] GlobalExceptionHandler swallowed required-param + ResponseStatusException as 500**

- **Found during:** Task 1 GREEN phase (first run after controller change)
- **Issue:** The plan's controller change correctly raised `MissingServletRequestParameterException` (absent verify) and `ResponseStatusException(400)` (blank verify), but the existing `GlobalExceptionHandler.handleGenericException(Exception)` catch-all was matching both first and returning **HTTP 500** with `ProblemDetail{type=internal,title=Internal Server Error,status=500}`. This violated the LOCKED CONTEXT contract that "missing/blank → 400" — the IDOR was technically blocked, but the wire status was wrong, and any downstream client retry/alerting logic keyed on 5xx vs 4xx would have misclassified the event as a server fault.
- **Fix:** Added two specific `@ExceptionHandler` methods to `GlobalExceptionHandler`:
  - `handleMissingRequestParam(MissingServletRequestParameterException)` → 400 with `type=https://jtoye.uk/errors/missing-parameter`
  - `handleResponseStatusException(ResponseStatusException)` → preserves the embedded status code + reason via `HttpStatus.resolve(ex.getStatusCode().value())`, falling back to 500 if the status code is non-standard. This is general-purpose: it also fixes a latent bug where any prior code path raising `ResponseStatusException` would have been masked as 500.
- **Files modified:** `core-java/src/main/java/uk/jtoye/core/common/GlobalExceptionHandler.java` (+40 lines)
- **Commit:** `48c0914` (folded into the GREEN fix commit since it is the same logical change — without it the controller fix produces wrong status codes)
- **Scope justification:** This is in scope per Rule 1/2: my task's controller change DIRECTLY produces these exceptions, and they MUST surface as 400s per LOCKED contract. I did not touch any handler unrelated to my task's exceptions, and the `handleGenericException` fallback is unchanged.
