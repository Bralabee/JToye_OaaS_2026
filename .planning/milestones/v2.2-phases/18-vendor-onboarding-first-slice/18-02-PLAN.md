<objective>
Deliver the vertical submit slice: a vendor can create an onboarding (`DRAFT`), submit it (`DRAFT → VERIFYING`), and read its live status + per-gate breakdown — driven by an onboarding state machine that mirrors the Order triad and is the **sole writer of `Shop.published`**. This plan also stands up the data-driven gate-chain *registry* (`OnboardingGate` interface + `GateChainRunner`) that 18-03/04/05 plug concrete gates into with zero further edits here.

Purpose: make submit work end-to-end (HTTP → state machine → DB → HTTP) and lock the go-live authority into one guarded transition, so no caller can flip a storefront live outside the onboarding flow. The async gate recompute also **consumes `onboarding.auto-approve`**: when enabled, a fully-passing onboarding auto-advances `PENDING_APPROVAL → APPROVED` with no manual review, making the headline "go live without manual review" path reachable (DRAFT → VERIFYING → PENDING_APPROVAL → APPROVED, then the vendor's go-live in 18-05 → LIVE); the default (`false`, design-doc §9 open decision) leaves it at `PENDING_APPROVAL`.
Output: state-machine config/service, `VendorOnboardingService`, gate-chain registry + runner (with the auto-approve wiring), the onboarding controller + DTOs, `ShopService.setPublished`, and unit + integration proofs.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vendor client → /onboarding API | Untrusted request body; must not carry tenant_id or a caller-chosen published flag |
| onboarding flow → Shop.published | Only the guarded GO_LIVE/SUSPEND transition may change go-live visibility |
| request thread → @Async gate worker | TenantContext must be re-established or RLS writes silently fail/deny |
