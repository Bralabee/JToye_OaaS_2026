# Quick task: the KDS offline banner outlives its cause because one 429 discards a good refresh

Closes #561.

## The mechanism, measured — not the one the issue guessed at

#561 listed three candidate mechanisms and said none had been run. It is **(3), the
product-side one**, and the trigger is not what the title suggests.

`fetchOrders()` on the full (non-incremental) path issues **1 list request + one
`/detail` request per active ticket**. `Brixton Village Grill` — the board the E2E vendor
lands on — has **18 active tickets**, so that is **19 concurrent requests**, fired as a
single `Promise.all`.

The `online` handler (`kitchen/page.tsx:379`) deliberately takes that full path on
recovery, so an offline blip produces **19 + 19 = 38 requests inside ~400 ms**.

The tenant limiter is `Bandwidth.capacity(120).refillIntervally(100, 1 min)` — one lump
per minute, so **whatever else the tenant spent in the same 60 s window is carried
state**. That is precisely "state left by the specs that ran first", which is where #561
correctly stopped.

Two arms, captured from Playwright traces against the live Compose stack (2026-08-05):

| arm | `/api/v1/orders*` | statuses | lowest `X-RateLimit-Remaining` | `:339 [mobile]` |
|---|---|---|---|---|
| `kitchen-flow.spec.ts` alone | 38 (19 + 19) | **38 × 200** | **79** | PASS |
| after the 3 mobile specs that precede it | 38 (19 + 19) | 28 × 200, **10 × 429** (`Retry-After: 12`) | **0** | FAIL |

Identical request pattern; the only difference is the tenant's remaining token budget.

`fetchKitchenOrderDetails` uses `Promise.all`, so those ten 429s **reject the whole
read** — including the list request that succeeded and the eight details that succeeded.
`fetchOrders`'s `catch` sets `syncFailed = true`, `deriveFeedState` returns
`status: "error"`, `alerting` stays true, and the banner never clears. Nothing retries:
the trace shows **zero further requests** for the remaining ~20 s, because the next
attempt is the 60 s poll.

**What this means in a kitchen**, which is why it outranks a red test: a board that went
offline for a moment keeps announcing *"Orders are not refreshing"* for up to a minute
after the network is back, **while holding completely current data**. The test's own
comment already named the cost — *"A warning that outlives its cause is how a kitchen
learns to ignore warnings."*

## Tasks

- **T1 — a regression test that forces the condition instead of inheriting it.**
  Intercept a subset of `/api/v1/orders/*/detail` and return a real 429, then assert the
  banner clears anyway. Suite-ordering is not a test contract; this must fail for the
  stated reason on the current build and pass after. Run the fail direction FIRST and
  record its real output.
- **T2 — `frontend/lib/kitchen-orders-api.ts`:** `fetchKitchenOrderDetails` moves from
  `Promise.all` to `Promise.allSettled` and reports which orders failed, rather than
  discarding every success when one request fails.
- **T3 — `frontend/app/dashboard/kitchen/page.tsx`:** treat the read as successful
  (advance `lastSyncedAt`, clear `syncFailed`) when the list read succeeded **and every
  active order ended up with a detail, fresh or held**. The board already falls back to
  `held.get(o.id)`, so a partial failure still renders a complete board.
  **Keep `syncFailed = true` when the list read threw, or when some active order has no
  detail at all** — an incomplete board must still say so. That invariant is not traded away.
- **T4 — verification.** New test both directions; repro arm green **with the 429s still
  present in the trace** (that is what proves 429-*intolerance* was the cause, not the
  429s); control arm still green; jest + `npm run build` (the tsc gate — jest does not
  type-check); `scripts/docs-freshness.sh --write`.

## Explicitly not done

- **Not** raising the 20 s timeout in the spec. A longer wait over a broken clear
  condition is a green test over a dead feature, and #561 says so.
- **Not** disabling or loosening the rate limiter.
- **Not** bounding the detail-fetch concurrency. It would reduce 429s and is worth
  considering, but it changes board-refresh latency and is a separate decision — recorded
  as a follow-up rather than smuggled in here.
