# Quick 261025-8p7: a stale card draft's PaymentIntent is cancelled before its order is deleted (issue #1038) Summary

The 03:00 UTC stale-draft job now cancels a card draft's Stripe PaymentIntent (as `abandoned`, with an
Idempotency-Key, on the vendor's connected account for direct-charge routing) with no transaction open. It deletes
the order only after Stripe reports the intent canceled and a re-read in its own short transaction shows it is
still the same DRAFT. Drafts with money on them, or where anything is in doubt, are kept with a
`WARN event=stale_draft_kept`. Drafts with no payment are deleted exactly as before.

## Deviations from Plan

**1. [Rule 1 - Bug] NULL paymentStatus with no reference is deleted as no-payment, not kept.**
- **Found during:** Task 1 GREEN.
- **Issue:** `orders.payment_status` is nullable (V22 adds it with `DEFAULT 'NONE'`, no NOT NULL). Design 1, read
  literally ("reference null AND status NONE"), would keep such a legacy row for ever and WARN every night. That
  would silently break R-1 for a row that has no Stripe object at all.
- **Fix:** `isNoPaymentStatus` treats NULL like NONE. `noPaymentDraft_isDeletedWithoutAskingStripe` gained the
  NULL-status draft, plus a check that `directChargeAccountFor` is never called. The test still passes pre-fix by
  design, and arm A turns it red.
- **Files:** ScheduledCleanupService.java, ScheduledCleanupServiceTest.java. The test file change rode in GREEN
  commit 55071c62.

**2. [Rule 3 - Blocking] The IT's `Container.ExecResult` was fully qualified.** Importing
`org.testcontainers.containers.Container` clashes with the `@Container` annotation import.

**3. Arm B shape.** The plan allowed "delete before calling Stripe, OR regardless of the returned status". I used
the first form. Under the second, the money-moved tests would stay green, because Phase C's re-read on an
unstubbed `findById` returns empty and keeps the draft. The first form reds every named test.

Otherwise the plan was executed as written.
