<objective>
Stop `ScheduledCleanupService.cleanupStaleDraftOrders` from deleting a storefront card DRAFT while its Stripe
PaymentIntent is still payable (issue #1038, observed on staging 2026-10-24: 7 intents in
`requires_payment_method` whose orders had been deleted). From now on, a card draft's intent is cancelled at
Stripe first, and the order is deleted only once Stripe says the intent is canceled. Every draft with money
on it, or in doubt, is kept and retried at the next run.

Purpose: if a customer completes an orphaned intent, Stripe captures money for an order that does not exist, and
the kitchen sees nothing. The fix also keeps the published R-1 promise (abandoned checkouts deleted after 24 h) for
card drafts, which today get deleted while their intent is still payable.
Output: two PaymentService methods, the reworked cleanup, the unit matrix, the NOSUPERUSER IT arm, the
canceled-webhook pin, recorded RED/GREEN and break-arm evidence, updated R-1 note and yml comment, regenerated
metrics, and a CHANGELOG entry.

The design comes from the orchestrator (owner said "fix #1038"). It is planned as written, with ONE refinement that
the code forces:

- Design 1: a stale DRAFT with paymentReference null AND paymentStatus NONE is deleted exactly as today.
- Design 2: a stale DRAFT carrying a pi_ reference is retrieved and cancelled at Stripe FIRST and OUTSIDE the
  per-tenant DB transaction. Cancelable-and-unpaid statuses are requires_payment_method, requires_confirmation and
  requires_action. The order is deleted only when Stripe reports canceled (or it already was), in its own short
  transaction, after a re-read. The Stripe call is a new `@CircuitBreaker(name = "stripe")` method in PaymentService.
  REFINEMENT, with the reason: only the Stripe NETWORK call runs outside a transaction. The direct-charge routing
  (`StripeConnectService.resolveSettlementRouting(Order)`, the `retrieveClientSecret(Order, String)` pattern) is
  resolved INSIDE the tenant-pinned read transaction and carried out as a plain account id. That method reads
  `shops` and `vendor_onboarding` under FORCE RLS. Its `@Transactional(readOnly = true)` overload is
  self-invoked from the Order overload, so it opens no transaction. TenantSetLocalAspect sets the tenant only
  inside a transaction (measured; see the comment in ScheduledCleanupServiceIntegrationTest.draftCountFor). Outside
  a transaction, the routing would resolve empty for every connected-account vendor. Each direct-charge intent
  would then be retrieved on the platform account (404 resource_missing) and its order kept for ever, so R-1 would
  silently break for exactly the vendors Phase 30 routes to their own accounts.
- Design 3: succeeded, processing and requires_capture are kept with a WARN. Stripe error, open circuit and
  Stripe-not-configured are kept with a WARN and retried next run. A non-pi_ reference, or a paymentStatus other
  than NONE without a pi_ reference, is kept with a WARN. The code measured at planning time writes only pi_
  references: PublicStorefrontService:1581 and OrderPaymentLinkService:168 both store
  `PaymentIntentResult.paymentIntentId()`, and `plink_` appears nowhere in core-java/src/main. The non-pi_ branch is
  the safe default for anything future, not a live path.
- Design 4: R-1 keeps 24 (do NOT change the value). The manifest `note` and the yml comment gain a sentence. The
  published page `frontend/app/legal/retention/page.tsx` is NOT edited (reasoning in Task 2).
- Design 5: measured at planning time, `PaymentService.handleWebhookEvent` has no `payment_intent.canceled` case.
  The event falls to `default -> log.debug("Unhandled Stripe event type")` after the dedup INSERT and returns
  normally. No fix is needed; Task 1 pins it with a unit test so a future handler cannot turn cancel-then-delete
  into a 500 loop.

Planner decisions (discretion, recorded):
- `cancelAbandonedPaymentIntent(String paymentIntentId, String connectedAccountId)` returns the Stripe status
  String after the call. The cleanup deletes only on `PaymentService.STRIPE_STATUS_CANCELED` ("canceled"). A
  String keeps the Mockito stubs in both test classes trivial. The cleanup treats any value it does not recognise
  as keep.
- The cancel carries an Idempotency-Key, `abandonedIntentCancelIdempotencyKey(id)` = "abandoned-draft-cancel-" +
  id. It is package-private and asserted against the production expression, exactly like `intentIdempotencyKey`.
  The reason is the AGENTS.md oaas-money rule 2 (every mutating Stripe call rides a key). The one cost is that
  Stripe replays a stored failed result for the same key for up to about 24 h. The only effect is that the draft
  stays one more run (keep is the safe direction), and nothing can be deleted because of it.
- `requires_capture` is never cancelled: cancelling would release an authorised hold the shop may still capture;
  the webhook owns that order.
- The shared "stripe" breaker (sliding window 10, 50%, 30 s open) can be opened by cleanup failures at 03:00 UTC,
  refusing checkouts for 30 s. Accepted and recorded, T-8p7-04. The breaker name stays as the design states.
- Out of scope, named so nobody widens the diff: the 7 already-orphaned staging TEST intents have no order left for
  this job to find, so cancelling them is plan 30-09's re-routed `cancel-drafts` work. Issue #1031 (a server
  CANCEL leaves the intent payable) is a separate issue. `retrieveClientSecret(Order, String)` is left unchanged,
  and the new helper's Javadoc cross-references it. The pre-existing approximation on the published retention
  page (a daily 03:00 job deletes "24 hours after you start it" up to about 48 h) is recorded in the SUMMARY under
  "Observations for the owner"; the orchestrator decides whether it is filed.
