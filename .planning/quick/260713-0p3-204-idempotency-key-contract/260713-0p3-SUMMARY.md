# Quick Task 260713-0p3: Uniform Idempotency-Key Contract (#204 / AI-2) Summary

**A generic, tenant-scoped `Idempotency-Key` HTTP header contract (V50 `idempotency_keys` + `IdempotencyService.execute`) that closes the duplicate-order gap: a retried `POST /api/v1/orders` (and `/customers`) now replays the original response and mints zero duplicate rows, with the store's PII isolated under FORCE RLS.**

## Accomplishments
- Added the `idempotency_keys` store (V50) — composite PK `(tenant_id, endpoint, idempotency_key)`, ENABLE+FORCE RLS, no `_aud` — mirroring the V47 precedent.
- Built `IdempotencyService.execute`: reserve-first `INSERT ... ON CONFLICT DO NOTHING` + replay + complete in one transaction, with a defensive `set_config('app.current_tenant_id')` GUC pin before any raw-JdbcTemplate store access.
- Wired `orders.create` + `customers.create` to the contract via `@Idempotent`; advertised the header in OpenAPI on exactly those ops through a springdoc `OperationCustomizer`.
- Proved the behavior end-to-end under Testcontainers: same-key replay (1 row), the concurrent same-key race (exactly 1 order, no 500), 422 on payload mismatch, and cross-tenant RLS enforcement under the NOSUPERUSER `rls_test_role` downgrade.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Duplicate `Idempotency-Key` OpenAPI parameter**
- **Found during:** Task 3 (OpenAPI snapshot regen)
- **Issue:** springdoc auto-documented the raw `@RequestHeader` method param AND the `IdempotencyHeaderCustomizer` added its own — so the header was listed twice (one bare, one rich) on each op.
- **Fix:** annotated the `@RequestHeader` param with `@Parameter(hidden = true)` in both controllers so only the customizer's documented parameter (description + `maxLength: 64`) is advertised.
- **Files modified:** `OrderController.java`, `CustomerController.java`
- **Commit:** `102c0db`

**2. [Rule 1 - Bug] Order integration-test isolation (count(*) pollution)**
- **Found during:** Task 3 (first integration run — 2 failures)
- **Issue:** the order test seeded a shared shop per `@BeforeEach` (idempotent reuse), so `SELECT count(*) FROM orders WHERE shop_id = ?` counted orders from sibling test methods on the same container (expected 1, saw 2/3). The idempotency mechanism was correct; only the assertion's scope was polluted.
- **Fix:** each test method now seeds a fresh shop+product (unique slug/SKU), isolating the count assertion.
- **Files modified:** `OrderIdempotencyIntegrationTest.java`
- **Commit:** `102c0db`

### Constraint-driven adjustment

Imports in `GlobalExceptionHandler` and `IdempotencyService` adjusted accordingly. The PLAN's `files_modified` listed these under `common.idempotency`; they were relocated by design.
