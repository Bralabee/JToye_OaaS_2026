<objective>
Add a uniform, tenant-scoped `Idempotency-Key` HTTP header contract across mutating endpoints (issue #204 / AI-2), and adopt it for the two paths the ACs require: `POST /api/v1/orders` (dashboard/authenticated) and `POST /api/v1/customers`. The mechanism is a generic dedup store (`idempotency_keys`, V50) keyed `(tenant_id, endpoint, idempotency_key)`, mirroring the V47 `processed_order_events` precedent (ENABLE+FORCE RLS, reserve-first `INSERT ... ON CONFLICT DO NOTHING`, no `_aud` mirror). A repeated key replays the ORIGINAL response (status + body) and never mints a duplicate row; a concurrent same-key race yields exactly one row; a same-key-different-payload is rejected 422; cross-tenant isolation of the store is proven under a NOSUPERUSER role (the store's response_body carries real PII - customerName/Email/Phone).

Purpose: today `POST /api/v1/orders` (dashboard) is not idempotent at all - a retried POST mints a duplicate order. Refunds have a bespoke, entity-local header dedup and guest checkout has a body-level key; neither generalizes. This slice gives the platform one reusable, one-annotation-cheap contract and closes the highest-risk duplicate-order gap.

Output: V50 migration + a generic `IdempotencyService`, the `@Idempotent` annotation, RFC 7807 409/422 mappings, an OpenAPI OperationCustomizer, orders+customers wired to the contract, a committed audit doc, and Testcontainers proof including the concurrent race AND a cross-tenant RLS-enforcement test.
</objective>

<architecture_decision>
DECIDED (from the coupling sweep): idempotency orchestration lives in a NEW
`@Transactional IdempotencyService.execute(...)` invoked from the CONTROLLERS.
The create SERVICES (`OrderService.createOrder`, `CustomerService.createCustomer`)
and their CONSTRUCTORS are left UNTOUCHED. Rationale:

1. `OrderServiceTest` and `CustomerServiceTest` are Mockito unit tests
   (`@ExtendWith(MockitoExtension.class)` + `@InjectMocks`) with 25+ direct
   `createOrder(request)` / `createCustomer(request)` calls. Changing either
   service constructor or the `create*` signature would break them all.
2. The reserve INSERT MUST join the create's transaction so a failed create
   rolls the key back ("at-least-once" per V47; research pitfall #2). Because
   `IdempotencyService.execute` is `@Transactional` and calls the class-level
   `@Transactional` `orderService.createOrder` (Propagation.REQUIRED joins the
   outer tx), the reserve -> create -> complete all commit/rollback together on
   ONE connection. Do NOT use REQUIRES_NEW for the reservation.
3. We deliberately do NOT capture the servlet response with a HandlerInterceptor
   + ContentCachingResponseWrapper (research "Opt-in" section): it would need
   SSE-stream and RFC-7807-error exclusion and cannot join the create tx.
   Storing the serialized DTO inside the tx (as Refund/Order already do) is
   house-consistent and the research's explicit recommendation.

RLS GUC - BELT AND BRACES (RESEARCH pitfall #1 is the #1 trap, and this codebase
already shipped one live RLS-hiding bug on exactly the "the aspect will set it"
assumption - the OrderStateChangeListener N1 fix): `TenantSetLocalAspect`
(security/TenantSetLocalAspect.java:43-44) has a `@Before execution(*
JdbcTemplate.*(..))` pointcut that sets the GUC from `TenantContext` when a real
transaction is active, and in the web-request path `JwtTenantFilter` populates
`TenantContext` before interceptors/controllers run - so the aspect SHOULD cover
the store's JdbcTemplate calls. But aspect ordering is untested for this new
path, so IdempotencyService.execute MUST ALSO issue an explicit defensive
`SELECT set_config('app.current_tenant_id', ?, true)` at the top of its
transaction, mirroring OrderStateChangeListener.java:83-90. Trivial cost,
removes the entire class of silent-RLS-hide failures.

RLS TESTING CAVEAT (IntegrationTestSupport class javadoc): the Testcontainers
bootstrap role is a Postgres SUPERUSER, which bypasses even FORCE ROW LEVEL
SECURITY. Behavior tests (replay/race/422) may run as-is, but any claim about
RLS ENFORCEMENT is only real under the NOSUPERUSER downgrade pattern - the
house precedents are ShopPromotionsRlsPolicyIntegrationTest (dedicated
`rls_test_role` NOSUPERUSER NOBYPASSRLS LOGIN + `SET LOCAL ROLE` per tx,
STATE.md decision line 123), ReviewsRlsPolicyIntegrationTest,
VendorOnboardingRlsIntegrationTest, ScheduledCleanupServiceIntegrationTest,
ShopImageCrossTenantIntegrationTest.
