<objective>
Fix issue #771. A review's `photoUrls` come from the client and are never checked. GDPR erasure then physically deletes every one of them from Blob, under the erasing tenant. So a customer with a COMPLETED order can name the shop's own catalogue images on a review, file an erasure, and destroy the vendor's product and shop images, including ref-counted media_asset derivatives.

Two guards, one rule:
1. **Erasure (load-bearing, per the orchestrator).** Rows already in the database may carry vendor URLs, and a creation-time check does nothing for them. Erasure deletes an object only if both of these hold:
   - (a) its key is `<erasing tenant>/reviews/<that review's orderId>/<one plain name>`. This is an ALLOW-list, so it fails closed.
   - (b) no product, shop or media_asset row in the tenant references it. This is an independent second layer.
   Everything else is detached from the review but kept, and counted at WARN.
2. **Creation.** `ReviewService.createReview` applies the same rule and refuses anything else with a typed RFC 7807 400.

Purpose: a customer action can never destroy a vendor's catalogue, or another customer's review photo. The Article-17 record still claims only deletions that happened.

- `ReviewPhotoKeys` (the one rule);
- `StorageService.publicKeyOf` (the one URL-to-key parse);
- the erasure allow-list and the catalogue reference check;
- creation validation with a typed 400;
- NOSUPERUSER + Azurite integration arms F and G, shown RED first and then proven with six break arms;
- updated unit tests, green doc gates and a CHANGELOG entry.

No migration.

## Design decisions taken by the planner (Claude's discretion — the executor implements them as written)

- **DD-1: one rule, one owner.** New final utility class `uk.jtoye.core.review.ReviewPhotoKeys`.
  - `prefix(UUID tenantId, UUID orderId)` returns `tenantId + "/reviews/" + orderId + "/"`.
  - `isReviewPhotoKey(String key, UUID tenantId, UUID orderId)` is true iff the key starts with that prefix AND the remainder is ONE plain name matching `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`. A leading alphanumeric excludes `.` and `..`. The character class excludes `/`, `?`, `#`, `%` and `\`.
  - Its Javadoc is the contract for any future review-photo upload path: store at `prefix(tenant, orderId) + <random uuid>.<ext>`.
  - Binding to the ORDER, not only the tenant, closes the cross-customer variant: customer X naming customer Y's review photo. `orderId` is unique per review (`existsByOrderId`).
- **DD-2: one URL-to-key parse.** Add `public Optional<String> publicKeyOf(String url)` to StorageService.
  - It returns the key `delete(url)` would address: the text after `publicUrl + "/"`, or empty for null, blank or external input.
  - Refactor `delete(url)` to take its key from `publicKeyOf`, behaviour-identical. The existing StorageServiceTest delete tests (`:248-315`) and the storage/product integration tests prove that.
  - Classification and deletion then cannot disagree about a URL.
- **DD-3: the erasure allow-list is the load-bearing guard** (orchestrator point 1).
  - While collecting each review's URLs inside the transaction, a URL goes forward for post-commit deletion only if both hold:
    - `publicKeyOf(url)` is present;
    - `ReviewPhotoKeys.isReviewPhotoKey(key, tenantId, review.getOrderId())` is true.
  - Everything else is RETAINED: not deleted, but still detached from the review, since `setPhotoUrls(null)` is unchanged.
  - This is an allow-list because deny-list guards fail open (memory trap_denylist_guard_fails_open). It covers rows planted before this fix, which is why arm F seeds its review by SQL and bypasses the creation path.
- **DD-4: catalogue reference check, an independent second layer** (orchestrator point 1).
  - New Spring Data native query on `MediaAssetRepository`: `long countCatalogueReferences(@Param("tenantId") UUID tenantId, @Param("objectKey") String objectKey)`. It returns the total number of references to that key, summed across:
    - `products.image_url`;
    - any element of `products.additional_image_urls`;
    - `shops.logo_url`;
    - `shops.banner_url`;
    - `media_asset.object_key` (exact match);
    - the media_asset thumbnail sibling, mirroring `thumbnailKeyFor` exactly.
  - Every table clause carries an explicit `tenant_id = :tenantId` predicate, and the aspect pins the GUC.
  - A stored URL references key k when, after stripping any `?` query and `#` fragment, it ends with `/` + k or equals k. That makes the match independent of host and base URL.
  - Excluded, with reasons recorded in the Javadoc:
    - the `_aud` tables: history, not live references;
    - other tenants' rows: erasure runs under the erasing tenant's RLS, and a foreign hotlink is display-only, so it gets no veto;
    - `product_media`: it carries no key; its asset's `object_key` is checked.
  - No `::` cast anywhere in the native query string; use `CAST(... AS ...)`.
  - A candidate is deletable only if it passes DD-3 AND the count is 0. The code may skip the query when DD-3 already refused. Break arm 1 then forces DD-3 open, which is the proof that this layer alone protects every catalogue column under real RLS.
  - Policy for a review-path key the catalogue references: RETAIN it. A delete would break a live catalogue image, the #771 harm; see T-771-03.
- **DD-5: WR-02 stays honest with no schema change** (orchestrator point 1, last sentence).
  - `photos_deleted` keeps counting only objects the store removed. Retained objects are never counted, because they are not deletions.
  - The in-transaction erasure INFO log reports four numbers: URLs detached, URLs eligible for post-commit deletion, retained as not this review's photo, retained as referenced by the catalogue. When either retained count is above 0, it also logs a WARN with both counts and the record id.
  - Logs carry no URLs and no email.
  - No new column and no V68. The record never over-claims, and every retained object is either catalogue content or not provably the subject's upload, since no upload path has ever written review photos.
  - `ErasureOutcome` and `GdprController.ErasureResponse` are unchanged, so there is no OpenAPI diff.
- **DD-6: creation validation** (orchestrator point 2).
  - In `ReviewService.createReview`, after the existing order checks and before the Review is built, each entry of `request.getPhotoUrls()` must be non-null and satisfy `publicKeyOf(url)` plus `isReviewPhotoKey(key, shop.getTenantId(), request.getOrderId())`.
  - The first failure throws the new `uk.jtoye.core.exception.InvalidReviewPhotoException` (a RuntimeException). `GlobalExceptionHandler` maps it to 400, title "Invalid Review Photo", type `https://jtoye.uk/errors/invalid-review-photo`.
  - The detail names the index (for example `photoUrls[2]`) and the rule shape `<tenant>/reviews/<orderId>/<name>`, and NEVER echoes the submitted URL.
  - `null` and `[]` stay accepted; the value is stored exactly as today.
  - Object existence is not checked. There is no upload path yet, and a key naming a missing object renders a broken image and can only ever delete itself.
  - 400 rather than 422 matches the sibling review refusals and the orchestrator's guidance.
- **DD-7: displaced goods** (Incremental Betterment Doctrine, orchestrator point 2). Stated plainly: **in practice, no non-empty photoUrls value is accepted today**, because nothing yet writes under `<tenant>/reviews/<orderId>/`.
  - Displaced: an API caller could attach any URL, external or platform, and the storefront rendered up to three of them. Why the replacement is strictly better:
    - that path let any submitter place third-party images (tracking pixels, unrelated content) on a vendor's public storefront;
    - it let a submitter arm the #771 deletion;
    - it has no first-party client: the frontend never POSTs a review, the MCP server has no review tool, and the seeder writes no photos.
  - Preserved:
    - reviews with a rating and a comment, unchanged;
    - existing rows, which keep rendering exactly as before (no migration, no backfill);
    - erasure still detaches every URL from the review;
    - erasure still deletes a genuine review photo (arm F positive control).
  - Lost: erasure no longer deletes own-tenant objects outside the review's order path. None of those can be a customer upload, so the only capability lost is the defect itself.
- **DD-8: contracts and runtime.**
  - CreateReviewRequest is untouched, so there is no OpenAPI snapshot change. `OpenApiSnapshotTest` in the full integration suite proves the shape is unchanged, and the runtime snapshot gate is unaffected.
  - The new constraint reaches machine clients as a stable RFC 7807 type.
  - MCP: N/A. Creating a review is a customer storefront action and no review tool exists.
  - Web-perf, SEO and client-persisted identity: N/A, no page or client-state change.
  - No migration (orchestrator point 5): nothing needed one.
  - The dev runtime is NOT rebuilt: it would then run unreviewed, unmerged code, and the orchestrator rebuilds after merge. Runtime parity is therefore NOT claimed. The end-to-end proof for this change is the real-Postgres, real-Azurite, real-Spring-context integration arms.
