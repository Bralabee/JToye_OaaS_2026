<objective>
Fix the image uploader so a vendor uploading a normal large phone photo (12-20MB) succeeds
with no visible quality loss, instead of being rejected by a misleading pre-compression gate.

Today `frontend/components/ui/image-uploader.tsx:142` rejects any file over 10MB BEFORE
`compressImage()` runs, with the self-contradicting message "File too large. Maximum 10MB
(will be compressed before upload)". The canvas pipeline that would have shrunk the file
never gets a chance. The authoritative server cap is 5MB (core-java multipart max-file-size
5MB / storage.max-file-size-bytes 5242880) and is correct — this is a frontend-only fix.

Purpose: Vendors must be able to upload real phone photos. The compression pipeline exists;
it just runs in the wrong order relative to the size gate.

Output:
- Reordered pipeline: browser-safety preflight (50MB) -> compress -> enforce 5MB server cap.
- Non-transparent PNG -> JPEG conversion + JPEG quality step-down for stubborn files.
- GIF-specific honest hard limit (canvas cannot preserve animation).
- Honest error copy everywhere.
- Jest coverage of the new gate order; docs/metrics.json resynced.
</objective>

  <action>
Rewrite the validation and compression logic. Keep the exported `ImageUploader` component
signature and props identical (consumers products/page.tsx and shops/page.tsx must not break).

Add named constants near the existing MAX_DIMENSION/JPEG_QUALITY:
- `SERVER_MAX_BYTES = 5 * 1024 * 1024` with a comment noting it mirrors the authoritative
  core-java cap (application.yml multipart max-file-size 5MB / storage.max-file-size-bytes
  5242880). Do NOT touch the server.
- `BROWSER_SAFETY_MAX_BYTES = 50 * 1024 * 1024` with a comment: guards the canvas decoder
  from absurd files only; this is NOT the upload limit.
- `JPEG_QUALITY_LADDER = [0.85, 0.75, 0.65]` (reuse JPEG_QUALITY=0.85 as the first rung).

Export these PURE, DOM-free helper functions (needed so jsdom can unit-test them — no canvas,
no Image, no URL API inside them; they read only file.type / file.size / numbers):
- `validateFileType(fileType: string): string | null` — returns the existing invalid-type
  error string or null. Allowed: image/jpeg, image/png, image/webp, image/gif.
- `preflightSizeGate(file: { type: string; size: number }): string | null` — the NEW door gate
  that replaces the old 10MB check. Rules: (a) if `file.type === "image/gif"` and
  `file.size > SERVER_MAX_BYTES`, return a GIF-specific honest message explaining animated GIFs
  cannot be compressed without losing animation, so the 5MB limit is firm for GIFs; (b) else if
  `file.size > BROWSER_SAFETY_MAX_BYTES`, return an honest browser-safety message that names the
  50MB cap and does NOT promise compression it cannot deliver; (c) otherwise return null.
  A normal 12-20MB photo MUST pass (return null).
- `chooseEncoding(fileType: string, hasAlpha: boolean): { type: string; qualities: number[] }` —
  pure encoding policy. GIF -> { type: "image/gif", qualities: [] } (no re-encode). PNG WITH
  alpha -> { type: "image/png", qualities: [] } (lossless, keep PNG). Everything else — JPEG,
  WebP, and NON-transparent PNG -> { type: "image/jpeg", qualities: JPEG_QUALITY_LADDER }.
- `enforceServerLimit(sizeBytes: number): string | null` — returns null if
  `sizeBytes <= SERVER_MAX_BYTES`, else an honest message that compression could not get the
  image under 5MB and the user should try a smaller image.

Add an internal (not necessarily exported) `hasAlphaChannel(ctx, w, h): boolean` that samples
the 2D canvas ImageData and returns true if any pixel alpha byte is < 255. This is the alpha
detection required to decide PNG-keep vs PNG->JPEG. It is canvas-dependent, so it stays internal.

Rewrite `compressImage(file)` as the canvas orchestrator using the above policy:
- GIFs reaching here are already <= 5MB (preflight rejected larger). Return the original File
  unchanged so animation is preserved.
- Load the image, compute target dimensions honoring MAX_DIMENSION=1600 and NEVER upscaling
  (only shrink when w or h exceeds MAX_DIMENSION; otherwise keep native size).
- Draw to canvas, then for PNG determine `hasAlpha` via hasAlphaChannel; call chooseEncoding.
- If the chosen plan has an empty qualities list (transparent PNG), encode a single PNG blob.
- Otherwise iterate JPEG_QUALITY_LADDER, encoding via canvas.toBlob at each quality; stop at the
  first result whose size <= SERVER_MAX_BYTES. If none fit, return the smallest produced (the
  lowest-quality rung) — do NOT upscale or raise dimensions to try harder; let handleFile's
  enforceServerLimit reject it honestly.
- Rename the output file extension to match the chosen type (.jpg for JPEG, .png for PNG).
  Keep the toBlob-null fallback returning the original file.

Rewrite `handleFile` to run the pipeline in this exact order and set errors via setError:
  1. validateFileType(file.type) -> if non-null, setError and return.
  2. preflightSizeGate(file) -> if non-null, setError and return. (This replaces the old
     `file.size > 10 * 1024 * 1024` block entirely — delete that block and its message.)
  3. Existing dimension validation (loadImage + min-dimension check) unchanged.
  4. Show preview, set uploading state (as today).
  5. const compressed = await compressImage(file).
  6. const overLimit = enforceServerLimit(compressed.size); if non-null: setError(overLimit),
     clear preview, set uploading false, and RETURN WITHOUT POSTING (do not send an oversized
     multipart the server will 413/reject).
  7. Otherwise proceed with the existing FormData POST of `compressed`.

Sweep the whole file for misleading copy: remove any "Maximum 10MB" / "will be compressed
before upload" text. Every user-facing size message must be honest about what actually happens.
Do NOT place code fences in comments; keep comments as prose.
