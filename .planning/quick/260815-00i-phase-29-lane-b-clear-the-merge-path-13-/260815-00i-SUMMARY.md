## 5. The DEF-29-5 decision, stated rather than assumed

`k8s/base/configmap.yaml:16` was
`"http://keycloak.jtoye-infrastructure.svc.cluster.local:8080"` — a Service in a namespace
this repository does not create. It is now **`"http://keycloak:8080"`**.

**Short name, NOT an FQDN, and here is why.** The target namespace is owned by each overlay
and never by the base — `k8s/base/kustomization.yaml:5-8` records the reason a base cannot
own it (a base shipping every environment namespace collapses each overlay's `namespace:`
transformer into an ID conflict). Therefore **no single FQDN can be correct for both
staging and production**: an FQDN would have to be patched per overlay for no gain, while
the same-namespace short name resolves correctly in every overlay by definition.

**The Service is real and rendered by this repo** — name `keycloak`, `type: ClusterIP`,
port `8080`, at `k8s/base/keycloak/keycloak-deployment.yaml:412-435`. That file's own
contract comment at `:421` already asserted *"app-config keycloak.admin.base-url points at
keycloak:8080"* — **a claim that was false the day it was written and is true as of this
commit**.

**Behaviour dimension:** `keycloak.admin.enabled` is `"false"` in the base ConfigMap
(line 15), so the value is inert until an operator enables deprovisioning (#102). This
changes what happens the **first time it is enabled** — from "host does not resolve" to
"the in-cluster Keycloak". `k8s/local` overrides the key at
`k8s/local/configmap-patch.yaml:97` (`http://host.minikube.internal:8085`), so the local
render is untouched; LOC-1 still passes asserting it by key name
(`LOC-1 OK (8 keys shimmed by name, 9 render occurrence(s))`).

**`redis.host` (line 262) deliberately NOT touched** — D-09 moved Redis to a managed
endpoint addressed by `ipBlock` and staging patches the host in its own overlay. A
same-shaped edit on an adjacent line is exactly how an unrelated regression rides along.

**The edit is value-only, no line added or removed** — a decision forced by this lane's own
earlier work: `k8s/LOCAL.md:536` now cites `k8s/base/configmap.yaml:364`, so inserting an
explanatory comment above line 16 would have silently broken the citation just repaired.
Verified after the edit: line 364 still reads `  stomp.broker.mode: "relay"`.

**Goldens.** `--snapshot pre-29B` taken first, then `--write`. `git diff --numstat` reports
exactly `1 1` per golden — counted over the **whole file** rather than by a positional
scan, because `kubectl kustomize` sorts map keys alphabetically and a source-order scan has
been defeated by that in this repo before. Both changed lines are the
`keycloak.admin.base-url` value; nothing else changed anywhere in either render. Value read
back **out of the rendered goldens**, not the source:
`k8s/goldens/staging.yaml:195` and `k8s/goldens/production.yaml:194` both
`keycloak.admin.base-url: http://keycloak:8080`.

## 7. Findings — things measured that contradict or refine the plan

The plan's tables were measured 2026-08-15 and can rot; a contradiction is a finding, not
an inconvenience.

**1. Gates were run from the WORKTREE, not the main checkout — a deliberate deviation.**
The plan said to run all ten from the main checkout because `check-runtime-freshness` and
the config-drift gates derive the compose project name from the directory. **Neither of
those is among the ten.** More importantly, the main checkout does not contain this lane's
commits, so measuring there would have measured the wrong tree and every "after" number
would have been meaningless. All ten resolve their own repo root from `BASH_SOURCE`, so
they scanned the worktree correctly. Recorded rather than silently done.

**2. My derived `refresh: N field(s) rewritten` was 11; the actual was 12.** The plan
explicitly warned not to predict N and to predict the SET instead — that instruction was
right and the SET matched exactly. My side-derivation of 11 was wrong because the writer
counts a **block-form `sites:` entry per LINE** (ollama's two changed lines are two fields)
while an **inline array is one field** (go-ci-setup's two sites share one). The exact
assertion — the twelve site strings — was unaffected.

**3. Correction to the plan's description of `minio-mc:594`.** The plan says `:594` "is a
comment or prose reference". It is **neither**: it is
`MINIO_MC_IMAGE_REF: minio/mc:${MINIO_MC_IMAGE_TAG:-latest}`, a live env-var assignment
that deliberately echoes the launch reference at run time. The conclusion is unchanged
(`:584`, the `image:` line, is the right site and is what the refresh chose) — but the
reason it is right is "it is the image definition", not "the other one is a comment". This
correction is written into the DEF-29-7 entry.

**4. `INTEGRATIONS.md:22` — kept the plan's 674-680 rather than tightening to 676-680.**
The `deploy:`/`resources:` prefix is scaffolding and 676-680 is strictly the device
reservation, so a tighter citation was available. The plan's own table describes the target
as "the `deploy.resources.reservations.devices` block", which is 674-680, and both satisfy
C-3 and land the reader on the reservation. Kept the pre-declared range: deviating without
a correctness reason only makes review harder. Noted so the choice is visible.
