<objective>
Testers anywhere should see real-looking kitchens on the landing page, and be able to order from them.

Per the owner decisions of 2026-11-02 (D-01..D-04) and the owner's confirmation rulings of the same
day:
- An ordered, per-environment list of featured shop slugs (D-02) leads the landing kitchen row before
  location is shared. It stands in honestly when location is shared and nothing is within the radius,
  and gives way to nearby kitchens when they exist (D-03).
- Featured cards carry a small editorial Featured label (D-04).
- Staging gets three demo kitchens, seeded through the real onboarding API by a new staging-seed stage,
  kept apart from the Phase 30 test tenant and from billing (D-01).
- The demo kitchens take orders on staging, labelled "(demo)", staging only (D-05). Tooling proves an
  order is accepted and clears stale orders.

D-01 AS RULED (owner confirmation, 2026-11-02): THREE demo tenants, "J'Toye Demo — <kitchen name>", one
kitchen each. The cause, measured:
- V43 declares `uq_onboarding_tenant UNIQUE (tenant_id)`.
- `VendorOnboardingService.transition` publishes only `onboarding.getShopId()` at GO_LIVE.
- `ShopService.setPublished` is the only writer of `published`.
So one tenant can take exactly one shop live through the real API; `DemoDataSeeder.upsertShop` documents
the same and bypasses it in dev only. Each kitchen is its own seller of record, "<kitchen name> (demo)".

MEASURED PAYMENT PATH (D-05). Read in code on 03eb939a; the runtime proof is the orchestrator's
post-deploy `--stage order --kitchen` run.
- How a guest order is paid is decided PLATFORM-WIDE, not per shop or tenant:
  `core-java/src/main/java/uk/jtoye/core/storefront/PublicStorefrontService.java:1603`
  `if (paymentService.isConfigured())`. When true, the card branch (`:1603-1657`) persists the order
  DRAFT and creates a PaymentIntent. When false, the cash/COD branch (`:1658-1689`) writes PENDING,
  PaymentStatus NONE and method "Unpaid".
- `PaymentService.isConfigured()` (`core-java/src/main/java/uk/jtoye/core/payment/PaymentService.java:164-166`)
  is "STRIPE_API_KEY is non-blank" (`application.yml:836`). `k8s/base/core-java-deployment.yaml:650-655`
  injects it from the Secret stripe-credentials, and the staging render carries it.
- `GuestOrderRequest` has no payment-method field, so a customer cannot choose cash.
- Consequence: on staging, cash is unreachable for EVERY shop, including the demo kitchens. Every
  storefront order is a card order.
- With NO enabled connected account:
  - `StripeConnectService.resolveSettlementRouting`
    (`core-java/src/main/java/uk/jtoye/core/payment/StripeConnectService.java:342-362`) returns empty
    when the tenant's connect status is not ENABLED.
  - `resolveDestinationAccount` (`:398-407`) returns empty.
  - `PaymentService.createPaymentIntent` (`PaymentService.java:239-266`) then sets neither
    transfer_data nor Stripe-Account, giving a plain PLATFORM-account PaymentIntent. Its own javadoc
    (`:199-202`) says "falls back to the platform account".
  - No refusal sits on that path: PublicStorefrontService never reads StripeConnectStatus.
- Card at a demo kitchen therefore WORKS without Connect. The customer pays with a Stripe test card, the
  charge lands in the platform's TEST balance, and the webhook settles the order CAPTURED. It is the same
  path the staging test kitchen used in plan 29-18, before Connect existed.
- Refunds of such charges: `RefundService.java:158-163` allows CONFIRMED, PREPARING, READY or COMPLETED
  only; `:224-241` uses no routing, so it is a plain platform refund.
- Cancel (`OrderStateMachineConfig.java:87-120`) is legal from DRAFT through READY and refunds nothing.
- Recorded in D17 and the SUMMARY: demo card orders are platform TEST charges. Routing them to a
  kitchen would need per-tenant Connect onboarding, which is the owner's hosted Stripe step: out of
  scope, follow-up. The cash path at demo kitchens appears only if staging ever runs without a Stripe
  key; clear-orders still handles it.
