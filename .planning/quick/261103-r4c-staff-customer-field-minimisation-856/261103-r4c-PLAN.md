<objective>
Issue #856 / SW-TND-08: field-level minimisation of customer contact data for STAFF, enforced in the API.

Owner ruling 2026-11-03 (locked, not re-litigated here):
- Option B (WINDOWS #29, ruled 2026-10-09) STAYS. Every customer endpoint still needs an honoured grant, and STAFF can still look a customer up at the counter. No access gate in this plan is widened or narrowed.
- ADDED: a caller whose best honoured grant on the order's or customer's shop is STAFF sees customer NAME + PHONE everywhere, but NOT the customer email, and NO address on a COLLECTION order. The rule is applied when the DTO is built for the response (by the caller's role on the row's shop), never in the UI, because a client-side hide leaves the data in the response. SHOP_MANAGER and above, GROUP_ADMIN and realm admin are unchanged. Basis: UK GDPR Art 5(1)(c).
- Delivery-address reading (recorded, as the ruling asked): STAFF DOES perform the delivery hand-off. `OrderService.transitionOrder` gates all six state transitions, mark-ready and complete included, at `ShopRole.STAFF`, and `frontend/components/dashboard/kitchen/kitchen-ticket.tsx` prints the address on a DELIVERY ticket. So the DELIVERY address is KEPT for STAFF; only non-DELIVERY orders lose it. Current write paths store no address on a COLLECTION order (`FulfilmentPolicy`: "A COLLECTION order ... must not persist an address"), so in practice this strips legacy or mis-classified rows. It is still enforced, because the rule must not depend on the data having always been clean.

Surfaces found (verified on main c1a38cd5, not assumed):
- Order DTOs: `OrderDto` and `OrderDetailDto`, built only by `OrderMapper` and only inside `OrderService` (rg over core-java/src/main: no other producer for vendor callers; `WebhookDeliveryService` sends an order envelope to a Group-admin-configured endpoint, which is machine-to-machine export and out of scope, see the threat register).
- STAFF-reachable OrderService exits: getOrderById, getOrderByNumber, getOrderDetailById, getAllOrders, getOrdersByStatus, getOrdersByShop, getKitchenBoard, getOrdersByCustomer, transitionOrder (all six transitions), acknowledgeAllergyNote. NOT reachable by STAFF, so left untouched: createOrder and updateOrder (SHOP_MANAGER on the same shop), voidOrder (GROUP_ADMIN). Leaving createOrder untouched also keeps the stored `orders.create` idempotency bytes and `IdempotencyFingerprintGoldenTest` exactly as they are.
- Customers: `CustomerController.CustomerDto` is built only by `CustomerMapper.toDto` inside `CustomerService`: getCustomerById, getAllCustomers, updateCustomer (createCustomer is SHOP_MANAGER-gated on the origin shop, so it is left untouched for the same golden reason).
- Kitchen board live feed: SSE (`OrderSseService`, event `order-state-change`) and STOMP (`OrderStateChangeListener` to `StompDestinations.kitchen`) both send `OrderStateChangeEvent` = (orderId, tenantId, orderNumber, previousStatus, newStatus, timestamp, shopId). The broadcast already carries no customer data, and clients refetch `/orders/kitchen`, which IS minimised. So nothing per-subscriber is needed, and the plan adds a guard test instead of a change.
- Cook sheet (`CookSheetDto`): carries customerName + allergyNote only. That is within the rule, so no change.
- Dashboard landing data: `frontend/app/dashboard/page.tsx` renders `order.customerEmail` from GET /orders, behind an `order.customerEmail &&` guard. The server change covers it, and it already tolerates absence.
- MCP `read_orders` (`mcp-server/src/tools/read-orders.ts`) forwards the caller's token to GET /api/v1/orders, /orders/shop/{id} and /orders/{id}/detail. It inherits the rule by construction: no MCP change. An allowlisted machine client is GROUP_ADMIN-equivalent under the existing `isGroupAdmin()` design and keeps full contact (unchanged).
- Frontend: `OrderDetailPanel.tsx`, `dashboard/page.tsx` and `kitchen-ticket.tsx` already guard email and address. The one place that breaks is `frontend/app/dashboard/customers/page.tsx`, which renders `{customer.email}` with a Mail icon unconditionally and calls `setValue("email", customer.email)`, and `frontend/types/api.ts` declares `Customer.email: string`.

Ordering: tdd_mode is on and the quick-mode constraint puts the RED test first. Task 1 is the end-to-end RED test through the real filter chain (HTTP to service to DTO to JSON). Task 2 turns it green across every exit point. Task 3 makes the frontend tolerate absence and the contract and metrics honest. The RED IT drives HTTP and seeds with JDBC, so it compiles on today's tree and fails on assertions, not on compilation.

Purpose: a kitchen-only account no longer receives customer email addresses (or a collection customer's address) it has no operational need for, while the counter lookup and hand-off keep working.
Output: one STAFF-signed acceptance IT (RED, then GREEN, both recorded), one broadcast-shape guard, the server-side minimiser, a frontend that renders absence cleanly, a description-only OpenAPI update, and refreshed doc metrics.
