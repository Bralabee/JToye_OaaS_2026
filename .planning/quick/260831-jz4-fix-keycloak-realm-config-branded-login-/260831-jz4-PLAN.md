<decisions>
**D-1 — SMTP values are LITERAL in the templates, not new envsubst placeholders.**
There are **three** independent render sites, each with its own envsubst allow-list:
`docker-compose.full-stack.yml:124,137`, `infra/docker-compose.yml:59`,
`infra/docker-compose.hostnet.yml:22`. A name missing from any one of them renders the **literal
`${NAME}` token** into that realm JSON — envsubst leaves unlisted names untouched — and Keycloak
would then use that token as the SMTP host. That trap is already written into the compose file's own
comment (lines 129-133) because it was measured once. Beyond the risk: `rg -uu mailhog
infra/docker-compose.yml infra/docker-compose.hostnet.yml` → **rc=1, zero hits**, and hostnet uses
`network_mode: host`, so no single env value is correct across all three sites anyway — a
placeholder would relocate the wrongness, not remove it. And reusing the existing `SMTP_HOST` name
is actively harmful: `.env.example:149` sets `SMTP_HOST=smtp.example.com`, so any developer who
copied the example would render a dead public host into their realm.
Staging/production Keycloak does **not** consume these templates (no k8s manifest mounts
`realm-export*.json` — the only `k8s/` hits are comments counting a client id). Record that boundary
in the README; overrides there are k8s-side.

**D-2 — the application mechanism is the Admin API (README Route 2), NOT `kc.sh import --override true`.**
A full `--override true` import replaces the realm wholesale. The customer template ships
`users: []`, so importing it would **delete every storefront self-registration** in the running
realm. The README already says the Admin API is "the route to prefer when the realm has live users",
and both realms have live users. Use `kcadm.sh update realms/<realm>`, which is a GET-merge-PUT: it
touches only the fields you name and leaves users, clients and rotated secrets alone. Full import
stays documented as the fresh/empty-stack route only.

**D-3 — the templates are still edited, in the same commit.** They are the source of truth for a
fresh stack (`down -v`, a new machine, `e2e-nightly.yml` which tears down nightly). A runtime-only
change would be lost on the next teardown; a template-only change would never reach the running
realm (the realm is Postgres-backed). Both halves are required and both are verified.

**D-4 — `resetPasswordAllowed` on the VENDOR realm stays `false`.** Vendor accounts are
operator-provisioned; flipping self-service reset on is a security-posture change nobody asked for
and is not part of R-05/R-06/R-11. SMTP is still wired on the vendor realm because Keycloak uses it
for required-action mail (UPDATE_PASSWORD, VERIFY_EMAIL) and admin-triggered resets, and because the
finding named both realms. Do not change `resetPasswordAllowed`, `registrationAllowed`,
`verifyEmail`, `bruteForceProtected` or `passwordPolicy` on either realm.

**D-5 — branding keys, exact values.** On both realms:
- `"displayName": "J'Toye"`
- `"displayNameHtml": "<span style=\"color:#3A0B0D;font-weight:700;letter-spacing:0.01em\">J'Toye</span>"`
  (oxblood `#3A0B0D` is the shipped brand colour, PR #232)
- `"loginTheme": "keycloak"` — a **built-in** theme, pinned explicitly so a future Keycloak upgrade
  that changes the default login theme cannot silently restyle these pages. No custom theme.
Do **not** add `_note_*` keys at realm top level: unlike the `identityProviders[].config` map
(a free-form `Map<String,String>` Keycloak ignores), unknown top-level keys are deserialised into
`RealmRepresentation` and may fail the import. Rationale goes in the README.

**D-6 — `smtpServer` value, exact.** All values are strings in Keycloak's format:
`host: "mailhog"`, `port: "1025"`, `from: "no-reply@jtoye.local"`, `fromDisplayName: "J'Toye"`,
`auth: "false"`, `ssl: "false"`, `starttls: "false"`. The `jtoye.local` domain matches the existing
convention (`.env.example:343` `ALERTMANAGER_SMTP_FROM=alerts@jtoye.local`). `from` must be a
syntactically valid address or Keycloak rejects the send.

**Displaced goods (Incremental Betterment Doctrine): none.** Nothing user-visible is being removed.
The vendor realm's empty `smtpServer` currently makes every mail-sending flow fail; wiring it can
only widen the working set. The audit's stock-page inventory keeps every page it had — only the
header string changes.
</decisions>
