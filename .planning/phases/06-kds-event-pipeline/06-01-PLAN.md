    2. **Add WebSocket broadcast in handleOrderStateChange** (per D-03): After the existing `sseService.broadcast(event)` call (line 44) and BEFORE the TenantContext/DB session setup, add the WebSocket broadcast block. The broadcast needs the shopId from the order, so:

    ```java
    // WebSocket broadcast to KDS topic (per D-02, D-05)
    try {
        orderRepository.findById(event.orderId()).ifPresent(order -> {
            if (order.getShopId() != null) {
                String topic = "/topic/kitchen/" + event.tenantId() + "/" + order.getShopId();
                simpMessagingTemplate.convertAndSend(topic, event);
                log.debug("WebSocket broadcast to {} for order {}", topic, event.orderNumber());
            }
        });
    } catch (Exception e) {
        log.warn("WebSocket broadcast failed for order {}: {}", event.orderNumber(), e.getMessage());
    }
    ```

    Key design points:
    - Per D-01: Send the OrderStateChangeEvent as-is (lean payload, KDS fetches full detail via REST if needed)
    - Per D-02: Topic is `/topic/kitchen/{tenantId}/{shopId}` — tenantId from event, shopId from order lookup
    - Per D-05: shopId resolved from Order record via orderRepository.findById
    - Per D-06: Entire block wrapped in try-catch. Fire-and-forget. WebSocket failure logs warning but does NOT throw — SSE + email + metrics continue unaffected.
    - The orderRepository.findById call here is SEPARATE from the later findById in sendEmailForState. This is intentional — the WebSocket broadcast happens before TenantContext is set, and the later call happens within the tenant-scoped context. Two lookups is acceptable for correctness.

    Note: Do NOT modify the existing SSE, email, or metrics logic. Do NOT change the @RabbitListener or @Transactional annotations.
