# Phase 25 Plan 02: Mutating-MCP Runtime Enablement (realm RW client + scopes + secret/config wiring) Summary

**One-liner:** Template-seeded `integration-orders-rw` Keycloak client (least-privilege `orders:write`+`customers:write`+`catalog:read`, both mappers, placeholder secret) + the `customers:*` scopes + `core-api` write default-grant + `INTEGRATION_ORDERS_RW_SECRET` fail-loud across all wiring sites + `ACCESS_MACHINE_CLIENT_IDS` VSA-02 allowlist — so 25-04 can re-import and mint a clean RW token that leaves no `shop_staff` cruft.

## What Was Built

Config/realm only — no code, no file overlap with the other Phase-25 plans (runs in parallel).

### Task 1 — Realm template surgery (`7837125`)
Four clone-edits to `infra/keycloak/realm-export.template.json` (the TEMPLATE; the rendered `realm-export.json` is regenerated by envsubst at compose start):
- **(a) `customers:read` + `customers:write` client scopes** — cloned from the `orders:read`/`orders:write` block shape (`include.in.token.scope:"true"`, `display.on.consent.screen:"false"`, empty `protocolMappers`, fresh distinct UUIDs). Only `customers:write` is enforced this phase (D-02); `customers:read` is defined-only for taxonomy symmetry.
- **(b) `integration-orders-rw` client** — verbatim clone of `integration-catalog-ro`: `serviceAccountsEnabled:true`, `standardFlowEnabled:false`, `directAccessGrantsEnabled:false`, `publicClient:false`, `clientAuthenticatorType:"client-secret"`; `secret:"${INTEGRATION_ORDERS_RW_SECRET}"` (placeholder, D-11); BOTH cloned protocol mappers `tenant-id-mapper` + `core-api-audience-mapper` with fresh ids (the audience mapper is mandatory — without `aud=core-api` the #88 AudienceValidator 401s before any scope check, Pitfall 3); `defaultClientScopes` = `orders:write, customers:write, catalog:read, web-origins, acr, roles, profile, email` (D-10 — write + read-for-discovery, pointedly NO `catalog:write`).
- **(c) SA user `service-account-integration-orders-rw`** — cloned from `service-account-integration-catalog-ro`, keeping `attributes.tenant_id: ["00000000-0000-0000-0000-000000000001"]` (RLS carrier claim; template import is not subject to the KC24 managed-attribute strip) and `realmRoles: ["default-roles-jtoye-dev"]`.
- **(d) `core-api` default-grant (D-03)** — appended `orders:write, customers:write` to `core-api`'s `defaultClientScopes` so every operator/dashboard token transparently carries them after the re-import.

Also refreshed the `orders:write` scope DESCRIPTION from "reserved" to "enforced (Phase 25)" to keep the realm doc consistent with the 25-01 `@PreAuthorize` gate.

### Rule 3 (blocking-issue clarification) — ACCESS_MACHINE_CLIENT_IDS scope
**1. [Rule 3 - clarification] `ACCESS_MACHINE_CLIENT_IDS` wired only where core-java exists**
- **Found during:** Task 2
- **Issue:** The plan acceptance says "present on the core-java service env in each compose", but `infra/docker-compose.yml` and `infra/docker-compose.hostnet.yml` define NO core-java service — they are infra-only (postgres + keycloak realm-render). There is no core-java env to set it on there.
- **Resolution:** Set it on `docker-compose.full-stack.yml` (the canonical local dev + E2E runtime, and the only compose that runs core-java). The plan's own automated verify greps ONLY `docker-compose.full-stack.yml` for this key, confirming full-stack is the intended target. The SECRET (a realm-render input) is still wired to all 3 composes, since all 3 render the realm.
- **Files:** docker-compose.full-stack.yml
- **Commit:** f075df2

### Note (not a deviation) — pre-existing correct-by-design duplicate id
The plan's `unique-id` acceptance jq (`[.. | .id? // empty] | length == (unique|length)`) returns `false` because of a PRE-EXISTING id shared by the realm's `defaultRole` and its `roles.realm[]` definition (`73a162d3-990e-4ede-a1c5-bd5c01f30e36`, present in committed HEAD at L50 + L359). This is CORRECT Keycloak export structure — `defaultRole` is a reference that legitimately carries the referenced role's id — and the realm has always imported cleanly. It is out of scope (pre-existing, unrelated to this task) and MUST NOT be "fixed" (changing the id would break the realm). The task's real requirement — fresh distinct UUIDs for every NEW id — is fully met; my 6 new ids add zero duplicates.
