# Phase 33 (plans 33-08 / 33-09): Code Review Report

**Reviewed:** 2026-08-09
**Depth:** standard

## Summary

The five priority lenses were each traced to ground truth, and four of them come back clean
against a genuine attempt to break them:

- **Injection / response splitting (lens 1) — clean, and defended twice.** The header value is
  built only from `PostcodeGeocoder.LocatedPostcode.key()`, which is
  `matcher.group(n).toUpperCase(Locale.ROOT)` over `[A-Za-z]{1,2}[0-9]{1,2}[A-Za-z]?` (+ optional
  `[0-9][A-Za-z]{2}`) — provably `[A-Z0-9]{2,8}`, so CR/LF/`;`/non-ASCII cannot reach
  `response.setHeader`. `SearchInterpretation.SAFE_KEY` re-checks at the sink. The raw `q` reaches
  the header on no path. On the SSR side the only `dangerouslySetInnerHTML` is the pre-existing
  JSON-LD, which is fed `shopListStructuredData(content, origin)` and never the query; the
  emphasis span renders `summary.term` as a React child (escaped), and `searchSummary`'s proximity
  branch discards `query` entirely — asserted by `search-interpretation.test.ts:197`.
- **Regex / DoS (lens 2) — clean.** `MAX_SEARCH_TERM_LENGTH = 12` is applied *before* the matcher
  and before either lookup, proven not by timing but by
  `verify(repository, never()).findById(...)` + `never()).findDistrictCentroid(...)`
  (`PostcodeGeocoderTest.java:407-408`). Both patterns have explicit bounded quantifiers and no
  nested repetition. A non-postcode `q` costs one anchored regex and zero round trips after the
  D-A flip.
- **Tenant isolation (lens 3) — clean.** The proximity tier calls the *same* private
  `nearestPublished` the `lat`/`lon` path calls, which calls `findPublishedNear` — `published =
  true` in **both** the row query and the count query. No new query was introduced.
  `postcode_centroid` is read via `findById` and one aggregate; it is never joined to `shops`, so
  no unplaceable/unpublished shop coordinate can leak through it. The exclusion disclosure is a
  fixed string asserted to contain no digits (`PROXIMITY_EXCLUSION_NOTE` +
  `expect(...).not.toMatch(/\d/)`), so no count is derivable by subtraction.
- **D-A flip correctness (lens 4) — clean, including the SE1/SE1P case the brief flags.** The
  range is closed on `[outward+"0AA", outward+"9ZZ"]` *plus* `length(postcode) = outward.length+3`.
  SE1P units are 7 characters and SE1's `unitLength` is 6, so the length guard excludes them
  regardless of collation — and the converse holds (an SE1P search cannot pull in 6-character SE1
  units). The lookup is also **complete**: every real key of that exact length beginning with the
  outward code is inside the bounds. The M1/M11 Testcontainers fixture is arranged so that
  dropping the guard changes *which shops come back*, not just the decimals, and a separate arm
  asserts that property of the fixture itself.
- **Frontend honesty (lens 5) — clean.** `interpretation` is written from exactly three sources:
  the parsed SSR header, the parsed axios header, and `TEXT_INTERPRETATION`. There is no
  postcode regex anywhere under `app/shop/`. The "type SE22, then type jollof" case is covered by
  a real arm (`shop-discovery-client.test.tsx:254`), and every absence assertion in both new test
  files is paired with a positive control.

What is left is a set of **five Warnings** clustered on one theme: the honesty contract that this
phase exists to establish has two ways to be silently switched off by configuration, and the
in-code documentation of the flipped ordering was only half-updated.

Two findings that a lighter pass would have produced were checked and **rejected as not real**,
and are recorded so they are not re-filed: (a) "the district range is collation-dependent" — the
length guard makes the result independent of collation in both directions; (b) "`headerValue()`
degrades to `text` while returning proximity results" — unreachable from `PostcodeGeocoder`,
because the key is `[A-Z0-9]{2,8}` by construction. The reachable form of (b) is WR-03.

### WR-02: WARN-level log fires on an expected, anonymous-reachable, per-keystroke condition

**File:** `core-java/src/main/java/uk/jtoye/core/geo/PostcodeGeocoder.java:242-244`

**Issue:** `locateDistrict` is called **only** from `locateSearchTerm`, i.e. only from the
anonymous public search path. It logs at **WARN** on every unresolved district, and the message
itself concedes the condition is routine:

> "This is expected for Northern Ireland (the dataset is GB-only) and for districts that do not
> exist."

Three things make this reachable at volume rather than occasionally:

1. `GET /public/shops?q=ZZ99` is unauthenticated and emits one WARN per request.
2. Every Northern Ireland customer trips it (`BT1`, `BT2`, …) as normal use.
3. `shop-discovery-client.tsx` fires a request **per keystroke** — `fetchShops` depends on
   `searchQuery`, and the effect at line 308 has no debounce (only the URL sync at line 345 is
   debounced). Typing `BT15GS` produces a request for the intermediate `BT1`, which is a WARN.

WARN is the level operators alert on. A WARN that fires on ordinary customer typing is how a WARN
channel stops being read. The sibling call in `locate()` (line 144) is correctly WARN — that one
is the authenticated vendor write path, where an unresolved postcode is genuinely actionable.

**Fix:** downgrade to `debug` on the search path, and say why the two levels differ.

```java
// DEBUG, not WARN, and the level is the decision. locate()'s miss is a vendor address that
// failed to geocode — actionable, rare, authenticated. This miss is a customer typing into a
// public search box: routine (every NI postcode), anonymous, and one per keystroke.
log.debug("Postcode district '{}' is not in the Code-Point Open dataset — search term not "
        + "resolved to a location (expected for Northern Ireland and for districts that do "
        + "not exist).", outward);
```

### WR-03: The postcode tier applies `defaultRadiusKm` with no validation, so a misconfigured radius makes the page state the opposite of the truth

**File:** `core-java/src/main/java/uk/jtoye/core/storefront/PublicStorefrontService.java:392-395`
(compare `:252-260`)

**Issue:** `listPublishedShopsNear` validates the radius **even when it is the platform default**:

```java
double radius = radiusKm != null ? radiusKm : defaultRadiusKm;
if (!Double.isFinite(radius) || radius <= 0.0) { throw new IllegalArgumentException(...); }
if (radius > maxRadiusKm) { throw new IllegalArgumentException(...); }
```

The postcode tier passes `defaultRadiusKm` straight into `nearestPublished` with none of that, on
the reasoning recorded in the `nearestPublished` javadoc ("the radius is a platform value rather
than a caller's"). But `default-radius-km` is `${GEO_DEFAULT_RADIUS_KM:5}` — an operator-tunable
env var — and the two paths then disagree about the same bad value:

| `GEO_DEFAULT_RADIUS_KM` | `?lat=51.47&lon=-0.07` | `?q=SE22` |
|---|---|---|
| `0` | RFC 7807 400, named ceiling | **HTTP 200, empty page** |
| `-1` | RFC 7807 400, caller-facing message | 400 from `GeoBounds.boxAround` blaming the caller for a server misconfiguration |
| `500` (> `max-radius-km`) | RFC 7807 400 | **HTTP 200, 500 km of results** |

The `0` row is the one that breaks this phase's own contract. The response is a genuine
proximity-filtered page, and the header correctly says
`proximity; postcode=SE22; precision=district; radiusKm=0.0` — but
`frontend/lib/search-interpretation.ts:147` rejects `radiusKm <= 0` and degrades to `text`, so the
storefront renders **`No kitchens match "SE22"`** over a page that was proximity-filtered and from
which text-matching kitchens were excluded. That is the "row lying about itself" failure class
33-09 exists to close, reachable by one environment variable, with no test covering it.

**Fix:** validate the platform radius once, at the point it becomes a query input, so both callers
inherit it.

```java
private Page<PublicShopDto> nearestPublished(double latitude, double longitude,
                                             double radiusKm, Pageable pageable) {
    // The radius is validated HERE, not only in listPublishedShopsNear, because the postcode
    // tier supplies a CONFIG value and a config value is as capable of being wrong as a
    // caller's. A zero/negative default is a startup-time error, never a silent empty page
    // that the storefront then reports as a text search.
    if (!Double.isFinite(radiusKm) || radiusKm <= 0.0 || radiusKm > maxRadiusKm) {
        throw new IllegalStateException(
                "jtoye.geo.default-radius-km must be > 0 and <= jtoye.geo.max-radius-km");
    }
    ...
}
```

A `@PostConstruct` assertion on `defaultRadiusKm` vs `maxRadiusKm` (failing the context loudly, in
the same spirit as the deliberately absent inline `@Value` defaults documented at lines 91-95)
would be strictly better, and closes the `500` row as well.

### WR-04: A correctness-critical header now rides a full-replacement operator override, and its omission fails silently *and falsely*

**File:** `core-java/src/main/java/uk/jtoye/core/config/CorsConfig.java:49,63` and
`core-java/src/main/resources/application.yml:641`

**Issue:** `config.setExposedHeaders(exposedHeaders)` **replaces** the list; it does not merge.
`CORS_EXPOSED_HEADERS` is advertised as operator-tunable and is asserted to be so
(`CorsExposedHeadersTest.allowlistIsConfigurable`). Any deployment that sets it — including one
that copies the pre-33-08 six-name list — silently removes `X-Search-Interpretation`.

Before 33-08 that omission degraded a *hint*: `lib/public-fetch-retry.ts` has a documented
exponential-backoff fallback for a missing `Retry-After`. After 33-08 the same omission produces a
**false statement on the page**: the browser's `headers.get()` returns `null`,
`parseSearchInterpretation` degrades to `text`, and `/shop?q=SE22` renders
`3 kitchens for "SE22"` over a distance-ordered, radius-filtered result set with the exclusion
disclosure suppressed. There is no server-side signal at all — the header is genuinely on the
wire, `curl` shows it, and every servlet-level test stays green. That is #412's recorded shape
with a worse payload.

Mitigating: no manifest, compose file, `.env.example` or doc in the repo currently sets
`CORS_EXPOSED_HEADERS` (verified with `git grep`), so the shipped default wins today. The defect is
that nothing prevents or reports the future omission.

**Fix:** make the name non-removable, and keep the list tunable.

```java
config.setExposedHeaders(exposedHeaders);
// The interpretation header is not a hint — omitting it makes the storefront state the WRONG
// reading of q, with no server-side symptom. So it is APPENDED rather than left to the
// operator's list, which is a full replacement and not a merge.
if (exposedHeaders.stream().noneMatch(SearchInterpretation.HEADER::equalsIgnoreCase)) {
    log.warn("cors.exposed-headers omits {} — appending it. A browser cannot read the search "
            + "interpretation without it, and the storefront would silently report a "
            + "proximity result as a text search.", SearchInterpretation.HEADER);
    config.addExposedHeader(SearchInterpretation.HEADER);
}
```

(If the append is judged too magical, the WARN alone is the minimum: it converts an invisible
false claim into an operator-visible one.)

### WR-05: The CHANGELOG describes the opposite algorithm to the one shipped

**File:** `docs/CHANGELOG.md:22`

**Issue:**

> "The district lookup is a **half-open range** plus a unit-length guard…"

The shipped query is a **closed** range (`postcode >= :rangeStart AND postcode <= :rangeEnd`), and
`PostcodeCentroidRepository.java:55-60` explicitly *rejects* the half-open form and records why:

> "CLOSED (`<=`) rather than the half-open successor form (`>= 'SE22' AND < 'SE23'`). The successor
> requires incrementing the outward code's final character, which has a carry case for a 9- or
> Z-suffixed code that the permissive search regex accepts…"

The CHANGELOG is the release-note-of-record and the first thing a future maintainer reads. As
written it invites exactly the "simplification" the code deliberately refused, and that
simplification has a live carry bug for outward codes the regex accepts.

**Fix:** `"The district lookup is a closed key range plus a unit-length guard…"` — one word.

### IN-01: Unreachable length guard in the unit branch

**File:** `core-java/src/main/java/uk/jtoye/core/geo/PostcodeGeocoder.java:201`

**Issue:** `if (key.length() <= MAX_KEY_LENGTH)` can never be false. `SEARCH_POSTCODE` bounds the
outward group at `[A-Za-z]{1,2}[0-9]{1,2}[A-Za-z]?` = 5 characters and the inward group at exactly
3, so `key.length()` is at most 8, which *is* `MAX_KEY_LENGTH`. The branch is dead, and dead
defensive code is the kind that later gets "tightened" to `< MAX_KEY_LENGTH` and starts silently
skipping every 8-character unit lookup (i.e. every `SE15 5BS`-shaped postcode) in favour of the
district. The same shape exists at line 133 in `locate()` and is pre-existing.

**Fix:** either delete it, or keep it and say it is a tripwire rather than a filter:

```java
// Belt-and-braces only: the regex caps this at 5 + 3 = MAX_KEY_LENGTH, so this can never be
// false today. Kept so a future loosening of SEARCH_POSTCODE cannot overflow the column.
```

### IN-03: A repeated key in the header value silently last-wins instead of being refused

**File:** `frontend/lib/search-interpretation.ts:128-133`

**Issue:** `pairs.set(...)` overwrites, so
`proximity; postcode=SE22; precision=district; radiusKm=5.0; postcode=ELSEWHERE` parses as
`postcode: "ELSEWHERE"` (which passes `SERVER_KEY`). Not reachable from this server —
`response.setHeader` replaces rather than appends, and the value is a single literal expression —
but the module's stated policy is that "anything else arriving here did not come from a server
this client understands", and a duplicate key is exactly that. Refusing is strictly stronger than
last-wins and costs one line.

**Fix:**

```ts
const key = part.slice(0, eq).trim()
// A repeated key is not something the server can emit, so it is refused rather than resolved.
if (pairs.has(key)) return TEXT_INTERPRETATION
pairs.set(key, part.slice(eq + 1).trim())
```

## Verification notes (what was checked and found sound)

Recorded so a later pass does not have to re-derive them:

- **District range soundness AND completeness.** For outward `O` of length `k`, the query is
  `[O+"0AA", O+"9ZZ"]` with `length = k+3`. Every real unit of district `O` is `O` + a 3-character
  inward code, hence length `k+3` and inside the bounds (complete). Every key of length `k+3`
  inside those bounds must begin with `O`, because a valid inward code is always exactly 3
  characters, so no other district can produce a key of that length in that range (sound). The
  `SE1`/`SE1P` and `M1`/`M11` cases both reduce to a length mismatch and are therefore
  collation-independent.
- **Null Island.** Triple-gated (`district == null || getUnits() <= 0 || lat == null || lon ==
  null`), with `DistrictCentroid` boxing both coordinates so a NULL cannot unbox to `0.0`, and the
  unit-test mock deliberately returns a row-of-NULLs rather than `null` so a `!= null` gate would
  fail the suite.
- **`PageImpl` total-recompute trap.** Avoided — `nearestPublished` returns `page.map(...)`, with
  the reason recorded inline at line 307.
- **Unpublished-shop leakage via `totalElements`.** `findPublishedNear` carries `published = true`
  in both the row and the count query, and the integration arm asserts the absence **at page size
  2** specifically because `PageableExecutionUtils.getPage` skips the count query when the page
  size exceeds the content size.
- **Metrics.** `docs/metrics.json` deltas reconcile: java files 255→256 (+1 new test class), jest
  files 97→99 (+2), playwright blocks 95→101 (+6 `test(` blocks in the diff);
  1580+944+81+101+48 = 2754 = `total_logical_invocations`.
- **OpenAPI snapshot.** `HttpServletResponse` correctly does not appear as a parameter; the
  `X-Search-Interpretation` response header is declared with a non-empty `{"type":"string"}` schema
  on both the `/public/shops` and `/api/v1/public/shops` entries.
