Purpose: D-1 forbids a geocoding API. RESEARCH.md resolved the dataset to OS Code-Point Open on a

**Two product limitations this creates. State them; do not let them be discovered later as bugs.**
Code-Point Open is **Great Britain only** — a Northern Ireland vendor will not geocode, will keep
their storefront, and will be absent from distance-ranked results (the remedy is an LPS commercial
licence, a business decision). Accuracy is **postcode-centroid (~100 m), not door-level**.

Measured on the 2026-08 Code-Point Open release during research. Re-verify; do not assume:
  codepo_gb.zip     14,461,176 bytes,  md5 42ecd9a7db141608dc6ab63f2dfb0bc3
  rows upstream     1,749,109
  rows after filter 1,748,230
  derived CSV       45.6 MB raw / 15.1 MB gzip -9
  transform time    12.0 s for all GB (awk)

NULL ISLAND — the sentinel lives in a DIFFERENT column from the coordinates.
879 rows carry `positional_quality_indicator = 90` with eastings/northings `0,0`. Loaded blind they
become "the nearest shop" to every customer on the platform. Filter on BOTH columns:
`pq != 90 AND easting != 0`. A single-column filter misses it.

OSGB36 -> WGS84, published OS constants (OSGB36->WGS84 is the negation of the documented
WGS84->OSGB36 set). Transverse-Mercator inverse on Airy 1830, then 7-parameter Helmert:
  Airy 1830  a = 6377563.396  b = 6356256.909  F0 = 0.9996012717
             lat0 = 49N  lon0 = 2W  N0 = -100000  E0 = 400000
  WGS84      a = 6378137.000  b = 6356752.3142
  Helmert    tx = +446.448  ty = -125.157  tz = +542.060   s = -20.4894e-6
             rx = +0.1502"   ry = +0.2470"  rz = +0.8421"
Measured accuracy against ONSPD's own WGS84 values over 25 GB postcodes: mean 1.45 m, max 3.28 m —
30x to 70x tighter than the ~100 m centroid error D-1 already accepts. Not a meaningful error source.

Postcode key shape, measured across all 1.75M rows: OUTCODE + ONE SPACE + INCODE, variable field
length 6 (45,237) / 7 (870,174) / 8 (833,698). NOT fixed-width — a padding-based parser mis-keys.
Emit the key SPACE-STRIPPED and UPPERCASED.

Attribution lines, read verbatim out of the shipped archive `Doc/licence.txt` (2026-08):
  Contains Ordnance Survey data (c) Crown copyright and database right {year}
  Contains Royal Mail data (c) Crown copyright and database right {year}
  Contains National Statistics data (c) Crown copyright and database right {year}

SHELL IDIOM — REQUIRED. `grep -c` exits **1** on a zero count, i.e. on the DESIRED state of an
absence check, and `cmd | grep -q X` under `pipefail` INVERTS on match (SIGPIPE -> 141). This repo's
hook blocks both. Always: `out=$(grep -c X f || true); grep -qx 0 <<< "$out"`.

count (33-02's importer asserts against this number, so it must be exact); the three OGL attribution
lines with the release year; the regeneration command; the refresh cadence (annual — postcode
centroids are stable, quarterly is not required); **the GB-only limitation and its NI consequence**;
**the ~100 m centroid accuracy limitation**; and a citation to the A1 confirmation in
`33-CONTROL-ARMS.md`.

**The derived CSV carries NO header row, and that is load-bearing for the check below.** The
researched pipeline emits bare `postcode,lat,lon` data lines (`print $3" "$4" "$1` through the
transform, then `sort`) with no column line. This matters because the Null-Island assertion is
`awk -F, '($2+0)==0 && ($3+0)==0'`: a header line makes `("lat"+0)==0 && ("lon"+0)==0` **true**, so a
header would score 1 and the check would FAIL on a perfectly correct dataset — the recorded
"expected-0 that is actually 1 on a correct tree" shape. Measured both ways during planning: with a
header, count = 1; without, count = 0.

So do not add a header, and do not let the assumption ride: the verify below asserts the first line is
a DATA row (a postcode-shaped first field), which fails if someone helpfully adds column names.

The artefact is binary — confirm it round-trips with `gzip -t` after commit
mangled.
  </action>
