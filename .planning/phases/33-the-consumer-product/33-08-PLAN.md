<decisions>

Three choices this plan makes on the reader's behalf. Each names what was rejected, because a decision
recorded only as its winner reads as though there was never a question. (**D-D**, the exclusion
disclosure, is a rendering decision and lives in `33-09-PLAN.md`.)

### D-A. The postcode tier runs THIRD, after FTS and after the LIKE fallback

`PublicStorefrontService.searchPublishedShops` (`:297-310`) already has a two-tier shape with a
"FTS returned nothing -> try something else" seam at `:304`. The postcode attempt slots in as the third
tier: it runs **only when both existing tiers returned an empty page**.

*Why.* It makes the byte-identical fall-through provable by construction rather than by inspection —
every query that returns results today takes a code path this plan does not touch, so 33-07's measured
healthy behaviour (`SE15` -> 2, `SE15 5BS` -> 1, `jollof` -> 2) is preserved mechanically. It also
keeps a shop literally named *"SE22 Kitchen"* winning a search for `SE22`, which is what a customer
typing a shop's name expects.

*Rejected: interpretation-first (postcode branch before FTS).* It answers `SE15 5BS` with "every
kitchen near you" instead of "the kitchen at that address", which is arguably the better product
answer — but it silently changes three measured behaviours and makes the fall-through control arm an
argument instead of a diff. **The resulting inconsistency is not hidden; it is disclosed** by the
header, and 33-09 renders the two cases differently. Flipping the order later is a single-statement
change and every test in this plan still applies.

*Cost of D-A, stated:* the centroid lookup is attempted only on a zero-result search, so `jollof`
costs zero extra queries.

**D-A is the question 33-09's owner walkthrough puts to the owner.** Do not treat it as settled beyond
this plan.

### D-B. The disclosure is a response HEADER, `X-Search-Interpretation`

| Option | Verdict |
|---|---|
| **A. Response header** | **CHOSEN.** `Page<PublicShopDto>` is untouched, so no consumer breaks. Declarable in OpenAPI via `@ApiResponse(headers = @Header(...))`. Assertable in MockMvc (`header().string(...)`), in Playwright, and in an in-page `fetch` |
| B. Wrapper DTO `{interpretation, page}` | Rejected — breaking. It changes the response shape for `shop-discovery-client.tsx`, `loadShopList` and `near-you-row.tsx` |
| C. Frontend re-derives the interpretation from the `q` it sent | Rejected — this is the "row lying about itself" failure class 33-07 exists to close. The UI would claim an interpretation the server may not have made |
| D. Infer proximity from `distanceKm != null` on the shops | Rejected — **it fails on the empty page**, which is the case where honesty matters most. "No kitchens within 3.1 miles of SE22" and "no kitchens match 'SE22'" are different sentences and a zero-result page carries no shop to hang the flag on |

*One correction to 33-PATTERNS.md §5, made rather than inherited:* the pattern map lists the MCP
`list_shops` tool as a fourth consumer that a wrapper DTO would break. It is not. Verified —
`mcp-server/src/tools/list-shops.ts:29` calls `coreGet("/api/v1/shops", bearer)`, the authenticated
tenant-scoped management endpoint, not `/public/shops`. 33-06-SUMMARY records the same. The
wrapper-DTO cost is three consumers, not four; the header still wins.

**The header's real cost, and it is the one that bites silently:** a cross-origin response exposes only
the CORS-safelisted headers to script. `CorsConfig` and `application.yml:638` carry an explicit
`cors.exposed-headers` allowlist precisely because this repo already shipped that defect once (#412 —
`Retry-After` was on the wire and `null` in every browser, and `curl` could not see the problem). The
frontend talks to core cross-origin (`:3000` -> `:9090`), so **`X-Search-Interpretation` must be added
to that allowlist in both places here.** Proving it in a *browser* is 33-09's CA-H; this plan can only
prove the filter emits it.

### D-C. No new configuration key: the radius is `jtoye.geo.default-radius-km`

33-02's standing instruction is *"33-05 and 33-06 must READ `jtoye.geo.*`, not add to it"*, and this
plan inherits it. `PublicStorefrontService` already holds `defaultRadiusKm` (5 km) injected with no
inline `@Value` default. The postcode search uses it.

*Rejected: a dedicated `jtoye.geo.postcode-search-radius-km`.* Nobody has a defensible number for it,
and reusing the platform default means the copy 33-09 renders — **3.1 miles** — is the same figure the
near-you row already quotes, converted through the same `frontend/lib/distance.ts`. Two radii would be
two numbers to keep in step and only one of them has a test.

Add a **second, differently-named** entry point to `PostcodeGeocoder`. Do not touch

**1. `DistrictCentroid.java`** — a Spring Data projection interface in `uk.jtoye.core.geo` with
`Double getLatitude()`, `Double getLongitude()`, `long getUnits()`. Getters return boxed `Double`
deliberately: see the aggregate trap below.

**2. `PostcodeCentroidRepository.findDistrictCentroid`** — the first non-primary-key query on this
table. Native `@Query`, named parameters only, nothing concatenated into SQL:

- `SELECT avg(latitude) AS latitude, avg(longitude) AS longitude, count(*) AS units FROM postcode_centroid WHERE postcode >= :rangeStart AND postcode <= :rangeEnd AND length(postcode) = :unitLength`
- Parameters `:rangeStart`, `:rangeEnd`, `:unitLength` are computed in **Java** (same reason
  `GeoBounds.boxAround` computes its box in Java): `rangeStart = outward + "0AA"`,
  `rangeEnd = outward + "9ZZ"`, `unitLength = outward.length() + 3`.
- **This is a CLOSED range (`>=` … `<=`), not the pattern map's half-open successor form.** The
  measured form (`>= 'SE22' AND < 'SE23'`) requires incrementing the final character, which has a
  carry case for a `9`- or `Z`-suffixed outward code that the permissive regex accepts even though no
  real district uses one. Every Code-Point Open inward code is digit + letter + letter, so `"0AA"` and
  `"9ZZ"` are the true inclusive bounds and there is no arithmetic to get wrong.
- **The length guard is not optional and is not redundant with the bounds.** `M11 1AA` stored as
  `M111AA` sorts inside `[M10AA, M19ZZ]`; only `length(postcode) = 5` excludes it. Measurement M-4:
  without the guard `M1` returns 6,422 units spanning M1 and M11..M19, whose mean is not Manchester.
- Write the comment block above the query in the `ShopRepository.findPublishedNear` house style,
  stating both reasons (index eligibility under `en_US.utf8`; the length guard) with the measured
  numbers. **Update the class Javadoc in the same change** — it currently claims "no `LIKE`, nothing
  an untrusted address string can steer", which stops being true the moment this method lands.

**3. THE AGGREGATE TRAP.** `SELECT avg(...) ... ` with no `GROUP BY` returns **one row of NULLs** when
nothing matches, not zero rows. A `result != null` check therefore always passes. Gate on
`getUnits() > 0` **and** both coordinates non-null, and return `Optional.empty()` otherwise.

**4. `PostcodeGeocoder.locateSearchTerm(String term)`** returning `Optional<LocatedPostcode>`, where
`LocatedPostcode` is a nested `record LocatedPostcode(Coordinate coordinate, String key, Precision precision)`
and `Precision` is a nested `enum { UNIT, DISTRICT }`.

- `MAX_SEARCH_TERM_LENGTH = 12` — return empty immediately for anything longer, before the matcher
  runs (outward 4 + inter-code spaces 4 + inward 3, with slack). This is the DoS control; the regex
  never sees an unbounded string.
- A new `SEARCH_POSTCODE` pattern, **anchored at BOTH ends** with the inward code optional:
  `^\s{0,4}([A-Za-z]{1,2}[0-9]{1,2}[A-Za-z]?)(?:\s{0,4}([0-9][A-Za-z]{2}))?\s{0,4}$`.
  Both-ends anchoring (`locate`'s is trailing-only) is what makes `"SE22 pizza"` a text search rather
  than a proximity one. Every quantifier stays bounded, no nested repetition.
- Group 2 present -> normalise exactly as `locate` does (concatenate, `toUpperCase(Locale.ROOT)`,
  reject over `MAX_KEY_LENGTH`) and try `repository.findById(key)`. Hit -> `UNIT`.
- Group 2 absent, **or** the unit lookup missed -> try `findDistrictCentroid` on the uppercased
  outward code. Hit -> `DISTRICT`. This is what makes `SE15 4QA` — this repo's permanent
  negative-control postcode, absent from Code-Point Open — return SE15-area kitchens instead of
  nothing.
- Miss on both -> `Optional.empty()`, with one `log.warn` naming **the normalised key only, never the
  raw term** (the raw `q` is arbitrary customer text; the key is `[A-Z0-9]{2,8}` by construction).
  Copy `locate`'s existing warn wording, including the Northern-Ireland / GB-only note.
- **The table is the authority, not the regex.** The shape test only nominates a candidate; a row in
  `postcode_centroid` is what decides. Restate that in the method Javadoc.

**5. Fixture** — append exactly one row to `postcode-centroids-fixture.csv`: a **real** `M11`-district
unit (key `M111AA` if that unit exists). Read its coordinate out of the committed dataset

**6. `PostcodeGeocoderTest`** — add a nested `@DisplayName`-labelled class for `locateSearchTerm`.
