<objective>
Settle #432: the `jtoye-customers` realm has `identityProviders` absent entirely and consumer sign-up
has exactly one route in.

Purpose: SC-5 has two limbs — populate the identity providers, **or** record a dated deliberate
decision. Both are legitimate; D-3 says so. RESEARCH.md establishes limb 1 is achievable *locally* (a
free Google OAuth client is legal against
`http://localhost:8085/realms/jtoye-customers/broker/google/endpoint`, since Google exempts localhost
from its HTTPS redirect-URI rule) but **not** in production: a production redirect URI needs HTTPS on a
resolving host, and `jtoye.co.uk` does not resolve while `DEPLOY_*_ENABLED` is false. Apple requires a
paid Developer Program membership; Meta requires app review. Both are the sixth-commercial-decision
class D-1 exists to avoid.

The owner answered Q-3 in `33-00`. Read it before starting.

**REVISED (plan-checker W2) — the CSP change is dropped, and here is the measurement.** I had planned to
add the Google origin to `form-action` in `frontend/lib/security-headers.ts`. That was wrong on two
counts, and the checker is right. First, **whose document governs**: the browser navigates J'Toye ->
Keycloak realm (governed by J'Toye's CSP) and then Keycloak -> `accounts.google.com` (governed by
**Keycloak's** CSP on Keycloak's own document). J'Toye's policy never sees the Google origin. Second,
the J'Toye -> realm hop is **already permitted** — `security-headers.ts:101` reads
`form-action 'self' ${keycloakSources.join(" ")}`, and the realm sources are already emitted in both
the bare and trailing-slash forms for exactly the recorded path-matching reason. So the change was
unnecessary, and its "control arm" could not have fired. `security-headers.ts` is removed from
`files_modified`. The path-matching trap is still recorded in `<interfaces>` because it will matter to
whoever enables the IdP.

Output: a dated ADR settling the criterion truthfully, plus committed-but-inert groundwork so whoever
resolves the production domain flips one variable rather than reopening this work.
</objective>

FOUR runtime traps, each recorded in this repo:

1. `infra/keycloak/realm-export-customers.json` is GITIGNORED (`.gitignore:164`). The tracked source of
   truth is `realm-export-customers.template.json`. Edit the template; never the rendered file.

2. The customer template is rendered by `envsubst` with an EXPLICIT allow-list, at
   `docker-compose.full-stack.yml:116` — the SECOND `envsubst` invocation, not the first:
     envsubst '$$CUSTOMER_STOREFRONT_REDIRECT_URIS $$CUSTOMER_STOREFRONT_WEB_ORIGINS $$CUSTOMER_VERIFY_EMAIL'
   A `${GOOGLE_CLIENT_ID}` placeholder not added here renders as an EMPTY STRING with no error. The
   allow-list exists so Keycloak's i18n role placeholders survive (the #80 pattern) — extend it, do
   not remove it.

3. `--import-realm` SKIPS a realm that already exists. Keycloak is Postgres-backed, so dropping the
   `keycloak_data` volume is a NO-OP. A template edit does NOT reach a running realm. Working routes:
   `kc.sh import --override true` with the server stopped, or a POST to
   `/admin/realms/jtoye-customers/identity-provider/instances` via the Admin API.

4. CSP path matching — a source expression carrying a PATH matches that path EXACTLY unless it ends in
   `/`. This has blocked customer sign-in on this realm before. `security-headers.ts` already emits
   each realm URL twice, bare and trailing-slash, for that reason. **This plan changes nothing there**
   (see the objective), but whoever enables the IdP must know the rule holds for anything they add.

KC24 unmanaged-attribute trap: KC24 STRIPS unmanaged attributes on admin-API user create. A brokered
first login provisions a user; if `tenant_id` or any custom claim the storefront relies on is expected
on that user, it must be declared MANAGED in the user profile first or it is silently dropped. Check
what `CustomerJwtVerifier` requires before enabling brokering.

`.env` trap: a line of the form `VAR=  # comment` resolves to the COMMENT TEXT, so a naive
is-configured guard reads TRUE on an effectively unset variable. Test any new guard against that shape.

SHELL IDIOM — REQUIRED. `grep -c` exits **1** on a zero count, i.e. on the DESIRED state of an absence
check, and `cmd | grep -q X` under `pipefail` INVERTS on match. This repo's hook blocks both.
Always: `out=$(grep -c X f || true); grep -qx 0 <<< "$out"`.
