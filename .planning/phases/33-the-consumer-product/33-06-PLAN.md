THE QUERY SHAPE. Use the `asin` haversine, not the spherical law of cosines:

  SELECT s.*,
         2 * 6371.0088 * asin(sqrt(
             power(sin(radians(s.latitude - :lat) / 2), 2)
           + cos(radians(:lat)) * cos(radians(s.latitude))
           * power(sin(radians(s.longitude - :lon) / 2), 2)
         )) AS distance_km
    FROM shops s
   WHERE s.published = true
     AND s.latitude IS NOT NULL AND s.longitude IS NOT NULL
     AND s.latitude  BETWEEN :latMin AND :latMax
     AND s.longitude BETWEEN :lonMin AND :lonMax
   ORDER BY distance_km ASC

WHY `asin` AND NOT `acos`. The `acos(sin·sin + cos·cos·cos Δλ)` form is the one usually reached for and
it has a real failure mode: for two nearly identical points floating-point rounding pushes the argument
to 1.0000000000000002 and Postgres raises `ERROR: input is out of range`. That is triggered by a customer
standing at the shop's own postcode centroid — a plausible input, reachable by any anonymous caller,
i.e. an unauthenticated 500. If `acos` is used for any reason it MUST be wrapped
`LEAST(1.0, GREATEST(-1.0, …))`.

WHY THE BOUNDING BOX. Measured on the live database: `sin`, `cos`, `acos`, `radians` are all
`proleakproof = f`; `float8lt/le/ge/gt/eq` are all `proleakproof = t`. Under a row-security barrier
Postgres will not push a non-leakproof user qual beneath the policy, so a haversine expression can never
be an index qual — the mechanism V44 documents for `ts_match_vq`. The float8 comparisons CAN sit below
the barrier and use the `shops(latitude, longitude)` btree from V61. At 3 published shops the index is
irrelevant; the box is there so the query needs no rewrite when it stops being irrelevant, and so the RLS
interaction is correct by construction rather than by luck.

RLS — NO NEW SURFACE IS REQUIRED. Live policy set on `shops`:
  shops_rls_policy   (tenant_id = current_tenant_id())
  shops_public_read  ((published = true) OR (tenant_id = current_tenant_id()))
With no tenant GUC, `current_tenant_id()` returns NULL, the second limb is NULL, and `published = true`
is the sole limb — exactly how `findByPublishedTrue` already serves `GET /public/shops` cross-tenant
(`ShopRepository.java:18-23` comment; call site `PublicStorefrontService.java:171`).

PAGING. Follow `fullTextSearchPublished` (`ShopRepository.java:54-57`) — a native `Page<Shop>` with an
explicit `countQuery`. Do NOT hand-build `new PageImpl<>(content, pageable, total)`: it silently REWRITES
`total` when `offset + size > total` (recorded trap).

Existing controller shape to EXTEND, not replace:
  @RequestMapping({"/public", "/api/v1/public"})
  @GetMapping("/shops")  … @RequestParam(required = false) String q … -> listPublishedShops(pageable)

SHELL IDIOM — REQUIRED. `grep -c` exits **1** on a zero count, i.e. on the DESIRED state of an absence
check, and `cmd | grep -q X` under `pipefail` INVERTS on match. This repo's hook blocks both.
Always: `out=$(grep -c X f || true); grep -qx 0 <<< "$out"`.
