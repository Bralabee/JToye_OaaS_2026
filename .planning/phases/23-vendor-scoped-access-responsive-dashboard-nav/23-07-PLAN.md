<objective>
Wire the persisted shop-context selection (built self-contained in 23-05) INTO the four
shop-scoped consuming screens so VSA-03's locked clause — "all shop-scoped screens operate on the
selected shop" — is actually met. Today the switcher persists a selection and gates the
"apply to all shops" action, but nothing consumes it: a GROUP_ADMIN who switches from "All shops"
to one shop sees zero change (products/orders/marketing/kitchen still span every shop). This plan
adds a `useShopContext()` hook over `getShopContext()`/`subscribeShopContext()` (23-05) and threads
it through Products, Orders, Marketing, and Kitchen:

1. **List narrowing** — when the context is a specific shop, narrow each list to that shop
   (Orders via the existing `?shopId=` server param; Products/Promotions/Announcements via a
   client-side filter over the already grant-scoped 23-03 result). "All shops" (GROUP_ADMIN only)
   keeps today's cross-shop behavior.
2. **Create-form default/constrain (D-08)** — product / order / promotion / announcement create
   forms default their shop to the selected shop and constrain it (no shop dropdown swap) when NOT
   in "All shops" context, so a single-shop context does single-shop writes only.
3. **Kitchen reconcile** — the KDS page already has a local `selectedShopId` + its own selector;
   make the global `getShopContext()` the source of truth (the page's local board state defaults
   from it) instead of two competing shop selectors.

Purpose: This closes the BLOCKER — VSA-03 was structurally half-built (switcher with no consumer).
It also gives D-08 its concrete single-shop-writes home. RLS (tenant) and the 23-03 server-side
read-scope (grant set) remain the real boundaries; this is the visible, per-shop UX layer on top.

Output: `hooks/use-shop-context.ts` + context wiring in the four dashboard screens + Jest behavior
proofs (products + orders narrowing, orders `?shopId=`, create-form default). No new endpoints.
</objective>
