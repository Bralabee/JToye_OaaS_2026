# 23-18 — WR-04: move shop-scope narrowing off the client and onto the server

**Issue:** #280
**Created:** 2026-07-26, by the v2.3 milestone backlog review
**Why now:** the review adjudicated WR-04 as a milestone blocker rather than a v2.4 item — it is the
only open v2.3 deferral that **misreports a vendor's own data back to them**.

## The defect

The products and marketing screens apply shop-scope narrowing **client-side, over a single
server-paginated page**. Three user-visible consequences:

1. **Wrong counts** — the header count is `filtered.length` (rows matching the shop *on this page*)
   instead of the true total for that shop.
2. **False empty state** — if page 1 holds no rows for the selected shop, the screen renders
   "No products in this shop" while rows exist on page 2+.
3. **Unreachable rows** — `<Pagination>` is driven by the *unfiltered* server totals, so paging is
   both wrong and cannot reach the selected shop's tail.

Compounding it: the fetch effects **do not list `contextShopId` as a dependency**, so switching shop
in the switcher does not even refetch (`products/page.tsx:135-139`;
`marketing/page.tsx:236-266`).

**Not a security defect.** The underlying set is already grant-scoped server-side (23-03), and
`use-shop-context.ts:19-22` documents itself as "a UX narrow, NOT a security boundary". This plan
does not change who can see what — only whether the screen tells the truth about it.

## Scope — three endpoints, not two

"Marketing" is a two-tab UI over **two independent domains**. So the API surface is:

| Screen | Endpoint | Controller | Service |
|---|---|---|---|
| Products | `GET /products` | `ProductController.java:54-65` | `ProductService.java:189-214` |
| Marketing → Promotions | `GET /promotions` | `PromotionController.java:39-50` | `PromotionService.java:36-51` |
| Marketing → Announcements | `GET /announcements` | `AnnouncementController.java:39-50` | `AnnouncementService.java:36-51` |

## The pattern to copy — it already exists

`OrderController.java:83-102` + `OrderService.java:296-303` already do exactly this, correctly:

```java
// controller
public ResponseEntity<Page<OrderDto>> getAllOrders(
        @RequestParam(required = false) UUID shopId, Pageable pageable) {
    Page<OrderDto> orders = shopId != null
            ? orderService.getOrdersByShop(shopId, pageable)
            : orderService.getAllOrders(pageable);
    return ResponseEntity.ok(orders);
}

// service — VSA-02 (D-02): explicit shop-scoped read requires at least STAFF on that shop
public Page<OrderDto> getOrdersByShop(UUID shopId, Pageable pageable) {
    shopAccessService.require(shopId, ShopRole.STAFF);
    return orderRepository.findByShopId(shopId, pageable).map(orderMapper::toDto);
}
```

Frontend counterpart: `orders/page.tsx:286-293` (`shopScope` string append) with
`}, [currentPage, contextShopId])` at `:273` — the refetch-on-context-change seam the two broken
screens lack.

## Scope calls made by this plan

1. **`/products/search` IS scoped here.** It returns a bare array with a deliberately frozen wire
   contract (`ProductController.java:80-93`) and the screen swaps to it at `searchQuery.length >= 2`
   (`page.tsx:150-158`). Left alone, the shop switcher would **silently stop applying the moment a
   vendor types two characters** — replacing a uniform defect with an inconsistent one, which is
   harder to notice. Fix is **additive**: an optional `shopId` filter param; the array return shape
   is not touched.
2. **Marketing's client-side `statusFilter` is NOT fixed here.** It shares the same `.filter(...)`
   expressions and is the same defect class (filtering one page), but it is a *separate* defect from
   WR-04 and widening this change would blur what is being verified. It is filed separately rather
   than silently carried — see "Follow-ups".
3. **No change to who can see what.** If a proposed edit would alter the grant-scoped result set for
   any user, it is out of scope and the plan is wrong.

### A1/A4/A5 — a note on what these tests do and do not prove

A1 (page 2 reachable), A4 (true total) and A5 (no false empty state) are proven at the **controller
and screen** level: the shop-scoped page owns its own `totalElements`, and the screen now renders the
server's total rather than `filtered.length`. They are **not** proven against a live multi-page
dataset in a browser — no seeded tenant here has a shop with >20 products. That is a real limit of
this evidence, recorded rather than papered over; the cheapest closure is a live check on the next
stack run.
