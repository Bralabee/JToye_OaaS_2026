<objective>
Close CR-02 — the real KDS transport is not shop-gated.

Purpose: 23-03 added `ShopScope` filtering to the SSE fan-out, but the kitchen board's live
channel is **STOMP**, not SSE. `frontend/app/dashboard/kitchen/page.tsx:277` subscribes to
`/topic/kitchen/${tenantId}/${selectedShopId}` via `useStomp`, and `OrderStateChangeListener:109`
publishes every `OrderStateChangeEvent` to that exact topic.
`TenantChannelInterceptor.validateSubscription` splits the destination and checks only
`parts[3]` — the tenant segment. The `{shopId}` segment is never checked against the
subscriber's grants (grep for `ShopAccessService|grantedShopIds` in that file returns 0).

A STAFF user granted only shop A can open a WebSocket, send
`SUBSCRIBE /topic/kitchen/{ownTenant}/{shopB-id}`, and receive every live order state change
for shop B — order ids, order numbers, status transitions — in real time. Shop ids are
discoverable: they appear in DTOs and public storefront URLs. This is the same leak class as
AUDIT-W0-01 (cited in `OrderSseService`'s own javadoc), one level down: fixed for tenants,
still open for shops.

Output: the primary live transport enforces the same shop boundary the SSE path already does.

```java
private void validateSubscription(StompHeaderAccessor accessor) {
    String destination = accessor.getDestination();
    if (destination == null) return;
    if (!destination.startsWith("/topic/")) return;

    UUID sessionTenant = getSessionTenant(accessor);
    String[] parts = destination.split("/");
    // parts: ["", "topic", "{feature}", "{tenantId}", ...]
    if (parts.length < 4) { throw new MessageDeliveryException("Topic subscriptions require a tenant segment"); }
    try {
        UUID destTenant = UUID.fromString(parts[3]);
        if (!destTenant.equals(sessionTenant)) { throw new MessageDeliveryException("Cross-tenant subscription denied"); }
    } catch (IllegalArgumentException e) {
        throw new MessageDeliveryException("Invalid tenant ID in destination: " + parts[3]);
    }
}
```

<why_securitycontextholder_is_wrong_here>
The STOMP CONNECT path calls `accessor.setUser(...)` but does **not** populate
`SecurityContextHolder`. After plan 23-08, an absent `Authentication` is still treated as a
trusted internal caller (a deliberately retained, measured decision — see 23-08's blast-radius
note). So if this interceptor called `shopAccessService.isGroupAdmin()` or
`grantedShopIds()`, those methods would see no principal, classify the WebSocket subscriber as
an internal caller, and **return true / unrestricted** — the gate would appear to be wired
while failing open.

The subscriber's identity must therefore be resolved explicitly from `accessor.getUser()` and
passed as parameters. Do not populate `SecurityContextHolder` on the STOMP inbound thread as a
workaround: that thread is pooled, and a missed cleanup would leak a principal onto an
unrelated subsequent frame.
</why_securitycontextholder_is_wrong_here>

  <behavior>
    - `canAccessShop(tenantId, userId, realmAdmin=true, shopId)` → true regardless of grants (D-03 bridge).
    - Caller holds a tenant-wide GROUP_ADMIN row → true for any shopId.
    - Caller holds SHOP_MANAGER/STAFF on shopA → true for shopA, false for shopB.
    - Caller holds NO grants at all AND strict-scoping is OFF → true (day-one implicit GROUP_ADMIN).
      **This is the preservation case — without it, every existing KDS client breaks.**
    - Caller holds NO grants AND strict-scoping is ON → false.
    - The method performs NO writes: no JIT provision, no directory upsert. A SUBSCRIBE frame must
      never mutate state.
  </behavior>

  <action>
    Add a read-only, explicit-identity variant of the group/grant decision to `ShopAccessService`,
    e.g. `public boolean canAccessShop(UUID tenantId, UUID userId, boolean realmAdmin, UUID shopId)`.

    It must mirror `isGroupAdmin()`'s decision ladder EXACTLY (see the excerpt in `<interfaces>`) —
    realm-admin bridge, then tenant-wide GROUP_ADMIN row, then the strict-scoping-OFF
    fully-ungranted implicit admin, then the per-shop grant lookup. If the two ladders drift, the
    STOMP boundary and the HTTP boundary will disagree, which is worse than either being wrong
    consistently. Factor the shared decision into one private helper taking an explicit
    `(tenantId, userId, realmAdmin)` so `isGroupAdmin()` and the new method cannot diverge, rather
    than duplicating the branches.

    Two constraints on the implementation:
    - It must **not** call `onRequest()`. That method performs the D-09 directory upsert and the
      D-04 JIT provision; a subscribe is a read and must not write. It also short-circuits on
      read-only transactions, which is not a state this path should depend on.
    - It must **not** read `SecurityContextHolder` or `TenantContext` for identity — every input
      arrives as a parameter. It may still rely on the transactional tenant GUC for the repository
      read (see the RLS note below).

    **RLS:** `shop_staff` carries ENABLE+FORCE RLS gated on `current_tenant_id()`. The repository
    read only returns rows when the tenant GUC is pinned, which `TenantSetLocalAspect` does from
    `TenantContext` on entry to this `@Transactional` service. The caller (Task 2) is therefore
    responsible for setting `TenantContext` around the call. Confirm this actually holds by
    observing a real row come back in the Task 3 test — if the GUC is not pinned the query returns
    zero rows, which would silently degrade to "no grants", and under strict-scoping OFF that
    would read as implicit-GROUP_ADMIN and fail OPEN. Assert against a genuine grant, not just
    against a denial.
