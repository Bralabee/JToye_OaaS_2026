<objective>
Close CR-01 — `@Cacheable` short-circuits the shop-access gate — and the two read-path
defects it is entangled with: WR-08 (scoped users lose all shop-less products) and WR-07
(a malformed CSV cell returns 403 instead of 400).

Purpose: `@Cacheable` on `ShopService.getShopById` and `ProductService.getProductById` wraps
a method body that contains the `require()` call. Spring's cache interceptor runs BEFORE the
method body, and `TenantAwareCacheKeyGenerator` builds `tenant:{tenantId}:{method}:{params}`
with **no user component** — so one authorized read poisons the entry for every other user in
the tenant for 15 minutes (shops) / 10 minutes (products). This is LIVE in the default
configuration; the phase SUMMARY's "no-op under strict-scoping OFF" framing is wrong, because
`ShopAccessService:156-158` states "Once a user holds ANY explicit grant, they are scoped even
under strict-scoping OFF" — a SHOP_MANAGER granted shop A is genuinely scoped by default, and
the cache bypasses their denial.

Critically, `CacheConfig` is `@Profile("!test")` while the proving suite runs
`@ActiveProfiles("test")` — **the entire bug class is invisible to the test suite by
construction.** A fix verified under the test profile proves nothing. This plan's proof must
run with caching genuinely on.

Output: a gate that executes on every call regardless of cache state, a read path that does
not silently hide legacy data, and a proof that can actually observe the bug.
</objective>

<policy_pairing>
Plan 23-08 Task 2 established the WRITE half of the null-shop policy:
**writes to a null-shop (tenant-wide) resource are GROUP_ADMIN-only** — `require(null, role)`
throws the typed 403 for a scoped caller.

This plan implements the READ half:
**reads of a null-shop resource are tenant-wide-visible to any granted user.**

That pairing is deliberate and additive. Before this phase, every product created through the
UI's "All Shops" default and everything `importFromImages` creates carries `shop_id = NULL`.
Today a scoped user's catalogue silently shows ZERO of them (WR-08) while opening one 500s
(CR-04) — simultaneously invisible and crash-inducing. Making them readable restores pre-phase
visibility rather than removing a working good (Incremental Betterment), and RLS still confines
them to the tenant.

This is a documented policy decision, not an incidental fix — surface it in the SUMMARY so the
user can accept or reject it.
</policy_pairing>

  <behavior>
    - `getShopById(A)` by an authorized caller → returns the shop AND populates the cache.
    - `getShopById(A)` by a DIFFERENT caller scoped only to shop B, with A already cached →
      `ShopAccessDeniedException` (403). The cache hit must not short-circuit the gate.
    - `getProductById(P)` where P belongs to shop A, called by a user scoped to shop B, with P
      already cached → `ShopAccessDeniedException`.
    - Caching still genuinely works: a second read by an authorized caller is served from the cache
      (the performance good is preserved, not traded away).
    - `unless = "#result == null"` semantics preserved — a null result is still not cached.
  </behavior>

  <action>
    Restructure both methods so the authorization decision executes on every invocation while the
    data load stays cached.

    **ShopService.getShopById** — the gate runs on the method PARAMETER, so split cleanly: an
    uncached public `getShopById(shopId)` that calls `require(shopId, ShopRole.STAFF)` first, then
    delegates to a `@Cacheable` loader holding the existing `findByIdAndTenantId(...).map(toDto)`
    body.

    **ProductService.getProductById** — the gate needs the loaded entity's `shopId`, so invert:
    call the `@Cacheable` loader FIRST, then gate on the returned DTO's `shopId` before returning
    it. Reading a cached DTO and then denying is correct — the authorization decision is what must
    run every time, not the database round-trip.

    **Self-invocation trap — this is the failure mode that makes the fix silently useless.** Spring
    uses proxy-mode caching (`CacheConfig` has no `AdviceMode.ASPECTJ` and no `exposeProxy`), so a
    plain `this.loadShopCached(...)` call NEVER passes through the caching interceptor and the cache
    would silently stop working — exactly the defect WR-01 documents elsewhere in this codebase.
    Avoid it by either (a) extracting the cached loader into its own small `@Component` collaborator
    (preferred — no proxy trickery, obviously correct), or (b) injecting a `@Lazy` self-reference.
    Task 3's proof asserts the cache is actually populated, so a self-invocation mistake will be
    caught rather than shipped.

    Delete the now-false residual comments: `ShopService.java:94-99` claims "a DENY always throws
    before any lookup and nothing is cached for an unauthorized caller" (true for the miss path,
    irrelevant to the exploitable hit path) and `ProductService.java:114-115` frames the test-profile
    cache no-op as a footnote rather than a coverage hole. Replace both with an accurate note stating
    the gate runs outside the cache boundary and why.

    Do NOT attempt to fix this by adding a user component to the cache key. That would multiply
    cache entries per user, defeating the cache's purpose, and it would leave the gate still
    structurally inside the cached body — the next refactor would reintroduce the bypass.
  </action>
