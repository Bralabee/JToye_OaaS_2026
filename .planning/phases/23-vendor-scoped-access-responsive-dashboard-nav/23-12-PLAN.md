<objective>
Close WR-05 (grant validates neither shop tenancy nor user existence), deliver the backend
half of CR-08 (`GET /api/v1/staff/me` — the server answering the GROUP_ADMIN question the
frontend currently guesses at from a client-side JWT parse), and close WR-10 (`user_directory`
hands every colleague's email to every caller under the default configuration).

Purpose: these three share the staff backend surface and are best changed together.
- WR-05: `shop_staff.shop_id REFERENCES shops(id)` and PostgreSQL referential-integrity checks
  **bypass RLS**, so the FK happily accepts another tenant's shop id. The grant is written
  "successfully", lands in the user's `grantedShopIds()`, and is then filtered out by RLS
  downstream — so there is no data leak, but the operator gets a silent success that confers
  nothing and no way to diagnose why the user sees no data.
- CR-08 backend: `isGroupAdminFromSession()` derives GROUP_ADMIN solely from the Keycloak realm
  `admin` role, while the backend's model is "anyone holding a NULL-shop GROUP_ADMIN row" — which
  under the default configuration is every JIT-provisioned user. `ShopAccessService.isGroupAdmin()`
  is already the single source of truth; this plan exposes it so the client can stop guessing.
- WR-10: before V52 this PII did not exist in the platform at all. FORCE RLS protects it
  cross-tenant; within a tenant it is broadly readable by default, and `GdprService` does not
  touch it.

Output: a staff backend that validates its inputs, tells a client what it may do, and minimises
the PII surface the phase introduced.
</objective>
