<canonical_pattern>
The Phase-23 access suites already authenticate the production way. Copy this — do not invent a new mechanism.

For **SecurityContext-based** tests (`ShopAccessEnforcementIntegrationTest` lines 477-490):
```java
private void authenticate(UUID sub, boolean realmAdmin) {
    Jwt jwt = Jwt.withTokenValue("test-token")
            .header("alg", "none")
            .subject(sub.toString())                       // UUID subject — the fail-closed gate requires this
            .claim("email", "user-" + sub + "@example.com")
            .claim("name", "Test User " + sub)
            .build();
    List<GrantedAuthority> authorities = realmAdmin
            ? List.of(new SimpleGrantedAuthority("ROLE_admin"))   // realm admin ⇒ implicit GROUP_ADMIN (day-one)
            : List.of();
    SecurityContextHolder.getContext().setAuthentication(new JwtAuthenticationToken(jwt, authorities));
}
```

For **MockMvc** tests, the equivalent per-request post-processor is:
```java
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.jwt;
// ...
mockMvc.perform(post("/api/v1/shops").with(jwt().jwt(j -> j
        .subject(UUID.randomUUID().toString())
        .claim("email", "e@example.com")))
        .authorities(new SimpleGrantedAuthority("ROLE_admin"))   // when the test acted as an admin
        ...)
```

**Access intent is the invariant.** A migration must reproduce the access the original test asserted, NOT hand every
test blanket admin:
- A test whose `@WithMockUser` acted as a general authenticated operator (create/update a shop, read a product) →
  give it a UUID-subject JWT with `ROLE_admin` (realm admin ⇒ implicit GROUP_ADMIN, matching day-one "everyone can do
  everything"). This is the common case.
- A test that deliberately asserts a DENIAL or a scoped/limited role → give it a UUID-subject JWT WITHOUT admin and,
  if it needs a specific shop grant, seed the matching `shop_staff` row (mirror `ShopAccessEnforcementIntegrationTest`
  / `ShopAccessJitProvisionTest` setup). Do not turn a "should be denied" test green by over-granting.
- If a test relied on JIT day-one provisioning, a UUID-subject JWT making a write-capable request auto-provisions
  GROUP_ADMIN while strict-scoping is OFF (the default) — confirm the assertion still means what it meant.

Never edit `ShopAccessService` or any main-source file. If a test cannot be made green without touching production
code, STOP and report — that would signal a real production regression, not test debt.
</canonical_pattern>
