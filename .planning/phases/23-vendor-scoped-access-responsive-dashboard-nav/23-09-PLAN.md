<objective>
Close CR-05 (role changes silently no-op **and report success**) and CR-06 (last-GROUP_ADMIN
guard is a check-then-act race), and fold in WR-02 (grants bypass Envers) and IN-03
(duplicated message string).

Purpose: VSA-04's promise is "a GROUP_ADMIN can list, grant, and revoke staff roles per shop".
Today **no role can ever be changed through the API**: `insertGrantIfAbsent` is
`ON CONFLICT ... DO NOTHING` with a conflict target that excludes `role`, so a downgrade
no-ops, the service re-selects the row carrying the OLD role, and returns HTTP 200 with the
UI toast "Access granted". The operator receives positive confirmation of a change that did
not happen. Separately the last-admin guard can be raced into a zero-admin tenant, which
under strict-scoping ON is a permanent lockout recoverable only by direct DB access.

Output: a staff write path that applies what it reports, cannot be raced into lockout, and
leaves a complete audit trail.
</objective>

  <behavior>
    - Grant (Alice, shop A, SHOP_MANAGER) where no row exists → row created, `created = true` → 201.
    - Grant (Alice, shop A, SHOP_MANAGER) again, identical role → no change, `created = false` → 200,
      canonical row returned. Idempotency preserved (the agent-readiness contract).
    - Grant (Alice, shop A, STAFF) where Alice already holds SHOP_MANAGER on shop A → **role is
      updated to STAFF**, `created = false` → 200, and the returned DTO carries STAFF (not the stale
      SHOP_MANAGER). This is the case that is currently broken in the security-relevant direction.
    - Grant (Alice, shop A, SHOP_MANAGER) where Alice holds STAFF → role upgraded to SHOP_MANAGER.
    - A concurrent duplicate grant does not produce an untyped `DataIntegrityViolationException` 500.
    - `shop_staff_aud` gains a revision for the create AND for the role change.
  </behavior>

  <action>
    Restructure `grant()` so the write goes through the Hibernate session rather than the native
    `ON CONFLICT DO NOTHING` insert. Envers only observes session-managed writes, so this fixes
    CR-05 and WR-02 together — a native upsert (`DO UPDATE SET role = EXCLUDED.role`) would fix the
    role change but leave the audit trail recording only revokes, which is the worse half of WR-02:
    "who granted whom GROUP_ADMIN on which shop, and when" is the single most forensically valuable
    question about this table and it is currently unanswerable.

    Shape: re-select the canonical row for `(tenantId, userId, shopId)` FIRST (the existing
    `findByTenantIdAndUserId(...)` + `Objects.equals(r.getShopId(), shopId)` filter is already
    written and correct — reuse it). Then:
    - absent → construct and `save()` a new `ShopStaff` with `created_by = currentCallerSub()`;
      `created = true`.
    - present with the same role → return it untouched; `created = false`. Do not write, do not
      bump a revision for a no-change replay.
    - present with a different role → `setRole(role)` on the managed entity and let the flush write
      it; `created = false`.

    Preserve race-safety, which the native `ON CONFLICT` was providing: wrap the insert branch so a
    concurrent duplicate surfacing as `DataIntegrityViolationException` is caught, the row re-selected,
    and the result returned as an idempotent replay rather than a 500. Note this loses `ON CONFLICT`
    elegance and gains audit correctness — that is the deliberate trade named in WR-02.

    Keep the two existing guards ahead of the write, unchanged in order: the tenant-wide-GROUP_ADMIN
    rule (`role == GROUP_ADMIN && shopId != null` → `IllegalArgumentException` → 400) and the D-11
    downgrade guard. **The D-11 guard becomes load-bearing here in a way it was not before:** it
    previously sat in front of a write that could not change a role anyway. Now that downgrades
    genuinely apply, that guard is the only thing preventing the sole GROUP_ADMIN being downgraded —
    confirm it still fires before the new update path, and note this in the javadoc.

    IN-03: the message "Cannot ... the last GROUP_ADMIN in this tenant — grant another GROUP_ADMIN
    first" appears twice with a one-word difference (lines 128-129 and 168-169). Extract to named
    constants so the wording cannot drift; keep the two variants distinct ("downgrade" vs "revoke")
    because plan 23-13 fixes the frontend copy that currently says "remove" on the grant path (IN-02).
  </action>

  <behavior>
    - One revoke of the sole tenant-wide GROUP_ADMIN → `LastGroupAdminException` → 409 (unchanged).
    - Two concurrent revokes targeting two DIFFERENT GROUP_ADMIN rows in a two-admin tenant → exactly
      one succeeds; the other blocks, re-reads `count == 1`, and 409s. The tenant never reaches zero
      GROUP_ADMINs.
    - Two concurrent downgrade-grants against a two-admin tenant → same outcome.
    - A revoke of a non-GROUP_ADMIN row is unaffected and takes no meaningful lock contention.
  </behavior>

  <action>
    Add a pessimistic-lock finder to `ShopStaffRepository`:

    ```java
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT s FROM ShopStaff s WHERE s.tenantId = :tenantId AND s.shopId IS NULL AND s.role = 'GROUP_ADMIN'")
    List<ShopStaff> lockTenantGroupAdmins(@Param("tenantId") UUID tenantId);
    ```

    Call it at the TOP of `revoke()` and at the top of the downgrade branch of `grant()` — before
    any counting — so the whole check-then-act sequence is serialized for the duration of the
    transaction. Because both concurrent transactions select the same row set, the second blocks
    until the first commits, then re-reads the true post-commit count and correctly 409s.

    Two correctness details to confirm rather than assume:
    - The lock query selects only tenant-wide (`shop_id IS NULL`) GROUP_ADMIN rows, which is the exact
      set the invariant is about. `grant()` already rejects shop-scoped GROUP_ADMIN grants, so this
      set and `countByTenantIdAndRole(tenantId, GROUP_ADMIN)` agree — verify that is still true after
      Task 1's changes, since a divergence would make the lock guard the wrong rows.
    - `shop_staff` carries FORCE RLS. Confirm the locking SELECT still runs under the pinned tenant
      GUC (it is inside the existing `@Transactional` service, so `TenantSetLocalAspect` applies) and
      that a lock taken by tenant A cannot be observed or blocked by tenant B.

    Do NOT switch the transaction isolation level, and do not add a deferred constraint trigger —
    a row lock is the smaller change and keeps the invariant expressed where its error message lives.
  </action>
