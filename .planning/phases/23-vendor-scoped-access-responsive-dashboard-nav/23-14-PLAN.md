<objective>
Close CR-07 — **enabling `strict-scoping` tightens nothing** — together with WR-09 (JIT hands
machine accounts permanent GROUP_ADMIN) and WR-01/WR-11 (the membership cache never engages, so
D-05's revocation guarantee is unproven and its eviction path is dead code).

**This plan deliberately revises locked decisions D-04, D-12 and D-05.** That is why it exists:
CR-07 is a design defect in the D-04/D-12 pair, not a code patch. It carries a decision
checkpoint so the user can accept or reject the revision before it ships.

Purpose: while `strict-scoping` is OFF (the default), `onRequest()` writes a **real, persistent**
tenant-wide GROUP_ADMIN row into `shop_staff` for every authenticated caller on their first
write-capable request. Flipping `ACCESS_STRICT_SCOPING=true` only stops *new* provisioning —
every user who has ever made a write request retains an explicit tenant-wide GROUP_ADMIN grant,
which `resolveMembership` honours unconditionally.

The concrete failure: a vendor with 20 staff runs for three months on the default, then enables
strict-scoping to lock down access before onboarding contractors. **Nothing changes.** All 20
still hold GROUP_ADMIN, can read and write every shop, create and delete shops, and manage
staff. The operator gets no signal that the control did not engage. The config comment claims ON
"makes ungranted non-admins deny-by-default so a vendor can genuinely tighten" — for any tenant
with existing usage, that is false. D-12's entire purpose was to be the off-ramp D-04 lacked,
and it is not reachable.

Output: a strict-scoping switch that does what it says, with no lockout risk and no silent
privilege retention.
</objective>

## The revision, stated explicitly

**D-04 (JIT lazy-provision) — REFINED, not reversed.**
Unchanged: the first authenticated request from an ungranted tenant user still auto-creates a
tenant-wide GROUP_ADMIN row while strict-scoping is OFF, preserving day-one "everyone can do
everything" exactly. **New:** those rows are explicitly marked with their provenance
(`grant_source = 'JIT'`) so they are distinguishable from a deliberate operator grant
(`grant_source = 'OPERATOR'`). D-04's rejection of fail-OPEN is strengthened, not weakened.

**D-12 (strict-scoping switch) — REVISED.**
Was: turning it ON stops new auto-provisioning.
Now: turning it ON stops new auto-provisioning **and stops honouring JIT-sourced tenant-wide
GROUP_ADMIN rows.** Operator-created grants are honoured unchanged. This is what makes the
off-ramp actually reachable — the property D-12 was written to deliver.

**Lockout safety (new sub-decision).** If de-honouring JIT rows would leave a tenant with zero
GROUP_ADMINs, the **oldest** JIT-sourced tenant-wide GROUP_ADMIN row (by `created_at`, tie-broken
by `id`) continues to be honoured as the bootstrap admin, and that fact is logged at WARN. The
realm-`admin` bridge remains an independent recovery backstop, but a tenant with no realm admin
must not be able to lock itself out — and CR-06's guard cannot help here because the flip is a
config change, not a revoke.

**D-05 (immediate revocation via membership-cache eviction) — MECHANISM CORRECTED.**
D-05's stated property is right and is preserved. Its mechanism was inert: `resolveMembership` is
`@Cacheable` but is only ever reached by self-invocation, and Spring's proxy-mode caching means
the interceptor never runs. The cache is never populated or read, the 5-minute TTL is dead
config, and every eviction targets keys that never exist. This plan makes the mechanism real and
proves the eviction, rather than leaving a documented guarantee resting on dead code.

**Incremental Betterment check — what this displaces, and how each is preserved:**
| Currently-working good | Disposition |
|---|---|
| Day-one "everyone can do everything" (strict OFF) | **Preserved exactly.** Nothing changes while the flag is OFF — JIT rows are still written and still honoured |
| Existing deliberate operator grants | **Preserved.** Only JIT-sourced rows are de-honoured |
| Tenant never locked out of staff management | **Preserved** by the bootstrap-admin rule, which did not previously need to exist |
| Machine/service callers | **Preserved** via 23-08's explicit allowlist; they simply stop acquiring GROUP_ADMIN rows by accident |
| Existing `shop_staff` rows written before V57 | **Preserved.** Backfill rule below |
</revised_decision_semantics>
