<objective>
Ship the GROUP_ADMIN-only staff-management REST backend (VSA-04): list the login-populated
directory + current grants, grant a `(user, shop|null, role)`, and revoke a grant — with the
last-GROUP_ADMIN 409 guard (D-11), immediate revocation via membership-cache eviction (D-05), and an
**idempotent grant** so a retried/duplicate grant replays cleanly instead of surfacing an untyped
unique-constraint 500 (CLAUDE.md agent-readiness contract — mutating endpoints must be provably
idempotent or return a typed conflict). Grant targets come from the `user_directory` (D-09);
invitations/account creation stay in Keycloak (out of scope). This is a Wave-3 sibling of 23-03 with
zero same-wave file overlap — both depend only on `ShopAccessService` (23-02) and neither modifies it.
(This plan does extend `ShopStaffRepository` from 23-01 with one native idempotent-insert method — a
legitimate downstream edit, 23-04 wave 3 is below 23-01 wave 1.)

Purpose: This is the write side of the access model — the screen (23-06) calls these endpoints so a
GROUP_ADMIN can genuinely scope staff, a grant/revoke takes effect on the target's very next request
with no stale window, and an agent (or a double-submit) re-issuing the same grant gets a stable,
typed replay rather than a 500.

Output: `StaffController` + `StaffManagementService` + the `ShopStaffRepository.insertGrantIfAbsent`
native method + record DTOs + `StaffManagementIntegrationTest`.
</objective>

| Boundary | Description |
|----------|-------------|
| caller → staff-management endpoints | only a GROUP_ADMIN (or realm-admin) may list/grant/revoke |
| revoke → target's cached membership | eviction must land before the target's next request |
| final GROUP_ADMIN → self-removal | must be blocked to avoid tenant-level lockout |
| retried/duplicate grant → unique index | a re-issued grant must replay, not surface a raw constraint 500 |
