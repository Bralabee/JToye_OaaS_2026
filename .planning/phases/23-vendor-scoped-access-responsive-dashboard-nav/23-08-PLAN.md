<objective>
Close CR-03 (system-principal fail-OPEN) and CR-04 (`require(null, role)` NPE) — the two
defects that live entirely inside `ShopAccessService`.

Purpose: `isSystemPrincipal()` currently maps "I cannot parse this identity" to
"unrestricted GROUP_ADMIN", and that path is reachable over HTTP on `/api/v1/staff`
(full `user_directory` PII read + self-grant of any role on any shop). This directly
contradicts locked decision **D-04**, which explicitly rejected fail-OPEN as
"unacceptable for an auth boundary". Separately `require(null, role)` throws NPE →
HTTP 500 on a field (`Product.shop_id`) that is nullable *by design*.

Output: a gate that fails CLOSED on every unparseable or unexpected identity shape,
keeps genuine internal and machine callers working through explicit mechanisms, and
never crashes on a null shop.
</objective>

    - `auth` is a Jwt whose `sub` does NOT parse as a UUID:
        · client-id claim is present in the configured machine allowlist → treated as a machine
          principal, shop-scoping bypassed (RLS still tenant-scopes it), logged at INFO once.
        · otherwise → DENIED with the typed `ShopAccessDeniedException`, never escalated.

  <action>
    Rework `isSystemPrincipal()` so trust is never inferred from an identity the service cannot
    parse. Per the confirmed gap in 23-VERIFICATION.md and locked decision D-04 (fail-open
    explicitly rejected), the ONLY shape that continues to bypass shop-scoping without an explicit
    declaration is `Authentication == null`.

    Introduce an explicit machine-principal allowlist rather than inferring trust: add a
    config-injected `@Value("${jtoye.access.machine-client-ids:}")` bound to a `Set&lt;String&gt;`
    (Spring converts a comma-separated list), **defaulting to EMPTY so the default posture is
    fail-closed**. Add the matching key under the existing `jtoye.access` block in
    `application.yml` as `machine-client-ids: ${ACCESS_MACHINE_CLIENT_IDS:}` with a comment
    explaining it is a key not a secret and that an empty value denies all non-UUID-subject tokens.
    Resolve the caller's client id from the standard Keycloak claims in preference order
    `azp`, then `client_id` — confirm which the project's tokens actually carry before relying on
    one; if neither claim is present the token is not a declared machine caller and is denied.

    Split the logic into two clearly-named private predicates so the two cases can never be
    conflated again: `isInternalCaller()` (auth == null) and `isDeclaredMachineClient(Jwt)`
    (non-UUID sub AND azp/client_id in the allowlist). Have `isGroupAdmin()` short-circuit on
    `isRealmAdmin() || isInternalCaller() || isDeclaredMachineClient(jwt)`.

    For the denial path: a request-scoped principal that is neither a UUID-subject vendor user nor
    a declared machine client must produce `ShopAccessDeniedException`, NOT the
    `IllegalStateException` that `currentUserId()` currently throws — an auth failure must be a
    typed 403, not an untyped 500. Guard the entry points (`require`, `requireGroupAdmin`,
    `grantedShopIds`) so the unparseable-subject case is converted before `currentUserId()` is
    reached.

    prevented by Spring Security rejecting unauthenticated requests with 401 before any gated
    service is entered.

    the measured blast radius above; that is a separate, larger change and is deferred with reason

    `NullPointerException` in BOTH the populated and empty cases (the reviewer confirmed this by

    Handle the null shop explicitly and BEFORE the map lookup, stating the policy in code:

    **Policy (write side): a null `shopId` denotes a tenant-wide / unassigned resource; only a
    GROUP_ADMIN may act on it.** A non-GROUP_ADMIN caller gets
    `new ShopAccessDeniedException(null, ShopRole.GROUP_ADMIN)`.

    half (legacy `shop_id IS NULL` products staying visible to scoped users) is implemented by plan
    23-09 in `ProductService`/`ProductRepository`, which depends on this plan. State the pairing in
    the javadoc so the two halves cannot drift: **writes to a null-shop resource are GROUP_ADMIN-only;
    reads of a null-shop resource are tenant-wide-visible to any granted user.** This pairing is
    additive — it preserves the pre-phase visibility of legacy catalogue data rather than silently
    removing it (Incremental Betterment).

    Note the `Membership` map may in future arrive as a deserialized `LinkedHashMap` (which would
    NOT reproduce the NPE) if the membership cache is ever made real — the explicit null guard makes
    the behaviour cache-state-independent, which is why the guard goes in `require` and not in a
    map-construction change.
