<objective>
Answer RESEARCH Open Question 2 with measurements and an owner decision: what do Jackson 3's
changed defaults do to the bytes this API publishes and to the inputs it accepts, and does Boot's
mapper keep them?

Purpose: D-01 moves the app to Jackson 3 but says nothing about its defaults
(SORT_PROPERTIES_ALPHABETICALLY, enum toString, FAIL_ON_NULL_FOR_PRIMITIVES, FAIL_ON_TRAILING_TOKENS,
date handling). Property order alone is harmless to every JSON consumer; a value-format change is a
published-contract change to the frontend, edge-go, MCP integrators and vendors' webhook endpoints,
which CONTEXT puts out of scope unless the framework forces it. Only the owner can accept that.

Output: a permanent wire-contract test, a measured diff and verdict, the owner's decision applied.
</objective>

  <context>

    the DSAR acknowledgement and the 401/429 problem bodies, and reads every request body. Undo cost:
    once Boot-4 pods have served responses and written outbox and webhook payloads in a chosen shape,

    (38-10) uses a dedicated frozen mapper, AMQP (38-08) and Redis (38-09) build their own mappers.

  </context>
  <options>
    <option id="jackson3-defaults">
      <name>A. Keep Jackson-3 defaults (no configuration)</name>
      <pros>Boot 4's intended state; nothing to remove later; fits ORDER-ONLY verdicts (JSON objects are unordered)</pros>
      <cons>Any VALUE-DIFF row or changed acceptance probe becomes a deliberate contract change to name in the PR and ADR-0006</cons>
