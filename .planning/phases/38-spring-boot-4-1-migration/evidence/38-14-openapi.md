### 3. The newly-required set

Query, run over every `components.schemas` entry. It emits each field in the new `required` array that is
absent from the old one:

```
jq -r --slurpfile o $SCRATCH/old.json '.components.schemas | to_entries[] | .key as $k
  | (.value.required // []) as $nr | ($o[0].components.schemas[$k].required // []) as $or
  | $nr[] | select(. as $f | $or | index($f) | not) | "\($k)\t\(.)"' docs/api/openapi-snapshot.json
  > $SCRATCH/newly-required.tsv                                         -> jq_rc=0
awk 'NF{n++} END{print n+0}' $SCRATCH/newly-required.tsv                -> 18   (> 0, not VOID)
distinct schemas                                                        -> 11
```

Completeness checks on the query:

- **No field left `required`.** The reverse query, old `required` minus new, prints nothing.
- **No `required` array sits outside a top-level schema, apart from these 6.** In both files the only other
  `required` arrays are the same 6 inline multipart request bodies: `/products/bulk/csv`, `/products/{id}/image`,
  `/products/{id}/image/analyze`, `/products/{id}/images`, `/shops/{id}/banner` and `/shops/{id}/logo`. Paths
  are unchanged (0 differ), so the top-level query sees every new entry.
- **The VOID branch fires on an empty set.** Run on an empty file, the count prints `VOID n=0`. On the real
  set it prints `non-empty n=18`.

What the inventory rows mean: 38-02's `RequestBodyConstraintEnforcementTest` built them on Boot 3.5.16 from
the live handler mappings. Each row is a `@Valid` request body property that rejects null. 38-02 also ran one
real request without `customerEmail` (row 11) and got 400 `errors/validation`. So on Boot 3.5 the server
already rejected every one of these 18 requests when the field was missing. springdoc 3.1.1 now writes the
constraint into the contract.

**The relation is exact, in both directions.** Each of the 43 distinct (DTO, property) pairs in the inventory
was looked up in the old and in the new snapshot:

```
 22 NotNull  old=true  new=true     springdoc 2.8.6 already documented @NotNull as required
 18 NotBlank/NotEmpty  old=false new=true     the 18 newly required pairs above (15 NotBlank + 3 NotEmpty)
  3 NotBlank old=true  new=true     already required on 3.5: CreateProductRequest sku/title/ingredientsText,
                                    each carrying an explicit @Schema(required = true) (CreateProductRequest.java:19/24/34)
  0 rows    new=false
```

So the new snapshot's `required` covers the whole enforced inventory. What is new is exactly springdoc 3's
mapping of `@NotBlank`/`@NotEmpty` to `required`. No field became required that the server did not already
require.
