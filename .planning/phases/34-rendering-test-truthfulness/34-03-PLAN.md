<feature>
  <name>Customer session external store with a synchronous, stable snapshot</name>
  <files>frontend/lib/customer-session-store.ts, frontend/hooks/use-customer-session.ts, frontend/hooks/__tests__/use-customer-session.test.tsx</files>
  <behavior>
    - `getSnapshot()` before any refresh returns `null`.
    - `getSnapshot()` returns the SAME object reference on repeated calls while nothing changed — a
      new object per call makes React re-render forever. Asserted with `toBe`, not `toEqual`.
    - `getServerSnapshot()` returns `null` and never touches `window`, `document` or `localStorage`.
    - `refresh()` awaits `getCustomerSession()`; when it resolves to a session, the snapshot becomes
      that session's `.profile` and every subscriber is notified exactly once.
    - A second `refresh()` resolving to an equivalent profile does NOT change the snapshot reference
      and does NOT notify — otherwise every 1s poll re-renders three headers.
    - `refresh()` resolving to `null` (signed out, or an aged-out session) clears the snapshot to
      `null` and notifies. A stale cached profile must never survive a null answer.
    - `refresh()` rejecting leaves the previous snapshot unchanged and does not throw to the caller.
    - `subscribe(cb)` on the FIRST subscriber attaches: `window` `focus`, `document`
      `visibilitychange` (acting only when `document.visibilityState === "visible"`), `window`
      `storage` (acting only on the two keys above), and the post-OAuth poll — `setInterval` every
      1000ms cleared by a `setTimeout` at 5000ms.
    - The teardown returned by the LAST unsubscribe removes all three listeners and clears both
      timers; a mount/unmount cycle leaves no listener and no live timer.
    - A `storage` event for an unrelated key triggers no refresh.
  </behavior>
  <implementation>
    Module-level `let cached: CustomerProfile | null = null` plus `listeners = new Set<() => void>()`,
    exported `subscribe` / `getSnapshot` / `getServerSnapshot` / `refresh`. Equivalence is decided by
    a stable key on the profile (read the field names out of `CustomerProfile` at
    `lib/customer-auth.ts:39`; prefer an id/sub, falling back to email) — not by JSON.stringify of
    the whole object, which would churn on any server-added field. The hook becomes
    `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)` returning
    `{ profile, refresh }`, where `refresh` is the store's exported function so the consumers'
    existing `refresh()` calls keep working.
  </implementation>
</feature>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser storage → UI identity | `jtoye-customer-logged-in` / `-expires-at` are attacker-writable markers; they must never by themselves produce a signed-in UI |
| server session (HttpOnly cookies) → client | `getCustomerSession()` is the only authority for "who is signed in" |
| module state → render | A module-level cache in a client bundle is per-tab, but a server render must never read it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-03-01 | Spoofing | `customer-session-store.ts` snapshot | mitigate | The store reads only `getCustomerSession()` (server truth); `isLoggedIn()` is never called. Playwright Block 1 asserts a planted marker yields a signed-out pill, and the break arm proves that block can fail |
| T-34-03-02 | Information Disclosure | stale cached profile after sign-out/expiry | mitigate | A `null` answer always clears `cached` and notifies; a Jest case asserts it and a break arm proves the case fails when the clearing is removed |
| T-34-03-03 | Information Disclosure | server render leaking a profile | mitigate | `getServerSnapshot()` returns `null` and touches no browser API; `app/layout.tsx` keeps `dynamic = "force-dynamic"` so nothing per-visitor is cached (ASVS V8) |
