## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| identity provider redirect → callback page | `?code=` and `?state=` arrive from a redirect the user's browser followed; both are untrusted input |
| callback page → post-auth navigation | `getAuthReturnUrl()` decides where the user lands after a successful exchange |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04-01 | Tampering | error copy rendered from query input | mitigate | Both error strings are module constants; no `setError` call takes a template literal or any `searchParams` value. Grep-asserted in the acceptance criteria |
| T-34-04-02 | Elevation of Privilege | open redirect via the return URL | accept | Unchanged by this plan — `safeReturnTo` (`customer-auth.ts:459`) already constrains it. `git diff --name-only -- frontend/lib/customer-auth.ts` must be empty at plan end |
| T-34-04-03 | Spoofing | one-time authorization code exchanged twice | mitigate | The effect guards the exchange with a ref so a strict-mode double invocation cannot burn the code, and the reason is written into the file |
| T-34-04-04 | Information Disclosure | the code/state landing in a log or a test artifact | accept | The spec uses a synthetic `not-a-real-code`; no real IdP code is ever recorded |
| T-34-04-SC | Tampering | npm installs | mitigate | Nothing is installed; `git diff --name-only -- frontend/package.json frontend/package-lock.json` must be empty |
