<objective>
Close the third coverage tier honestly: measure Java coverage across the unit suite AND the
Testcontainers suite, gate on the aggregate, and make a run that could not measure it VOID rather
than pass.

ROADMAP criterion 4, verbatim: *"#110 is narrowed to coverage ... JaCoCo, the
generated-but-unconsumed Go coverage profile, and a Jest `coverageThreshold` remain."*

Purpose: `build.gradle.kts:183-186` excludes the `testcontainers` tag from `test`, and
`integrationTest` runs ONLY that tag; both use `sourceSets["test"]`. RESEARCH measured what that
means for a threshold — LINE 62.12% from `test` alone against 87.55% aggregated, a 25.43-point gap,
with the integration suite contributing 607 tests across 132 classes. A "60% line" gate on `test`
alone would be satisfied with about two points of headroom over a codebase that is actually at
87.55%: incapable of catching a regression, and publishing a number wrong by a quarter of the
codebase. The orchestrator's directive is that this question is resolved by measurement, and the
measurement resolves it to AGGREGATE.

The second half is the hazard: the two suites run in DIFFERENT CI jobs, and `integration-tests` is
path-filtered and reports SUCCESS while skipping (`ci-cd.yaml:203, :211, :231`). A coverage gate
that depended on it would be wrong on exactly the runs that skip. So the gate runs under the same
guard as the suite it measures, VOIDs if its inputs are absent, and the job's skip notice states in
words that Java coverage was NOT evaluated on that run — success there must never read as coverage.

Output: the jacoco build wiring, an aggregate threshold gate, the CI hand-off, and a floor
calibrated against a real CI run.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI artefact hand-off | `test.exec` travels between two jobs as an artifact and is trusted by the aggregate report |
| a required check's SUCCESS → merge decision | The integration job reports success while skipping, by design |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-09-01 | Repudiation | a skipped integration job read as a coverage pass | mitigate | The gate runs only under the suite's own `if:` guard, and the skip-notice step states in words that Java coverage was not evaluated on that run |
| T-34-09-02 | Repudiation | a unit-only report passing as the aggregate | mitigate | The gate asserts the aggregate exceeds the unit-only figure when both are present, and VOID ARM 3 exercises exactly this case |
| T-34-09-03 | Repudiation | a stale report from `core-java/build/` | mitigate | Every path is `build-local`; the PATH ARM records both directories' timestamps |
| T-34-09-04 | Tampering | a floor lowered to go green | mitigate | Floors are constants in version control with their measurement, date, margin and the CI-vs-local comparison beside them |
| T-34-09-05 | Tampering | artifact substitution between jobs | accept | Both jobs run in the same workflow run under GitHub's artifact scoping; no external input is trusted. Recorded rather than mitigated because the platform boundary is the control |
| T-34-09-06 | Information Disclosure | coverage artefacts | accept | `.exec` and CSV carry class names and counters, no data and no secrets |
| T-34-09-SC | Tampering | build-plugin supply chain | mitigate | `jacoco` is a CORE Gradle plugin with the tool version pinned to the 0.8.12 measured here; no third-party plugin, no new dependency. `git diff -- core-java/build.gradle.kts` must show no `implementation`/`testImplementation` addition |
</threat_model>
