`DatabaseConfigurationValidator` (`core-java/src/main/java/uk/jtoye/core/config/`) emits, on the
`ApplicationReadyEvent` path:
- `DATABASE SECURITY CONFIGURATION CHECK`
- `Database username: {}`
- `User '{}' is NOT a superuser (RLS will be enforced)`
- `DATABASE SECURITY VALIDATION PASSED` on success
- `DATABASE SECURITY VALIDATION FAILED` on failure (which also refuses to start)
So the positive assertion is `grep -c "is NOT a superuser"` >= 1 AND
`grep -c "DATABASE SECURITY VALIDATION PASSED"` >= 1, and the negative is
`grep -c "DATABASE SECURITY VALIDATION FAILED"` == 0.

**Canonical-ref correction:** `WebSocketConfig` lives at
`core-java/src/main/java/uk/jtoye/core/websocket/WebSocketConfig.java`, not `.../config/`. The line
numbers CONTEXT.md and RESEARCH.md cite are right (`cors.allowed-origins` at 57-58,
`setAllowedOrigins` at 85, `enableStompBrokerRelay` + `setClientLogin`/`setSystemLogin` at 67-72);
only the package is wrong. Record the correction.

Anti-anecdote rules (`26-RESEARCH.md` § "Making the live proofs reproducible", restated in
`26-VALIDATION.md`):
1. One idempotent entry point — everything runs through `scripts/k8s-local-up.sh`. If the rehearsal
   cannot be re-run from a stopped cluster by one command, it is not reproducible.
2. Pin evidence to code identity — record the four image identities with the results.
3. Assert negatives with COUNTS, not eyeballs — a missing log line and an absent grep hit look
   identical otherwise.
4. Falsify the backup, don't confirm it — show a `jtoye_app` dump restoring to `products = 0` AND the
   `jtoye_backup` dump restoring to `products > 0`.
5. Prove the ingress path, not localhost — every live URL in the evidence must be
   `http://api.jtoye.local` or `http://app.jtoye.local`. A `localhost:9090` in the evidence means the
   compose apps were up and the XOR guard was bypassed, and the run does not count.
6. Capture the dry-run output VERBATIM — a dry-run that silently skipped an admission webhook and one
   that genuinely passed share the same exit code.

Environment facts to RE-PROBE before starting (research's host findings carry a 7-day validity and a
second session can drive this checkout — see the `env_concurrent_working_tree` memory): image
freshness, compose state, the minikube profile's state, the `jtoye_backup` role, and the
`jtoye-db-backups` bucket.

A1 stale-state caveat: a Stopped minikube profile preserves etcd, so namespaces and Secrets from the

namespaces before trusting anything.

PIT-8: `kubectl apply -f k8s/local/namespace.yaml` must precede `apply -k … --dry-run=server`,
because the dry-run does not create the Namespace it is validating.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer host → live cluster | Real mutating applies against a real API server |
| cluster pods → shared dev Postgres | The connection identity decides whether RLS applies |
| CronJob → host MinIO | Full-database dumps leave the database and land in object storage |
| rehearsal output → project record | Evidence becomes the basis for marking a requirement complete |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-38 | Tampering | applying to the wrong cluster | mitigate | ASVS V14. Every command runs through `scripts/k8s-local-up.sh` / `k8s_local_kubectl`, which refuse unless the resolved context is the configured local minikube profile and its server matches that profile's IP. `kubectl config current-context` is unset and the only other context is employer AKS. |
