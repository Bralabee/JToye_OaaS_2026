<!-- Two live blockers discovered during planning. Neither appears in CONTEXT.md or RESEARCH.md.
     Both are verified against the committed files. -->

**Blocker 1 — the local realm rejects the ingress callback.** `infra/keycloak/realm-export.template.json`
has NO `frontend` client (verified: `grep -c '"clientId" : "frontend"'` returns 0). The client the
frontend actually uses is `core-api` (`.env` and `.env.example` both set
`KEYCLOAK_CLIENT_ID=core-api`), and its `redirectUris` are exactly
`http://localhost:8080/*`, `http://localhost:3000/*`, `http://localhost:3100/*`,
`http://localhost:9090/*` — none of which match a NextAuth callback at
`http://app.jtoye.local/api/auth/callback/keycloak`. Keycloak would reject the authorize request with
`Invalid parameter: redirect_uri`. Its `webOrigins` is already `"*"` and
`post.logout.redirect.uris` is `"+"` (meaning: derive from redirectUris), so ONLY `redirectUris`
needs the additive entry.

**Blocker 2 — the frontend's OIDC client id is a hardcoded literal that does not exist in the dev
realm.** `k8s/base/frontend-deployment.yaml:64-65` sets `KEYCLOAK_CLIENT_ID` to the literal
`"frontend"`. That client does not exist in `jtoye-dev`, so the local pod would start an OIDC flow
against a nonexistent client. It is also a config-injection violation (GLOBAL_RULE_6 /
ARCHITECTURE_RULE_8) of exactly the class DEF-1 was. Fix: introduce an `app-config` key
`keycloak.client-id` whose BASE value is the string `frontend` — byte-identical to the current literal,
so staging and production render unchanged — and have the local overlay patch it to `core-api`. Add
staging/production configmap-patch entries only if those overlays need a different value; if not, say
so explicitly rather than adding noise.

Keycloak realm re-import recipe (from the `reference_keycloak_realm_reimport` memory — Keycloak is
Postgres-backed, so dropping the volume is a NO-OP for realms and `start-dev --import-realm` will NOT
overwrite an existing realm):
1. Edit the TEMPLATE (`realm-export.template.json`). The rendered `realm-export.json` is gitignored
   and produced by the `keycloak-realm-render` compose sidecar from `.env`; never edit it directly.
2. Re-render by restarting that sidecar service.
3. `kc.sh import` inside the Keycloak container with `--override true`.
4. Restart Keycloak, then re-run `infra/keycloak/configure-keycloak.sh`.
5. Tokens minted before the re-import are fail-closed; re-authenticate after.

D-06's proof requirement: the core-java pod log free of `Access refused for user` (already recorded in
plan 26-07) **and** a working KDS WebSocket subscribe against host RabbitMQ `61613`.

**Why `frontend/e2e/stomp-relay.spec.ts` cannot serve as that ingress-path proof as written** — three
structural mismatches, all verified in the file:
- it authenticates with a STUB cookie (`authjs.session-token: e2e-stub`), but `/dashboard/kitchen`
  gates server-side through `auth()`, which rejects a fake session and redirects to `/auth/signin`;
- it posts orders to `EDGE_URL` (default `http://localhost:8089`), i.e. edge-go — which the local
  ingress does NOT route (the overlay's two rules are core-java and frontend only);
- it waits on `networkidle`, which never settles on a page holding SSE and STOMP connections open (a
  repeatedly-caught trap in this repo).
It also skips entirely without `TEST_SHOP_ID`/`TEST_PRODUCT_ID`, and a skipped spec reported as a pass
is a false green. So this plan proves the relay two other ways — at the broker (Task 2) and through a
real browser session (Task 3) — and records the spec's limits as a deferred item.

Live vendor credentials ARE available: user `admin-user`, password in `.env` as
`KC_SEED_USER_PASSWORD`; `frontend/e2e/dashboard-mobile.spec.ts` reads them from
`E2E_VENDOR_USERNAME` / `E2E_VENDOR_PASSWORD` and passed 13/13 at 375px in Phase 23.

Split-horizon contract being proven (resolved at source level during planning against
`@auth/core@0.41.3`): the browser is redirected to the authorize endpoint on the browser-reachable
Keycloak (`localhost:8085`, from `KEYCLOAK_ISSUER` via `auth.ts`'s `kcPublicBase` fallback), then the
frontend POD exchanges the code server-side against `KEYCLOAK_ISSUER_INTERNAL`
(`host.minikube.internal:8085`). Auth.js makes NO discovery request because `authorization`, `token`
and `userinfo` are all explicitly overridden in `frontend/auth.ts:55-59`, and it validates the
id_token `iss` against `provider.issuer` — which is why `KEYCLOAK_ISSUER` must be the STAMPED public
issuer. If the login fails with a ~10s hang followed by a 401, that is the
`feedback_port3100` symptom: a server-side call went to the public URL instead of the internal one.
