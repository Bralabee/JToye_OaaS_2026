D-17 fix mechanism (built and diffed with kustomize v5.6.0 during planning — use this exact
shape). Replacing `includeSelectors: true` with `includeSelectors: false` +
`includeTemplates: true` + an explicit `fields:` list naming only

**Golden-snapshot convention — defined here because this plan owns `render-golden.sh`, and USED by
plans 26-02, 26-04 and 26-08 (`26-REVIEWS.md` Adjudication I).** A golden assertion of the form
"this edit added no selector line" must be anchored to a NAMED pre-change copy, never to a
git-history offset. `HEAD~1` depends on whatever commit granularity the executor happens to choose,
and the fallback form
`diff <(git show HEAD~1:<f> 2>/dev/null || cat <f>) <f>` compares the file **to itself** when the
`git show` fails: the diff is empty and the assertion passes vacuously. That form is FORBIDDEN
anywhere in this phase.

`render-golden.sh` therefore carries two modes beyond check/`--write`:
- `--snapshot <label>` — copy the CURRENT `k8s/goldens/{staging,production}.yaml` into
  `k8s/goldens/.pre/<label>/`. Exit 1 if `<label>` already exists, so a stale snapshot can never be
  silently reused; exit 2 if either golden is missing.
- `--diff-since <label>` — print a unified `diff` of `k8s/goldens/.pre/<label>/<target>.yaml` (the
  OLD side) against the current golden (the NEW side), for both targets, on stdout. Exit 0 when the
  snapshot resolved; **exit 2 when the snapshot directory or either file inside it is missing.** A
  missing baseline must make the assertion FAIL, never produce an empty diff.

Diff direction, so every criterion built on it reads unambiguously: a `<` line exists only in the
snapshot (REMOVED by the edit); a `>` line exists only in the current golden (ADDED by the edit).

Every such criterion is a three-part shape — resolve, inspect, then confirm the baseline was taken
at the right moment:
  1. `bash k8s/scripts/render-golden.sh --diff-since <label> > "$D"; echo "resolve_exit=$?"` prints
     `resolve_exit=0` (a `2` means the snapshot is missing and the assertion is VOID, not passed).
  2. `grep '^>' "$D" | grep -c '<forbidden pattern>'` returns 0.
  3. `test -s "$D"` (the edit was expected to change the render) or `test ! -s "$D"` (the edit was
     expected to change no byte) — this part is what catches a snapshot taken AFTER the edit.

`k8s/goldens/.pre/` is gitignored: the snapshots are transient scaffolding for one execution, not
committed artifacts, and `--write` must never touch anything under `.pre/`.

**DEF-4's out-of-band risk — CONFIRMED HIGH, the single most important finding in
`26-REVIEWS.md`.** `core-java/src/main/resources/application.yml:74` reads
`username: ${RABBITMQ_USER:jtoye}` while `k8s/base/core-java-deployment.yaml:140` injects
**`RABBITMQ_USERNAME`** from `rabbitmq-credentials`/`username`. `RABBITMQ_PASSWORD` *is* correctly
named and *is* read. So TODAY every k8s environment authenticates its primary AMQP pool as the
literal string `jtoye` while using the secret's real password. After this plan's rename it
authenticates as whatever `rabbitmq-credentials`/`username` actually HOLDS — for the first time, in
staging and production as well as locally.

**No static gate can catch a mismatch, by construction.** Secret VALUES never appear in a kustomize
render (only `secretKeyRef` names do), and `check-no-plaintext-secrets.sh` guarantees they never
will; the golden diff cannot see it either. There is a mitigating inference — for AMQP to be working
in staging/production today, the stored password must already authenticate the broker user `jtoye`,
which makes `username: jtoye` likely — but it remains an inference: the value is out-of-band and
unverifiable from this repository.

The rename therefore ships with an explicit operator confirmation (Task 2), recorded rather than
assumed. **If a mismatch is ever found, the correct fix is to change the SECRET so it holds the
broker user its password belongs to — never to revert the rename**, which would restore the
silent-default defect this phase exists to close.
