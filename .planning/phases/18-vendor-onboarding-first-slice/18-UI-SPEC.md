# Phase 18 — UI Design Contract

> Visual and interaction contract for the vendor-onboarding UI slice (follow-on plan 18-07). The six executed plans (18-01..18-06) were backend-only; this contract covers the surfaces that make onboarding VISIBLE and lets a vendor take a shop live. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Design language is LOCKED to the existing dashboard.** This is not a redesign. Every token below is lifted from the running app (`frontend/app/dashboard/*`, `frontend/components/ui/*`, `tailwind.config.ts`, `app/globals.css`). No serif/editorial direction (rejected 2026-04-19). Executors reuse existing components; they do not introduce a new visual system.

## Typography

Roles map to Tailwind's existing type scale (the app's de-facto system). Exactly **4 sizes** (12/14/18/36) and **2 weights** (regular 400 + semibold 600) govern every surface this slice builds.

| Role | Size | Tailwind | Weight | Line Height |
|------|------|----------|--------|-------------|
| Display (page title) | 36px | `text-4xl` | semibold 600 | ~1.1 (`leading-tight`) |
| Heading (card / section title) | 18px | `text-lg` | semibold 600 | ~1.4 (`leading-snug`) |
| Body / page subtitle | 14px | `text-sm` | regular 400 | 1.5 (`leading-normal`) |
| Label / meta | 12px | `text-xs` | regular 400 | 1.5 |

- Page subtitle renders at Body tier: `text-sm text-slate-600` regular 400 (no 16px tier exists in this contract).
- **Weight contract:** exactly two weights — **regular 400** (body, subtitles, nav, form labels — override the shadcn `Label` default `font-medium` with `font-normal`) and **semibold 600** (all headings including the page `<h1>`). Deliberate divergence from legacy pages' `font-bold` h1: at 36px the 600/700 difference is imperceptible and the 2-weight cap wins; do NOT propagate 700 into new code.
- Numeric/id values render `font-mono text-xs` (order-id idiom) where a raw identifier is shown (e.g. Companies House number echo).

## Color

The dashboard's dominant chrome is slate; the interactive accent token (`--primary`) is **blue-600**. Status/state uses a functional semantic palette in the established `bg-{hue}-100 text-{hue}-700` badge idiom (from `marketing/page.tsx` `statusBadgeClass`). Orange/emerald/slate remain the food-delivery brand family (orange is the storefront/marketing brand accent, e.g. the `REFUNDED` badge).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | white `#ffffff` + slate-50 `#f8fafc` | Card surfaces (white) on the slate-50 main scroll area (`bg-slate-50`) |
| Secondary (30%) | slate-900 `#0f172a` + slate-100 `#f1f5f9` | Dark sidebar chrome; muted card/table zebra + neutral badges |
| Accent (10%) | blue-600 `hsl(221 83% 53%)` = `--primary` | See reserved list below |
| Destructive | red `hsl(0 84% 60%)` = `--destructive` | Reserved — no destructive action is exposed this slice (see Copywriting) |

**Accent (blue-600) reserved for — explicit list, never "all interactive elements":**
1. The single primary CTA per surface (`Create application`, `Submit for verification`, `Go live`) — default `Button` variant (`bg-primary`).
2. The active sidebar nav item (`bg-blue-600 text-white shadow-lg shadow-blue-500/50`) — existing sidebar idiom.
3. Text links and focus rings (`focus-visible:ring-ring`, which resolves to blue-600).
4. The loading spinner border (`border-blue-600`).

**Semantic status palette (functional — a second colour axis, applied ONLY to state/gate badges and their inline icons; badge idiom `bg-{hue}-100 text-{hue}-700`):**

| Meaning | Hue | Applies to |
|---------|-----|-----------|
| Success / live | emerald | `LIVE`; gate `PASSED` |
| Ready / informational | blue | `APPROVED`; `PENDING_APPROVAL` |

| Failure / terminal-bad | red | `REJECTED`, `SUSPENDED`; gate `FAILED` |
| Neutral / not-applicable | slate | `DRAFT`, `WITHDRAWN`; gate `WAIVED` |

## Interaction Contract

**Primary focal point (status view):** the overall-state badge + the single state-driven primary CTA ("Submit for verification" / "Go live") — these are the only elements using the blue-600 accent on the page; everything else is slate chrome.

**Surface 2 (`/dashboard/onboarding`) is a single stateful page driven by `GET /api/v1/onboarding/me`:**

1. **No onboarding yet (404 from `/me`):** show the empty state → "Take your shop live" (see Copywriting) with the **create form** (a Card, not a dialog — this is the page's primary job):
   - `model` — required. Segmented toggle / `select`: `MARKETPLACE` ("J'Toye marketplace") vs `WHITE_LABEL` ("My own storefront"). Default `MARKETPLACE`.
   - `shopId` — required. `select` of the tenant's shops from `GET /api/v1/shops?size=100&sort=name,asc` (exact idiom from `marketing/page.tsx`: `<option value="">Select a shop</option>`).
   - `companyNumber` — optional `Input`, helper text "Companies House number — leave blank if you're a sole trader."
   - Submit button "Create application" (default variant) → `POST /api/v1/onboarding` (201) → transitions the page into the status view (`DRAFT`).
2. **`DRAFT`:** status view shows the aggregate + a primary button **"Submit for verification"** → `POST /api/v1/onboarding/submit` (200 → `VERIFYING`), then begins polling.
3. **`VERIFYING`:** gates render as `PENDING`/`Checking…`. **Poll `GET /api/v1/onboarding/me` every 4s** (client interval, cleared on unmount) until `status` leaves `VERIFYING`. This reflects the async gate-chain landing results without a manual refresh. Show a subtle "Running your compliance checks…" helper line.
4. **`ACTION_REQUIRED`:** a gate `FAILED` — surface each failed gate's `reason` and a re-submit affordance ("Re-run checks" → `POST /onboarding/submit` if the backend permits a resubmit; otherwise show guidance to fix product/allergen data). (ASSUMPTION A2: resubmit path — see Assumptions.)
5. **`PENDING_APPROVAL`:** all mandatory gates green, awaiting approval (auto-approve may advance this in the background — keep polling for a short window). No vendor action; show "Your checks passed — approval is being finalised."
6. **`APPROVED`:** enable the primary button **"Go live"**. Clicking opens a **confirmation dialog** (existing `Dialog` idiom), then `POST /api/v1/onboarding/go-live`.
   - **Go-live button enablement is state-driven:** enabled **only** when `status === "APPROVED"`. In any other state it is absent or `disabled`.
   - **Guard veto (400) handling:** if `go-live` returns 400 (backend guard rejects — e.g. allergen gate not passed), do NOT crash; show a destructive toast with the clear message (see Copywriting) and keep the gate breakdown visible so the vendor sees which check blocks them.
7. **`LIVE`:** success state — emerald `LIVE` badge, "Your storefront is live" confirmation, link to the public shop. Hide the go-live button.
8. **`SUSPENDED` / `REJECTED` / `WITHDRAWN`:** render the terminal badge + `reason`; no primary action (support-contact guidance only).

**API binding (all via `apiClient`, `/api/v1` prefix):**

| Action | Call | Success | Notable errors |
|--------|------|---------|----------------|
| Load status | `GET /onboarding/me` | 200 `OnboardingDto` | 404 → show create form |
| Create | `POST /onboarding` (`{model, shopId, companyNumber?}`) | 201 `OnboardingDto` | 400 validation, 409 already exists |
| Submit | `POST /onboarding/submit` | 200 `OnboardingDto` | 400 illegal transition, 404 |
| Go live | `POST /onboarding/go-live` | 200 `OnboardingDto` | 400 gates unsatisfied / illegal transition, 404 |

**Sidebar (Surface 3):** append to the `navigation` array in `sidebar.tsx`: `{ name: "Go live", href: "/dashboard/onboarding", icon: Rocket }` (lucide `Rocket`). Active-state styling is inherited from the existing map — no new styles.

**Banner (Surface 4):** on `/dashboard` home, above the stats grid, render a dismissible info banner while onboarding is not `LIVE`:
- No onboarding / `DRAFT` → amber banner "Finish setting up your shop to go live." + link "Start onboarding".
- `VERIFYING`/`PENDING_APPROVAL`/`APPROVED` → blue banner "Your onboarding is in progress." + link "View status".
- `LIVE` → no banner. Banner uses the `bg-{hue}-50 border border-{hue}-200 text-{hue}-800` info-strip idiom (spacing `p-4`, `rounded-lg`, `text-sm`).

## Assumptions (open judgment calls — recorded, not blocking)

- **A1 — Route:** signed-in surface at `/dashboard/onboarding` (inherits `DashboardShell` auth + chrome), not top-level `/onboarding`. Rationale: zero new layout, matches all dashboard pages.
- **A2 — Create form fields track the REAL backend DTO, not the task's prose.** `CreateOnboardingRequest` requires `{ model, shopId }` + optional `companyNumber`. There is **no** free-text "shop name" and **no** "FSA establishment identity" field in the create request — the FHRS gate resolves the establishment server-side from the selected shop. So the form selects an existing shop (`shopId`) rather than typing a shop name. If a shop must exist first, the empty state links to `/dashboard/shops` to create one.
- **A3 — Resubmit path:** the exposed controller has no explicit `RESUBMIT` endpoint; `ACTION_REQUIRED` recovery is modelled as re-calling `POST /onboarding/submit` (the runner fix in 18-06 anticipates resetting PENDING gates). If the backend rejects a second submit, fall back to in-page guidance ("fix the flagged data, then contact support to re-run"). Executor should confirm the transition table at build time.
- **A4 — Live status via polling** (4s interval while `VERIFYING`/`PENDING_APPROVAL`), not SSE. The onboarding backend exposes no SSE stream (unlike orders); short-lived polling is the pragmatic MVP choice and is dropped once a terminal/actionable state is reached.
- **A5 — `/for-operators` CTA visual:** the CTA adopts the primary-button treatment already present on that marketing page (extend, don't restyle). If that page has no primary button, use the default shadcn `Button` (blue-600). The marketing brand accent on the storefront is orange; do not force orange into the dashboard surfaces.
- **A6 — Font:** Inter is the active body font; the Geist woffs in `app/fonts` are not wired to `layout.tsx`. Use inherited Inter; introduce no new font.
