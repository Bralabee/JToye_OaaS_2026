<objective>
Declare the Index tier on the five resource-index surfaces CONTEXT.md names.

CONTEXT.md section 1 records the artefact this phase exists for: at 2560 the six-column orders table
sits inside a 1400px cap with roughly **900px of empty gutter to its right** — a data-dense surface
starved of width while the screen sits empty. CONTEXT section 3's second independent finding is that
resource indexes are the one case where the documented industry advice is to abandon the cap
entirely (Polaris prescribes a full-width page for lists with many columns; Carbon ships a
full-width modifier; GitLab offers a fluid preference; Lightspeed's shell is uncapped).

Purpose: after plan 35-02 these pages already inherit the 1700px Shell band, so the WIDTH is
mechanically free. What is not free is the CONTRACT. PATTERNS.md F-3: a spec measuring
`/dashboard/orders` at 1700 cannot tell a deliberate Index tier from a forgotten Detail cap — both
read identically. This plan makes the tier a declaration, which is what ORCH-03 requires — an
orchestrator decision (2026-08-29), see CONTEXT.md section 4b — and what makes plan 35-08's assertion
falsifiable.

Output: five pages carrying `data-width-tier="index"`, and jsdom assertions on the three of them
that already have mounted page tests.
</objective>

APPLICATION SHAPE for this plan — an IN-PLACE application: add `data-width-tier="index"` to the
existing root element of the component's LOADED return, and add NO class and NO wrapper node. Each of
these five pages has such an element (for example `app/dashboard/orders/page.tsx:516` returns a div
with a vertical-rhythm class).

**These pages do NOT return a single root element, and an earlier draft of this plan claimed they did
under a "measured on the tree" label. That claim was false and is corrected here.** Each of the five
renders an EARLY-RETURN LOADING BRANCH first — a centred spinner, verified present in
`app/dashboard/page.tsx`, `orders/page.tsx`, `products/page.tsx`, `customers/page.tsx` and
`shops/page.tsx`. An unverified claim carrying a measured label is itself a defect under this
project's falsifiability contract, and it is worse than no claim: a reader who trusts the label does
not re-check it.

TWO CONSEQUENCES, and they differ from the Detail tier's:
  - The loading branch does NOT need the Index tier. Index adds no class, so an untiered spinner
    branch is already uncapped and renders at the same width the tiered branch does. There is no
    width jump here, unlike plan 35-05's Detail surfaces where an untiered branch WOULD jump.
  - But the MARKER is absent while loading, so a browser assertion that queries the tier selector
    before the fetch resolves finds nothing. That is a timing fact, not a contract violation, and it
    is why plan 35-08 must wait on the marker rather than measure on network-idle. Do not "fix" it by
    tiering the spinner: a marker on a transient branch would claim the tier for a state that is not
    the page.

Verify the shape yourself at each site before editing rather than trusting this description — the same
rule that produced the correction above.

Adding no class is the whole point. The Index tier is "fluid to the Shell cap": it must not narrow
anything, and `WIDTH_TIER_CLASS.index` is the empty string precisely so a mechanical application
cannot accidentally introduce one. Do NOT wrap these pages in ContentTier — a wrapper div would add
a DOM node under `AnimatePresence` and motion-driven subtrees for no benefit.
