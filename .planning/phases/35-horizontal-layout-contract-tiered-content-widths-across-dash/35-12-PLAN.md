<objective>
Prove the phase, rather than assert it.

This repository's fifth quality dimension exists because a phase once shipped past four green gates
with a runtime missing its own configuration change and three merged UI pull requests, and the owner
caught it by eye. The two halves of that dimension are both live here: every acceptance criterion must
have been shown to FAIL before it is trusted, and the DELIVERED RUNTIME must match the branch.

A CSS-only change is exactly the shape that hides in this failure mode. The page renders, the status
code is 200, the suite is green, and none of that distinguishes a container built from this branch
from one built last week.

Purpose: this plan runs the evidence the earlier plans deliberately deferred rather than reading a
browser result off an unrebuilt container.

Output: a SUMMARY that is the phase's evidence record.
</objective>

    PART A — REBUILD AND PARITY.

    Rebuild the frontend image. Starting existing containers does not rebuild them, and a restored
    runtime after a source change is itself a code-changing event.

    Run `scripts/check-runtime-freshness.sh` FROM THE MAIN CHECKOUT, not from a worktree — the compose
    project name derives from the directory, so running it elsewhere makes it VOID for reasons that
    have nothing to do with the tree. It is per-service and fail-closed at exit 2: any built service
    that is missing or not running voids the whole run, and a partial pass is not a pass. If it names
    a service other than the frontend as stale, rebuild that too and record why it was stale.

    If a core-java rebuild turns out to be required, note that it always reds the alert-metrics gate
    until the order-metric seeding script has run. That is a known consequence of rebuilding, not a
    finding.

    Run `scripts/check-branch-behind-base.sh`. It must be clean, or a merge from the base must be
    recorded — a branch behind its base ships a runtime missing already-merged work, and no rebuild
    fixes that.

    Then prove parity BY CONTENT, not by a status code. Read the tier value out of the RUNNING
    artefact: fetch the stylesheet the running frontend actually serves and confirm it contains the
    declared shell, detail and marketing max-width values, with comments filtered out of the match. A
    filesystem search on the host answers a different question.

    PART B — MOBILE BYTE-IDENTICAL, PROVEN BY DIFF.

    This is the strongest available form of the mobile-safety claim and it is why the phase chose
    unconditional utilities over responsive variants: an empty diff is a property, not a sample.

    Generate the full stylesheet from the PRE-CHANGE tree and from this branch, using the same command
    and the same content set for both. Then diff them, filtered to the rules that can possibly affect a
    small screen: rules carrying no media query, and rules inside a media query whose breakpoint is
    below the large breakpoint. Every tier utility this phase adds is unconditional and every tier
    value exceeds any mobile viewport, so no tier rule can bind there.

    The expected result is that the only differences are ADDITIONS of the three tier rules and the
    REMOVAL of the retired scaffold rule, with nothing else moving in the below-large-breakpoint set.
    Record the actual diff output, including its size. If anything else moved, that is a finding and it
    is what this task exists to surface — do not explain it away.

    Guard against the arm that cannot fail: before trusting an empty diff, confirm the diff command
    can produce output at all by running it against two builds that genuinely differ. A diff whose
    baseline lookup silently failed compares a file to itself and reports clean.
  </action>

    PART A — THE ACCESSIBILITY RULE, VERIFIED WHERE IT CAN BE.

    RESEARCH read the rule's implementation out of the installed accessibility library and established
    that `scrollable-region-focusable` is RUNTIME-GEOMETRIC, not structural: its matcher requires the
    element's scroll width to exceed its client width by more than a 13-pixel buffer, plus a descendant
    rectangle outside the element's bounding rectangle. In jsdom both dimensions are zero, so the rule
    never applies.

    The consequence is a coverage finding, not a task: **the blocking per-PR jsdom accessibility gate
    merged in the previous phase is structurally unable to evaluate this rule and has been passing
    vacuously for it.** A green run of that gate is not evidence about a scroll region.

    So verify it where it can be verified: run the nightly dashboard accessibility sweep in a real
    browser against the rebuilt runtime, over the dashboard, orders and products routes, and record the
    result. Confirm the products scroll region still exposes its role, its accessible name and its
    tabindex. Record that this sweep is REPORT-ONLY — its own header says so — so it widens visibility
    rather than blocking, and do not describe it as a gate.

    The direction of risk here is reasoned rather than measured: widening means less overflow at large
    viewports, so fewer elements can match the rule, and the caps are inert at mobile. Record it as
    reasoned, and let the browser run be the measurement.

    PART B — FILE THE FOLLOW-UP.

    File a GitHub issue for the jsdom coverage gap. It must state: which rule, why jsdom cannot
    evaluate it, that the per-PR gate has therefore been passing vacuously for it, and that the only
    current verification is the report-only nightly sweep. Propose the direction — a real-browser
    assertion in the blocking lane, or an explicit recorded exemption — without deciding it. This is
    explicitly OUT OF SCOPE for this phase; do not expand the phase to fix it. Reference the issue
