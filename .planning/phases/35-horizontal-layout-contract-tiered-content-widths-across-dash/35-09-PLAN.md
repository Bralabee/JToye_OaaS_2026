<objective>
Measure the landing route's layout stability at a viewport where this phase's change can actually
bind, and declare the resulting control number.

This is ORCH-02 — an orchestrator decision (2026-08-29), see CONTEXT.md section 4b — and RESEARCH.md
section 2d is the finding behind it: the landing route is
the ONE surface whose tier value actually changes (1152 to 1280), and **every CLS instrument this repo
owns measures at a 375px viewport with 4x CPU throttling**, where a 1280px cap provably cannot bind.
`perf-budgets.ts` records the mobile control at 0.1793 and both landing and webhooks web-perf specs
pin a 375px viewport.

So without this plan, the phase's most-changed surface has an entirely unmeasured layout-stability
dimension — and the CLS evidence for this change would be vacuous by construction: a pass from an
instrument that cannot see the change is not a pass. RESEARCH offered two honest options and named
this one the falsifiable one; the second, "accept the gap and write it down", is what this plan
replaces.

Purpose: give the width change a CLS instrument that can fail.

Output: one declared, measured constant in `perf-budgets.ts` and one desktop describe in
`landing-webperf.spec.ts`.
</objective>

<measurement_protocol>
The number must be MEASURED, and measured the same way 0.1793 was. `perf-budgets.ts` records that
protocol in its own docblock and it is the standard to meet, not to approximate:

  CONTROL   pre-change build   running simultaneously on a second port
  TREATMENT this branch's build
  Both throttled identically, both at the same pinned viewport, run in the same session.

Steps:
1. Build the branch's frontend. Build a pre-change frontend from the phase's merge base into a
   separate directory or worktree and serve it on a second port.
2. Pin a desktop viewport — 1440 by 900, matching the config's desktop project, so the number is
   comparable to everything else the suite measures at that width. Do NOT pick 1920 or 2560: the
   marketing cap binds at both 1440 and above, so 1440 is sufficient to see the change and is the
   viewport the rest of the suite already uses.
3. Apply the SAME throttling helper to both arms. An unthrottled localhost measurement is explicitly
   forbidden by the project's web-performance contract.
4. Run each arm at least three times and record every value, not just the one you keep. A single run
   is a measurement of the runner.
5. Declare the CONTROL value as the new constant. The control is the honest baseline: it is what the
   route did before this phase touched it.

TWO THINGS THAT WOULD INVALIDATE THE RESULT, both of which have happened in this repo:
  - Reading the treatment arm off a container built before the edit. Rebuild, then verify parity.
  - Declaring a number from the first run that happened to pass. `perf-budgets.ts` records that a
    first draft of that file carried an invented 461,000-byte baseline and the assertion caught it;
    `scripts/check-no-measured-placeholders.sh` exists for this class and must stay green.
</measurement_protocol>
