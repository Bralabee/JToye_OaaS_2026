<objective>
Declare the Index tier on the eight remaining dashboard surfaces, resolving each of PATTERNS.md's
ambiguous cases explicitly rather than by default.

PATTERNS.md section 2 lists twelve surfaces that could defensibly take two tiers and refuses to
resolve any of them silently. Seven of those (A-3 through A-9) are in this plan's file set. Each gets
its resolution written AT THE SITE, because the failure mode is not getting it wrong once — it is the
next reader "fixing" it back without knowing a decision was made.

Purpose: plan 35-03 covered the five surfaces CONTEXT.md names by name. These eight are the rest of
the dashboard, and leaving them undeclared would produce exactly the half-shipped inconsistency the
contract exists to prevent: some dashboard pages declaring a tier and others inheriting one by
accident, with no way to tell which is which.

Output: eight surfaces carrying `data-width-tier="index"`, with jsdom assertions on the six that
already have mounted tests, and each ambiguity resolution recorded in a comment at its site.
</objective>

<ambiguity_resolutions>
Each of these is a decision, not a default. The rationale goes in a comment at the site.

A-3 `/dashboard/webhooks/[id]` — DETAIL ROUTE, INDEX CONTENT. Resolved INDEX. The reason to open the
page is the delivery log: a wide, multi-column, timestamp-heavy table with its own horizontal scroll
region. Capping it to the Detail width would make it scroll MORE than it does today at 1400, which is
a strict regression on the page's primary job. Tier by content shape, not route shape — this is the
single case that proves tier must be declared rather than inferred, because route-shape inference
gets it wrong. Say so at the site.

A-4 `/dashboard/finance` — LEDGER TABLE plus CHARTS. Resolved INDEX. The ledger is the surface's
reason to exist. The competing worry — that fixed-aspect charts stretched to 1700 read as very wide,
very short plots — is answered ADDITIVELY: if the charts need protecting, cap the CHART BAND inside
an Index page with a local wrapper. Capping the whole page to protect the charts would starve the
ledger, which is the defect being fixed. Do not add that local chart cap speculatively; plan 35-12's
visual capture at 2560 decides whether it is needed, and a chart cap added on a hunch is a scattered
literal.

A-5 `/dashboard/marketing` — TWO TABLES plus COMPOSER DIALOGS. Resolved INDEX. The competing reading
dissolves on inspection: the composers are Radix dialog content rendered in a portal, OUTSIDE the page
container, so the page tier cannot affect them either way. Only the tables are governed by this tier.

A-6 `/dashboard/kitchen` — KDS CARD BOARD. Resolved INDEX. A card grid that reflows into more columns
is the same argument as a wide table, and a kitchen display is the one dashboard surface likely to run
on a genuinely large screen. HAZARD: it is STOMP-live and driven by presence animation, so more
columns changes the reflow on every order transition. Its E2E specs must be re-run in plan 35-12.

A-7 `/dashboard/staff` — TABLE plus GRANT FORM. Resolved INDEX. The grant form lives inside a card
that is already narrower than the band and keeps its own width; tiering the page Detail to protect a
card would cap the tables for no gain.

A-8 `/dashboard/onboarding/approvals` — APPROVALS QUEUE. Resolved INDEX, and this is the
LOWEST-CONFIDENCE call in the phase. It is a queue, which is the resource-index case by name, but each
entry is a review card carrying narrative gate reasons — prose, not columns. Index is chosen because
Detail is the only dashboard tier requiring a new wrapper and a silent default would have shipped it
as Index anyway; choosing it deliberately is the honest version of the same outcome. State the low
confidence in the comment, and flag it for the human-verification pass in plan 35-13.

A-9 `/dashboard/media/review` — FLAGGED-MEDIA QUEUE. Resolved INDEX. Note it owns a 320px viewport
spec (`e2e/media-review-320.spec.ts`), the tightest viewport in the suite, which must be re-run.
</ambiguity_resolutions>
