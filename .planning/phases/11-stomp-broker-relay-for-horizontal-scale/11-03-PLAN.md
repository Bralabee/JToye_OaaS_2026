Add a new `messaging_alerts` group at the end of `infra/monitoring/prometheus/alerts.yml` (after the existing `business_alerts` group which ends around line 151). Follow the exact structure of existing alert groups.

```yaml
  - name: messaging_alerts
    interval: 30s
    rules:
      # STOMP broker message lag — unacknowledged messages in STOMP subscription queues
      # Queue names auto-generated by RabbitMQ for STOMP subscriptions match stomp-subscription-*
      - alert: StompBrokerLag
        expr: |
          sum(rabbitmq_queue_messages_unacked{queue=~"stomp-subscription.*"}) > 0
        for: 5s
        labels:
          severity: warning
          component: messaging
          service: rabbitmq
        annotations:
          summary: "STOMP broker message lag detected"
          description: "Unacknowledged STOMP messages: {{ $value }} (threshold: any > 0 for 5s). Kitchen broadcasts may be delayed."

      # RabbitMQ STOMP connections dropped — fewer connections than expected replicas
      # In relay mode, each core-java replica maintains at least 1 system STOMP connection
      - alert: StompConnectionsLow
        expr: |
          rabbitmq_connections < 2
        for: 2m
        labels:
          severity: warning
          component: messaging
          service: rabbitmq
        annotations:
          summary: "Low RabbitMQ connection count"
          description: "RabbitMQ has only {{ $value }} connections. Expected >= 2 in relay mode (1 system connection per replica). Check core-java replica health."
```

**Important notes:**
- The `StompBrokerLag` rule uses `queue=~"stomp-subscription.*"` regex. Per RESEARCH.md Assumption A1, exact queue naming needs runtime verification. If the pattern does not match, the executor should check RabbitMQ management UI (`http://localhost:15672/api/queues`) with STOMP plugin active and adjust the regex.
- The `StompConnectionsLow` rule uses `rabbitmq_connections` (total connections). Per RESEARCH.md Open Question 2, this metric may not distinguish STOMP from AMQP. The threshold `< 2` is conservative -- in relay mode with 2 replicas, there should be at least 4 connections (2 system STOMP + 2 AMQP). If this fires too often, increase the `for` duration.
- Both rules use `severity: warning` (not critical) since STOMP lag is a degradation, not a full outage. The existing Alertmanager route tree handles warning severity.
- Both rules include `service: rabbitmq` to match the existing label convention and Alertmanager `group_by: [alertname, service]`.
