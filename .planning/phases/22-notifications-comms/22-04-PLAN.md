<objective>
Bind the dead channels and fan every lifecycle event to email for both audiences (COMMS-01 + COMMS-02). Add the RabbitMQ topology (all new consumer queues + bindings, including the webhook fanout queue that 22-05 consumes), a `NotificationDispatchService` (recipient resolution D-04 → consent gate → render → EmailChannel/WhatsAppSmsChannel fan-out), and three new `@RabbitListener` consumers (order-vendor, onboarding, financial/refund) mirroring the working `OrderStateChangeListener`. The existing order-email path is left untouched (Pitfall 5 path A); no producer/flusher change (Pitfall 3 — all four dispatch branches already exist).

**COMMS-02 order-audience wiring (BLOCKER fix):** the pre-existing `OrderStateChangeListener → EmailNotificationService` path emails the CUSTOMER only. To reach the VENDOR (locked COMMS-02 target = "order: customer + vendor") this plan adds a NEW `order.notifications` durable queue + `OrderNotificationListener` that dispatches order events to the **vendor only** through the new `EmailChannel` — ALONGSIDE, never replacing, the legacy customer path. The customer is served by the untouched legacy path; the vendor by the new path; so the customer is NOT double-emailed.

Purpose: this is the orchestration that makes the vendor order email, the onboarding stall email (Phase 21's dangling seam), and payment/refund emails real, and it owns the single shared broker-topology file so the tracks don't conflict.
Output: RabbitMQConfig topology + dispatch service + recipient resolver + 3 listeners + Mailhog test helper + dispatch/landing integration tests.
</objective>
