<objective>
`MediaPendingReaper` permanently deletes the quarantined source bytes of vendor uploads that were
never processed, whenever the media dispatch path (RabbitMQ / the media outbox flush) is unavailable
for longer than the 15-minute reaper grace. The transactional outbox protects the *event*; nothing
protects the *object*. A transient infrastructure failure therefore produces unrecoverable loss of
user data.

**What this plan actually achieves — stated precisely, not as "closes a P0 data-loss defect":**

It converts **unbounded loss at 15 minutes** into **bounded loss at 72 hours**, and in exchange it
introduces **a new state where an upload is stuck without being terminal**. Both halves are real and
both are this plan's responsibility:

| | today | after this plan |
|---|---|---|
| bytes of an undispatched upload | deleted at ~15 min, unrecoverable | retained for 72 h, then reclaimed |
| vendor-visible outcome at 15 min | `FAILED` + "please re-upload" — wrong, but *actionable* | `DELAYED` + "queued, we're still trying" + a Check-again affordance |
| vendor-visible outcome at 72 h | (already lost) | `FAILED` + "the original upload was not kept" + Re-upload |
| recovery from a retained-bytes `FAILED` | re-upload only | one idempotent `POST /reprocess` click |

The good being displaced is **the 15-minute terminal-and-actionable outcome**. It is displaced
deliberately (it is wrong — it destroys data to reach it) and it is **replaced, not removed**: the
vendor still gets a distinct, explained, non-spinning state inside the same 15-minute window, and a
strictly better recovery path. Shipping D-01 without that replacement would leave the vendor on an
indefinite `Processing…` spinner (`asset-image.tsx:66-77`) with no reason and no affordance while the
72 h sweep deleted the bytes anyway — a regression by omission, which is a defect even with a green
suite.

The fix is **not** "turn the reaper off". Orphan cleanup is a real, working good — without it the
quarantine prefix grows without bound. The fix separates the two things the reaper currently
conflates: the cheap, reversible **state flip** and the irreversible **byte delete**; gates the flip
on durable evidence that the work was actually dispatched; suspends the sweep when the dispatch path
cannot be shown healthy from this JVM; and makes the resulting failure **recoverable from
quarantine** instead of forcing a re-upload.

Output: `V60`, a rewritten `MediaPendingReaper`, a new `MediaQuarantineRetentionSweep`, a worker
claim lock, a `POST /api/v1/media/{assetId}/reprocess` re-drive surface, the DELAYED + Re-process
vendor affordances, and 27 new Java tests + 6 new Jest tests whose *fail direction has been run and
recorded*.
</objective>

## 1. The mechanism, confirmed against source

| # | Claim | Evidence |
|---|---|---|
| 1 | The reaper runs every 10 min by default | `MediaPendingReaper.java:55` — `@Scheduled(fixedDelayString = "${jtoye.media.reaper-interval-ms:600000}")` |
| 2 | Cutoff = now − 15 min | `MediaPendingReaper.java:57`; `MediaProperties.java:66` — `private long reaperGraceMs = 900_000;` |
| 3 | The selection is *status only*, with no dispatch evidence | `MediaAssetRepository.java:32-34` — `WHERE a.status = PENDING AND a.createdAt < :cutoff`. No join to `media_event_outbox`, no attempts column, nothing. |
| 4 | It deletes the quarantine object **and** flips FAILED | `MediaPendingReaper.java:79-81` — `storageService.deleteByKey(asset.getObjectKey()); asset.setStatus(FAILED); asset.setFailureReason("Processing timed out — please re-upload");` |
| 5 | The delete is unconditional and unrecoverable, and reports nothing | `StorageService.deleteByKey` (`StorageService.java:288-299`) catches `Exception` and only `log.warn`s. It never aborts the caller and **never reports failure upward** — so no caller of it can ever know whether it worked. |
| 6 | The re-delivered event is then silently discarded | `MediaProcessingWorker.java:112-116` — a redelivered event on a non-PENDING asset logs `media_process_skipped reason=not_pending` and returns. |

**Verdict: CONFIRMED.** The reaper was written for a crashed worker (`MediaPendingReaper.java:18-24`
says so) and has no way to distinguish that from "the worker never ran at all".

## 2. Timing — the window is genuinely reachable

During a broker outage `MediaEventOutboxFlusher.publishRow` throws, increments `attempts`, and pushes
`next_attempt_at` out by `computeBackoffMillis(attempts, 5_000, 300_000)`. Cumulative delay to
`MAX_ATTEMPTS = 10`:

```
5 + 10 + 20 + 40 + 80 + 160 + 300 + 300 + 300  ≈ 1215 s ≈ 20 min
```

At the 15-minute reap cutoff the outbox row is still `PENDING` with ~7-8 attempts — **the event has
provably not been dispatched, and the evidence is one join away.** The reaper deletes the bytes
anyway.

## 3. Two corrections to the original brief

**(a) The reaper's own premise is largely false.** `RabbitMQConfig.java:389-410` sets
`factory.setAdviceChain(retryInterceptor())` (3 attempts, 1s→10s) and
`factory.setDefaultRequeueRejected(false)`. A worker that *crashes mid-process* leaves the message
**unacked**, so the broker requeues it — self-healing. A worker that *throws* is retried 3× then
dead-lettered to `media.process.dlq`. So the genuine "PENDING forever" population is much smaller
than the class the reaper reaps, and the class it does reap is dominated by *undispatched* work.

**(b) A second, independent defect in the same method.** The irreversible S3 delete happens *inside*
the `TransactionTemplate` callback (`MediaPendingReaper.java:75-84`) but is not transactional.
`MediaAsset` carries `@Version` (V59), so a concurrent worker flip makes the commit throw
`ObjectOptimisticLockingFailureException`, caught at `:63-65`. **The DB writes roll back; the object
deletes do not.** The tenant's whole batch loses its bytes while the rows still read `PENDING`.

## 4. The true state space — what distinguishes the cases

`media_event_outbox` (V58) is the only durable dispatch ledger, and it is queryable from the reaper's
side: same tenant GUC, `FORCE RLS` via `current_tenant_id()` (`V58__media_event_outbox.sql:40-52`),
one row inserted in the **same transaction** as the PENDING asset (`MediaAssetService.java:174`,
and again on the WR-01 reprocess path at `:215`). Every PENDING asset has one — including the
`BulkImportService` path, which routes through the same `acceptQuarantineAndQueue`. There is **no
purge** of the outbox anywhere in the tree.

| Real-world case | `media_asset` | latest `media_event_outbox` row | Bytes | Reap today | Correct |
|---|---|---|---|---|---|
| A. Broker / flusher outage | PENDING | `PENDING`, attempts>0 | present | **deleted — LOSS** | leave alone |
| B. Outbox retry-exhausted | PENDING | `FAILED`, `poison=false` | present | **deleted — LOSS** | leave alone (resurrection re-leases it, `MediaEventOutboxRepository.java:47-56`) |
| C. Corrupt payload | PENDING | `FAILED`, `poison=true` | present | deleted | flip FAILED, **keep bytes** |
| D. Dispatched, consumer down/absent | PENDING | `SENT` | present | deleted | flip FAILED **keeping bytes** |
| E. Dispatched, dead-lettered to DLQ | PENDING | `SENT` | present | deleted | same as D |
| F. Worker in flight, slow | PENDING | `SENT` | present | bytes deleted, row write may roll back | flip FAILED keeping bytes; the worker's own claim lock (D-04) makes the flip harmless |

**A and B are fully distinguishable and are the loss cases.** D, E and F are *not* distinguishable
from each other by the outbox row alone. That residual is what D-02 (never delete on the timeout
path) makes **non-destructive** rather than perfectly classified — see D-05 for exactly what the
suspension circuit can and cannot observe.

`media_asset.version` (V59) is a JPA optimistic counter only (`MediaAsset.java:102-110`). There is no
other signal on the asset row.

**A FAILED asset row retains everything needed to recover** — `object_key` (still the quarantine
key), `sha256`, `content_type`, and the placement intent `product_id` / `is_primary` / `sort_order`
are all untouched by the reaper. The *only* thing missing after a timeout-reap is the bytes.

<decisions>

### D-01 — Gate the stall sweep on durable dispatch evidence, and fail CLOSED on absence. **ACCEPTED**

Reap-eligible ⟺ the **latest** `media_event_outbox` row for the asset (by `created_at DESC`) is
`SENT`, **or** is `FAILED AND poison = true`. Everything else — `PENDING`, `FAILED AND poison =
false`, **and no row at all** — is left completely untouched.

*Trade-off, stated plainly:* an **absent** row is ambiguous (pre-outbox row? future purge? manual
delete?) and the repo's standing rule is that a missing or empty discovery result is never "clean".
Cost of failing closed: a genuinely orphaned asset with no outbox row is never stall-classified —
which is exactly why **D-03's retention sweep is unconditional** and collects it anyway on the
retention horizon.

### D-02 — Split the reversible flip from the irreversible delete. The timeout path NEVER deletes. **ACCEPTED**

`MediaPendingReaper` loses its `StorageService` dependency entirely (constructor parameter and field
both removed). It can flip `PENDING → FAILED`; it is structurally incapable of deleting an object.
This also closes the "delete escaped the rolled-back transaction" defect from §3(b) by construction.

*Alternative rejected:* "delete after commit instead of inside the tx" — fixes §3(b), leaves the
data-loss defect untouched. Strictly weaker.

### D-03 — A separate, unconditional, long-horizon retention sweep, terminated by a REAL sentinel. **ACCEPTED**

New `MediaQuarantineRetentionSweep`, cloned from `WebhookRetentionCleanup` (per-tenant,
`TransactionTemplate`, GUC pinned). It deletes a quarantine object when **all** of:

1. `status <> 'ACTIVE'` — a live derivative is never a candidate; **and**
2. `object_key` contains `/quarantine/` — the derivative convention is `<tenant>/media/<id>.webp`
   (`MediaProcessingWorker.java:151-152`) and a V53-backfilled key is
   `<tenant>/products/<pid>/<uuid>.<ext>` (`V53__media_asset.sql:189`), so neither can ever match;
   **and**
3. `quarantine_reclaimed_at IS NULL` — **the sentinel**; **and**
4. `quarantine_expires_at < now()`, **or** (`quarantine_expires_at IS NULL AND created_at < now() −
   retention`) — the second arm collects rows that predate V60.

**M1 — why the sentinel is a new column and not `quarantine_expires_at = NULL`.** The draft's
termination marker was "set `quarantineExpiresAt = null`". For every row the *legacy* arm selects,
`quarantineExpiresAt` **is already null** — that is the arm's own predicate. So the marker was a
no-op, the same rows were re-selected on every hourly tick forever, `deleteByKey` was re-called on
already-deleted objects forever, and because `deleteByKey` swallows every exception
(`StorageService.java:296-298`) nothing would ever have complained. `quarantine_reclaimed_at` is a
column no selection predicate can already satisfy, so stamping it genuinely terminates the row.
Falsified by AC-3.2 — run the sweep twice **against real Postgres**, assert exactly one delete **and**
that a real `findReclaimableQuarantine` returns 0 rows on tick 2.

**Where each guard lives, because it determines where its criterion can live.** Guards 1, 3 and 4 are
clauses of the `findReclaimableQuarantine` **`@Query`**; guard 2 (`/quarantine/`) is Java in the
sweep. A criterion whose BREAK edits a JPQL string is therefore only falsifiable where the query
actually executes — i.e. **Testcontainers, not Mockito**. Against a `@Mock MediaAssetRepository` the
stub does the filtering and the JPQL edit changes nothing, which is exactly how AC-3.2 and AC-3.3(a)
were vacuous until this pass. Guard 2's criterion is correctly a unit test, because guard 2 is
correctly unit code.

Guards 1, 2 and 3 are deliberately **independent and individually breakable**, and each fixture is
built so that **only the guard under test stands between it and the delete** — see AC-3.3, which fixes
the draft's vacuous ACTIVE fixture (a `/media/` key, which guard 2 already blocked, so removing guard 1
could not produce the stated RED) **and** the layer that fixture was asserted at.

The sweep stamps the sentinel **only when `deleteByKeyChecked` returns true** (F-5). A transient S3
error therefore leaves the row for the next hourly tick — correct retry, not the M1 loop, because a
*successful* delete terminates it.

*This is the Incremental Betterment obligation discharged:* Phase 24's working good was "the
quarantine prefix cannot grow without bound". That good is preserved — it now happens on a declared
72-hour policy horizon instead of as a 15-minute accident.

### D-04 — NO automatic re-drive. The worker takes a claim lock. **REVISED — the draft's automatic re-drive is REMOVED**

The draft had the reaper insert a fresh outbox row for a stalled `SENT` asset (up to a budget). That
creates a **worker/worker race on one asset and calls it harmless without evidence.** Traced against
source, the mechanism is real:

- The second event publishes within ~5 s of the reaper's insert (`MediaEventOutboxFlusher` polls
  fast), while the first worker may still be inside `normalize` / `putBytes` / Ollama.
- The worker's **only** interlock is `asset.getStatus() != PENDING` (`MediaProcessingWorker.java:112`)
  — a check the in-flight worker has not yet invalidated, because it flushes `ACTIVE` at `:169`.
- Both workers then `putBytes` the same derivative key (`:153-154`), both run `placeOnActive` →
  `MediaAssetService.placeAsset` (`:278-293`), which repoints `product_media` and calls
  `releaseAsset(displaced)` — and `releaseAsset` **physically deletes the displaced asset's object
  and row at ref-count 0** (`MediaAssetService.java:300-309`).
- The loser of the `@Version` race (V59) throws `ObjectOptimisticLockingFailureException` out of the
  `@Transactional` listener into the retry advice; on a bad interleaving that path ends at
  `media.process.dlq` (`setDefaultRequeueRejected(false)`).

V59 exists *precisely* because reaper/worker concurrency was already a real hazard. Manufacturing a
second concurrent writer on a schedule, to fix a data-loss bug, is not an acceptable trade.

**Two changes replace it:**

1. **The reaper never enqueues anything.** A stalled asset with dispatch evidence is flipped `FAILED`
   **retaining bytes**, with a distinct reason. Recovery is exclusively human-initiated (D-06). No
   scheduled component can create a second in-flight event. Proven by AC-2.9
   (`verifyNoInteractions(mediaEventOutboxRepository)` across every reaper path).

2. **The worker claims its row.** `MediaProcessingWorker.onMediaEvent` replaces
   `mediaAssetRepository.findById(event.assetId())` with a new
   `mediaAssetRepository.lockForProcessing(id)` carrying `@Lock(LockModeType.PESSIMISTIC_WRITE)`
   (`SELECT … FOR UPDATE`). Under Postgres READ COMMITTED — Spring's default isolation, and the
   dependency is load-bearing and must be stated in the javadoc — a second worker on the same asset
   **blocks** until the first commits, then re-reads the *committed* row, sees `ACTIVE`/`FAILED`, and
   takes the existing `not_pending` skip. Exactly one worker ever runs the pipeline for one asset.

   This makes the **manual** re-drive safe too, which the "just remove the automatic one" answer does
   not: the residual window (reaper flips FAILED → vendor immediately presses Re-process → a slow
   original worker retries and finds PENDING again) is closed by the same lock.

   Lock scope: one `media_asset` row, held for the pipeline duration. The only contender is another
   worker for the *same asset*. The reaper's `findStalePending` is a plain MVCC read and does **not**
   block; only its flush would, and if it does, it then loses the `@Version` race and the tenant batch
   rolls back — which is now harmless, because D-02 guarantees the reaper has no side effect to leak.
   That argument is only valid *because* of D-02, and is recorded as such.

### D-04a — The claim lock's hold time is BOUNDED and the bound is stated (m5). It interacts with 27-04.

`lockForProcessing` takes `SELECT … FOR UPDATE` **inside** the `@Transactional` `@RabbitListener`, and
that transaction wraps the entire pipeline (`MediaProcessingWorker.process`, read from source):

| Stage | Source | Cost |
|---|---|---|
| `storageService.getBytes(quarantineKey)` | `:126` region | one S3/MinIO GET, ≤ 5 MB (`spring.servlet.multipart.max-file-size: 5MB`) |
| `mediaNormalizer.normalize(raw)` | `:134` region | **CPU-bound** — sniff, bomb guard, decode, EXIF strip, resize, WebP encode (forks `cwebp`) |
| `storageService.putBytes(derivative)` + `putBytes(thumbnail)` | `:153-154` | two S3/MinIO PUTs |
| `applyAdvisoryVision(...)` → Ollama | `:165` → `ImageAnalysisService:179,217` | **OFF by default** (`MEDIA_VISION_ENABLED:false`, `application.yml:219`); when ON, bounded by an explicit `.timeout(Duration.ofSeconds(30))` |
| `saveAndFlush` + `placeOnActive` + `deleteByKey` | `:169-177` | DB + one S3 DELETE |

**Stated worst case, shipped defaults (vision OFF):** S3 round trips plus one 5 MB CPU transcode —
seconds, not minutes. **Stated worst case with `MEDIA_VISION_ENABLED=true`:** the same **plus 30 s**,
the reactive timeout being the only thing that makes it finite. That is the number to quote; there is
no separate DB statement timeout in play (`application.yml` sets `connection-timeout: 30000` on
Hikari, which governs *acquiring* a connection, not holding one).

**Why this now needs saying, when it did not before.** A blocked loser holds **two** bounded resources
for the winner's full pipeline duration: its **AMQP consumer thread** and its **Hikari connection**.
At today's concurrency 1 there is one media consumer per replica and no loser can exist within a JVM.
**27-04 raises `media.process` concurrency**, so the loser becomes reachable in-process and consumes
one of `maximum-pool-size` (**10 in prod**, `application-prod.yml:14`; 20 base) — which is the same
scarce pool 27-04's own `check-consumer-thread-budget.sh` exists to budget. The design is still
correct; the *unstated* hold time was the gap.

**The bound is declared, not merely described.** Add `jtoye.media.claim-lock-timeout-ms` (default
`10000`), env-indirected as `${MEDIA_CLAIM_LOCK_TIMEOUT_MS:10000}` alongside the other four keys, and
have the worker issue `SET LOCAL lock_timeout = <value>` on the pinned connection **immediately before**
`lockForProcessing` — the same `session.doWork` seam that already pins the tenant GUC, so no new
mechanism is introduced and `SET LOCAL` dies with the transaction exactly as the GUC pin does.
Consequences, stated honestly rather than hidden:

- The loser no longer blocks unboundedly. It fails with a Postgres `55P03 lock_not_available`, which
  Hibernate surfaces as `PessimisticLockingFailureException`, escapes the listener into the existing
  retry advice (3 attempts) and — on exhaustion — reaches `media.process.dlq`.
- **That is an acceptable outcome and it is not a regression**, because the loser had nothing to do:
  by the time it re-acquired, the winner's committed row is `ACTIVE`/`FAILED` and the existing
  `not_pending` skip discards it. A redelivery after the winner commits takes the skip path.
  **The residual is a DLQ'd no-op message, not lost work** — say so in the runbook.
- **Postgres has no "wait N then proceed" for `FOR UPDATE`.** `jakarta.persistence.lock.timeout` is
  not honoured as a numeric wait by the Postgres dialect (only `NOWAIT` / `SKIP LOCKED`), which is
  why this is `SET LOCAL lock_timeout` and not a JPA `@QueryHint`. Do not "simplify" it to a hint.
- **`SET LOCAL lock_timeout` is not `statement_timeout`.** It bounds only the wait to *acquire* the
  lock. The winner's own hold time is bounded by the table above, not by this key.

**Alternative considered and rejected:** `NOWAIT` (fail instantly). It converts every benign
same-asset redelivery race into an immediate exception, removing the small legitimate window in which
a loser would have acquired and cleanly skipped. A 10 s wait absorbs that window; 0 s does not.

**If the executor judges the DLQ'd no-op unacceptable**, the fallback is: keep the unbounded wait, do
**not** add the key, and record D-04a as an **accepted risk** in the summary with the worst-case hold
time from the table above and the prod pool size it is measured against. That is a legitimate
outcome — what is *not* legitimate is shipping this lock with no stated bound at all.

`process_attempts` is retained but re-purposed honestly: it counts **manual re-drives**, incremented
only by `redriveFromQuarantine`, and bounded by `jtoye.media.max-process-attempts` (default 3) so a
vendor cannot loop a permanently-broken asset through the pipeline (T-27-03). It is **not** a
publish-attempt counter (`media_event_outbox.attempts` is that) and **not** `COUNT(*)` of outbox rows
(which the WR-01 re-upload path also increments).

### D-05 — Suspension circuit: broker-reachability + LOCAL listener liveness. It does **NOT** subsume a remote-consumer probe. **REVISED**

**M2 — what the draft claimed, and why it was false.** The draft suspended the tick on
`AmqpAdmin.getQueueInfo("media.process").getConsumerCount() == 0` and claimed this detected case D
("dispatched, consumer down"). `getQueueInfo` performs a passive queue declare and returns the
**broker-wide** consumer count; `MediaProcessingWorker` (`@RabbitListener`) and `MediaPendingReaper`
(`@Scheduled`) are both `@Component`s in **the same JVM**. So whenever the reaper ticks with its own
listener container running, `consumerCount >= 1` **by construction**. The `== 0` branch is
structurally unreachable in the delivered runtime; the only branches that ever fire there are
throw/null/absent-bean — i.e. "the broker is unreachable from this JVM". Case D was never observable.

**What the circuit actually is, restated:**

| Arm | Signal | What it covers | Falsifiable where |
|---|---|---|---|
| 1 — reachability | `ObjectProvider<AmqpAdmin>` absent, `getQueueInfo` throws, or returns `null` | The broker is unreachable from this JVM — case A, the outage case. **This is the arm that fires in the delivered runtime.** | unit (AC-2.6) + live (broker stopped) |
| 2 — local consumer | `RabbitListenerEndpointRegistry` has no container for `media.process`, or `container.isRunning() == false`, or `getActiveConsumerCount() == 0` | *This* JVM's consumer is down while the connection survives — a single-replica deployment's real case D | unit + integration by `registry.getListenerContainer(id).stop()` (AC-2.7) |
| 3 — broker-wide zero | `getQueueInfo().getConsumerCount() == 0` | Belt-and-braces for a deployment where this JVM is not itself a consumer | **unit only.** Labelled: structurally unreachable while this JVM's container runs. |

**Not covered, stated rather than implied:** a *remote replica's* dead consumer (`--scale
core-java=N`, N>1) is invisible to arms 1–3, because this JVM's own consumer keeps the broker-wide
count ≥ 1. Case D on a multi-replica deployment is therefore made **non-destructive** by D-02 (the
reaper cannot delete), **not detected**. The draft's claim that "D-05 subsumes the broker-health
circuit — one mechanism, not two" is withdrawn: it is a *broker-reachability + local-liveness*
circuit, and there is a residual it does not see.

**Consequence of a misfire is now small**, which is why this is acceptable: with D-02 and D-04 in
force, a false "alive" reading causes at worst a premature vendor-visible `FAILED` **with bytes
retained** and a one-click Re-process — not data loss. Suspension is `WARN` + a
`media.reaper.suspended` counter, and forever-suspended is survivable because D-03's retention sweep
is deliberately **not** gated on it.

*Alternative rejected:* an Actuator `RabbitHealthIndicator` probe — global, coarse, and reports UP
while `media.process` has zero consumers.

### D-06 — Recovery is a first-class surface, not a re-upload. **ACCEPTED**

`POST /api/v1/media/{assetId}/reprocess` → `202` + `MediaAcceptDto`. Requires retained bytes
(`quarantine_expires_at IS NOT NULL AND quarantine_reclaimed_at IS NULL`); requires
`status <> ACTIVE`; requires `process_attempts < max-process-attempts`. Sets `status → PENDING`,
`process_attempts += 1`, `failure_reason → NULL`, `flagged → false`; inserts a fresh outbox row in
the same tx. Mirrors `MediaController.keep` (`:69-84`) exactly for authorization:
`@PreAuthorize("hasAuthority('SCOPE_catalog:write')")` plus the VSA-02
`shopAccessService.require(resolveOwningShopId(asset), SHOP_MANAGER)` gate applied **after** the RLS
`findById`, so a foreign asset is a 404 and never a 403 oracle (`MediaAssetService.java:356-359`).
Carries the uniform `Idempotency-Key` contract via `IdempotencyService.execute("media.reprocess", …)`
and RFC 7807 typed errors.

### D-07 — The worker's *read-failure* path stops deleting; its *validation-veto* path keeps deleting. **ACCEPTED**

`MediaProcessingWorker.fail(...)` (`:239-245`) currently deletes on every failure. A D3 validation
veto (bomb / spoof / undecodable — `:139-147`) should keep deleting: those bytes are worthless and
possibly hostile, and that is a Phase 24 good worth keeping. But the read-failure path (`:129-133`,
"Could not read the quarantined upload") is a transient S3 condition; deleting there converts a blip
into permanent loss. Split it: `failRetainingBytes` (read failure — no delete, markers untouched,
re-drivable) and `failAndDiscard` (validation veto — deletes and stamps `quarantine_reclaimed_at`).

### D-08 — Retention default 72 h, not 7 days. **ACCEPTED**

72 h (259_200_000 ms) covers any realistic broker outage plus a weekend, while bounding the F-3
public-bucket exposure window. Operator-tunable via `MEDIA_QUARANTINE_RETENTION_MS`.

### D-09 — V60 is metadata-only; no backfill, so the RLS-backfill trap does not apply. **ACCEPTED**

`ADD COLUMN … NOT NULL DEFAULT 0` and `ADD COLUMN … TIMESTAMPTZ` (nullable) are metadata-only in
Postgres 11+ — no table rewrite, no per-row UPDATE; the default is recorded in
`pg_attribute.attmissingval` with `atthasmissing = true`. This is the identical argument
`V59__media_asset_version.sql:22-25` makes, and it is why the recurring `trap_rls_migration_backfill`
(V25 → V44 → V57) is genuinely inapplicable rather than merely unmentioned. **No `UPDATE` statement
may appear in V60** — and AC-1.3 asserts this against the *applied* schema (`atthasmissing`), not
against the file.

`MediaAsset` is `@Audited` (`MediaAsset.java:40`), so **all three columns must also be added to
`media_asset_aud`** or the first UPDATE of any asset row throws `column "process_attempts" of
relation "media_asset_aud" does not exist`. V59 dodged this only because `@Version` is excluded from
Envers by project convention (`V59:18-20`). This trap gets its own test with its own break (AC-1.4).

### D-10 — The DELAYED state is derived, not a new status. **NEW (M4)**

A stalled upload must be vendor-visible and explained. The cheap wrong answer is a new
`MediaAsset.Status.DELAYED` — which would change the state machine, break the worker's
`status != PENDING` skip, break the `MediaAssetStatus` wire enum, and require a migration.

Instead: `MediaAssetDto` gains a derived `boolean delayed`, computed server-side in
`MediaAssetService.toDto` as `status == PENDING && createdAt < now − reaperGraceMs`. Server-side
because the threshold is a config value the client does not know. No new status, no migration, no
change to any existing predicate. Additive by construction.

Two surfaces consume it:

- `asset-image.tsx` renders a **third** PENDING presentation: `delayed` → an amber "Taking longer
  than usual" card with the reason and a Check-again control, instead of the indefinite spinner.
- `findReviewQueue()` additionally selects `status = PENDING AND createdAt < :delayCutoff`, so a
  stalled upload **appears in the review queue** rather than being visible only as an inline tile.
  This is a deliberate, enumerated widening of the review queue's meaning ("needs vendor attention"),
  and `MediaReviewQueueIntegrationTest` is expected to need a fixture assertion update — recorded
  here so it is not absorbed as an accident.
