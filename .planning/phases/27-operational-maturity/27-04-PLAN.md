## A. Consumer concurrency and prefetch — CONFIRMED, and the cause is not the obvious one

**A1 — confirmed.** There is no `prefetch`, `concurrentConsumers`, `concurrency` or
`listener.` anywhere under `core-java/src/main/resources/`. Verified with a positive control on the
same directory (`grep -rc "rabbitmq" core-java/src/main/resources/*.yml` → `application.yml:3`), so
this is a real zero and not an already-0 grep.

**A2 — THE KEY FINDING. The properties would not have worked even if they were set.**
`RabbitMQConfig.java:402-411` declares:

```java
@Bean
public SimpleRabbitListenerContainerFactory rabbitListenerContainerFactory(
        ConnectionFactory connectionFactory, MessageConverter jsonMessageConverter) {
    SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
    factory.setConnectionFactory(connectionFactory);
    factory.setMessageConverter(jsonMessageConverter);
    factory.setAdviceChain(retryInterceptor());          // :408
    factory.setDefaultRequeueRejected(false);            // :409
    return factory;
}
```

The bean name is `rabbitListenerContainerFactory`. Boot's
`RabbitAnnotationDrivenConfiguration.simpleRabbitListenerContainerFactory` is annotated
`@ConditionalOnMissingBean(name = "rabbitListenerContainerFactory")` — read from the bytecode of
`spring-boot-autoconfigure-3.5.16.jar` during planning (`javap -v` on
`RabbitAnnotationDrivenConfiguration.class`, `name=["rabbitListenerContainerFactory"]`), and
**independently re-confirmed by bytecode during revision**. So Boot's factory backs off, and
`SimpleRabbitListenerContainerFactoryConfigurer` — **the only consumer of
`spring.rabbitmq.listener.simple.*`** — is never applied to this project's factory.

Consequence: adding `spring.rabbitmq.listener.simple.prefetch: 4` to `application.yml` today would
be a no-op that reads as a fix. **The factory must be repaired before any property can matter.**
This is the single most important finding in this plan and the fail direction of AC-2 is built on it.

**A3 — confirmed defaults.** With the configurer never running, the container's own defaults apply:
`AbstractMessageListenerContainer.DEFAULT_PREFETCH_COUNT = 250` (bytecode-verified via
`javap -constants` on `spring-rabbit-3.2.12.jar`) and `SimpleMessageListenerContainer` starts one
consumer per queue. Boot's own configuration metadata lists `spring.rabbitmq.listener.simple.prefetch`
and `.concurrency` with `defaultValue: null`, i.e. Boot adds no override of its own.

**A4 — confirmed CPU-heavy and serial.** `MediaProcessingWorker.onMediaEvent`
(`MediaProcessingWorker.java:89-120`) is a single `@RabbitListener` on `media.process`.
`MediaNormalizer.normalize` (`MediaNormalizer.java:75-108`) runs, in order: magic-byte sniff →
header-only megapixel bomb guard → full decode → aspect-fit → WebP encode → thumbnail bound → second
WebP encode. Two encodes per message.

**A5 — CORRECTION to the head-of-line framing.** With exactly one consumer the messages are serial
regardless of prefetch, so prefetch 250 does not add head-of-line blocking *within* a replica. What
it does add is **unfair distribution across replicas**, and that is strictly worse at 3 replicas
than at 1: on a burst of 300 uploads the first replica to attach can buffer up to 250 unacked
messages in its local prefetch window while replicas 2 and 3 sit idle with nothing to fetch. Replica
counts are `k8s/base/core-java-deployment.yaml:10` = 3, `k8s/staging/kustomization.yaml:63-65` = 2,
`k8s/production/kustomization.yaml:60-62` = 3, `k8s/local/kustomization.yaml:162-164` = 1. State the
defect as unfair distribution, not as head-of-line blocking.

**A6 — the pod CPU limit caps the answer.** The pod CPU limit is `1000m` and memory
`1Gi` (`k8s/base/core-java-deployment.yaml:432-436`). WebP encoding goes through
`scrimage-webp:4.6.6` (`core-java/build.gradle.kts:54-55`), which forks the native `cwebp` binary
per encode (`core-java/Dockerfile:33` pins `-Dcom.sksamuel.scrimage.webp.binary.dir=/usr/bin`). So
concurrency above ~2 on a 1-core pod buys no throughput and costs process and RSS headroom against a
1Gi limit whose JVM already commits 75% as heap (`core-java/Dockerfile:60,76-77`). **The measurement
in Task 2 must be run under a 1-CPU constraint or it will produce a number that only exists on the
dev workstation.**

**A7 — this settles the global-vs-per-listener question.** `OrderStateChangeListener`
(`OrderStateChangeListener.java:75-123`) at concurrency > 1 loses per-order ordering. Its dedup table
`processed_order_events` is keyed `(tenant_id, order_id, new_status)` — it prevents *repeats*, not
*reordering*. Two rapid transitions on one order could deliver the PREPARING email before the
CONFIRMED one and push the KDS states out of order. A global concurrency setting therefore trades
away a working good to fix an unrelated queue. **Reject global; go per-listener.**

**A8.** `orderEventsFanoutQueue` is an `AnonymousQueue`, which is
`durable=false, exclusive=true, autoDelete=true` (bytecode-verified on
`spring-amqp-3.2.12.jar`; also asserted by `RabbitMQConfigFanoutQueueTest.fanoutQueueIsEphemeral`).
It is a per-JVM SSE fan-out queue: extra consumers on it add nothing and churn UI ordering. Leave at 1.

in `main/resources`.** The revision brief (D-E) restores that fact correctly.

**But D-E's stated consequence does not hold on the Gradle test classpath, and this was measured.**
D-E concludes the configurer bean "does not exist on the `test` profile, and constructor-injecting it
fails context startup for every Spring test on that profile." Three measurements say otherwise:

1. **Both files land on the test runtime classpath under the same name**:

   which returns the **first** match only. Gradle's `sourceSets.test.runtimeClasspath` places
   `resources/test` ahead of `resources/main`, so the **test-resources file wins and the
   main-resources file is shadowed**. The Rabbit exclusion never applies under Gradle.
2. **The project declares no AMQP `ConnectionFactory` bean at all.** `grep` over both source trees
   for a `@Bean`-declared `ConnectionFactory` returns only `CacheConfig.java:69`
   (`RedisConnectionFactory`). `RabbitMQConfig.rabbitListenerContainerFactory` *requires* a
   `ConnectionFactory` parameter, so if `RabbitAutoConfiguration` were genuinely excluded the context
   would already fail today, before any change in this plan.
3. **The real integrationTest artifact shows a live `CachingConnectionFactory`** — 45 occurrences in
   `core-java/build-local/test-results/integrationTest/TEST-uk.jtoye.core.media.MediaProcessingWorkerIntegrationTest.xml`
   (run 2026-07-25T22:58:24, 4 tests, 0 failures). `CachingConnectionFactory` is produced by
   `RabbitAutoConfiguration.rabbitConnectionFactory` and by nothing else here. It ran.

**Verdict, and why D-E's prescription is still adopted in full.** The blocker as phrased would not
fire under `./gradlew test`; a criterion written as "remove the null-guard, watch every Spring test
fail" is therefore **UNFALSIFIABLE as stated** and must not be written that way (AC-9 replaces it).
But the exclusion is real, it is shipped inside the fat jar, and it takes effect for any run that
activates the `test` profile from the packaged artifact rather than the Gradle classpath. The current
behaviour depends entirely on an **undocumented classpath-shadowing accident** that a rename, a
`processTestResources` change, or a `spring.config.location` override would silently reverse — and
the reversal's symptom is a context that will not start. So:

> **`ObjectProvider<SimpleRabbitListenerContainerFactoryConfigurer>` with a no-op when absent is
> adopted (D-01).** It is correct under both readings, it removes the dependency on the accident,
> and its load-bearingness is proven by AC-9 — which builds the context **without** a configurer bean
> via `ApplicationContextRunner`, and does **not** rename any file.

## C. `setForkEvery(4)` — comment verified, mechanism PROVEN, root cause identified

`setForkEvery(4)` is at `core-java/build.gradle.kts:144`; the comment is at `:136-143`. Its claim —
"RabbitMQ listener + reactive HttpClient selector threads are not all reclaimed between classes" — is
**confirmed from a real run artifact**, not inferred. The artifact named in B above contains:

- 54 occurrences of `SimpleMessageListenerContainer`, including stack frames through
  `SimpleMessageListenerContainer$AsyncMessageProcessingConsumer.run(SimpleMessageListenerContainer.java:1328)`
- 45 occurrences of `CachingConnectionFactory`
- 27 occurrences of `Attempting to connect to: [localhost:0]`

So listener containers **do** start in the Testcontainers suite and **do** spawn consumer threads
that connect-retry a dead port for the life of the context.

**The root cause is A2.** Twenty-two test files register
`spring.rabbitmq.listener.simple.auto-startup=false` — including the shared
`core-java/src/test/java/uk/jtoye/core/testsupport/IntegrationTestSupport.java:67`, whose comment
calls it "belt-and-braces … so the context boots without a live broker even if a future profile tweak
re-enables it". Because Boot's configurer never runs, that property has never had any effect; the
only thing preventing a broker connection is the dead port `spring.rabbitmq.port=0` at
`IntegrationTestSupport.java:66`. Repairing the factory makes 22 files' stated intent effective for
the first time, which should remove the thread accumulation and may retire or relax `forkEvery(4)`.

**The existing comment states the failure mode of the pre-fix `forkEvery(0)` run explicitly:** "run in
ONE fork the whole 24-class suite accumulates enough live threads to hit a **native-thread
OutOfMemoryError**." That is the documented, expected outcome of AC-8's third arm, which is why that
arm carries an abort condition and a wall-clock ceiling rather than a timing expectation.

## D. STOMP publish path — CONFIRMED, and D-09-as-drafted is unimplementable AND an availability regression

Re-read during revision, `OrderStateChangeListener.java:105-121`:

```java
// WebSocket broadcast to KDS topic (fire-and-forget per D-06)
try {                                                                    // :107
    orderRepository.findById(event.orderId()).ifPresent(order -> {       // :108
        if (order.getShopId() != null) {                                 // :109
            String topic = StompDestinations.kitchen(                    // :110
                    event.tenantId(), order.getShopId());
            simpMessagingTemplate.convertAndSend(topic, event);          // :111
            log.debug("WebSocket broadcast to {} for order {}", topic, event.orderNumber());
        }
    });
} catch (Exception e) {                                                  // :114
    log.warn("WebSocket broadcast failed for order {}: {}", event.orderNumber(), e.getMessage());
}

sendEmailForState(event);                                                // :119
```

Two independent defects in the draft's D-09:

1. **Unimplementable.** The destination is built *inside* the `ifPresent(...)` lambda, which is
   inside the `try`. There is no point "outside the try" where the destination exists. The draft's
   prescribed placement cannot be written.
2. **An availability regression, which is the more serious of the two.** A throw that escapes the
   swallowing catch propagates out of the `@RabbitListener` → the `retryInterceptor()` advice chain
   (3 attempts, `RabbitMQConfig.java:390-400`) → `AmqpRejectAndDontRequeueException` →
   `setDefaultRequeueRejected(false)` at `:409` routes it to `order.state-changes.dlq`. And
   `sendEmailForState(event)` at `:119` **never runs**. Because the destination is deterministic per
   `(tenant, shop)`, a shape defect is not intermittent — it fires on *every* message for that
   tenant. So the draft's guard converts "the KDS silently stops updating" into "**all order-state
   processing and all order confirmation/preparation emails stop for that tenant**". That is a
   textbook Incremental Betterment violation: a working good (order emails, dedup bookkeeping)
   traded away to add a new one.

**Other confirmed facts.** The SUBSCRIBE-side guard is `TenantChannelInterceptor.java:136-141`. The
sole builder is `StompDestinations.kitchen` (`StompDestinations.java:51-53`) — a `private`
constructor, `final` class, one public factory method. `SimpMessagingTemplate.convertAndSend` appears
**exactly once** in main source, at `OrderStateChangeListener.java:111`. `StompDestinationsTest` has
4 tests, all asserting properties of the string `kitchen()` returns.

**The honest coverage note.** `kitchen(UUID, UUID)` takes UUIDs, whose `toString()` can never contain
`/`. So on today's tree the construction-time assertion cannot fire from bad *input* — it fires from
a bad *shape constant* (`SEPARATOR`, `TOPIC_PREFIX`) or a future overload, which is precisely the
#266 regression class. Moving the guard into the builder does mean it no longer sees a caller that
**bypasses** `kitchen()` entirely; that residual is covered by a separate, falsifiable call-site
assertion (T6.3), not by silence. Cross-reference **#289** (STOMP shop-gate hard-coded to the kitchen
topic) — the same one-feature assumption, recorded there, is why a *general* destination guard in the
builder is the right home for this.

## F. The connection-budget interaction — the draft's M6 fix was the WRONG EQUATION IN THE WRONG PLACE

`k8s/scripts/check-connection-math.sh` computes, per environment,
`replicas × HikariPoolSize + fixed extras ≤ 80% of (max_connections − reserved)`. Run live during
revision:

```
Postgres budget: max_connections=200, reserved=3, app-usable=197, 80% budget line=157
k8s prod (HPA max+surge)     11 replicas x pool 10  + keycloak(20)+backup(1)+exporter(2) = 133  -> OK (<= 157)
k8s staging (HPA max+surge)  11 replicas x pool 10  + keycloak(20)+backup(1)+exporter(2) = 133  -> OK (<= 157)
compose dev (--scale 2)       2 replicas x pool 20  + keycloak(20)+exporter(2)+healthcheck(2) = 64  -> OK (<= 157)
PASS: connection-pool math fits Postgres max_connections=200 with >=20% headroom.   exit=0
```

**The draft proposed adding an `endpoints × concurrency` term to this script. That is wrong and must
not be done.** A pod **cannot** open more connections to Postgres than its Hikari
`maximum-pool-size` — the pool *is* the cap. Consumer threads contend *for* pool connections; they do
not create new ones. Adding them to a cluster-wide `max_connections` budget double-counts and asserts
an exhaustion that cannot physically occur. And the arithmetic confirms the criterion would have been
inert anyway: the draft claimed a `default-concurrency: 3` break would fail this gate at "24 threads",
but the compose-dev row sits at 64 against a budget of 157 — adding even 27 gives 91, still OK. The
break would not have fired.

**The hazard the draft correctly identified is real, but it is intra-pod, not cluster-wide:**
N consumer threads holding pool connections starve HTTP request handling *inside one pod*. The
correct equation is

```
Σ(concurrency over all 9 listener endpoints)  +  httpReserve  ≤  maximum-pool-size
```

per profile. Pool sizes: `application.yml:18` `${DB_POOL_SIZE:20}` (base/dev),
`application-prod.yml:14` and `application-staging.yml:11` `${DB_POOL_SIZE:10}`.

**Run the numbers on the CURRENT tree before writing the gate, because they are alarming.** Nine
endpoints at concurrency 1 = **9 consumer threads against a prod pool of 10**, leaving **1**
connection for all HTTP request handling at worst-case saturation. This is an *existing* condition,
not one this plan introduces — and it means the new gate may legitimately FAIL on the correct,
unmodified tree. That is the "expected-0 that is actually 1 on a correct tree" shape from the standing
proof rules. **T5 runs the gate on the unmodified tree first and records its verdict. If it fails
there, the constant is NOT tuned to make it pass** — the finding is recorded, and the remedy is either
raising `DB_POOL_SIZE` or bounding `mediaMaxConcurrency`, decided by a human at the T2 checkpoint.

`check-connection-math.sh` is **left byte-unchanged**; its equation is correct for what it measures.

## Trust Boundaries

| Boundary | Description |
|---|---|
| broker → consumer thread | Message payload names the tenant; the thread has no ambient identity (**#284**) |
| consumer thread → Postgres session | The GUC pin is the only thing standing between the worker and every other tenant's rows |
| consumer thread pool ↔ Hikari pool | Two bounded resources contending **inside one pod**; exhausting one starves the API |
| publisher → STOMP relay | A destination string becomes an AMQP routing key on a shared broker (#266, #289) |
| measurement harness → shared dev stack | The baseline run CPU-constrains and loads a stack a second session may own |
