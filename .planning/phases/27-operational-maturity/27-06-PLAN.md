### The `awk` range trap — measured, and it is why AC-1.3 does not use the drafted form

27-00's AC-7.3 asserted
`awk '/^  ops-contracts:/,/^  [a-z-]+:$/' … | grep -c 'chmod +x'` returns 2. **That form is broken
regardless of the number**: `ops-contracts:` itself matches the range's END pattern, so the range
collapses to a single line. Measured against four real jobs of that shape:

| Job | old range form | new flag form |
|---|---|---|
| `branch-parity` | **1 line, 0 chmod** | 35 lines, 1 chmod |
| `openapi-compat` | **1 line, 0 chmod** | 43 lines, 1 chmod |
| `security-scan` | **1 line, 0 chmod** | 55 lines, 0 chmod |
| `k8s-validate` | 59 lines, 5 chmod | 57 lines, **5 chmod** |

`k8s-validate` survives only because the digit `8` fails `[a-z-]+`. So on a correct tree the drafted
assertion returns **0** — and `grep -c` printing 0 **exits 1**, killing the harness under `set -e`.
The stated "returns 2" was never reachable and the break could never fire. **Use the flag form**, and
carry `k8s-validate` -> 5 as a mandatory control, because an extractor that returns 0 for everything
would otherwise satisfy a `== 3` assertion by accident on exactly one broken day.

<decisions>

- **D-01 — A new `ops-contracts` job, not extra steps on `k8s-validate`.** These gates are not
  k8s-scoped; overloading a job named for kustomize validation makes its failures unreadable, and the
  first person to see `K8s Kustomize Secret Guard` fail on an EOL date will assume the gate is broken.
- **D-02 — Three steps, and `check-alert-rules.sh` is one of them (D-K).** The orphan is the reason
  this plan asserts `== 3` rather than `== 2`. A gate that both owners believed the other had wired is
  the exact failure mode this phase exists to make impossible.
- **D-03 — Exit 2 fails the job.** No `continue-on-error`, no `|| true`, no `if: always()` softening.
  The gates' whole contract is that "could not check" is never "clean"; a CI wiring that inverts that
  at the last step would waste every falsifiability proof in the phase.
- **D-04 — The outbound dependency is accepted, and the amber/red dates are written into the header.**
  `check-dependency-horizons.sh` calls `endoflife.date`; an outage turns the job RED via exit 2. That
  is deliberate. To keep a *horizon-driven* red from being misread as an outage, the header states the
  dates the job goes amber and red with **no code change** — driven by rabbitmq 4.3's vendor horizon
  of 2026-11-30 against the 90-day warn window: **amber ~2026-09-01, red 2026-12-01**.
- **D-05 — `docker` is a declared prerequisite of the third gate.** `check-alert-rules.sh` runs
  `promtool` via `docker run --rm --entrypoint=promtool prom/prometheus:v2.48.0` (`promtool` is not
  installed on hosts, and the image's ENTRYPOINT is `/bin/prometheus`, so a bare
  `docker run … promtool` exits 1 with `error: unexpected promtool`). `ubuntu-latest` runners have
  docker; the gate VOIDs without it. The image pull is a second outbound dependency and is stated.
- **D-06 — `needs:` membership is decided by a checked fact, not a preference.** `ops-contracts`
  carries no job-level `if:` and the workflow has no `paths:` filter, so it cannot skip and is
  therefore *eligible* for the deploy `needs:` list. If it is added, the enumerating comment at
  `:596-605` is updated in the same edit (AC-1.6). If it is not added, the SUMMARY records why.
- **D-07 — An UNKNOWN horizon row does not make this job permanently red.** 27-02 hands 27-00 a
  `rabbitmq-k8s` row that is unresolvable from this repo (**measured: `grep -rn 'image:.*rabbitmq' k8s/`
  returns nothing** — the only `rabbitmq` strings under `k8s/` are the configmap host/port and the
  `rabbitmq-credentials` Secret refs). Under 27-00's schema (D-Q/D-09b) that row is UNKNOWN with a
  dated `manual_review`: **printed on every run, counted as `unknown=1`, exit 0 — and exit 1 the day
  the review lapses.** This plan does not add a flag, an allowlist or a `|| true` to achieve that;
  it verifies the property holds (AC-1.9). Rejected alternative: wiring the gate with
  `continue-on-error` "until the row is resolved" — that is the `|| true` under a different name, and
  nothing would ever make it come back off.
- **D-08 — This plan does not edit a single gate script.** If a gate has to change to be wireable,
  that is a finding about the gate and is reported, not absorbed. Every script is in
  `files_NOT_modified_by_design`.
- **D-09 — Issue #115 stays OPEN.** 27-00 satisfied bullet 1 (a documented load-test baseline) and
  committed the artifact; the second bullet (edge<->core contract check + a dependency-down fault test
  in CI) is untouched. This plan posts the comment citing 27-00's artifact and files the follow-up.
  Closing an issue two-thirds undone is "green by construction" in issue form.

</decisions>
