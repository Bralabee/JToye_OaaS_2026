# 27-05 — Webhook fan-out is dead: untrusted-package deserialization

## Objective

Outbound webhook fan-out has **never worked**. Every event routed to `webhook.deliveries` fails
deserialization, exhausts its retries and dead-letters. Fix the cause, prove the path end-to-end,
and make the failure class impossible to reintroduce silently.

This plan exists because Phase 27's other plans **alert on this symptom and dispose of its residue
without fixing it** — 27-03 adds `DeadLetterQueueNonEmpty`, 27-02 purges the queue. Shipping those
alone would page an operator for a bug the phase declined to fix, and the alert would re-fire
immediately.

## Verified problem statement

**Every claim below was measured on the running stack on 2026-07-26. Commands and outputs are the
ones actually run.**

**1. The exception, from `docker logs <core-java>`:**
```
ERROR uk.jtoye.core.config.RabbitMQConfig - RabbitMQ message processing failed after 3 retries: Failed to convert message
org.springframework.amqp.AmqpRejectAndDontRequeueException: Exhausted retries — routing to DLQ
  at uk.jtoye.core.config.RabbitMQConfig.lambda$retryInterceptor$0(RabbitMQConfig.java:396)
Caused by: org.springframework.amqp.rabbit.support.ListenerExecutionFailedException: Failed to convert message
Caused by: java.lang.IllegalArgumentException: The class 'uk.jtoye.core.order.OrderStateChangeEvent'
  is not in the trusted packages: [java.util, java.lang].
  at org.springframework.amqp.support.converter.DefaultJackson2JavaTypeMapper.getClassIdType(...:179)
```

**2. The cause** — `core-java/src/main/java/uk/jtoye/core/config/RabbitMQConfig.java:385-387`:
```java
@Bean
public MessageConverter jsonMessageConverter() {
    return new Jackson2JsonMessageConverter();      // ← no trusted packages
}
```
`DefaultJackson2JavaTypeMapper` defaults its allowlist to `[java.util, java.lang]`. Resolving
`__TypeId__` to an application class is therefore rejected.

**3. Why only this listener** — and this is the load-bearing distinction:

| Listener | Shape | Needs `__TypeId__` → class? | Works today |
|---|---|---|---|
| `OrderStateChangeListener`, `MediaProcessingWorker`, the 3 notification listeners, `PaymentEventAuditListener` | single-method `@RabbitListener(queues=…)` with a **typed parameter** | **No** — Spring infers the target type from the method signature | ✅ |
| **`WebhookFanoutListener`** | **class-level `@RabbitListener` + 5 `@RabbitHandler` methods** | **Yes** — the type must be resolved to select the handler | ❌ **always fails** |

So the defect is invisible everywhere except the one listener that uses multi-handler dispatch. KDS,
media processing and notifications all work, which is why this went unnoticed.

**4. Blast radius — measured:**
- `webhook.deliveries.dlq` depth **9** (`rabbitmqctl list_queues`)
- x-death `reason: rejected`, `count: 1`, routing key `order.state.pending`,
  `__TypeId__: uk.jtoye.core.order.OrderStateChangeEvent`
- **oldest x-death `2026-07-15T11:46:18Z`, newest `2026-07-26T15:33:51Z`** — the producer is **live**,
  not historical (management API peek, `ackmode=reject_requeue_true`, depth re-asserted at 9 after)
- `webhook_subscription` = **0 rows across 6 tenants**, `webhook_delivery` = **0 rows** — previously
  read as "nobody subscribed". It is not: **no event has ever reached the fan-out logic**, so a
  subscription could not have produced a delivery even if one existed.

**5. What this means for the feature.** Phase 22 shipped outbound webhooks (#205) with a passing
suite. The tests exercise `WebhookFanoutListener` by direct invocation, not through the converter, so
the suite is green and the runtime is dead. This is the recorded green-by-construction failure mode,
in a new place.

## Decisions

- **D-01 — Trust `uk.jtoye.core`, never `*`.** `Jackson2JsonMessageConverter(String... trustedPackages)`
  exists in spring-amqp 3.2.12 (verified by `javap`). Trust-all (`*`) restores a deserialization-gadget
  surface on a broker that carries tenant data; a scoped allowlist gets the same result with no such
  surface. Rejected alternative: converting `WebhookFanoutListener` to single-method dispatch with a
  manual type switch — it would work, but it hides the defect rather than fixing it, and the next
  multi-handler listener would fail the same way.
- **D-02 — This blocks 27-02's disposition checkpoint.** Once the converter is fixed, the 9 dead
  letters become **replayable**, not merely disposable. Deciding their fate before the fix would
  discard messages that can now be processed correctly. 27-02 must adjudicate *after* this lands.
- **D-03 — Guard the class, not the instance.** The failure is silent for any future class-level
  `@RabbitListener` + `@RabbitHandler` listener. Ship a test that fails when a multi-handler listener
  exists whose payload types are not resolvable by the configured converter.
- **D-04 — Correct the false javadoc.** `WebhookFanoutListener`'s class comment states *"Any
  unexpected payload type is ignored (no dead-letter — this queue has no DLX)"*. The queue **does**
  have a DLX (`RabbitMQConfig` `webhookDeliveriesDeadLetterExchange` → `webhook.deliveries.dlq`,
  currently holding 9 messages). A comment asserting the opposite of the topology is how this stayed
  unexamined; fix it in the same change.
- **D-05 — Do not widen scope to the fan-out logic itself.** Whether `fanout()` behaves correctly
  once messages arrive is unproven and out of scope beyond AC-3's end-to-end proof. Anything found
  there is recorded, not absorbed.

## Threat model (ASVS L1)

| # | Threat | Mitigation |
|---|---|---|
| T-27-05-1 | **Deserialization gadget** via an over-broad trusted-package allowlist | D-01 scopes to `uk.jtoye.core`; AC-5 forbids `*` with a positive control |

| T-27-05-3 | **Tenant data written to disk** by the diagnostic peek/archive | Any archive path is gitignored and never staged; assert non-stageability before writing |
| T-27-05-4 | Fixing the converter **unblocks a flood** of previously-rejected events | The DLQ holds 9, not thousands; replay is operator-gated in Task 3 |
