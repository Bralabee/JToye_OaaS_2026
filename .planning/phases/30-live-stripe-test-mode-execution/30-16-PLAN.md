  <decision>Does the single-use payment-link token travel in the URL path (/pay/{token}, as PAY-04 issues today and D-03 names) or in the URL fragment (/pay#token=…)?</decision>
  <context>
    The token is a bearer credential for a customer's payment. A path token appears in every request line: Traefik, core-java
    and frontend access logs (the page load and the preview/redeem API calls). A fragment never leaves the browser in a request
    line; the page posts it in a JSON body, which is the rule this project already follows for /invite (V77) and the DSAR
    download link (V75). Changing later breaks every link already sent (links live at most 7 days; none exist in production).
    Reversibility: costly (a published URL shape and API contract).
  </context>
  <options>
    <option id="path">
      <name>Path, as built: /pay/{token}</name>
      <pros>Matches D-03's wording and PAY-04's issued URL; no backend URL change; GET preview by path</pros>
      <cons>The token is written to access logs at three layers on every open; diverges from the project's own fragment rule for bearer tokens</cons>
    </option>
    <option id="fragment">
      <name>Fragment: /pay#token=…</name>
      <pros>The token never appears in a request line or access log; consistent with /invite and /data-request; a link pasted into chat stays out of server logs</pros>
      <cons>PAY-04's issued URL changes (staging links already sent stop resolving); a body-token preview and redeem are added beside the path redeem; the page reads location.hash</cons>
    </option>
  </options>
