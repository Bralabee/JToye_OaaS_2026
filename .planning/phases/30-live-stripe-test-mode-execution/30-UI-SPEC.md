## S1 — Storefront card checkout (#957)

**Focal point (primary visual anchor):**
- **Step 1, normal state:** the oxblood "Place order · £X" CTA (unchanged).
- **Step 1, card unavailable:** the amber "Card payments are unavailable" notice at the top of step 1. It is the first thing on the screen, and the CTA beneath it is visibly disabled and points back to it via `aria-describedby`.
- **Step 2, normal state:** the oxblood "Pay £X" CTA.
- **Step 2, failed state:** the amber "Card payment couldn't load" block, which takes the CTA's place.
- One `h1` per step, unchanged: "Checkout" on step 1, "Payment" on step 2.

**What changes:**
- **Pre-POST fail-loud.** When `shop.acceptsCardPayments === true` and `publishableKey()` is null, the page does **not** POST.
  - Render a notice at the **top of step 1**, in the K3 slot directly after `ShopAvailabilityNotice`. When both apply, availability comes first.
  - Notice: `role="alert"`, `id="card-payments-unavailable"`.
  - Layout follows `ShopAvailabilityNotice`: `flex items-start gap-3 rounded-xl border border-amber-600 bg-amber-50 p-4`, with an `AlertTriangle` icon (`h-5 w-5 text-amber-700`, `aria-hidden`), a headline at 16/600 and a detail line at 14/400.
  - "Place order" is `disabled` with `aria-describedby="card-payments-unavailable"`. The `belowMinimum` / K3 rule applies: a button may be disabled only when the reason is on screen.
  - In the "How you'll pay" card, the card line becomes the copy row "How you'll pay (card unavailable)".
- **Post-POST defence in depth.**
  - When a confirmation carries a `clientSecret`, step 2 renders **in every case**. The render guard becomes `if (paymentState)`, not `if (paymentState && stripePromise)`.
  - Inside step 2 the payment-details card shows one of three things:
    - **Loading:** a `Skeleton` with `min-h-60` and a `role="status"` line reading "Loading secure card form…"
    - **Ready:** the Payment Element.
    - **Failed:** an amber `role="alert"` block. This applies when the key is absent, `loadStripe` rejects or resolves `null`, or `PaymentElement` fires `onLoadError`. The failure copy is the "Card payment couldn't load" row.
  - "Try again" (`h-11`, outline style) appears **only** when a key is present (a script or network failure). It re-runs `loadStripeOnce`. With no key, a retry cannot succeed, so there is no button.
  - "Back to details" stays.
- **Connected-account initialisation.** `[VERIFIED gap, code read 2026-10-21]`
  - `PaymentService.java:207` creates `DIRECT_CHARGE_VENDOR_MOR` (and split-deposit) PaymentIntents **on the vendor's connected account** (`setStripeAccount`). The browser initialises Stripe.js with no `stripeAccount` (zero occurrences in `frontend/`), so `confirmPayment` for a direct-charge order cannot find the intent. Destination charges are unaffected.
  - Contract: `GuestOrderConfirmation` (and S3's redeem response) gain an additive, nullable `stripeAccountId`.
  - When it is present, the page calls `loadStripeOnce(stripeAccountId)` (`loadStripe(pk, { stripeAccount })`); when it is absent, it calls `loadStripeOnce()`.
  - This is a prerequisite for PAY-03's direct-mode browser order, and the planner must place it in the #957 PR or the Connect PR.
- **Customer order page, DRAFT.** In `app/shop/[slug]/orders/[orderNumber]/page.tsx`:
  - For `status === "DRAFT"`, the status line reads "Awaiting payment", not "Order in Progress".
  - `ORDER_STATUS_COPY` gains `DRAFT: { label: "Awaiting payment", desc: "Waiting for your payment" }`.
- **Unchanged (goods preserved):**
  - The lazy-Stripe rule (#793): no Stripe on the form or on cash checkout.
  - Idempotency-key rotation on "Back to details".
  - The allergen record, `SellerBlock` and totals on step 2.
  - The Pay CTA's classes and copy.
  - The "Secured by Stripe" line.
  - `redirect: "if_required"`; `return_url` stays `/shop/{slug}/orders/{orderNumber}`.
  - The cash "Pay on collection" line for a shop with `acceptsCardPayments === false`. Its removal belongs to the backend `allow-unpaid-storefront-orders` gate, not this contract.

## S2 — Kitchen and orders: the server's refusal reason (#958)

**Focal point:**
- **Before a tap:** the "Awaiting payment" badge on the card or row. It sits in the card's header row beside the order number, which is where a cook looks first.
- **After a refused tap:** the refusal sentence. On the New lane it is the inline `role="alert"` block directly above Accept. On the grid it is the destructive toast.
- No new headings. The KDS and Orders page heading structure is unchanged.

**Server contract the UI depends on** (30-RESEARCH.md §#958):
- A refused SUBMIT / CONFIRM / START_PREP on an order awaiting payment returns RFC 7807 with `type: https://jtoye.uk/errors/awaiting-payment` and `title: "Awaiting payment"`.
- `detail` is **exactly** the "Server refusal detail" copy row.
- `detail` carries no issue number. Today's "(#461)" suffix must go, because it reaches staff UI.

**Kitchen grid** (`kitchen/page.tsx` `handleBump`, today a bare `catch {}` at `:623-631`):
- `catch (error)` calls `describeLoadError(error, fallback)`.
- The toast is the `destructive` variant: title "Order not updated", description = `.message` (the server `detail` when present).
- The fallback, for when there is no server body, is the kitchen fallback row.
- The board still re-reads (`fetchOrders()`), so the optimistic move reverts. That behaviour is preserved.

**New lane Accept** (`kds-new-lane.tsx` `describeAcceptFailure`):
- New first branch: when `response.data.type === AWAITING_PAYMENT_PROBLEM_TYPE` and `detail` is a non-empty string, show `detail` in the card's existing inline `role="alert"` (`border-2 border-red-700 bg-white … text-red-800`).
- The stock branch, "moved elsewhere" branch and generic branch are unchanged. Without the new branch, an awaiting-payment refusal falls through to the generic "Check your connection", because the re-read still says PENDING. That generic text is the very defect this fixes.

**`AwaitingPaymentBadge`**:
- Shown wherever `isAwaitingPayment(order)` is true: on New-lane cards, on grid cards (beside the fulfilment badge) and on Orders-list rows (beside `UnverifiedContactBadge`).
- Style: `Badge variant="outline"`, `flex w-fit items-center gap-1 border-2 border-amber-700 bg-white text-amber-800`, with a lucide `Hourglass` at `h-3 w-3 aria-hidden`. If `Hourglass` is absent from lucide 1.56.0, use `CreditCard`.
- Visible text is "Awaiting payment". It has a `title` and an `sr-only` sentence, both the badge explanation row, and `data-testid="awaiting-payment"`.
- It renders nothing when `paymentStatus` is absent (an older backend). Not recorded is not unpaid, per the F20 rule.

**KDS Accept / Start Preparing stay enabled** on an awaiting-payment card. A disabled button on a touch screen gives no feedback (the
project rule recorded at `checkout/page.tsx:1801-1812`). The badge warns before the tap, and the server's refusal explains after it.

**Orders list** (`orders/page.tsx`):
- For an order where `isAwaitingPayment` is true, the `DRAFT → Submit` and `PENDING → Confirm` transition buttons are **not rendered**, and the badge takes their place.
- `Cancel` stays, so a vendor can still clear an abandoned DRAFT (D-02's manual operation).
- The existing toast path already uses `describeLoadError`, so a refusal that reaches it shows the new `detail` unchanged.

## S3 — `/pay/{token}` payment-link page (D-03)

### Data contract (backend additions this page requires)

The redeem endpoint (`POST /api/v1/public/payment-links/{token}/redeem`) **consumes the link before it returns**: `markUsedIfUnused`
runs at `OrderPaymentLinkService.java:293`, before the Stripe retrieve at `:306`. Its response carries no shop name, no order number and no
connected account. So:

1. **Non-consuming preview: RESOLVED, in Phase 30 scope** (orchestrator ruling 2026-10-21, under D-03: a link must be payable end-to-end, and a link scanner burning a single-use link breaks that). Three parts ship together:
   - (a) the preview endpoint;
   - (b) the "Continue to payment" press, which is the only thing that calls redeem;
   - (c) the check that Stripe.js has loaded **before** redeem (sequence steps 2a and 2b).

   Add `GET /api/v1/public/payment-links/{token}` (read-only, rate-limited, tenant-less bearer lookup as in redeem).
   - It returns `shopName`, `orderNumber`, `amountPennies`, `currency`, `purpose` (`UPFRONT|DEPOSIT|BALANCE`), `expiresAt` and `state` (`ACTIVE|USED|EXPIRED|REVOKED|PAID`).
   - It returns `seller` only if the planner chooses to reuse `SellerBlock`.
   - The page needs this to show *who* is asking for *how much* before a stranger's link is opened, which is the anti-phishing minimum. It also needs it to say a link is dead **without** consuming anything.
   - Precedent: `/invite`'s preview-then-press flow.
2. **Redeem response, additive:** `stripeAccountId` (nullable; see S1). Redeem's existing status codes stay as they are.
3. **When the preview call itself fails** (429, network, 5xx — never 404/409/410, which have their own states):
   - The card shows the `h1` "Pay for your order" with no amount.
   - Below it is the "We couldn't check this link just now" alert, plus "Try again", which re-GETs the preview.
   - "Continue to payment" is **not** offered in this state, so the link is never spent without the customer having seen who is asking and for how much.

### Focal point and heading structure

- **Focal point:** the amount block. The 24px/600 `h1` ("Pay {shopName}") and the 24px/600 amount directly beneath it read as one unit: who is asking, and for how much. The oxblood CTA is the secondary anchor; it is "Continue to payment" before the press and the inherited "Pay £X" after it.
- **Exactly one `h1` per page.** It is the 24px/600 state heading, which is replaced on each state change and receives focus.
  - The moved `CardPaymentForm` contains **no `h1`**. Its only heading is `<h2>Payment details</h2>` (14px/600). The 20px/700 "Payment" `h1` belongs to the checkout page's step 2, stays in `checkout/page.tsx`, and is **not** moved into the shared form.
  - So on `/pay` the outline is: `h1` state heading → `h2` "Payment details", with no second `h1`.
  - The executor must keep it that way: `CardPaymentForm` never renders an `h1`.

### Layout (mobile-first, 360px first)

- `PublicShell` → `<div className="px-4 py-8">` → one card: `mx-auto max-w-md rounded-2xl border border-cream-100 bg-white p-6`.
- Inside the card, top to bottom:
  1. Shop name at 14/400 slate-600
  2. `h1` at 24/600 (purpose-specific; see copy)
  3. Amount at 24/600 `tabular-nums` slate-900
  4. "Order {orderNumber}" at 14/400 slate-600
  5. Expiry line at 12/400 slate-600
  6. Single-use note (body)
  7. CTA, full width, `h-12`
- After the press, the payment-details card from `CardPaymentForm` renders **inside the same column** under the amount block. The amount block stays visible, so the customer always sees what they are paying.
- Focus: on every state change the new state's `h1` receives focus (`tabIndex={-1}`, `focus:outline-none`), the pattern the order page uses at `headingRef`. Loading states use `role="status"`; failure blocks use `role="alert"`.
- No motion beyond `Loader2 animate-spin`, which `prefers-reduced-motion` already covers in `globals.css`.

### Interaction sequence

1. **Mount:** GET preview, while showing the "Checking" state. Stripe is **not** loaded.
2. **Press "Continue to payment":**
   - a. If `publishableKey()` is null, go to the *unavailable — link not used* state. **Do not redeem.**
   - b. Otherwise `await loadStripeOnce()`. On reject or `null`, go to *unavailable — link not used*. **Do not redeem.** This proves Stripe.js loads before the single-use link is spent.
   - c. POST redeem. On 409, 410 or 404, go to the matching dead-link state. On 502 or another 5xx, go to *unavailable — link opened*.
   - d. `replaceState` to `/pay` (with the resume entry, see Storage), then `loadStripeOnce(stripeAccountId ?? undefined)`, then `stripe.retrievePaymentIntent(clientSecret)`:
     - `succeeded` → *already paid*
     - `processing` → *processing*
     - otherwise → mount `Elements` + `CardPaymentForm` (`returnUrl = origin + "/pay?acct=" + (stripeAccountId ?? "")`; `onSucceeded` → *payment received*; `onLoadError` → *unavailable — link opened*)
3. A declined card keeps the form mounted with the existing inline red error. The PaymentIntent is still payable, so the customer retries in place.
4. **`/pay` with Stripe's redirect query** (`payment_intent_client_secret`, `redirect_status`): load Stripe with `acct` when present, retrieve the PaymentIntent and show *payment received*, *processing* or *redirect failed*. **`/pay` with no query** shows the *no link* state.
