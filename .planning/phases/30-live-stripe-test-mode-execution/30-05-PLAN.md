<objective>
Issue #958 (P1), PR 2 part 1 of 4 — the server refuses to start work on an unpaid order. Branch:
`fix/958-awaiting-payment-gate` (cut in plan 30-04).

Root cause (30-RESEARCH §#958): the payment guard sits on one edge (CONFIRMED→PREPARING) of a three-edge path; SUBMIT and
CONFIRM are unguarded, and the customer's "Received"/"Confirmed" emails come from the outbox events those transitions
write. The fix gates all three edges at the single chokepoint every caller funnels through (`OrderService.transitionOrder`:
dashboard, kitchen, REST, MCP), before any mutation, with a typed RFC 7807 problem the UI can show verbatim. A second
defect on the same path: the payment-success webhook resets any order to PENDING, so a link paid on a CONFIRMED order
regresses it and re-sends "Received".

Design decisions (Claude's discretion, recorded): status 409 Conflict rather than invalid-state-transition's 400 — the
request is well-formed and conflicts with the order's state; clients key on the stable `type`. AwaitingPaymentException is
its own class (not a subclass) so no existing InvalidStateTransitionException catch swallows it.
Policy D-05 stands: the consumer pays, by link or card, before service — no cash at fulfilment.
Output: the gate, the typed problem, the status-preserving webhook, tests, counts.
</objective>
