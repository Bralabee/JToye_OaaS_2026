<objective>
Issue #957 (P0), PR 1 of the phase, part 1 of 4 — the build channel, proven end to end. Branch: `fix/957-card-checkout-payment-step`.

Root cause (30-RESEARCH §#957, verified on the running staging bundle): `frontend/Dockerfile` declares no
`ARG NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` and CI passes no such build-arg, so `next build` never inlines the key, the
browser's `getStripe()` returns null and the checkout silently falls back to the form after a 201 created an unpaid
DRAFT. This plan opens the channel (Dockerfile ARG, compose build arg, CI build-arg), moves the key read into one
loader module, and adds the two gates that keep it open: the deploy-time repository-variable guard (staging needs
`pk_test_`, production refuses it — D-06, D-08) and the served-chunk check that reads the key out of the running
artifact after every staging deploy.

Purpose: the key can only reach the browser through a build channel the repo enforces, and a deploy that would ship a
missing, live or wrong-mode key is refused before it happens.
Output: the channel, `frontend/lib/stripe-loader.ts`, two gate scripts with `--selftest`, CI wiring, the env-contract
allowlist row removed.
</objective>
