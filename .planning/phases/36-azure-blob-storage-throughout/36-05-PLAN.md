  <name>Task 1: Owner decides the storage account names, regions and redundancy</name>
  <decision>Which storage account names, regions and SKUs do staging and production use for media and for backups?</decision>
  <context>
    Account names are 3-24 lowercase alphanumerics, globally unique across Azure, and are embedded
    in every persisted image URL in staging/production (D-06: raw endpoint). They go into
    k8s/staging and k8s/production overlays and the committed goldens in 36-09, so they must be
    decided now. Nothing is created in this phase; Phase 29 creates them, so a name chosen now
    could be taken by someone else before then -- the runbook tells Phase 29 to create promptly
    and gives the fallback rule. D-01 requires the backup account in a DIFFERENT region from
    staging; the cluster is in uksouth, so the recommended backup region is ukwest (its pair,
    assumption A12, confirmed in Phase 29 with az account list-locations).
  </context>
  <options>
    <option id="option-a">
      <name>Short names, LRS everywhere (recommended)</name>
      <pros>Cheapest; staging media jtoyestgmedia (uksouth), staging backup jtoyestgbackup (ukwest), prod media jtoyeprodmedia (uksouth), prod backup jtoyeprodbackup (ukwest); regional separation of backups comes from the backup account's own region, as D-01 asks</pros>
      <cons>Short names are more likely to be taken; LRS media has no zone redundancy (staging is a rehearsal environment)</cons>
    </option>
    <option id="option-b">
      <name>Suffixed names for uniqueness, LRS media, ZRS backups</name>
      <pros>A random 4-character suffix (e.g. jtoyestgmedia7k2q) almost guarantees availability; ZRS keeps backups through a zone loss inside ukwest</pros>
      <cons>Longer URLs; ZRS costs more; the suffix is arbitrary</cons>
    </option>
    <option id="option-c">
      <name>Owner supplies names/regions/SKUs</name>
      <pros>Full control</pros>
      <cons>Must still pass the availability check in Task 2</cons>
    </option>
  </options>
