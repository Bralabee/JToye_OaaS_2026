<objective>
Stop completed orders being deleted from under their ledger rows, and give Group admins an auditable void (D-10; RWO-018 UXT-018, P0).

Purpose: today any shop manager can DELETE a COMPLETED order, leaving financial_transactions rows that point at a 404. The delete
guard is reversible and lands first; the reversing-ledger representation is a one-way door (financial records vendors will rely
on), so the owner confirms it at a checkpoint before it is written.

Output: the delete guard, the void endpoint, V78 with its stepwise test, ledger entry kinds and netted aggregates.
</objective>

<feature>
  <name>Delete guard and void with a reversing ledger entry</name>
  <files>OrderService, OrderController, Order, V78, FinancialTransaction*, EntryKind, two exceptions, GlobalExceptionHandler</files>
  <behavior>
    - COMPLETED order -> DELETE -> 409 order-not-deletable (status COMPLETED in the body); GET still 200
    - PENDING order -> DELETE -> 204 (unchanged behaviour for DRAFT/PENDING)
    - Group admin void {reason:"Test order"} on COMPLETED -> 200; order GET 200 with voidedAt/voidedBy/voidReason; financial_transactions holds the SALE and one REVERSAL of the negated amount; summary revenue for that order nets to 0
    - same void again -> 200 no new row; different reason -> 409 order-already-voided
    - SHOP_MANAGER void -> 403; blank reason -> 400
    - void on a CONFIRMED order with no SALE row -> 200, no ledger row; the order leaves the kitchen board
  </behavior>
  <implementation>Columns not status; reversal written only when a SALE exists; finder keyed by entry kind.</implementation>
</feature>
