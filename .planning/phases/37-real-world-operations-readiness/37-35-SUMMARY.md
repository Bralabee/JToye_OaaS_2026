# Phase 37 Plan 35: No unapplied promotions and no reviewer surnames in public data Summary

**The public API no longer advertises a discount that checkout never applies. It no longer publishes a reviewer's surname either. Both public promotion reads, `GET /public/shops/{slug}/promotions` and `ShopConfigDto.activePromotions`, return an empty list for every shop. The public storefront service no longer holds the promotion repository, so no flag can turn them back on (D-17). The vendor's promotions, their CRUD and the stored rows are unchanged. Public reviews now name the author as first name plus last initial ("Grace Ann Pemberton" becomes "Grace P."), derived at read time by `ReviewerDisplayName`. The stored review keeps the full name for erasure and export. Each half was RED against the unfixed tree and GREEN after the change. The integration arms assert absence over the whole response body.**

## Goods displaced, and how each is accounted for (Incremental Betterment)

- **Public promotion data**, removed on purpose. It was the defect: a claim with no data behind it (D-17). The vendor's data is kept in full: the rows, `PromotionService`, `/api/v1/promotions` CRUD and the dashboard marketing page. The IT's vendor arm proves the list still shows the row and that the row is still `active`.
- **The `activePromotions` field and the promotions endpoint.** Both stay, as an array and as a 200, so the storefront's contract and its SSR payload parse unchanged. Only the content is empty.
- **The 404 for an unknown slug** on the promotions read is kept and asserted.
- **The reviewer's full name.** No authenticated vendor view of reviews exists: `ReviewDto` is built only by `ReviewService.toDto`, whose two callers are the public list and the customer's own POST, and `rg -uu ReviewDto core-java/src/main/java` returned rc 0 with only those sites. There was therefore no vendor mapping to keep separate. The full name stays where it is needed:
  - the `reviews` row (asserted by the stored-name arm);
  - the GDPR erasure (V67, `GdprService`, which reads the repository and not the DTO);
  - the Article 15 export (`DsarAccessExportService`, likewise).

### Plan wording that did not hold (recorded, not relabelled)
- **"Public toDto uses it; a vendor endpoint that returned the full name keeps it (separate mapping; listed in the SUMMARY)."** No vendor review endpoint exists (see Goods displaced), so no separate mapping was needed. The truth "any authenticated vendor view keeps the full name" holds vacuously for the API. The data the vendor's tooling relies on (erasure, export) reads the stored name and is unchanged.
- **Display form on the POST response.** The POST response, which goes to the customer who wrote the review, also carries the display form, because it is a `/public/**` endpoint and shares the one `toDto`. The customer typed their own name, so nothing is lost to them.
- **The 'Customer' fallback.** The plan says blank → null "so the UI shows 'Customer'". The server half (null) is done. The storefront today renders `review.customerName || "Anonymous"` (`shop-detail-client.tsx:809`), so changing that copy is 37-36's.
