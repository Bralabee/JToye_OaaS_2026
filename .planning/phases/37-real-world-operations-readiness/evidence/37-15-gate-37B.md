### 1.6 D-06 impact: who loses access when the rebuilt core starts (read-only)

**The only stack access before the checkpoint.** One SELECT ran through
`docker exec -e PGOPTIONS='-c default_transaction_read_only=on' jtoye-postgres psql -U jtoye -d jtoye -v ON_ERROR_STOP=1 -c "$Q"`,
a plain `-c`, not a heredoc. rc=0.

**The rule it encodes** is `ShopAccessService.isGroupAdminForUser` / `isBootstrapAdmin` under strict scoping ON:
- a realm admin (D-03 bridge) is always honoured;
- an OPERATOR tenant-wide GROUP_ADMIN is honoured;
- a JIT tenant-wide GROUP_ADMIN is de-honoured, except for the tenant's oldest JIT admin
  (`created_at`, then `id`) when the tenant has no OPERATOR GROUP_ADMIN (the WARN-logged bootstrap admin);
- shop-scoped grants are honoured whatever their source;
- a user with no `shop_staff` row at all, who is an implicit Group admin only under strict OFF, has no access.

The last category is not in the plan's wording ("users whose rows are only JIT"). It is listed because the
running runtime is strict OFF, and its ungranted users lose access at the flip too (Rule 2: a complete
impact list).

**Query** (`d06-query.sql`, verbatim):

```sql
WITH ss AS (SELECT * FROM shop_staff),
people AS (
  SELECT tenant_id, user_id FROM ss
  UNION
  SELECT tenant_id, user_id FROM user_directory
),
tenant_op_ga AS (
  SELECT DISTINCT tenant_id FROM ss
  WHERE shop_id IS NULL AND role = 'GROUP_ADMIN' AND grant_source = 'OPERATOR'
),
jit_ga_ranked AS (
  SELECT tenant_id, user_id,
         row_number() OVER (PARTITION BY tenant_id ORDER BY created_at, id) AS rn
  FROM ss
  WHERE shop_id IS NULL AND role = 'GROUP_ADMIN' AND grant_source = 'JIT'
),
per_user AS (
  SELECT p.tenant_id, p.user_id,
         count(s.id)                                                         AS grant_rows,
         count(s.id) FILTER (WHERE s.grant_source = 'OPERATOR')              AS operator_rows,
         count(s.id) FILTER (WHERE s.grant_source = 'JIT')                   AS jit_rows,
         count(s.id) FILTER (WHERE s.shop_id IS NOT NULL)                    AS shop_scoped_rows,
         bool_or(s.shop_id IS NULL AND s.role = 'GROUP_ADMIN' AND s.grant_source = 'JIT') AS jit_tenant_ga
  FROM people p LEFT JOIN ss s ON s.tenant_id = p.tenant_id AND s.user_id = p.user_id
  GROUP BY p.tenant_id, p.user_id
)
SELECT t.name AS tenant,
       left(t.id::text, 8) AS tenant_id8,
       left(u.user_id::text, 8) AS user_id8,
       CASE WHEN d.email IS NULL THEN '(no directory row)'
            ELSE left(d.email, 1) || '***@' || split_part(d.email, '@', 2) END AS masked_email,
       lower(coalesce(d.email,'')) IN ('admin@jtoye.com','adminb@tenantb.com') AS realm_admin_in_export,
       u.grant_rows, u.operator_rows, u.jit_rows, u.shop_scoped_rows,
       CASE
         WHEN lower(coalesce(d.email,'')) IN ('admin@jtoye.com','adminb@tenantb.com') THEN 'KEPT (realm admin)'
         WHEN coalesce(u.jit_tenant_ga, false) AND o.tenant_id IS NULL AND j.rn = 1 THEN 'KEPT (bootstrap admin, WARN-logged)'
         WHEN coalesce(u.jit_tenant_ga, false) AND u.shop_scoped_rows > 0 THEN 'LOSES Group admin (keeps shop roles)'
         WHEN coalesce(u.jit_tenant_ga, false) THEN 'LOSES ACCESS (JIT Group admin)'
         WHEN u.grant_rows = 0 THEN 'LOSES ACCESS (ungranted; implicit admin only under strict OFF)'
         ELSE 'unchanged'
       END AS under_d06,
       to_char(d.last_seen, 'YYYY-MM-DD') AS last_seen,
       (SELECT count(*) FROM shop_staff)     AS total_shop_staff_rows,
       (SELECT count(*) FROM user_directory) AS total_user_directory_rows,
       (SELECT count(*) FROM tenants)        AS total_tenants,
       current_setting('is_superuser')       AS superuser,
       current_setting('transaction_read_only') AS read_only
FROM per_user u
JOIN tenants t ON t.id = u.tenant_id
LEFT JOIN user_directory d ON d.tenant_id = u.tenant_id AND d.user_id = u.user_id
LEFT JOIN tenant_op_ga o ON o.tenant_id = u.tenant_id
LEFT JOIN jit_ga_ranked j ON j.tenant_id = u.tenant_id AND j.user_id = u.user_id
ORDER BY t.name, under_d06, masked_email
```

`read_only = on`. The query saw data: these are non-zero counts, not a VOID.

**Verdict on the dev stack: NOBODY loses access.** Each tenant's only JIT Group admin is its bootstrap
admin, and the two realm admins are kept by their token role. Tenant C (the third tenant) has no
`shop_staff` and no `user_directory` row.

**What the query cannot see:**
- Realm admins are identified by matching emails against the realm export (`infra/keycloak/realm-export.json`:
  `admin@jtoye.com`, `adminb@tenantb.com`), not against live Keycloak. V76's `realm_admin_seen_at` is not
  on the running database yet. A realm admin added by hand in live Keycloak would be classed by its grants
  instead. In this data the only gap is that such a user would show as "LOSES ACCESS (ungranted)" when they
  are in fact kept, so the list could only over-state losses.
- Seeded vendor accounts that have never signed in have no `user_directory` row and no grant. They lose no
  existing access, and from the rebuild on they need an invitation or a grant.
