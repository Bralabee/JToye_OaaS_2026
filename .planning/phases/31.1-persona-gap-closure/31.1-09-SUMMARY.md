# Phase 31.1 Plan 09: The acknowledged and recorded allergen sets on every order contract Summary

**Every order contract now carries two separate allergen facts. The confirmation, its replay, the tracking response, the order history, and the vendor list and detail views each state what the customer acknowledged at checkout (the V69 order columns) and, on single-order views, what the kitchen recorded (the V63 line snapshot). Advisory flags are kept apart from both sets, and the channel shows whether the shop entered the order. NULL ("not recorded") never collapses into 0 or [] on any field. The history list reads order columns only, and a Hibernate fetch-count guard proves it loads no order lines.**

## Accomplishments

**Confirmation and replay (D-08).** `GuestOrderConfirmation` now carries four fields:
- `acknowledgedAllergenMask`
- `acknowledgedAllergens` (names, in bit order)
- `recordedAllergens` (the snapshot union)
- `recordedAllergenFlags` (advisory)

Both `placeGuestOrder` and `replayConfirmation` build them from the order. A replay therefore shows the same four values the first response showed. The test asserts JSON-node equality.

**Tracking (D-07/D-08).** `trackOrder` sets the same four fields plus `placedVia`. A shop-entered order tracks as `placedVia: "VENDOR"` with both acknowledged fields set to JSON `null`, and its recorded set is still shown. Two more cases stay distinct:
- A pre-V69 row tracks with JSON `null`, not `0` and not `[]`.
- An acknowledged all-zero basket gives `0` and `[]`.

**History without an N+1 (T-31.1-31).** `getCustomerOrders` sets the acknowledged mask, the names and `placedVia` from columns only. `recordedAllergens` stays `null` there, and the `@Schema` documents it as tracking-only. The guard reads Hibernate's `CollectionStatistics("uk.jtoye.core.order.Order.items").getFetchCount()` around the service call and requires 0. In the same test, `trackOrder` must read exactly 1, so the zero is shown to be a measurement and not a blind instrument.

**Vendor views.**
- `OrderDto` gains `allergenAckMask`, `allergenAckAt` and `placedVia`, all NON_NULL.
- `OrderDetailDto` gains the same three plus `acknowledgedAllergenNames`, filled in the existing `fillAllergens` hook. The existing `allergenNames`/`allergenFlags` are unchanged, and flags are never merged into either set.
- The kitchen board inherits the new fields through `toDetailDto`.

**MCP, no code change.** `mcp-server/src/tools/read-orders.ts` `buildPath` (l.46-48) sends an `orderId` call to `/api/v1/orders/{id}/detail`, and l.76 forwards `JSON.stringify(res.body)` unchanged. The `orderId` detail call therefore carries the four detail fields. The list call carries the three OrderDto fields when they are recorded.
