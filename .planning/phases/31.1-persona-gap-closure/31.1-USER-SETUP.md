## Why it is required

core-java refuses to start without a 64-hex-character key (31.1-07, D-19), and `k8s/base/core-java-deployment.yaml` references the Secret with no optional flag. A staging or production rollout of 31.1 without `dsar-credentials` holds every core-java pod in `CreateContainerConfigError`, naming the Secret. Create the Secret BEFORE the rollout. Commands: `k8s/QUICK_START.md` Step 1, `k8s/DEPLOYMENT.md`, and `docs/runbooks/sealed-secrets.md` (the sealed manifest goes in the overlay's `resources:` list).

Never reuse a key across environments, and never commit one. Rotating a key makes the stored address of every in-flight data-subject request unreadable, so let the request queue drain first.

| [ ] | `keycloak.admin.customer-realm` matches the environment's customer realm | base sets `jtoye-customers` | The customer realm is not configured in any k8s environment yet (open defect #299). Patch this key per overlay once that realm exists. |

**Why it is required.** A verified DSAR erasure is reported complete only after the subject's customer-realm sign-in account is deleted, or proven absent. With the admin seam off, the account step returns NOT_CONFIGURED. The personal data is still erased, but the request stays open and is retried. After `DSAR_MAX_PROCESS_ATTEMPTS` sweeps (default 5) it is parked FAILED, with `event=dsar_account_deletion_exhausted` logged at ERROR, and the subject receives no completion email.

**Side effect to accept before enabling.** The same switch arms tenant-offboard deprovisioning: offboarding a tenant then disables and logs out its vendor users in `keycloak.admin.realms`.

**Verification after enabling.** A verified erasure for a test address ends `COMPLETED` with `account_deletion_status` `DELETED` or `NONE_FOUND`:

```sql
SELECT status, account_deletion_status FROM dsar_request ORDER BY received_at DESC LIMIT 1;
```
