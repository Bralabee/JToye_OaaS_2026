# Phase 31.1 Plan 17: Single-use Article 15 export download Summary

**The emailed Article 15 link now works: `/data-request/download` takes the token from the URL fragment, strips it from the address bar, and spends it only on "Show my data" via `POST /api/v1/public/gdpr/dsar/export`. That endpoint hands over the decrypted document once, using one locked UPDATE. Every refusal returns the same 404, and an hourly purge destroys any export nobody collected.**

## Accomplishments

- **The consume (D-01 single use).** `DsarExportDownloadService.consume` runs one statement. A `FOR UPDATE` subquery picks the row only while it is unconsumed, unpurged and unexpired. The UPDATE stamps `consumed_at` and NULLs the payload, which V75's CHECK requires to happen together. It returns the ciphertext read under the lock, and the decrypt runs in the same transaction.
- **One refusal.** Blank, unknown, expired, purged and used tokens all throw `DsarExportUnavailableException`. The handler turns that into one constant 404 problem body: title "Data export unavailable", code `DSAR_EXPORT_UNAVAILABLE`, `no-store`. The IT compares the three bodies byte for byte.
- **No way to spend the token by accident.** There is no GET mapping. The page sends nothing until the press, and a double click still sends one POST. The token lives in a ref and never in storage, so this plan adds no client-storage key.
- **The page.** It is a PublicShell server component with noindex metadata and the title "Your data — J'Toye". It shows a summary, the J'Toye account, and one section per vendor: who runs the shop, your details, orders (pennies shown as £, timestamps in en-GB Europe/London), reviews, message preferences and staff directory. An "About this copy" section follows. Every field in the document is shown through a generic record view, all as text. "Save as file" writes `jtoye-my-data-<date>.json` from the exact response bytes.
- **The purge.** `DsarExportPurgeJob` runs hourly. The interval has an inline default, so a missing key never switches it off. It NULLs the payload and stamps `purged_at` on unconsumed exports whose `expires_at` has passed, and logs only a count.
- **Declared everywhere it must be:** retention row R-15 plus a claims rule, an `ssr-routes.conf` STATIC line, a link-graph allowlist entry, OpenAPI snapshot additions (the operation plus `ExportRequest`, with no deletions), and the `SystemPrincipalGuardTest` scan list.

## Decisions Made

See `key-decisions` in the frontmatter. The page also handles one case beyond the plan. Any failure other than the typed 404 (a 5xx or a network error) keeps the token in memory and offers "try again". The server rolls the consume back on failure, so the link was not spent, and showing "unavailable" would have wrongly sent the subject to request a new copy.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The planned consume SQL would have returned NULL**
- **Found during:** Task 1 GREEN
- **Issue:** `UPDATE ... SET payload_ciphertext = NULL ... RETURNING payload_ciphertext` returns the post-update value, which is NULL, on PostgreSQL 15.
- **Fix:** `UPDATE ... FROM (SELECT ... FOR UPDATE) prior WHERE e.id = prior.id RETURNING prior.dsar_request_id, prior.payload_ciphertext`. The concurrency arm and T2-C2 show the lock is required.
- **Committed in:** `bb2a608a`

**2. [Rule 1 - Unfalsifiable assertion] Cache-Control assertion strengthened** (T1-A1 above). Committed in `35623fdb`.

**3. [Rule 3 - Blocking] The retention page had to publish R-15**
- **Issue:** `retention-table.a11y.test.tsx` asserts the page publishes every manifest row, field by field. The plan's manifest row would have failed it, and the plan had no rule for the new integer in `claims.manifest`.
- **Fix:** I added an R-15 row and the `PERIOD_PREPARED_DATA_COPY` constant to `frontend/app/legal/retention/page.tsx`, and a claims rule (FIVE becomes SIX in both headers). The plan's claim key `jtoye.gdpr.dsar.export-link-ttl-hours` is not a valid flat key, so I used `dsar_access_export_hours`.
- **Committed in:** `593874ce`

**4. [Rule 2 - Missing critical] SystemPrincipalGuardTest did not scan the new request path**
- **Issue:** the "stays green" truth was vacuous, because the scan list did not name the new files.
- **Fix:** I added `DsarExportController.java` and `DsarExportDownloadService.java`. T2-S proves the scan fires.
- **Committed in:** `593874ce`

**5. [Rule 3 - Blocking] Link-graph orphan guard**
