### Locked Decisions

#### Carried forward from Phase 31 (not re-asked; see `31-CONTEXT.md`)
- Phase 31 **D-01..D-03** stand:

#### DSAR fulfilment (#777 #778 #838 #839 #871)
- **D-01:** **ACCESS is delivered as an emailed, time-limited, single-use download link.**
  - The fan-out worker assembles the subject's data across every tenant, then emails a link to the verified address.
  - The link token is stored only as a hash with an expiry, the same rule as the verification token (V62).
  - PII is never sent as an email attachment.
  - The request reaches a completed state only after the export is produced and the email is sent.
  - The researcher picks the export format and link lifetime.
  - **Reversibility:** costly. The download endpoint and the token table become a contract that emails already sent point at.
- **D-02:** **ERASURE for a subject with no `customers` row anonymises in every tenant that holds the email hash. It covers:**
  - order PII: customer name, email, phone, delivery address and notes;
  - review author text.

  Order rows, amounts and the VAT ledger are KEPT; tax records have their own retention. This is the V42/V67 shape: tenant-scoped predicates, and object-storage deletes only after commit (#764/#771).
  - The fix is in `GdprService.eraseSubjectByDigest`, which today iterates `customers` rows only (`GdprService.java` ~449-458).
  - The worker's `tenantsErased` count must reflect real erasures.
  - **Reversibility:** one-way. An anonymising erasure cannot be undone; that is its purpose.
- **D-03:** **Erasure DELETES the customer's sign-in account** (the customer-realm Keycloak user), so the person can no longer sign in and see their orders.
  - Run it the way #102/V49 deprovisions an IdP user: after commit, best-effort, logged. A Keycloak outage must not roll back the data erasure.
  - The request is not reported complete until the account deletion is confirmed, or is recorded as outstanding and retried.
  - **Reversibility:** one-way. A deleted IdP user cannot be restored.
- **D-04:** **A minimal signed-in customer account page** with "Download my data" and "Delete my account".
  - Both lodge through the EXISTING DSAR intake (`DsarIntakeService`) with the email pre-filled, and are still email-verified, so there is one path, not two.
  - **#839:** the verification link resolves to a friendly web-app confirmation page on every runtime, including compose. It must never show raw JSON or point at an unreachable host.
  - **#871:** NO marketing-consent machinery is built, because the platform sends no marketing.
    - The privacy notice states plainly that it only emails about orders and requests.
    - `/unsubscribe` points to a real platform route, not "contact the vendor".

#### Allergen acknowledgement contract (#784 #785 #787)
- **D-05:** **A stale acknowledgement is REFUSED, not recorded.**
  - The storefront submit carries the allergen set the panel showed.
  - If the set the server computes for the basket at submit differs, the server returns a typed **409** (RFC 7807, stable problem type) carrying the current set.
  - Checkout re-renders the panel, and the customer must tick again.
  - The platform never records an acknowledgement of a set the customer was not shown.
  - The rule is enforced on the SERVER. The client-only gate is the #784 defect.
  - **Reversibility:** costly. This is a new error contract on the guest-order endpoint, and clients must handle it.
- **D-06:** **The acknowledgement record on the order = the acknowledged 14-bit mask plus an acknowledged-at timestamp.**
  - Same bit layout as V63 `order_items.allergen_mask` / `AllergenCatalog`, so "acknowledged A vs snapshot B" is directly comparable.
  - Nullable with NO backfill: NULL means "not recorded", exactly V63's and V66's rule.
  - Do not add a DEFAULT in a later migration.
  - **Reversibility:** one-way. It is a Flyway migration on `orders` plus the `orders_aud` mirror in the same migration (Order is `@Audited`).
- **D-07:** **Vendor-entered orders do not require an acknowledgement.** This covers the dashboard, the API, and MCP `create_order`.
  - They persist with the acknowledgement NULL ("not recorded").
  - Surfaces show that the order was taken by the vendor.
  - Storefront orders MUST carry an acknowledgement, enforced on the server.
  - No breaking change to the MCP `create_order` contract.
- **D-08:** **The recorded set is shown to the customer** on three surfaces:
  - the order confirmation page;
  - the confirmation email (the durable record);
  - the tracking / My Orders page.

  Reconciliation flags appear as separate advisory text, never merged into the declared set (Phase 31 D-03).
- **D-09:** **#787: a product save whose ingredient text names an emphasised allergen that is not declared SUCCEEDS but returns a typed warning naming it.** The vendor form asks the vendor to tick it or confirm.
  - Until declaration and text agree, every storefront surface shows wording like "Ingredients name: MILK – check with the shop", never "No allergens".
  - Reuse `OrderAllergenAggregator`'s emphasis parser; do not write a second one.
  - The flag is never merged into the declaration.

#### Seller and platform identity (#789 #794)
- **D-10:** **The statutory trader details** (CCR 2013 Sch 2, E-Commerce Regs 2002 reg 6) are:
  - the legal name (the company, or a sole trader's own name);
  - a geographic address;
  - at least one of phone or email;
  - the company number when it is a company (already captured by onboarding);
  - the VAT number when VAT-registered.

  Nothing beyond the statutory minimum. Food-business registration and FHRS stay with Phase 33's #788.
- **D-11:** **Placement:**
  - The legal entity (legal name, company number, VAT number, trading or registered address) lives at tenant/onboarding level.
  - Contact details (phone, email, premises address) live per shop, in the existing and currently empty `Shop.phone` / `Shop.email`.
  - A multi-site owner enters the entity once.
  - **Reversibility:** costly. It is a schema migration, and every surface reads from these two levels.
- **D-12:** **A new trader-identity onboarding gate.** The onboarding state machine is the sole writer of `Shop.published` (Phase 18), so no shop goes live without the D-10 details.
  - There are no real tenants yet: demo and seed shops are BACKFILLED with details, not grandfathered.
  - Watch the RLS migration-backfill trap: a bare UPDATE on a FORCE-RLS table matches 0 rows, so loop over tenants.
- **D-13:** **Customer emails and the durable confirmation present the SHOP as the seller:**
  - From name "Shop name via J'Toye", and Reply-To set to the shop email when one exists;
  - the body names the seller's legal identity, address and contact;
  - it says J'Toye is the platform, not the seller;
  - it carries a cancellation statement: freshly prepared food is exempt from the 14-day cancellation right under CCR reg 28.

  The same seller block appears on the shop page and at checkout, before purchase.
- **D-14:** **#794: the platform's registered office is taken from the public Companies House record for company 16471464.**
  - It is injected through the existing build config, not hard-coded, and set in every runtime.
  - The owner confirms the value at an execution checkpoint before it ships.

#### Allergy notes and labels (#812 #817 #860 #861)
- **D-15:** **#812: a dedicated "allergy or dietary note" field at checkout, separate from delivery notes.**

- **D-17:** **#861: label download asks for the production date** (default today), and use-by is computed from it with the product's shelf life.

## Summary

Phase 31 shipped the shells of four legal-floor mechanisms; persona testing showed each one stops one step short of the customer. Every gap is reproducible from source this session. The DSAR worker erases through `customers` rows only, and on the dev runtime **all 129 orders have `customer_id IS NULL`**, so a storefront subject's erasure matches nothing. ACCESS is an explicit stub that logs a count. The allergen acknowledgement is a client-only checkbox. Nothing reconciles ingredients against the declared mask at save time. All 5 shops have null phone and email, and no legal-entity fields exist. The platform registered office ARG is wired into the Dockerfile but no CI or `k8s-local-up.sh` build passes it. [VERIFIED: GdprService.java:449-458, DsarFanoutWorker.java:153-159, GuestOrderRequest.java, live dev DB query `2|5|3|5|2|7|129|129|t`, ci-cd.yaml:1518-1523]

The phase is mostly **additive wiring onto machinery that already exists**: the V62 DSAR queue, the V42/V67 erasure routine, the #102 Keycloak admin seam, the V63 snapshot and `OrderAllergenAggregator`, the onboarding gate registry, the RFC 7807 handler and the V50 idempotency store. The planner's real work is in seven places where a naive implementation fails silently:

1. **The worker never holds the subject's address.** V62 says a readable-address column "must never" exist, but D-01 has the worker email it. (Open Question 1. Owner ruling needed before the ACCESS plan.)
2. **`erasure_records.subject_customer_id` is `NOT NULL`.** A guest-subject erasure cannot write its evidence row without a migration.
3. **#787's own repro (`butter (MILK)`) has no `**` markup.** The emphasis parser D-09 says to reuse would return zero flags.
4. **A new onboarding gate needs the V43 inline CHECK rewritten.** The constraint is `vendor_onboarding_gate_gate_type_check`, read from the live DB. In-flight onboardings also have no row for the new gate, so the go-live guard would pass them.
5. **D-05 makes every existing guest-order caller fail.** That covers 9 Java test classes and `scripts/seed-order-metric.sh`.
6. **Phase 38 is rewriting `KeycloakAdminClient`, `GlobalExceptionHandler`, `DsarIntakeService` and the OpenAPI snapshot.** It has also captured Jackson-2 golden fixtures for `GuestOrderRequest`, `OrderDto` and `ProductDto`, all of which this phase changes.
7. **The E-Commerce Regulations require an email address.** D-10's "phone OR email" under-states reg 6(1)(c).

**Primary recommendation:** Lead with the six P0s as backend RED→GREEN plans (TDD mode is on), each owning exactly one Flyway version: V68 to V73, assigned up front. Put an owner checkpoint on the DSAR address-recovery design before the ACCESS plan. Write all new code Jackson-agnostic. Finish with a single coordinated runtime-parity wave that waits for Phase 38-17's use of the shared compose stack.

### Pattern 1: DSAR erasure for guest subjects (D-02, #777)
**What:** extend `eraseSubjectByDigest` so it matches `customers` rows (unchanged path) PLUS the distinct emails on `orders` and `reviews` in the pinned tenant, compares digests in Java, and anonymises through ONE shared routine.
**Why this shape:** the V42 comment (GdprService.java:419-423) warns that "a parallel implementation would diverge from the policies that permit its audit scrub". Extract the order/review/aud/photo core of `eraseCustomerData` into `anonymiseSubjectInTenant(tenantId, Optional<UUID> customerId, Set<String> emailVariants)` and have both entry points call it.
**Key points:**
- Matching: `SELECT DISTINCT customer_email FROM orders WHERE tenant_id = ? AND customer_email IS NOT NULL` ∪ the same over `reviews`, then `DsarSubjectDigest.of(email).equals(digest)` in Java. Several stored spellings ("Grace@x", "grace@x ") may match one digest, and every one must be erased, because `findByCustomerEmail…` is an exact match.
- Use **tenant-predicated** finders (`findByTenantIdAndCustomerEmail`) for orders as well as reviews (#764 lesson). `OrderRepository.findByCustomerEmailOrderByCreatedAtDesc(String)` carries no tenant predicate [VERIFIED: OrderRepository.java:111].
- `ErasureRecord` for a no-customer subject: `subject_customer_id` must become nullable (V68). The subject hash must be `DsarSubjectDigest.of(...)`, the normalised digest. Note that the existing `eraseCustomerData` hashes the RAW email (`sha256Hex(originalEmail)`, GdprService.java:305), which is inconsistent with the DSAR digest. Record that as an observation; do not silently change the meaning of historic rows.
- The scrub must also null the new `allergy_note` column (V72) on both the live row and `orders_aud`. `scrubOrdersAudit`'s SQL lists its columns explicitly [VERIFIED: OrderRepository.java:135-139].
- `tenantsErased` increments only when an anonymisation actually changed rows (orders + reviews > 0).

### Pattern 2: Server-enforced acknowledgement (D-05/D-06, #784/#785)
**What:** `GuestOrderRequest.acknowledgedAllergenMask` (Integer, 0..16383, required at the service for storefront orders). In `placeGuestOrder`, union `product.getAllergenMask()` over the SAME product entities the loop already loads (PublicStorefrontService.java:913-965). If it differs, throw `AllergenAcknowledgementStaleException`, mapped to 409 `https://jtoye.uk/errors/allergen-acknowledgement-stale` with properties `code`, `currentAllergenMask`, `currentAllergens` (names) and `lines` (per-item attribution). Then persist the mask, the timestamp and `placed_via='STOREFRONT'`.
**Why:** this is one read in one transaction, so the acknowledged mask equals the V63 snapshot union **by construction**, and a test can assert that equality. Throwing inside `@Transactional createGuestOrder` rolls the idempotency reservation back. The client's intent signature must include the mask, so a re-acknowledged resubmit gets a new key [VERIFIED: checkout/page.tsx:309-333 builds the intent; lib/checkout-idempotency.ts].
**Missing mask:** a typed 400/422 `allergen-acknowledgement-required` (distinct type) keeps the "refuse" semantics without overloading the stale 409.
**Problem-type convention:** `https://jtoye.uk/errors/<slug>` plus a `code` property [VERIFIED: GlobalExceptionHandler.java:520 `"https://jtoye.uk/errors/idempotency-conflict"`, :572 `problem.setProperty("code", "SHOP_PUBLISH_NOT_ACCEPTED")`]. The existing 409 `idempotency-conflict` must stay distinguishable. That is why a new type slug is needed, not a reused one.

### Anti-Patterns to Avoid
- **Looking anything up on a DSAR request thread.** The intake, verify and download endpoints stay opaque and tenant-blind (`SystemPrincipalGuardTest` scans for this).
- **Re-implementing the allergen parser in TypeScript** for menu cards. Expose server-computed flags instead.
- **Storing allergen masks in the localStorage cart item.** That is a stale copy, the #785 defect in a new place. Fetch the live product index (the `indexProductsById` precedent).
- **Reading the order allergen aggregate on `OrderDto` / list endpoints.** That is a measured N+1 (V63 note). Use order-level columns (ack mask, allergy note) for lists and the snapshot aggregate for single-order detail and tracking.
- **One transaction spanning tenants** in the worker (measured StaleStateException; DsarFanoutWorker.java:49-57).
- **`@Transactional` on a private worker method.** It is silently non-transactional.

## Common Pitfalls

### Pitfall 1: The worker cannot email anyone — it never holds the address
**What goes wrong:** D-01 (email the export link) and #777's expected completion email both need the subject's address. `dsar_request` holds only `subject_email_sha256`, and V62 states "There is no readable-address column here, and there must never be one" [VERIFIED: V62__dsar_request.sql, privacy-property section].
**How to avoid:** owner ruling (Open Question 1) before the ACCESS plan. Until then, plan the erasure path (it does not need the address, except for the KC lookup, which can use matched plaintext rows) and keep ACCESS behind the checkpoint.
**Warning sign:** a plan task that says "email the verified address" with no field to read it from.

### Pitfall 2: `erasure_records.subject_customer_id` is NOT NULL
[VERIFIED: V42__gdpr_erasure_completeness.sql:27 `subject_customer_id  UUID        NOT NULL,`] A guest-subject erasure will throw on insert, roll back the whole tenant's erasure, and the worker will release it for retry forever until FAILED. Ship V68 before the code.

### Pitfall 3: Superuser tests hide RLS failures
`GdprErasureIntegrationTest` runs as the Testcontainers superuser (the #764 history). The #777 acceptance requires a NOSUPERUSER arm. Use the `ALTER ROLE … NOSUPERUSER` recipe in `DsarFanoutIntegrationTest` / `GdprErasureReviewRlsIntegrationTest`, plus a precondition proving the rows are visible ("RLS blinds the verification query").

### Pitfall 4: Exact-match email finders miss case variants
The digest normalises (trim + `toLowerCase(Locale.ROOT)`); the SQL finders do not. Erase per stored spelling that matches the digest.

### Pitfall 5: D-05 breaks every existing guest-order caller
Callers today: 9 Java test classes (`GuestCheckoutIdempotencyIntegrationTest`, `GuestCheckoutOnlinePaymentIntegrationTest`, `GuestCheckoutStockConvergenceIntegrationTest`, `MoneyPathExecutionIntegrationTest`, `PublicStorefrontServiceTest`, `OrderAllergenSnapshotIntegrationTest`, `StockDecrementLocationTest`, `CrossTenantSpoofIntegrationTest`, `RateLimitInterceptorTest`) and `scripts/seed-order-metric.sh` [VERIFIED: rg -uu over core-java/src/test, scripts]. Without updates they go red, and the scope-gate memory says to run the FULL suite.

### Pitfall 6: #787's repro has no `**` markup
`collectFlags` considers only `**…**` spans [VERIFIED: OrderAllergenAggregator.java javadoc "Only EMPHASISED runs are considered"; IngredientMarkupParser delimiter `**`]. The persona typed `rice, butter (MILK), pepper`. A literal reuse yields zero flags and the acceptance test stays red after the "fix". On dev data, 11 of 36 products use `**` and 3 contain capitalised words [VERIFIED: live query `11|3|36`]. The vendor form gives no emphasis guidance [VERIFIED: products/page.tsx:684-691 placeholder only]. Treat caps as emphasis (Pattern 3) and add helper text to the form.

### Pitfall 7: The new gate passes in-flight onboardings vacuously
`approveGuard` checks only rows that exist. An onboarding submitted before the deploy has no `TRADER_IDENTITY` row. Use the explicit PASSED requirement in `goLiveGuard` plus materialise-on-refresh (Pattern 4).

### Pitfall 8: `@Async` email methods lose the tenant
Load everything in the listener (Pattern 5). A lookup inside the async method reads zero rows under FORCE RLS and sends a seller block with nothing in it.

### Pitfall 9: The export table is a new non-RLS PII store
`dsar_access_export` must be exempted in `RlsContractTest.EXEMPT_TABLES` by addition with a written reason (the V62 precedent). Keep it short-lived: consume on download (payload set NULL), purge at expiry (retention row), token hash only, optionally encrypted payload.

### Pitfall 10: Article 9 — the allergy note is health data
A dedicated "allergy note" field solicits special-category data ("My child is allergic to peanuts"). The project's recorded position is that the vendor is the controller for such data, and that the platform must not process it for its own purposes [VERIFIED: docs/legal/article-9-allergen-basis.md, Finding 1]. The **acknowledged mask is NOT health data**: it is the basket's product set, consistent with the Extension's "this is product data, not health data". Make the note explicitly optional. Label it with a short notice that it goes to the named shop to prepare this order. Exclude it from every derivation and analytics. Include it in erasure scrubs and in the ACCESS export. Record it in the Article 9 doc as an extension. See Open Question 6.

### Pitfall 11: "No allergens" also appears on the VENDOR products list
[VERIFIED: frontend/app/dashboard/products/page.tsx:539 `No allergens`] The persona saw the wording there. Fix it with the same flag field, not only the storefront.

### Pitfall 12: The idempotency fingerprint shifts with new request fields

## Open Questions

1. **How does the worker reach the subject's address? (BLOCKS the ACCESS plan; touches D-01, D-03 and the #777 completion email.)**
   - Known: `dsar_request` stores only the digest, by an explicit V62 rule. The worker sees plaintext only in matched tenant rows. A subject with an account but no orders exists only in Keycloak. A subject with no data anywhere cannot be told so.
   - **Option A (recommended):** at intake, store the address AES-256-GCM-encrypted (`subject_email_ciphertext`, key in a secret) and NULL it when the request reaches COMPLETED / FAILED / EXPIRED. This satisfies D-01 literally, gives Art. 15 a "we hold nothing" reply, and gives the KC lookup and the completion email an address. It amends V62's "must never" rule, which needs an owner ruling and a V62-style written justification in the migration.
   - **Option B:** derive the address from matched rows (orders/reviews/customers, plus a digest scan of KC customer-realm users). No new stored address, but no reply is possible when nothing matches, which arguably fails Art. 15 and D-01's "completed only after … the email is sent".
   - **Option C:** the verification link doubles as the download link (verify first, then return to the same link). This honours V62 fully but contradicts D-01's "emails a link"; it needs D-01 amended.
   - Recommendation: a `checkpoint:decision` before the ACCESS plan; plan the erasure path to work under all three.
2. **Is an email address mandatory in the seller block?** Reg 6(1)(c) says yes; D-10 says phone OR email. Recommend email mandatory.
3. **Backfill route for D-12.** Seeder + e2e fixtures (recommended) versus Flyway with invented values. Confirm that staging/production databases hold no real tenant whose published shop would then show an empty seller block (the dev DB has 2 tenants, both demo).
4. **Compose: should `KC_ADMIN_ENABLED` default to `true`?** Without it D-03 is inert on the canonical runtime, and #777's "can no longer sign in" cannot be shown live. Enabling it also arms the tenant-offboard sweep in dev.
5. **Merge order with Phase 38.** 38 is at plan 2 of 19. If 38 merges first (likely), 31.1 rebases onto Boot 4 and must port its new Jackson uses and extend 38's response goldens. Ruling needed so the plan carries the right closing tasks.
6. **Article 9 for the allergy note (D-15).** Confirm that the free-text note is acceptable under the vendor-as-controller position with an inline notice, and record it in `docs/legal/article-9-allergen-basis.md`.
7. **Does the acknowledgement cover advisory flags too?** D-05/D-06 cover the declared mask. A change to a product's ingredients text that adds a flag but not a declared bit would not trigger a 409. Recommend declared-only (as written), with flags shown but not acknowledged.
