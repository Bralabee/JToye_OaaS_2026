# Phase 31.1 Plan 11: Erasure deletes the customer's sign-in account Summary

**A verified DSAR erasure now deletes the subject's `jtoye-customers` Keycloak account after every tenant's erasure has committed. The request is COMPLETED only once the deletion is confirmed (DELETED) or no account exists (NONE_FOUND). The subject then receives a plain-text completion email. An outage costs a retry, never the erasure. The compose stack turns the admin seam on by default (D-22).**

## Accomplishments

- **V72** adds `dsar_request.account_deletion_status` and `dsar_request.account_deletion_attempts`.
  - `account_deletion_status` is `VARCHAR(16)`, nullable, with no backfill. `ck_dsar_request_account_deletion_status` limits it to DELETED, NONE_FOUND, OUTSTANDING or NOT_CONFIGURED.
  - `account_deletion_attempts` is `INT NOT NULL DEFAULT 0`.
  - The migration has a V62-style header. It has no `${` anywhere, no RLS change and no `_aud` mirror, because `dsar_request` is not tenant-scoped.
- **`KeycloakAdminClient`** gains two methods, re-proved on the Boot 4 tree (D-21).
  - `findUsersByEmail(realm, email, token)` sends a GET with `exact=true`. The address is a URI variable, so `@` becomes `%40` and `+` becomes `%2B`; both are measured.
  - `deleteUser(realm, id, token)` sends a DELETE. It returns true on 2xx and false on 404, and throws `KeycloakAdminException` naming the realm on any other failure.
  - The parsed shape is the new record `CustomerRealmUser`.
- **`KeycloakAdminProperties.customerRealm`** (default `jtoye-customers`) is separate from the vendor `realms` list.
- **`CustomerAccountDeletionService.deleteCustomerAccount(String)`** returns `AccountDeletionResult` (DELETED, NONE_FOUND, NOT_CONFIGURED or FAILED).
  - It only ever uses the customer realm.
  - It trims and lower-cases the address for the search, then re-checks each returned user's email (`equalsIgnoreCase`) before deleting.
  - It never throws. It logs the realm and the exception class, never the address.
- **`DsarFanoutWorker`**:
  - The claim also returns `subject_email_ciphertext`.
  - After a tenant loop with zero failures, the worker decrypts the address and runs the account step.
  - DELETED or NONE_FOUND → `complete()` writes the status and increments attempts in the same UPDATE that NULLs the ciphertext. Then the email is sent.
  - FAILED or NOT_CONFIGURED → the request goes back to VERIFIED, OUTSTANDING or NOT_CONFIGURED is recorded, attempts is incremented and the ciphertext is kept.
  - At `max-process-attempts` the request becomes FAILED, the ciphertext is NULLed and `event=dsar_account_deletion_exhausted` is logged at ERROR.
  - A missing ciphertext, a decrypt error or a thrown exception all count as FAILED, so the sweep survives an interruption.
- **`DsarOutcomeMailer.sendErasureCompleted`** shares the From address and the `notification.email.enabled` switch with the verification mailer, and never throws. It logs `event=dsar_outcome_sent type=ERASURE` only. The copy says:
  - what was erased;
  - that order and tax records were kept with the subject's details removed (UK tax law);
  - whether the sign-in account was deleted or did not exist;
  - where the privacy notice is (`<app origin>/legal/privacy`).
- **Config:**
  - `application.yml` adds `customer-realm: ${KC_CUSTOMER_REALM:jtoye-customers}`.
  - Compose sets `KC_ADMIN_ENABLED` to `${KC_ADMIN_ENABLED:-true}` and adds `KC_CUSTOMER_REALM`.
  - The k8s base configmap gets the key, and the deployment reads the env from it. The goldens each gain 6 lines and lose none.

- the request stays NOT_CONFIGURED and is retried;
