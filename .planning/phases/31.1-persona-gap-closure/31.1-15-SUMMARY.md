# Phase 31.1 Plan 15: The checkout acknowledges what it showed Summary

**The checkout now does four things:**
- It sends the allergen set the panel showed, as `acknowledgedAllergenMask`, signed into the Idempotency-Key intent.
- When the server answers 409 `allergen-acknowledgement-stale`, it re-renders the panel from the server's `currentAllergens` and makes the customer tick again.
- It refuses, with no POST, when no set could be loaded.
- It shows the recorded set on the confirmation, and it has a dedicated 500-character allergy note field sent as `allergyNote`.

## Accomplishments

**The ordering hazard is closed client-side.** Before this plan, `page.tsx` sent no `acknowledgedAllergenMask`. Once 31.1-30 rebuilds the stack with 31.1-03's enforcement, that would have meant a 422 for every customer. The RED run shows it: the POST body's mask was `undefined` (`evidence/31.1-15-red-task1.json`). After GREEN, the body carries `25` for a Gluten/Fish/Peanuts basket.

**#785 recovery (Task 1, the tracer).**
- `readStaleAllergenProblem` recognises the 409 by its problem type, before `describeOrderError`. The idempotency 409 keeps its own path.
- The page then does five things:
  - holds `{currentAllergenMask, currentAllergens}` as the shown set;
  - unticks the box;
  - sets the panel's alert to `ALLERGEN_ACK_STALE_COPY`;
  - focuses the box;
  - re-fetches the catalogue.
- The 31-14 gate refuses again until the customer re-ticks. The changed mask then changes the intent signature, so a new key is minted.
- A lost reply with no response is not a stale acknowledgement. The box stays ticked, and the retry resends the same key and mask.

**T-31.1-53.** If the mask is null at submit, the catalogue is fetched once more.
- Still unresolved: the submit is refused with `ALLERGEN_ACK_UNAVAILABLE_COPY` and no POST is made. The test asserts exactly 2 product GETs.
- Resolved late: the set is shown and the customer is asked to tick again. It is never sent on the strength of a tick given to a NOT RECORDED panel.

**D-08 (Task 2).** `RecordedAllergenSet` renders from the response, never from the basket. The test also covers a response that differs from the client's view.
- Acknowledged set: "You confirmed you had read: …".
- Recorded set: "Recorded on your order: …".
- `null`, `[]` and a list render three different statements.
- Flags render as separate "Check — …" lines.
- It appears on the COD confirmation and on the card payment step. An absent field from an older backend is read as `null`.

**D-15.** The `#allergy-note` textarea sits under order notes.
- It has `maxLength` 500, a polite `N of 500` count, and help text naming the shop, linked by `aria-describedby`.
- It is held only in React state. A break arm proves that writing it to storage turns the test red.

**Copy unchanged.** `ALLERGEN_PANEL_SUBLINE_COPY`, the three panel states and `ALLERGEN_ACK_ERROR_COPY` are untouched. `errorKind` defaults to `"unticked"`, so every earlier caller renders exactly what it did before.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Four existing checkout suites answered every GET with the shop**
- **Found during:** Task 1 GREEN.
- **Issue:** `checkout.test.tsx`, `checkout-idempotency.test.tsx`, `stripe-lazy-load.test.tsx` and `vat-preview.test.tsx` mocked `publicApiClient.get` with the shop payload for every URL, `/products` included. Their catalogue therefore never resolved. Under T-31.1-53 the checkout correctly refuses that state, and the server would 422 it anyway, so 13 tests failed.
- **Fix:** Each harness gains `mockShop(shop)`, which serves a catalogue (p0..p9, mask 0) for `/products` and the shop for everything else. Every `mockedGet.mockResolvedValue({ data: X })` became `mockShop(X)`, 10 sites in total.
- **Assertions:** none changed. The diff is harness lines plus a comment.
- **Committed in:** `48e39dad`.

**2. [Rule 1 - Test correctness] The blank-note arm asserted the JS object, not the wire body**
- **Found during:** Task 2 GREEN.
- **Issue:** The body is `{...orderIntent, idempotencyKey}`, so an `undefined` member stays an own property. axios serialises with `JSON.stringify`, which drops it. That is the same rule the intent signature documents.
- **Fix:** The arm now asserts on `JSON.parse(JSON.stringify(body))`, and asserts the mask is still present.
- **Committed in:** `f369b393`.

**3. [UI-SPEC precedence] Recorded-set border uses amber-600, not the plan's amber-200**
- The 31 UI-SPEC measured amber-200 at 1.25:1 against the 3:1 boundary requirement and replaced it with amber-600.

**4. [Scope, additive] Order-notes placeholder**
- "Any special requests or dietary requirements..." became "Any special requests...". The dietary guidance moved to the dedicated field and was not dropped (Incremental Betterment).

**5. [Robustness] Race spec on more than one worker**
- With `PLAYWRIGHT_WORKERS > 1`, only the desktop project runs. The two projects would otherwise edit and restore the same demo product at the same time. The default is 1 worker, so both projects run sequentially.
