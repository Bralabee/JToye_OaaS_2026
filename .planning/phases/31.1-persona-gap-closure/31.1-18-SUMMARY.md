# Phase 31.1 Plan 18: The customer sees the order's allergen record after the order Summary

**The per-shop order page and /track now render the order's allergen record from the tracking response through the shared RecordedAllergenSet. That covers what the customer confirmed, what the kitchen recorded, the advisory Check lines, a stated reason when the shop placed the order, and whether the shop has read the customer's allergy note (London time). My Orders states the confirmed set on every row and links to the full record, with no extra request per order.**

## Accomplishments

**#785 / D-08, tracking pages (Task 1, the tracer).**
- `/shop/{slug}/orders/{orderNumber}` renders `RecordedAllergenSet` below the status block, from `GET /public/orders/{n}?email=`. The request is still bound to number + email; a test asserts the call.
- `/track` renders the same block from the guest lookup. Its signed-in auto path gets the order from the history list, whose recorded set is null by design. The page tracks that source:
  - the recorded line reads "Recorded on your order: not loaded with your order list.";
  - a "Show what the kitchen recorded" button loads the tracking response, on a tap only;
  - a later list entry never overwrites a full response for the same order.

**D-07 / D-06.** `acknowledgementStatement(acknowledged, placedVia)` maps the two fields to exactly one of four sentences:
- the list the customer confirmed;
- declared none;
- "This order was placed by the shop for you, so no allergen confirmation was recorded.";
- not recorded.

The component and My Orders both quote it.

**#812 / D-15.** When `allergyNoteProvided` is true the block says:
- "Your allergy note was sent to {shop}.";
- then either "The shop has not marked it as read yet." or "Read by the shop at 18:05."

The time is `Intl.DateTimeFormat("en-GB", {timeZone: "Europe/London"})`, plus " on 5 Oct" when that day is not today in London. The block has no prop for the note text, and the response does not carry it (T-31.1-67).

**My Orders (Task 2).** Each row carries a strip with:
- "Allergens you confirmed: Gluten, Milk", or the vendor-placed, not-recorded or declared-none sentence;
- a "Full allergen record" link to `/track?order=…`. Its accessible name is "Full allergen record for order ORD-…".

The link is a sibling of the card link and reuses the card's sessionStorage email handoff (WR-09). Six rendered orders make zero requests.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Correctness] /track's signed-in path would have rendered the list's by-design null as "not recorded"**
- **Found during:** Task 1 design. 31.1-09 documents that the history list's recordedAllergens is always null.
- **Issue:** Rendering that null through the block states "not recorded" about orders that do have a recorded set. Fetching the detail automatically was ruled out, because `track-signed-in.test.tsx` asserts that the auto path makes no by-number lookup, and the plan says existing track suites stay unchanged in assertion.
- **Fix:** `recorded` accepts `undefined` = NOT LOADED, with an explicit on-tap load through number + email. A `trackedByNumber` guard stops a later list entry replacing a full response.
- **Files modified:** `recorded-allergen-set.tsx`, `app/track/page.tsx`.
- **Verification:** two track tests; arms A4 and A5 each red.
- **Committed in:** `79d1bffc`.

**2. [Rule 3 - Blocking] `frontend/lib/customer-orders.ts` was not in the plan's file list**
- **Issue:** My Orders reads `OrderSummary`. Without the new fields on that type, the build would not type-check the row's `order.acknowledgedAllergens`.
- **Fix:** a type-only `extends PublicOrderAllergenRecord`. There is no runtime change.
- **Committed in:** `154c051a`.

**3. [Rule 1 - Test correctness] The N+1 test's text query could not match**
- **Issue:** `getAllByText("Allergens you confirmed: Milk")` cannot match text split across the name `<span>`.
- **Fix:** count rows by `data-testid` and assert each row's text.
- **Committed in:** the GREEN commit `154c051a`, disclosed in its message. The fetch-count assertion itself is unchanged, and B1 shows that it fails.

**4. [Additive copy] "The shop has not marked it as read yet."**
- Beyond the planned sent and read lines. Without it, a sent-but-unread note looks the same as a sent note whose status is unknown.

**5. [Additive] My Orders link target**
- The plan says "the tracking page". The row links to `/track?order=…`, the same target the card already used; `OrderCard` is never given a slug. That target now lands on the full record (by-number lookup via the email handoff), which the race test pins.
