# Phase 31.1 Plan 04: Stripe Lazy Load on Cash Checkout (#793) Summary

**The checkout now imports `loadStripe` from `@stripe/stripe-js/pure` and calls it at most once, only after an order confirmation carries a clientSecret. A cash checkout no longer injects js.stripe.com or picks up `__stripe_mid`/`__stripe_sid`. A jest proof covers all four paths, and a network-level Playwright acceptance spec with a non-vacuity control is ready for 31.1-30's live run.**

## Accomplishments

- `checkout/page.tsx`:
  - The default-entry import (which injected Stripe's script at module load on every checkout) is replaced with the `/pure` entry.
  - The module-scope `stripePromise` is deleted.
  - A ref-memoised `getStripe()` is called in exactly one place: where a confirmation with a clientSecret moves the page to the payment step.
  - Render reads a state copy, because changing a ref does not re-render.
- `handleCreateOrder`'s idempotency logic is untouched, and the five existing checkout suites keep their assertions. Their only change is the mocked module name.
- `stripe-lazy-load.test.tsx` pins four behaviours:
  - the default entry is never imported;
  - a cash order calls `loadStripe` 0 times;
  - a card order calls it exactly once, and Elements gets that promise. The card form alone, a re-render, and a back-and-resubmit add no further calls;
  - with no publishable key, it is never called.
- `cash-checkout-no-stripe.spec.ts` walks a real cash COLLECTION order with no route stubs:
  - It records every request at context level, from the first navigation onward.
  - It asserts zero Stripe requests (any `stripe.com`/`stripe.network` host) and zero Stripe cookies.
  - It refuses to pass unless the same listener also saw a core-API request and the order POST.

## Decisions Made

- **No `acceptsCardPayments` gate on the load** (RESEARCH Pattern 6 mentioned one). The clientSecret, which only a card-configured server returns, already proves the order is a card payment. Gating on the client-side shop fetch would make card payment depend on a fetch that degrades silently.
- **The type comes from `/pure`.** `/pure` exports no `Stripe` type, so `StripePromise = ReturnType<typeof loadStripe>`. This avoids even a type-only reference to the default entry.
- **Fraud signals unchanged on the card path.** This follows the owner choice; `setLoadParameters` is not called.
- **The e2e host check covers all of `stripe.com` and `stripe.network`.** This is strictly stronger than the three named hosts, which are still listed for traceability.
- **The jest page load is lazy (dynamic import inside each test).** The throwing default-entry factory therefore surfaces as a named assertion failure, which is valid RED, not a suite load crash, which `tdd.md` classes as INVALID_RED.

## Deviations from Plan

None in behaviour. Two choices refine the plan's wording rather than depart from it; both are recorded above:

- The e2e Stripe-host match is widened to any `stripe.com`/`stripe.network` host. The three hosts the plan names are all still matched.
