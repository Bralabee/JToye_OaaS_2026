# Phase 31.1 Plan 08: DSAR key wired into every runtime Summary

**Every runtime that starts core-java now hands it DSAR_ENCRYPTION_KEY from a secret: compose and start-dev from the gitignored .env (verify-env checks 64 hex), the nightly from openssl rand -hex 32, and every k8s overlay from Secret dsar-credentials with no optional flag. The env-contract gate gained a must-supply rule because it scored the key's empty default as safe and could not fail.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] check-env-contract.sh could not report the key as unsupplied**
- **Found during:** Task 2
- **Issue:** The plan's fail-direction criterion was vacuous. With the env entry removed, the unmodified gate exits 0, because application.yml's `${DSAR_ENCRYPTION_KEY:}` empty default scores as "pass by rule (safe non-local default)" (count 90 before injection). A generic rule that makes an empty default a violation would wrongly fail nine optional knobs (ACCESS_MACHINE_CLIENT_IDS, ANTHROPIC_API_KEY, COMPANIES_HOUSE_API_KEY, NOTIFICATION_UNSUBSCRIBE_ONE_CLICK_BASE_URL and the four WHATSAPP_* ones), so the gate cannot tell the cases apart by rule alone.
- **Fix:** A `MUST_SUPPLY_CORE` list, the opposite of an allowlist. Each entry needs a reason. A listed name that no manifest injects is a violation, and no allowlist entry can excuse it. An entry goes STALE when the placeholder stops being read or when its defaults stop being exactly empty, and an entry also on the (b) allowlist is a hygiene error. This is the plan's "classify it by its rule" route: the entry tightens the gate and hides no channel.
- **Files modified:** k8s/scripts/check-env-contract.sh
- **Verification:** three break arms (unsupplied, stale, allowlist overlap) each rc 1; restored tree rc 0
- **Committed in:** 88cccc78

**2. [Rule 2 - Missing critical] Operator docs omitted the new required Secret**
- **Found during:** Task 2
- **Issue:** The secrets template says QUICK_START Step 1 covers every Secret, and the sealed-secrets runbook and DEPLOYMENT.md list the required ones. A deploy that followed them without `dsar-credentials` would leave core-java pods in CreateContainerConfigError.
- **Fix:** Added the creation command (QUICK_START, DEPLOYMENT), the table row and the sealed resource line (runbook), and the required-list entry.
- **Files modified:** k8s/QUICK_START.md, k8s/DEPLOYMENT.md, docs/runbooks/sealed-secrets.md
- **Verification:** check-doc-versions rc 0, check-doc-metrics rc 0, gitleaks clean
- **Committed in:** 88cccc78

**3. [Plan interpretation] k8s-local-secrets.sh requires the .env key rather than generating one**
- **Found during:** Task 2
- **Issue:** The plan allowed "the local .env value (or a freshly generated one)". A generated key would differ from compose's over the SHARED dev database and would change on every re-run, which makes in-flight requests undecryptable.
- **Fix:** DSAR_ENCRYPTION_KEY is in REQUIRED_VALUES and gets a 64-hex refusal. The local `.env` already carries a key (Task 1).
- **Committed in:** 88cccc78

**4. [Plan interpretation] core-java/.env.example entry is commented**
- **Issue:** `scripts/run-app.sh` sources core-java/.env after the root .env, so an active `DSAR_ENCRYPTION_KEY=CHANGE_ME` copied from the example would override a real root key.
- **Fix:** It is documented as inherited, following the file's own DB_MIGRATION_PASSWORD precedent, with the generation command.
- **Committed in:** 7f2daa9c
