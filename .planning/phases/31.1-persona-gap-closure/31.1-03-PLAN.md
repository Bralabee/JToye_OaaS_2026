<objective>
Make the allergen acknowledgement a server-enforced, recorded fact (#784 P0, #785 P0; D-05, D-06, D-07).

Purpose: today the checkbox gates the client only; the POST carries no acknowledgement, a direct
API call bypasses it, and a vendor edit between render and submit records a set the customer never
saw (persona run: acknowledged Gluten/Fish/Peanuts, recorded Gluten/Eggs/Fish/Peanuts/Milk). This plan
adds the acknowledged mask to the guest-order contract, refuses a missing one (422) and a stale one
(409 carrying the current set), and records mask + timestamp + channel on the order.

Output: V69, the two typed exceptions and handlers, the persisted columns, vendor orders marked
VENDOR with NULL ack, every existing caller updated, and the OpenAPI snapshot regenerated.
The checkout UI that sends the mask and re-renders on 409 is 31.1-15.
</objective>

<scope_note>
Why the 22 files stay in one plan (checker scope_sanity, revision 2026-10-05). The caller sweep cannot be
split off without leaving the tree red or weakening D-05.

- **The refusal and the callers are one change.** Task 1 makes POST /public/shops/{slug}/orders refuse a body
  with no acknowledgedAllergenMask (422). That is D-05 (the rule is on the SERVER) and D-07 (storefront orders
  MUST carry an acknowledgement). From that commit, every existing guest-order caller that sends no
  acknowledgement gets 422: the 9 test classes in Task 3 and scripts/seed-order-metric.sh. The integration
  suite goes red, and the seed script fails on the rebuilt runtime in 31.1-30.
- **Moving the callers to a later plan** leaves this plan finishing red. That is not allowed.
- **Moving the callers to an earlier plan** does not work either. They can only send the field once
  GuestOrderRequest.acknowledgedAllergenMask exists, and that field is Task 1's contract. Moving it earlier
  would ship an acknowledgement field the server does not enforce, which is the #784 defect, for one plan.
  It would also add a second writer of docs/api/openapi-snapshot.json at the head of the 8-plan snapshot
  chain, adding one wave to the critical path.
- **Context budget.** Of the 22 files, 12 belong to Task 3's mechanical sweep: one field per request
  builder through the GuestOrderAcknowledgements helper, read only at the builder site, plus the
  regenerated snapshot.
  - The estimate is 230,000 tokens, 23% of the project's configured 1,000,000-token window
    (.planning/config.json context_window). That is under the ~40% target for a TDD plan and the ~50%
    per-plan ceiling.
  - Estimate calibration has no history yet (factor 1, confidence low).
  - The estimate is above the 100,000-token smart-zone schema default. That default is advisory and is not
    set in this project's config.
</scope_note>
