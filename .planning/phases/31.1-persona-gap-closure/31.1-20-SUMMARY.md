# Phase 31.1 Plan 20: DSAR confirm link opens a friendly web page on every runtime Summary

**The "Confirm your data request" email now links to the web app's `/data-request/confirm#token=…` in every runtime. The page clears the fragment, confirms only when the person presses "Confirm my request", and shows distinct confirmed / already-confirmed / invalid copy, never JSON. A config contract test pins each runtime's link to its own web origin.**

## Accomplishments

- **#839 closed in the checkout.** `DsarVerificationMailer` builds `{verify-base-url}#token=<token>`, with a default of `http://localhost:3000/data-request/confirm`. Before this, compose emailed `http://localhost:8080/api/...?token=`, where nothing listens. The k8s environments emailed the API host, which answers a click with raw JSON. So no requester could confirm. The javadoc now explains the fragment. The API's GET companion stays, because links already sent carry `?token=`.
- **`/data-request/confirm`** mirrors 31.1-17's download page. It is a server component (PublicShell, noindex/nofollow, title "Confirm your data request — J'Toye") wrapping a client island. The island reads the fragment once and removes it with `replaceState`. It holds the token in a ref and POSTs `{token}` to `/api/v1/public/gdpr/dsar/verify` only on the press, even if the button is pressed twice. The answer comes from `status`: `verified` gives "Your request is confirmed", `already_verified` gives "This request is already confirmed", and anything else gives "This link can't be used", with "Make a new request" (/shop/account) and "Read our privacy notice". An absent or empty token goes straight to the invalid state with no request. A 5xx keeps the token and offers a retry. `CONFIRM_COPY` is exported.
- **Every runtime points at its own web origin.** Compose now sets `DSAR_VERIFY_BASE_URL` and `DSAR_EXPORT_DOWNLOAD_BASE_URL` on `http://localhost:3000` (shown by `docker compose config`). The k8s `gdpr.dsar.verify-base-url` is set per environment: `https://app.olajay.co.uk/…` in base and production, `https://app-staging.olajay.co.uk/…` in staging, `http://app.jtoye.local/…` in local. The goldens were regenerated, one line each.
- **`DsarLinkConfigContractTest`** reads 8 runtime sources: the application.yml default, the compose env, the k8s base, 3 overlays and 2 goldens. For each it asserts that both bases end in their page path, contain no `/api/`, `?` or `#`, and share the origin of that runtime's unsubscribe/tracking link. It fails closed on a missing file, document or key.
- **The route is declared:** `ssr-routes.conf` has a STATIC line, and `link-graph.test.ts` allowlists the page as emailed-link-only.
- **`e2e/dsar-verify-link.spec.ts`** is #839's written acceptance. It lodges an intake for a unique address and reads that address's email via Mailhog `/api/v2/search`, failing if there is none. It decodes the transfer encoding and takes the link from the email itself. It asserts the link's origin is the frontend's and its path is `/data-request/confirm`, with no query. It asserts no verify request before the press and that the fragment is cleared. It then asserts the confirmed copy, that the page is not JSON, and "already confirmed" on reopen, with screenshots at 390/768/1280.
