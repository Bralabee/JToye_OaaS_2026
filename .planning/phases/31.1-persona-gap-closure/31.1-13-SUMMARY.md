# Phase 31.1 Plan 13: The allergy note the shop must acknowledge Summary

**A customer's allergy request is now its own field, not a line in the delivery notes. V73 stores it on `orders.allergy_note`, separate from `notes`. The vendor's order detail, order list, kitchen board and the MCP detail call all carry it. A new endpoint, `POST /orders/{id}/allergy-note/acknowledgement`, lets STAFF of the order's own shop confirm they read it. The platform records who confirmed it and when. The first confirmation stands and later calls return it unchanged. The customer's tracking page shows that the note arrived and when it was read, but never shows the note's text. An erasure, by either entry point, removes the note from the order and from every audit revision. It keeps who read it and when.**

- It logs the order number only, never the note.
- The endpoint has the same `SCOPE_orders:write` gate as every other order mutation. It declares 200, 400, 401, 403, 404 and 409 in OpenAPI.

## Agent-readiness record (Cross-Cutting Quality Contracts)

- **Idempotency:** the endpoint is idempotent by construction. The first write wins and every repeat returns it, so no Idempotency-Key is needed. This is declared in the `@Operation` description.
- **Typed errors:** `shop-access-denied` 403, `invalid-state-transition` 400, the existing not-found 404, and the optimistic-lock 409.
- **Least privilege:** `SCOPE_orders:write` plus STAFF on the order's own shop.
- **MCP:** no tool, deliberately. The acknowledgement asserts that a person in the kitchen read the note, which an agent cannot truthfully assert. `read_orders`' detail call carries the note and the acknowledgement fields with no MCP code change.

## Decisions Made

See `key-decisions` in the frontmatter. The two with downstream consequences:
- **On OrderDto, a missing field means "no note" or "not acknowledged".** 31.1-22 (KDS and vendor view) must read absence that way on the list. The detail DTO writes null instead.
- **The acknowledgement WHO is the JWT subject (a UUID), not a display name.** 31.1-22 will want to resolve it to a person through `user_directory` for display. The stored value stays the stable principal.

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] The Article 20 admin export now carries the note**
- **Found during:** Task 3.
- **Issue:** The plan's file list covered erasure but not `GdprController.OrderExport`. The 31.1-02 rule says a new PII column must be covered by erasure AND by the Article 20 export. The plan's own Article 9 text says the note "is included in the ACCESS export".
- **Fix:** Added `OrderExport.allergyNote` and filled it in `exportCustomerData`. Updated `GdprControllerTest`'s positional constructor call. The new admin arm asserts the export carries the note.
- **Files modified:** `GdprController.java`, `GdprService.java`, `GdprControllerTest.java`. The OpenAPI snapshot gains `OrderExport/properties/allergyNote`.
- **Committed in:** `3dfe65c5`.

**2. [Rule 1 - Correctness] The acknowledgement time is truncated to microseconds before it is stored**
- **Found during:** Task 2 design.
- **Issue:** `OffsetDateTime.now()` carries nanoseconds and the system offset, while `TIMESTAMPTZ` stores microseconds. The first response would therefore state a value that differs from every later read of "the same" acknowledgement.
- **Fix:** `OffsetDateTime.now(ZoneOffset.UTC).truncatedTo(ChronoUnit.MICROS)`. The test asserts the response instant equals the SQL instant, and that a repeat returns the same instant.
- **Committed in:** `7818ae6d`.

**3. [Plan detail] The V73 CHECK pairs who with when; it does not require a note**
- **Issue:** The plan sketched only the columns. A CHECK of the form "acknowledgement implies note" would reject the state an Article 17 erasure produces (note NULL, who/when kept).
- **Fix:** The CHECK is `(ack_at IS NULL) = (ack_by IS NULL)`. The "a note must exist" rule is the service's typed 400. Break arm T2C proves the service rule is load-bearing.
- **Committed in:** `38c0f3ab`.

**4. [Plan detail] A second erasure arm through the admin path**
- **Issue:** The plan named the DSAR worker path only. The two entry points reach `orders_aud` through two different statements (`scrubOrdersAuditByEmail` for a guest, `scrubOrdersAudit` for a customers row). One arm cannot prove both.
- **Fix:** Two arms. T3A and T3B show each statement independently red.
- **Committed in:** `0be05f38` / `3dfe65c5`.
