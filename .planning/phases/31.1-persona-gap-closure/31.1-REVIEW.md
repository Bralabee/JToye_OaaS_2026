## Summary

Scope was the 277 paths that differ between `4b454bfe` and HEAD. Most attention went to the
production code the brief prioritised. I read all eight migrations V68..V75 in full. I read the
whole DSAR/GDPR path: intake, cipher, fan-out worker, access-export assembly, download, purge,
expiry, outcome mailer and Keycloak account deletion. I traced the allergen acknowledgement through
`PublicStorefrontService.createGuestOrder` to `GlobalExceptionHandler` and the checkout page, and
the trader-identity gate through `VendorOnboardingService`, the state-machine guard and
`GateChainRunner`. I also covered the order-email context, the label service and the
allergy-note acknowledgement. For the frontend I read in full the DSAR confirm and download
clients, the account page, the checkout submit logic, the basket and product allergen helpers,
the kitchen allergy-note block and the storage-key registry. Test files, docs and k8s/CI
manifests were only diffed or spot-checked for wiring (DSAR key secret, DSAR URLs, reserved
slugs). No finding below comes from a test file.

Several things held up under checking:

- **Migrations V68..V75 are sound.** Every new column is nullable with no backfill. Each
  `_aud` mirror is added in the same migration as its column. V71 has ENABLE + FORCE RLS
  through `current_tenant_id()`, and its `_aud` policies match V65.
- **The guest-order acknowledgement is enforced on the server.** A missing mask returns 422, a
  mismatched mask returns 409, and the check is equality against the same `Product` reads the
  V63 snapshot captures.
- **The export download is single-use.** One `UPDATE … FROM (… FOR UPDATE)` spends the token,
  and the decrypt runs in the same transaction.
- **The new code logs no PII,** with one older exception (WR-07).

The two blockers are both availability or liveness defects:

- **CR-01:** a claimed DSAR request is never reclaimed after a crash or an exception.
- **CR-02:** the public shop page now needs two pooled connections per request, which can
  exhaust the pool.

The warnings are mostly gaps in what was meant to be delivered: the erasure scope is narrower
than the access scope, "may contain" conflicts with the new capitals heuristic, and the DSAR UI
gives some customers dead ends or untrue messages.

## Critical Issues

### CR-01: A DSAR request claimed as IN_PROGRESS is never reclaimed — one exception or pod restart strands the batch for good, along with the subject's encrypted address

**File:** `core-java/src/main/java/uk/jtoye/core/gdpr/DsarFanoutWorker.java:138-153, 202-228, 326-335, 523-540, 583-586`; `core-java/src/main/java/uk/jtoye/core/gdpr/DsarRequestExpirySweep.java:44-51`

**Issue:**

1. **The claim commits before any work starts.** `CLAIM_SQL` moves up to 25 rows from
   `VERIFIED` to `IN_PROGRESS` and commits in its own `TransactionTemplate`.
2. **Nothing ever selects `IN_PROGRESS` again.** The claim only reads `status = 'VERIFIED'`.
   `DsarRequestExpirySweep` only touches `PENDING_VERIFICATION`. `rg "IN_PROGRESS"` over
   `core-java/src/main` finds only the claim and the enum. Nothing in the codebase reads
   `claimed_at`.
3. **The loop in `executeLodgedRequests` (202-228) has no per-request try/catch.** These calls
   can throw after the claim has committed:
   - `listTenantIds()` (583-586);
   - the terminal `UPDATE`s in `completeAccess` (326-335), `complete` (523-540) and
     `release*`;
   - any `RuntimeException` from `outcomeMailer.sendAccessExportReady` that is not a
     `MailException`.

   One such exception aborts the loop and leaves every remaining claimed row `IN_PROGRESS`.
4. **A pod termination during a sweep does the same.** That includes a routine rolling deploy.
   This phase made a sweep much longer: per tenant it collects ACCESS data, then it calls
   Keycloak and SMTP for every request.

The consequences:

- The subject's verified Article 15/17 request is never answered.
- `subject_email_ciphertext` stays on the row indefinitely. V70's CHECK only forces NULL in
  terminal states, and `IN_PROGRESS` is not one.
- This breaks the published retention promise (`/legal/retention`, manifest row R-14): "delete
  it when the request is completed, cannot be completed, or expires".

**Fix:** Reclaim stale claims in the claim itself, and isolate each request:

```java
private static final String CLAIM_SQL = """
        UPDATE dsar_request
           SET status = 'IN_PROGRESS', claimed_at = NOW(), process_attempts = process_attempts + 1
         WHERE id IN (
               SELECT id FROM dsar_request
                WHERE completed_at IS NULL
                  AND (status = 'VERIFIED'
                       OR (status = 'IN_PROGRESS' AND claimed_at < NOW() - make_interval(mins => ?)))
                ORDER BY received_at
                FOR UPDATE SKIP LOCKED
                LIMIT ?)
        RETURNING id, request_type, subject_email_sha256, process_attempts, subject_email_ciphertext, received_at
        """;
// and in executeLodgedRequests:
for (Map<String, Object> request : inOrder) {
    try { /* dispatch as today */ }
    catch (RuntimeException e) {
        log.error("event=dsar_request_crashed request={} error={}", request.get("id"), e.getClass().getName());
        // leave it IN_PROGRESS; the stale-claim arm above returns it after the lease
    }
}
```

The lease must be longer than the longest plausible sweep (for example 60 min). The existing
`process_attempts` / `max-process-attempts` exhaustion then bounds the retries.

### CR-02: The public shop page now holds two pooled connections per request — a burst of concurrent requests the size of the pool deadlocks the storefront

**File:** `core-java/src/main/java/uk/jtoye/core/storefront/PublicStorefrontService.java:79, 552-558`; `core-java/src/main/java/uk/jtoye/core/onboarding/TraderIdentityService.java:64-78, 172-179`; `core-java/src/main/resources/application-prod.yml:14-16`

**Issue:**

1. `PublicStorefrontService` is `@Transactional(readOnly = true)` at class level.
   `getShopBySlug` runs `shopRepository.findBySlugAndPublishedTrue` inside that transaction.
   With `open-in-view: false` the session keeps that physical connection until the transaction
   ends.
2. `getShopBySlug` then calls `traderIdentityService.findPublicSeller`. That method is
   `NOT_SUPPORTED`, which suspends the outer transaction but does not release its connection.
   It then runs `publicSellerTx`, which is `PROPAGATION_REQUIRES_NEW`, on a second connection.
3. So every `GET /public/shops/{slug}` needs two connections at the same time. This is the SSR
   fetch behind every storefront page view and crawl.
4. Production's pool is 12 (`DB_POOL_SIZE:12`, `connection-timeout: 30000`) and Tomcat serves
   up to 200 threads. 12 simultaneous shop-page requests can each take their first connection,
   then all wait for a second one that never frees. Each fails with
   `SQLTransientConnectionException` after 30 s, and the cycle repeats under sustained load.

`OrderStateChangeListener.emailContext` (line 219) applies the same pattern to every order
email, inside the listener's transaction.

Before this phase the endpoint used one connection, so the change makes the public storefront
less available under load.

**Fix:** Make sure no connection is held when the seller read starts. The simplest option is to
take `getShopBySlug` out of the class-level transaction, so the shop lookup returns its
connection before the seller transaction opens:

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public PublicShopDto getShopBySlug(String slug) {
    Shop shop = shopRepository.findBySlugAndPublishedTrue(slug)   // own short read; connection released
            .orElseThrow(() -> new ResourceNotFoundException("Shop not found: " + slug));
    PublicShopDto dto = toPublicShopDto(shop);                   // confirm it touches no lazy association
    dto.setSeller(traderIdentityService.findPublicSeller(shop.getTenantId(), shop));
    return dto;
}
```

The alternative is to do the seller read inside the existing transaction with an explicit GUC
set and reset. Whichever you choose, add a test that runs N+1 concurrent requests against a pool
of size N.

### WR-01: A DSAR erasure is narrower than the DSAR access — marketing consent and staff-directory rows the export reports are never erased

**File:** `core-java/src/main/java/uk/jtoye/core/gdpr/DsarAccessExportService.java:270-300`; `core-java/src/main/java/uk/jtoye/core/gdpr/GdprService.java:383-386, 531-552, 598-628`

**Issue:** The Article 15 export matches the subject's digest directly against three sources:

- `notification_suppression.recipient`;
- `marketing_opt_in.recipient`;
- `user_directory.email`.

The Article 17 path (`matchSubjectInTenant` / `eraseSubjectByDigest`) only finds spellings on
`customers`, `orders` and `reviews`. As a result:

- **`marketing_opt_in` is never touched by any erasure.** `MarketingOptInRepository` has no
  delete method, and `GdprService` never references the table. An erased subject's marketing
  opt-in survives, so `ConsentGate` can keep allowing marketing mail to the address. This
  happens after `DsarOutcomeMailer` has told them "We have completed your request to erase the
  personal data held for this email address".
- **`user_directory` is only deleted by exact spellings taken from the other three tables**
  (`deleteByTenantIdAndEmail(tenantId, spelling)`). Two cases miss rows:
  - A subject whose only presence is a staff-directory row matches nothing, so nothing is
    erased.
  - A staff row stored as `grace@x.com` survives when the orders carry `Grace@X.com`, because
    the deletion is an exact match on the order spelling.

  Yet the export lists exactly these rows under `staffDirectory`.

**Fix:** Build `SubjectMatch` from the same sources the export reads. In
`anonymiseSubjectInTenant`, delete the matched `marketing_opt_in` rows and delete
`user_directory` rows by digest match rather than by order spelling. Keep `notification_suppression`
on purpose (it is what honours the unsubscribe) and say so in the completion email.

### WR-02: The new capitals heuristic flags "MAY CONTAIN NUTS" as an undeclared ingredient and tells the vendor to add it to the declaration — against D-16

**File:** `core-java/src/main/java/uk/jtoye/core/order/OrderAllergenAggregator.java:189-205, 216-240`; `core-java/src/main/java/uk/jtoye/core/product/ProductMapper.java:39-49`; `core-java/src/main/java/uk/jtoye/core/storefront/PublicStorefrontService.java:1433-1444`; `frontend/app/dashboard/products/page.tsx` (`tickAllergenAndResave`)

**Issue:**

1. `capitalisedRuns` treats any run of three or more ASCII capitals as emphasis, so
   `"Flour, sugar. MAY CONTAIN NUTS"` yields `NUTS`.
2. `AllergenCatalog.resolveBits("NUTS")` maps it to bit 7.
3. Every caller passes only `declaredMask` to `aggregate`. None passes `may_contain_mask`. So a
   product whose vendor correctly recorded nuts as a cross-contact risk (V74) is still flagged.
4. The flag appears in four places:
   - the vendor's save warnings, whose one-click "tick" action ORs the bit into `allergenMask`,
     which is exactly the merge D-16 forbids;
   - the public `undeclaredIngredientAllergens` ("the ingredients list mentions Nuts, which the
     kitchen has not declared");
   - the V63 `order_items.allergen_flag_mask` snapshot;
   - the order email.

"MAY CONTAIN …" in capitals is the usual UK label wording, so this will fire on correctly
entered products.

**Fix:** Pass the may-contain mask into reconciliation and do not flag a bit already recorded as
may-contain. Also skip capital runs that directly follow `MAY CONTAIN`/`TRACES OF`:

```java
public record ItemAllergens(String productName, int declaredMask, String ingredientsText, int mayContainMask) {}
...
if (!AllergenCatalog.hasAllergen(item.declaredMask(), bit)
        && !AllergenCatalog.hasAllergen(item.mayContainMask(), bit)) alreadyFlagged.add(bit);
```

### WR-03: The menu card says "No allergens declared" for a dish with a "may contain" risk, and never shows the may-contain line

**File:** `frontend/lib/product-allergens.ts:74`; `frontend/app/shop/[slug]/shop-detail-client.tsx:140-157`

The may-contain line only appears in the dish modal (`product-detail-modal.tsx:285`). The basket

### WR-04: The download page tells the subject "Your link has not been used" when it cannot know that

**File:** `frontend/app/data-request/download/download-client.tsx:84-96, 130-134`

**Issue:** Every non-404 failure goes to `failed`, and that state shows "Your link has not been
used — please try again". That includes a network error with no `status`. The server spends the
token and NULLs the payload in a transaction that commits before the response is written
(`DsarExportDownloadService.consume`). A dropped connection or a proxy reset after the commit
therefore produces exactly this state while the export is already destroyed. The retry then gets
404 "already been used", having just been told the opposite.

**Fix:** Only claim the link is unused for a definite server-side refusal (a 5xx that carries a
response). For an error with no response, say "We could not confirm whether your data was shown;
if this link no longer works, request a new copy."

**File:** `frontend/app/data-request/confirm/confirm-client.tsx:189`; `frontend/app/data-request/download/download-client.tsx:169`; `frontend/app/shop/account/page.tsx:22-29`; `core-java/src/main/java/uk/jtoye/core/gdpr/DsarOutcomeMailer.java` (ACCESS body: "you can make a new request"); `core-java/src/main/java/uk/jtoye/core/gdpr/DsarAccessExportService.java:367`

### WR-06: An ACCESS request released for retry still runs after a later ERASURE for the same subject, and answers "no data held"

**File:** `core-java/src/main/java/uk/jtoye/core/gdpr/DsarFanoutWorker.java:208-227, 344-358`

**Issue:** The in-batch sort by `received_at` (208-215) was added because an ACCESS lodged before
an ERASURE was sometimes answered after it, with "no data held". The sort only orders requests
inside one batch. The failing sequence:

1. The ACCESS fails once, for example `lookupCustomerAccounts` returns FAILED or the email send
   fails.
2. `releaseAccess` puts it back to `VERIFIED`.
3. The loop continues and executes the later ERASURE for the same subject.
4. On the next sweep the ACCESS collects nothing and emails `NO_VENDOR_DATA_STATEMENT`.

That is the outcome the sort was meant to prevent, now reached through any transient failure.

**Fix:** When a request is released, skip any later request for the same `subject_email_sha256`
in the same sweep. Or make the claim refuse an ERASURE while an older ACCESS for the same digest
is still open:
`AND NOT EXISTS (SELECT 1 FROM dsar_request a WHERE a.subject_email_sha256 = r.subject_email_sha256 AND a.request_type = 'ACCESS' AND a.completed_at IS NULL AND a.received_at < r.received_at)`.

### WR-07: The per-tenant failure log in the erasure path writes `e.getMessage()`, which can carry subject PII

**File:** `core-java/src/main/java/uk/jtoye/core/gdpr/DsarFanoutWorker.java:386-387`

**Issue:** The line is older than this phase, but the path it guards now runs the new guest

