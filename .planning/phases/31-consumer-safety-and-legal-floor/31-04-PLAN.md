<objective>
Build the substantive new logic of LGL-03: a Java-side allergen catalogue, span-text to allergen-bit
resolution, and the order-level aggregation with a reconciliation flag. Pure logic only — no
persistence, no DTO, no UI.

Purpose: the roadmap's actual complaint is that *"every allergen statement the platform makes resolves
to an integer a vendor hand-types into a CSV column … and is **never reconciled** against the
ingredients text in the adjacent column."* The QA council filed the same defect as `A11Y-02`
(CRITICAL) with runtime proof: with `allergenMask: 0` and `**milk**` in the ingredients text, the
emphasis renders and the allergen panel is **absent** — a sighted user sees a bolded allergen, a
blind user gets nothing. Severity is critical because the failing direction is **under**-declaration,
on the one surface in this product that can physically injure someone.

Three measured gaps make this real work rather than assembly:
  - **There is no Java allergen bit-to-name table at all.** The old `PublicStorefrontService.ALLERGEN_NAMES`
    was deleted on 2026-07-30. The table exists only at `frontend/types/api.ts:490-516`. D-04 puts the
    aggregate on the KDS, which is fed from the backend, so a Java copy is unavoidable.
  - **`AllergenSpan` carries offsets and nothing else** — `record AllergenSpan(int start, int end)`.
    Resolving a span's text to an allergen bit exists in neither language.
  - **No set-union aggregation over order items exists anywhere in the tree.** The only
    `getItems().stream()` in `core-java/src/main/java` is a `mapToLong().sum()`.

Output: two pure classes and three test files. Nothing in this plan writes to a database or changes a
response body; 31-10 does that.
</objective>

<interfaces>
THE 14 BITS — the authoritative table today, `frontend/types/api.ts:490-516`, read this session.
The Java copy must agree on every pair, in this order:

  0 Gluten · 1 Crustaceans · 2 Eggs · 3 Fish · 4 Peanuts · 5 Soybeans · 6 Milk
  7 Nuts · 8 Celery · 9 Mustard · 10 Sesame · 11 Sulphites · 12 Lupin · 13 Molluscs

Alongside them TypeScript exports `hasAllergen(mask, bit)`, `toggleAllergen(mask, bit)` and
`getAllergenNames(mask)`. The Java catalogue needs the `hasAllergen` and `getAllergenNames`
equivalents; `toggleAllergen` is a vendor-form concern and is NOT needed server-side.

THE PARSER TO REUSE, NEVER FORK — `IngredientMarkupParser.parse(String raw)` returns
`ParsedIngredients(String plainText, List<AllergenSpan> spans)`. Its own header states it is
*"the SINGLE SOURCE OF TRUTH for the markup transform"*, used by the save path (which caches spans
into `products.allergen_spans`) AND by `ProductLabelService.buildRenderModel`, which RE-PARSES fresh
at render time so stored offsets can never go stale. Its markup rules are: `**` delimiters, non-nested
left-to-right pairing, `****` strips to nothing, a dangling `**` is kept literal, a lone `*` is
literal, and it NEVER throws on vendor input. A second parser would diverge from a legally operative
PPDS label.

`AllergenSpan` is `record AllergenSpan(int start, int end)` — 17 lines, offsets only. So
`plainText.substring(start, end)` yields the emphasised WORD, and mapping that word to a bit is the
new logic.

DO NOT BREAK `ProductLabelService`. It is the PPDS / Natasha's-Law label pipeline (V41) and consumes
the same data. Its existing tests are the regression arm and must stay green with no edit to their
expectations.

⚠ D-01 IS BINDING AND THIS PLAN MUST NOT VIOLATE IT. `Customer.allergenRestrictions` is an Article 9
special-category field. Nothing in this plan reads it, imports it, or takes it as a parameter. The
aggregation is over the ORDER's own products only. There is no customer-versus-product comparison
anywhere in this phase — D-02 is explicit that the platform never learns the customer's allergies.
If a signature in this plan would accept a customer mask, the design is wrong.

⚠ THE RECONCILIATION IS ADVISORY, NOT AUTHORITATIVE. Its output is a "Check" flag naming a possible
undeclared allergen. It must NEVER silently widen the declared mask, because a text match is a
heuristic and rewriting a vendor's legally operative declaration from a heuristic is a worse defect
than the one being fixed. Declared and flagged are two separate outputs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vendor free-text ingredients -> parser and resolver | Untrusted vendor prose crosses into a safety-relevant computation |
| declared mask -> published allergen statement | An integer a vendor hand-typed becomes a claim shown to a consumer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-04-01 | Tampering | Reconciliation silently widening the declared mask | mitigate | Declared and flagged are separate outputs; a dedicated test asserts the declared set is unchanged in the presence of a flag, and its break arm is run |
| T-31-04-02 | Information disclosure | Article 9 customer allergen profile reaching this code path | mitigate | D-01: no customer type is imported; asserted by grep in both tasks' verifies because a compiler cannot express the constraint |
| T-31-04-03 | Denial of service | Pathological vendor ingredients text | mitigate | Reuse `IngredientMarkupParser`, which is fail-soft, non-nested, left-to-right and never throws; the resolver does bounded word-boundary matching over an explicit finite synonym list, with no regex backtracking |
| T-31-04-04 | Repudiation | A flag that fires on everything and is therefore ignored | mitigate | The synonym list is explicit, conservative and hand-written; a non-allergen negative case is a required behaviour, not an optional one |
| T-31-04-05 | Tampering | The two allergen tables drifting apart | mitigate | Cross-language parity test reading both files from disk, with a positive control asserting 14 pairs were extracted from each before comparing |
| T-31-04-SC | Tampering | package installs | accept | No package added; both classes are plain Java and the parity test is plain Node |
</threat_model>
