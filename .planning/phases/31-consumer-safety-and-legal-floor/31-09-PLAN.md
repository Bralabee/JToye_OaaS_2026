<objective>
Execute lodged data-subject requests across every tenant, in the background, without any human ever
holding cross-tenant read.

Purpose: D-17 is the reconciling design for a real conflict. A single cross-tenant DSAR desk appears
to require the cross-tenant operator identity this project has refused **twice** — most recently and
explicitly in Phase 33's D-2. The resolution is that no human holds that reach; only a scheduled job
does, and `ShopAccessService.java:625-640` already records the rule: *a request thread never enters
`asSystem`; only background entry points do.* 31-05 built the request half. This is the background
half, and it is the half that makes the published single point of contact real rather than a promise.

Two measured facts shape how this is built:

  - **There is no production `asSystem` caller to copy.** `SystemPrincipal.asSystem(` occurs exactly
    once in `core-java/src/main/java`, at `MediaProcessingWorker.java:298`, **inside a javadoc
    comment** — with `TenantContext.set(` appearing across 25 files as the live control. Real
    invocations exist only in 6 test files. This worker is the FIRST production caller, so it is
    built from the class contract, not from an example.
  - **`asSystem` does NOT grant cross-tenant reach**, and misreading it as a tenancy escape is the
    single most dangerous mistake available here. `SystemPrincipal.java:44-50` is explicit: *"The
    marker is an AUTHORISATION declaration, not a tenancy escape … it says nothing whatsoever about
    which tenant's rows it can see, and it cannot be used to reach another tenant's data."* Reach
    comes from iterating tenants and pinning the GUC — which is per-tenant by construction, and that
    IS the control.

Output: one scheduled worker cloned from `WebhookRetentionCleanup`, and a Testcontainers test that
proves the fan-out under real RLS.
</objective>

tenant-loop precedents (explicit GUC pin plus per-tenant error isolation), and
`MediaQuarantineRetentionSweep` already establishes cloning it as the house move. Its shape:

  @Scheduled(fixedDelayString = "${...}")     on the public entry point
  listTenantIds()                              native query, SELECT id FROM tenants
  for each tenant: try { perTenant(...) } catch (Exception e) { log.error(... "continuing") }
  perTenant: TenantContext.set(tenantId)
             try { transactionTemplate.execute(status -> { pinTenantGuc(tenantId); ...work... }) }
             finally { TenantContext.clear(); }
  pinTenantGuc: entityManager.unwrap(Session.class).doWork(conn -> prepared statement
                "SELECT set_config('app.current_tenant_id', ?, true)")
  constructor builds `new TransactionTemplate(transactionManager)` — NOT @Transactional

TWO HAZARDS ITS OWN COMMENTS RECORD, BOTH LOAD-BEARING HERE:

  1. **One transaction per tenant, NEVER one spanning all.** `ScheduledCleanupService.java:44-56`
     records the measured failure: the RLS GUC is transaction-local (`set_config(..., true)`), so
     under a single transaction tenant A's deferred cascade flushed AFTER the GUC had switched to
     tenant B, FORCE RLS filtered those rows to 0, a `StaleStateException` followed, and the whole
     job rolled back having cleaned nothing.
  2. **`TransactionTemplate`, not a `@Transactional` private method.** Spring self-invocation
     bypasses the proxy, so no transaction starts at all and the query runs with a NULL tenant.

THE ERASURE ROUTINE TO REUSE, NOT REWRITE — `GdprService.eraseCustomerData` already anonymises rather
than deletes (`[REDACTED]`, `redacted@erased.invalid`), reaches guest orders, scrubs `*_aud` history
and deletes review photos, and writes the `ErasureRecord` proof row. V42's tenant-scoped UPDATE
policies on `orders_aud`/`customers_aud` exist SOLELY to permit that scrub. Writing a second erasure
routine would diverge from the one those policies were written for.

⚠ `GdprService.eraseCustomerData` IS KEYED BY `customerId`, NOT BY EMAIL. Finding the customer for a
hashed subject is new work. Whatever lookup is added must be tenant-scoped like everything else — the
worker's reach comes from the tenant loop, not from a query that ignores the wall.

⚠ `TenantContext.clear()` IN A `finally`, ALWAYS. These are pooled threads; a stale tenant left on a
returned thread is a cross-tenant read waiting to happen on an unrelated request.

⚠ DO NOT "SIMPLIFY" `asSystem`'s RESTORING `finally`. `SystemPrincipal.java:53-63` states the
lifecycle: the outermost exit `remove()`s rather than setting `false`, and nested declarations restore
the prior value. A stale system marker on a pooled thread is an elevation of privilege.
