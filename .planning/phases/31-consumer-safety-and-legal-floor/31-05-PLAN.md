<objective>
Build the data-subject-request intake: the request-thread half of D-16/D-17. A published commitment
to a single point of contact, backed by nothing that can execute it, is the fail-open shape this
project keeps paying for — so the privacy notice 31-11 publishes must point at something real.

Purpose: the shipped `uk.jtoye.core.gdpr` package implements Articles 17 and 20 already, but its
endpoints are **vendor-admin, single-tenant and keyed by `customerId`**, behind
`@PreAuthorize("hasRole('admin')")`. There is no consumer-facing intake, no email-keyed lookup and no
cross-tenant path. D-16 adds the intake; 31-09 adds the worker.

The boundary D-17 draws is the whole design and it is not negotiable: **intake is a request,
execution is background.** `ShopAccessService.java:625-640` records the rule that a request thread
never enters `asSystem` — only background entry points do. That is how a single cross-tenant DSAR
desk is reconciled with a project that has refused a cross-tenant operator identity twice: no human
ever holds cross-tenant read, only a scheduled job does.

Output: one migration, one entity, one public endpoint, and the two security tests that prove the
boundary holds.
</objective>

THE RLS DECISION, AND WHY IT IS EXPLICIT. `RlsContractTest.everyPublicTableHasRlsAndForce` walks
`pg_class WHERE relkind='r' AND relnamespace='public'::regnamespace` and asserts BOTH
`relrowsecurity` AND `relforcerowsecurity` unless the table name is in `EXEMPT_TABLES`. A second
sweep additionally requires every RLS-enabled table to carry at least one policy, so a half-measure
fails too.

`dsar_request` is **pre-tenant by construction**: an anonymous data subject lodges it from the public
internet before any tenant is known, and its whole purpose is to be actioned across every tenant.
There is no value to put in a `tenant_id` column, and under FORCE RLS with no GUC the row would be
invisible to the very worker that must read it. So it takes the **`postcode_centroid` exemption
shape**: added to `EXEMPT_TABLES` **by addition**, with a written justification that says what the
table holds, why there is no tenant dimension, and — the load-bearing part — **why adding RLS would
be worse than not adding it**. Read the existing `postcode_centroid` entry
(`RlsContractTest.java:120-134`) and follow it literally. The sweep assertion itself is NOT touched.

`ErasureRecord`'s field shape is the model, and one rule carries forward verbatim:
`subject_email_sha256` is `@Column(length = 64)` and holds a **hash**. V42's stated rule is that the
plaintext email is NEVER stored. The DSAR intake is keyed by email, which makes this rule the single
most important thing in the schema: an intake table full of plaintext emails is a new PII store
created by a privacy feature.

IDEMPOTENCY: `uk.jtoye.core.common.idempotency.IdempotencyService.execute(...)` is the generic
reserve-first store already used by `orders.create` and `customers.create`. Its typed exceptions
`IdempotencyConflictException` and `IdempotencyPayloadMismatchException` are rendered as RFC 7807 by
`GlobalExceptionHandler`, and `config/IdempotencyHeaderCustomizer.java:30` advertises the header
centrally in the OpenAPI document. Reuse all of it; the header is declared on the controller method
as `@RequestHeader(value = "Idempotency-Key", required = false) String idempotencyKey`, exactly as
`CustomerController.java:74-86` does.

⚠ `IdempotencyService` is TENANT-SCOPED — `idempotency_keys` is `(tenant_id, endpoint, key)` under
FORCE RLS (V50). A platform-level endpoint has no tenant. Read `IdempotencyService` before wiring:
if it cannot serve a tenant-less caller, do NOT weaken it and do NOT invent a parallel store —
implement idempotency on `dsar_request` itself with a unique constraint over
`(subject_email_sha256, idempotency_key)` and replay the original response on conflict, and record
that decision in the SUMMARY with the measurement that forced it.

THE PUBLIC-ENDPOINT SHAPE: `PublicStorefrontController` is the precedent —
`@RequestMapping({"/public", "/api/v1/public"})` at `:47`, `@PostMapping` with `@Valid @RequestBody`
at `:192`. That is how a mutating endpoint reachable without a JWT is written here.

⚠ THE EXISTING RATE LIMITER IS PER-TENANT. `security/RateLimitInterceptor.java` +
`config/RateLimitConfig.java` bucket by tenant, and a platform-level endpoint has no tenant — so it
would fall into whatever the no-tenant path does today. Read that path before relying on it. This
endpoint needs its **own bucket keyed by client IP** via the existing `security/ClientIpResolver.java`,
because an unauthenticated erasure request is a weapon if it is unlimited.

`GdprController.CustomerExport` carries `Integer allergenRestrictions` (`:72-81`) — the Article 9
field IS in the Article 20 export today, recorded as correct and tested in
`docs/legal/article-9-allergen-basis.md`. D-01 does not change that. **This intake must not widen who
can trigger that export.** The existing `@PreAuthorize("hasRole('admin')")` on `GdprController` is
not weakened, not moved, and not inherited by the new controller.
