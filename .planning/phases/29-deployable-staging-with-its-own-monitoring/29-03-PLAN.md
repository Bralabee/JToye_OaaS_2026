<objective>
Make the two live gates this phase depends on capable of running against a cluster — and prove they
can still fail.

**Blocker B is the sharpest finding in the research.** DPLY-03's literal criterion is
"`check-alert-liveness.sh` + `check-alert-metrics.sh` exit 0 **against the staging target**".
Measured: `check-alert-metrics.sh` contains **0** `docker` references and needs only `PROM_URL` —
it works through a port-forward today. `check-alert-liveness.sh` contains **13**, and two of its
assertions are hard-bound to the compose runtime:
- **L-0** calls `command -v docker`, `docker inspect "$PROM_CONTAINER"` and `docker exec … md5sum`,
  and every failure path is `void` (exit 2). Against a k8s Prometheus this exits **2**, and the
  script's own doctrine says VOID is never clean.
- **L-3** requires the alert destination to be inspectable via the Mailhog HTTP API and VOIDs if it
  is not. D-17 makes the real destination Gmail, which has no such API.

A phase SUMMARY that records exit 2 and reads it as "environment not ready" would be recording the
criterion failing. So the script changes — additively, and without weakening what it asserts.

DPLY-05 needs a gate that does not exist at all. Microsoft's own agnhost recipe supplies the two
arms: `TIMEOUT` on denial, silence on success. The control arm runs FIRST, because a broken probe
reads as a perfect security posture.

Purpose: the instruments must exist and be falsifiable before the runtime they measure exists.
Output: two cluster-capable gates, both declared to `check-gate-enforcement.sh`.

Branch: `phase-29-research`. Never commit to main.
</objective>
