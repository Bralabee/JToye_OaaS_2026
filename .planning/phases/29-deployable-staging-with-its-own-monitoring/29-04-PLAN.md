<objective>
Close **Blocker D**: under the enforcing CNI D-01 puts on the cluster, the current NetworkPolicies
deny every managed datastore, and every `core-java` replica would CrashLoop with the logs pointing
at the database layer.

`k8s/base/networkpolicies/20-core-java.yaml` permits exactly three egress shapes: kube-dns; the
`jtoye-infrastructure` **namespace** on the datastore ports; and `ipBlock: 0.0.0.0/0` with RFC1918
excluded, **port 443 only**. D-09 moves Postgres and Redis OUT of the cluster. Neither is in a
`jtoye-infrastructure` namespace, so those rules do not apply. And:
- a public-access Flexible Server is a public IP on port **5432** -> the 443-only rule denies it;
- a private-access (VNet-injected) server is inside `10.0.0.0/8` -> excluded by `except[]`;
- Azure Cache Basic is TLS on **6380** -> denied by the same 443-only rule.

This is #271's exact failure shape recurring through a different door — which is why #271, closed
2026-08-04, is still listed in DPLY-02. Do not re-open it. Extend the same mechanism.

Layer on the Cilium-specific limitation: `ipBlock` cannot select pod or node IPs, and Microsoft's
FAQ states even `cidr: 0.0.0.0/0` still blocks them; the documented workaround is to add
`namespaceSelector: {}` / `podSelector: {}` peers alongside the `ipBlock`.

Purpose: DPLY-01 and DPLY-05 fail together on this defect. A NetworkPolicy set corrected for the
managed endpoints is also the thing that makes a denied-connection capture meaningful.
Output: egress rules that permit exactly the managed endpoints and nothing more, with INV-7 moved
in the same commit.

Branch: `phase-29-research`. Never commit to main.
</objective>

The Postgres rule is the SHAPE to copy (20-core-java.yaml:73-109): its own egress rule holding
exactly ONE port, so a `replacements:` fieldPath means "the Postgres port" and not "whichever port
sorts first". Its header already explains why splitting one six-port rule into two rules over the
same peer is a shape change with no security change.

The index-coupling contract (k8s/base/kustomization.yaml:103-111): `spec.egress.1` IS the Postgres
rule in both policies. kustomize renders MAP keys alphabetically but preserves LIST order, so the
index addresses the authored order. Inserting a rule AHEAD of index 1 silently retargets the
replacement. New rules therefore go AFTER the existing ones, at stable indices, and the comment
says which index is which.

INV-7's current declaration (k8s/scripts/check-render-invariants.sh:337-358):
  declare -A NETPOL_INFRA_EXPECTED=(
    [core-java-allow]="__DB_PORT__ 5672 6379 9000 9093 61613"
    [pg-backup-allow]="__DB_PORT__ 9000"
  )
  INFRA_NAMESPACE_LABEL="jtoye-infrastructure"
Its header: "Adding a datastore port to a policy MUST be accompanied by adding it here. That is the
intended friction: an egress allow-list is a security boundary, and a gate that silently accepted
new holes in it would not be one."

The `replacements:` block that must be REPEATED in base AND every overlay that patches the key —
measured, not assumed (k8s/base/kustomization.yaml:113-119): with the block in base only and
k8s/local patching db.port to 5433, the local render still emitted 5432.

check-connection-math.sh's two known blindnesses (Pitfall 6):
  RESERVED=3 at :81 is the PostgreSQL default; **Azure reserves 15**.
  MAX_CONNECTIONS is parsed from docker-compose.full-stack.yml regardless of what the managed
  server offers. Live run today: `max_connections=200 … 11 replicas x pool 12 + keycloak(20) +
  backup(1) + exporter(2) = 155 -> OK (<= 157)`. A B1ms server offering 50 would pass that gate and
  CrashLoop. The fix is a NEW PARSED INPUT (the rendered app-config `db.max-connections` added by
  plan 29-02), never a hardcoded number.
