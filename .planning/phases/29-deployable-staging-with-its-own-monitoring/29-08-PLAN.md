<objective>
Deploy Keycloak into the cluster and give it — and Grafana — a way in from the internet.

`k8s/base/ingress.yaml` carries an instruction written for exactly this moment (:84-88): *"IF AN
IN-CLUSTER KEYCLOAK IS EVER DEPLOYED: the host rule and the TLS SAN come back TOGETHER WITH its
Service and Deployment, in that order — never before them."* D-02 makes that condition live, and
#296's hardening conditions with it. This plan executes that instruction.

The ordering is not style. `k8s/base/ingress.yaml:47-88` records that all SANs share ONE `jtoye-tls`
Secret issued as a **single ACME order**, and a failed challenge fails the whole order — so adding
`auth-staging.olajay.co.uk` to the SAN list before its DNS A record exists would stall issuance for
`api-` and `app-` too. INV-6 fails CI when an Ingress backend does not resolve to a Service in the
same render, which is the mechanism that enforces half of it; the DNS half is plan 29-10's, and this
plan's SAN additions are what plan 29-10 waits for.

Three things carry across from compose unchanged and are load-bearing: `KC_DB_POOL_MAX_SIZE: "20"`
(because `check-connection-math.sh:58-59` parses that literal out of the compose file as
`KEYCLOAK_POOL` — a different k8s value means the gate is measuring the wrong number silently),
`KC_METRICS_ENABLED: "true"` (or the `keycloak` scrape job stays DOWN and L-1 fails), and the
Postgres-backed realm behaviour (a volume drop is a no-op; `--import-realm` SKIPS an existing realm;
re-import is `kc.sh import --override true` PLUS a restart).

Purpose: DPLY-01 needs an IdP on a resolvable hostname; DPLY-03 needs the `keycloak` scrape target.
Output: Keycloak in the render, four host rules, four SANs, and a staging ingress that says noindex.

Branch: `phase-29-research`. Never commit to main.
</objective>

`start-dev` is a DEVELOPMENT mode. On a public hostname behind TLS, evaluate `start --optimized`
with `KC_PROXY_HEADERS=xforwarded` and `KC_HTTP_ENABLED=true` (TLS terminates at the ingress).
Whichever is chosen, the file header states the choice, the reason, and what it costs.

  keycloak.realm.redirect-uris  base "https://app.olajay.co.uk/*"

Adding a host is an `op: add` to BOTH lists, in this order (k8s/staging/ingress-hosts-patch.yaml
already explains why JSON6902 and why index-coupling is a FEATURE — IngressSpec.rules carries no
patchMergeKey, so a strategic merge REPLACES the whole list and silently drops every backend):
  - op: add
    path: /spec/tls/0/hosts/-
    value: auth-staging.olajay.co.uk
  - op: add
    path: /spec/rules/-
    value:
      host: auth-staging.olajay.co.uk
      http: { paths: [ { path: /, pathType: Prefix,
              backend: { service: { name: keycloak, port: { number: 8080 } } } } ] }
  (and the same pair for grafana-staging.olajay.co.uk -> service grafana, port 3000)
