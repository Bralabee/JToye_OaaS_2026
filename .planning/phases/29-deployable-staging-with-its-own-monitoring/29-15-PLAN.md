<objective>
Close **#99** — "the CI/CD deploy half is theatre" — for real.

The job's other named defects (the branch gate, image drift, the kustomize bypass, the Swagger smoke
test) were already fixed in Phase 26. The remaining half is that **it has never run**. So the closing
evidence for #99 is one green deploy run, not a workflow file that reads correctly.

Two changes make that possible and honest.

**D-04: no long-lived kubeconfig.** The `Configure kubeconfig` step decodes
`secrets.KUBE_CONFIG_STAGING` — a long-lived credential with cluster access sitting in a repo secret.
It is replaced by `azure/login@v2` with a federated identity credential and
`az aks get-credentials`. Federated subjects are EXACT MATCH with no wildcards, and `deploy-staging`
runs on main AND declares `environment: staging`, so the environment subject is the correct and
tighter one. Everything downstream — `kustomize edit set image`, the render assertion, `apply -k`,
the rollout waits, the smoke tests, the rollback — is already correct and needs no change.

**The runtime-parity analogue.** `scripts/check-runtime-freshness.sh` compares Docker
`.Metadata.LastTagTime` on a local daemon and can only ever VOID against a cluster. The doctrine it
serves — a phase is not done until the delivered runtime matches the branch — is exactly what a
staging deploy needs, and Phase 26 shipped a runtime missing its own config change past four green
gates. The job already asserts the RENDER pins `:${github.sha}` before apply; this plan adds the
other half AFTER rollout: read the running pods' image digests and assert they equal the digests
pushed for that commit.

Purpose: DPLY-02's largest single issue, and the thing that makes every future phase deployable.
Output: a green deploy run, from a workflow with no long-lived cluster credential in it.

Branch: `phase-29-research`. Never commit to main.
</objective>
