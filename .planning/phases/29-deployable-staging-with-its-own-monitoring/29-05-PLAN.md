<objective>
Write the three scripts that create the staging estate — and make every one of them refuse to run
against the wrong cluster.

The operator's host has exactly one kube context: `sipbihs2aks`, which is **EMPLOYER
infrastructure**. Every `kubectl` in this phase must pass `--context` explicitly or run after
`az aks get-credentials`, never against the ambient default. That is this phase's analogue of
`k8s/local`'s compose-XOR guard, and it is stricter, because the failure mode is not a broken dev
stack but somebody else's production.

Three scripts, three jobs:
- `azure-staging-provision.sh` — the resources (AKS with an enforcing dataplane, PostgreSQL **16**
  Flexible Server, Azure Cache Basic, a static public IP, a user-assigned identity with a GitHub
  federated credential). No cloud-provisioning script exists in this repo at all;
  `scripts/k8s-local-up.sh`'s structure is the nearest shape.
- `staging-secrets.sh` — the eight-plus out-of-band Secrets, mirroring `scripts/k8s-local-secrets.sh`
  exactly, plus this phase's three new credentials.
- `staging-bootstrap.sh` — cert-manager, the RabbitMQ cluster operator and the ingress controller,
  applied from pinned release URLs with recorded sha256, deliberately OUTSIDE `k8s/` so 5,900 lines
  of upstream CRDs do not balloon the goldens.

This plan WRITES and dry-runs them. Plan 29-10 RUNS them.

Purpose: nothing about the estate should be typed twice or remembered.
Output: three idempotent, guard-first, dry-run-capable scripts.

Branch: `phase-29-research`. Never commit to main.
</objective>

| Boundary | Description |
|----------|-------------|
| operator shell -> Azure subscription | A mutating `az` command reaches whichever subscription is active |
| operator shell -> kube-apiserver | A `kubectl apply` reaches whichever context is ambient — here, the employer's |
| bootstrap script -> upstream release assets | ~1.4 MB of third-party YAML applied with cluster-admin |
| environment -> Kubernetes Secrets | Credential values pass through a shell |
