Phase 29 disposition for #300 (DPLY-02): closed as superseded for deployed environments by decision D-23; the local path is accepted as it is.

The issue asked for sealed-secrets or external-secrets so that a cluster would not take its secrets from a local .env. For deployed environments Phase 29 delivered that by a different mechanism: Azure Key Vault is the source of truth, read through the Secrets Store CSI driver with one Workload Identity per secret-reading workload. The staging build renders 11 SecretProviderClass objects and no SealedSecret, ExternalSecret or plaintext Secret exists in any overlay's build (.planning/phases/29-deployable-staging-with-its-own-monitoring/evidence/29-27-measurements.txt, lines 38 to 57), and live pods read the vault through it (.planning/phases/29-deployable-staging-with-its-own-monitoring/evidence/29-14-tracer.txt, lines 947 to 1000).

The local overlay stays on the gitignored .env: scripts/k8s-local-secrets.sh applies those values to a single-user development host, where Docker Compose is the canonical runtime and a minikube overlay is an occasional check. A secrets operator there would add a controller and a trust root to protect values that never leave the machine, for no deployed benefit. Revisit only if the local environment ever stops being single-user.
