<objective>
DPLY-04: PITR per #101, with a restore proven **by row count on a restored database, two-arm**.

The arm that matters is arm A, and the ROADMAP states why: *arm A must demonstrate that a zero-row
dump still passes the pipeline's own byte-size and `pg_restore --list` checks — 26-07's L4 measured
exactly that (arm A `products 0` while clearing `MIN_BACKUP_BYTES` by 149x). A single green arm is
not evidence.*

The mechanism arm A exercises is real in this database and not hypothetical: a dump taken as a
FORCE-RLS-subject role captures **zero rows from every tenant-scoped table**, and both of the
pipeline's own safety checks — a byte floor and a TOC listing — pass over that dump comfortably,
because schema and TOC entries are large and rows are not. `infra/backups/create-backup-role.sql`
exists precisely to prevent it, which is also why `jtoye_backup`'s BYPASSRLS attribute was verified
from the database side in plan 29-10 rather than inferred.

D-10 sets the shape: provider PITR restore to a new server plus a row-count comparison, AND the
existing `pg-backup-cronjob` logical dump stays as the provider-independent second line, with arm A
running through the logical-dump path.

Pitfall 8 is a cost hazard with teeth: PITR **always creates a new server** and does not overwrite.
Server parameters are not applied, firewall rules are not copied, you cannot restore across public
and private access, and on Burstable there is **no on-demand backup** — so the drill uses a
timestamp, not "back up now". The restored server bills at the source SKU until deleted.

Purpose: this is DPLY-04, and #101.
Output: a scripted, repeatable drill; two recorded arms; a corrected design document.

Branch: `phase-29-research`. Never commit to main.
</objective>

The pipeline's own checks that arm A must show PASSING over a zero-row dump (backups.md:286-288):

The CronJob's credential contract, which the drill must NOT restate (k8s/base/pg-backup-cronjob.yaml:49-108):
  DB_USER      <- secretKeyRef postgres-credentials / backup-username
  PGPASSWORD   <- secretKeyRef postgres-credentials / backup-password
  with the in-file comment: "dumps as the BYPASSRLS backup role — the app role would capture 0 rows
  from FORCE-RLS tenant tables"

Provider PITR facts (Microsoft Learn, backup-restore concepts):
  - restore ALWAYS creates a NEW server; it never overwrites
  - server PARAMETERS are not applied to the new server
  - FIREWALL RULES are not copied
  - you cannot restore across public and private access
  - no on-demand backup on Burstable -> the drill restores to a TIMESTAMP
  - retention 7-35 days, RPO ~5 min
  - the restored server bills at the source SKU until deleted (~£0.06/hr for a B2s)

The false claim to correct: docs/architecture/SYSTEM_DESIGN_V2.md:657 states "WAL-G to S3 (PITR)".
No WAL-G exists anywhere. #101 names correcting it as a separate acceptance criterion, and ADR-0002
(accepted in plan 29-01) supersedes the WAL-G direction with provider PITR.

    restore to a NEW server, re-apply the firewall rule (they are not copied), connect, count rows
    per tenant-scoped table, compare against the source, print a two-column table, and DELETE the
    restored server.

    Put the delete in a `trap … EXIT`, not at the end of the happy path. PITR creates a second
    billable server and a drill that fails partway would otherwise leave it running at the source
    SKU indefinitely. This is the same discipline `check-no-plaintext-secrets.sh:46` uses for temp
    files, scaled to a cloud resource.

    Use a timestamp, not an on-demand backup: Burstable does not support on-demand backup, so a drill
    written around "back up now" would fail on the SKU this estate uses.

    Exit codes 0/1/2 with the house doctrine. VOID (2) on: missing `az`/`psql`/`pg_restore`, a
    restore that never reaches a ready state, an unreachable restored server, or ZERO tables
    discovered to compare — "found nothing" is never "clean", and a comparison over an empty table
    list would pass vacuously.

    Count rows as a role that can SEE them. Under RLS an unpinned query returns 0 rows on a full
    table, so the comparison must either run as a BYPASSRLS role or pin the tenant GUC, and the
    script must print which — otherwise a perfect-looking `0 == 0` match would be RLS blinding the
    instrument on both sides.

    Wire the gate per `check-gate-enforcement.sh`'s default-deny. This one legitimately needs Azure
    credentials and a live server, so a `gate-enforcement.conf` entry is likely correct — but state
    the reason against the stated bar ("inspects something a GitHub-hosted runner does not have"),
    and prefer wiring if the deploy job's credentials would reach it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backup role -> every tenant's data | `jtoye_backup` holds BYPASSRLS, the one sanctioned exception to the RLS wall |
| logical dump -> AWS S3 | Tenant data leaves Azure to an off-provider bucket |
| drill -> Azure control plane | A restore creates a second billable server holding a full copy of production-shaped data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-13-01 | Information Disclosure | A restored server holding a full data copy, left running and reachable | mitigate | `trap … EXIT` deletes it; the firewall rule re-applied to the drill's own address only; deletion confirmed by listing servers afterwards |
| T-29-13-02 | Elevation of Privilege | A BYPASSRLS role beyond its purpose | mitigate | `jtoye_backup` is LOGIN + BYPASSRLS and read-only by grant; its attributes were verified from the DB side in plan 29-10 and are the documented, least-privilege exception |
| T-29-13-03 | Repudiation | A green backup pipeline over an empty artifact | mitigate | Arm A is the whole point: the zero-row dump is shown PASSING the byte floor and TOC listing, with the ratio recorded |
| T-29-13-04 | Information Disclosure | Tenant data in an off-provider S3 bucket | accept | D-12's deliberate choice — a provider-independent second line is worth the boundary crossing. The bucket is private (the media bucket's public-read prefix is a separate bucket and a separate concern) |
| T-29-13-05 | Denial of Service | Drill cost leaking past the estate ceiling | mitigate | The drill's cost is recorded in hours x SKU rate; the trap prevents an indefinitely-running second server |
| T-29-13-06 | Repudiation | A row comparison blinded by RLS on both sides, reading `0 == 0` as a match | mitigate | The counting role and GUC state are printed; a control arm proves the query can see rows before any comparison is trusted |
| T-29-13-SC | Tampering | npm/pip/cargo installs | mitigate | None in this plan |
