<objective>
Expansion: DPLY-03, part A — Prometheus and its exporters running IN k8s, scraping the staging workloads with the compose
corpus. The ROADMAP notes this fails on the current tree by construction: k8s ships zero monitoring manifests; everything Phase 27
built is compose-scoped (deferred-items §5). D-16: plain kustomize, hand-written Deployments, the SAME rule file as
infra/monitoring; exporters point at the managed endpoint and the in-cluster Redis.

Pattern 1 (RESEARCH): check-alert-liveness.sh maps rules to jobs through EXPORTER_GAUGES, DIRECT_JOBS and SERVICE_JOB_MAP and
VOIDs on an unknown job, so the k8s scrape config must keep the eight job names and labels; only targets change. Pattern 2:
the core-java Service exposes only 9090 and a ClusterIP scrape would load-balance a constant `instance` across replicas — a
headless Service + dns_sd_configs does it once, correctly. Blocker B: liveness is docker- and Mailhog-bound; PROM_EXEC (carried
from the branch) and a sink abstraction make it runtime-agnostic.
Output: the monitoring component (Prometheus + exporters), two exporter identities, the gate changes, check-alert-metrics rc 0.
</objective>
