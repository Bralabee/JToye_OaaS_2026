<objective>
Expansion from the proven slice: D-34(b), owner ruling 2026-10-19 — fix the defect plan 29-14 found, inside Phase 29 and
before persona testing (29-26 and 29-27 now depend on this plan).

**The defect (measured live at a784e7e2, evidence/29-14-tracer.txt lines 1010-1046; deferred-items.md; WINDOWS #50).** A vendor
PNG became an ACTIVE 640x480 WebP derivative on jtoyestgmedia and the vendor product DTO returns it, but the anonymous menu
returns `"imageUrl":null,"imageUrls":[]` for the same product and the storefront renders no image.
`PublicStorefrontService.toPublicProductDto` (line ~1771) reads only the flat `products.image_url` /
`additional_image_urls` columns; the asset-first dual-read (`ProductService.resolveAssetFirst`, D-03a, line ~97) is applied
to vendor DTOs only, and the Phase 24 pipeline never writes the flat primary column. Production is affected the same way.

**Design, decided by reading the code — each choice measured or justified:**
- **One resolution rule, reused, not a second one.** The vendor rule is `ProductMediaRepository.findPrimaryActiveObjectKey`
  (primary row, joined asset ACTIVE) followed by `StorageService.urlForKey`. The public path runs that exact predicate,
  batched over the menu's product ids (one query, not one per product), plus ONE public visibility predicate: `flagged = false`.
  `ProductService` (the vendor path) is not modified. A vendor-rule oracle case in the integration test holds the two together.
- **Flagged ACTIVE primaries stay off the public storefront until the vendor's Keep clears the flag.** Phase 24 D-04 keeps a
  flagged image live for the VENDOR (review queue, unchanged); nothing was public before this plan, so no public good is
  displaced. The vision stage is off by default and fails open to unflagged (MediaProcessingWorker ~313-335), so this bites
  only when IMG-03 is enabled. Reversibility: reversible — one predicate.
- **No DTO shape change, so no frontend code change.** The storefront already reads `imageUrls` first and `imageUrl` as the
  fallback (shop-detail-client.tsx ~118, product-detail-modal.tsx ~65-68), the Product JSON-LD uses `imageUrls[0] || imageUrl`
  (structured-data.ts ~115), images render through a plain img element (safe-image.tsx; next.config.mjs ~20 says no
  remotePatterns entry is needed), and CSP img-src admits `https:` (lib/security-headers.ts ~94). So the fix fills the two
  existing fields: `imageUrl` = the resolved primary, legacy column as fallback; `imageUrls` = that value then the flat
  gallery, exactly as built today. The flat gallery stays: `ProductService.addAdditionalImage` (POST /{id}/images) is still the
  live gallery writer, while the dashboard's only pipeline upload is the primary (frontend/lib/media-api.ts ~75).
- **No migration, no RLS policy.** `getShopProducts` and `getShopConfig` call `resolvePublicShopForSlug`, which sets
  `TenantContext` to the slug's tenant, and `TenantSetLocalAspect` pins `app.current_tenant_id` before every repository call
  inside the transaction. So the media read runs as the slug tenant, and V53's FORCE RLS tenant policies on media_asset and
  product_media admit exactly that tenant's rows. A NULL-tenant public-read policy (the V84/V87 pattern) would be WORSE: it
  would let any unpinned read see every published shop's asset rows, FAILED rows and failure reasons included. Task 1 proves
  this as the runtime role (case 12) and with a break arm (BA-4). Measured: the Flyway head is V88 and no branch or worktree
  carries a V89; V89 stays unused, and if the measurement contradicts the code reading, Task 1 STOPS (the migration path is
  then a re-plan, not an improvisation).
- **OpenAPI snapshot gate: no impact.** No endpoint, field or annotation changes. OpenApiSnapshotTest (contract vs source tree)
  runs and stays green with docs/api/openapi-snapshot.json unchanged. The runtime half, check-openapi-snapshot-fresh.sh, needs
  the compose runtime, which this plan does not rebuild (lane B has no compose authority), and staging's OpenAPI is
  auth-gated (#549). Recorded as N/A with that reason.

**Goods this rework could displace (Incremental Betterment), each accounted for:** the seeded demo catalogue's flat
`/products/seed/` images and every other legacy-only product are byte-identical (case 4, BA-6); the flat gallery is still
served (cases 1 and 4); a product with no image still renders the SafeImage placeholder (imageUrl stays null); the vendor
dashboard is untouched (ProductService not in the diff); the staging menu keeps every dish it listed (Task 4 continuity check).

**Lanes (orchestrator ledger).** Tasks 1-2 may run in a lane-B worktree: they never apply anything and only read staging. Task 3
is the orchestrator's merge, push and image handoff. Task 4 deploys, so it runs only in lane A. From the first image carrying
29-16's literal, staging app mail fails until 29-22. That is 29-16's documented ordering, not a regression from this plan.

Purpose: a photo a vendor uploads reaches every public storefront surface (the menu card, the dish modal, Product JSON-LD) on staging and,
by the same code, production — before testers judge the storefront.
Output: the fix with its NOSUPERUSER proof and break arms; a committed live spec; staging redeployed at a recorded IMAGE_SHA;
the photo proven rendering, with the before-state as the fail arm.
