**THE PHASE TRACER.** This plan carries the `type="tracer"` slice of the whole phase: ONE path — a vendor login
through the public edge to a dashboard with real rows — wired through every layer the phase modifies: the subscription-pinned
estate (29-01, 29-07, 29-09), the platform (29-03, 29-11), the enforcing NetworkPolicies (29-02), the platform components
(29-10), Key Vault → CSI → Workload Identity (29-12, 29-13), the application fixes (29-05, 29-08), the realm (29-04) and the
real-flow seed (29-06). It is verified end to end before ANY expansion plan starts: every plan from 29-15 onward depends on
this one.

Task order: Task 1 builds the tooling the tracer runs — the login spec, its off-by-default switch, and deploy.sh's
--context / --image-tag / preflight / DEPLOYED_SHA record — and gates each piece with its own fail arms against stubs and
offline renders, touching no cluster and no public host. Task 2 is the tracer and LEADS the live portion: its first move is the
red run, and it is the first task that takes a one-way step (the first production-issuer ACME orders, the first migration
of the managed database). The tooling was split out of the tracer at plan-check so that a defect in a script or spec
surfaces before any one-way step, not halfway through the live run. The plan stays one plan with four tasks rather than two plans: every expansion plan
depends on 29-14 as the phase tracer, and the split adds no scope — it moves the old Task 1's tooling ahead of its live
steps. Task 3 falsifies the tracer; Task 4 proves runtime identity.

A tracer is production-quality, not a prototype: the path it proves is the path staging keeps. What it deliberately does NOT
include (expansions): monitoring (29-23/29-24), Mailpit + required STARTTLS (29-16/29-22), Stripe settlement (29-18), PITR
(29-20), the DPLY-05 denial capture (29-17), edge fidelity and trusted proxies (29-15), the CI deploy gate (29-21/29-27), the
customer realm wiring and one-click unsubscribe (29-26). Mail sent during the seed fails to deliver until Mailpit exists, and
the ordering is fixed: plan 29-16 (wave 7) writes the D-20 STARTTLS `.required` literal into application-prod.yml, and plan
29-22 (wave 8) creates Mailpit — serving TLS from its first start — together with the cluster-CA truststore. So from this
plan until 29-22 every send fails on DNS for mailpit.jtoye-staging.svc.cluster.local; it never meets a TLS-less Mailpit,
because none ever exists in staging. Sending is asynchronous (EmailNotificationService @Async), so no request path depends
on it, and the readiness group is Spring Boot's default readinessState group (no `management.endpoint.health.group` in
either yml), so no probe depends on it. Task 2 reads both back from the running artifact, and Task 3's arm 6 shows the
readiness claim can fail. Recorded rather than hidden.

Purpose: DPLY-01 first, proven by content and identity, with its fail directions.
Output: a running staging, the L7 evidence, the falsification arms, runtime-parity proof and the Workload Identity/Blob checks.
