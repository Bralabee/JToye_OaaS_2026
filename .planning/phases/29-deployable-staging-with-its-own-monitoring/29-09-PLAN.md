<objective>
Ship the three remaining runtime pieces — the broker, the staging mail trap and the certificate
issuer — and close the supply-chain paperwork for everything this phase introduced.

**The broker.** D-09 moves RabbitMQ in-cluster via the cluster operator so the STOMP plugin is under
our control and the version becomes declared in-repo. That last part is a deliverable, not a chore:
`infra/dependency-horizons.yaml`'s `rabbitmq-k8s` row currently reads `pin: unknown` with a manual
review expiring **2026-10-26**. Pinning `RabbitmqCluster.spec.image` explicitly is what resolves it.
Verified in the operator source: `additionalPlugins: [rabbitmq_stomp]` automatically adds the
**61613** `stomp` port to the client Service, and plugin changes need no pod restart.

**The mail trap.** D-13 is a deliberate asymmetry: application mail in staging is captured and
inspectable, never delivered — no accidental real mail from a rehearsal environment — while alert
email (D-17) is real, because that email is the phase's entire point. Mailhog is therefore a
**staging overlay** resource, never base. An application-email black hole in production would
silently swallow real vendor mail.

**The issuer.** Nothing in this repo defines a `ClusterIssuer`; `k8s/base/ingress.yaml:8` only
references one. Let's Encrypt enforces duplicate-certificate rate limits and a failed HTTP-01 order
burns weekly quota, so staging issues against `letsencrypt-staging` until a certificate is actually
produced.

Purpose: the last manifests before a real deploy, plus the horizon rows that keep them honest.
Output: broker, mail trap, issuer, and a `check-dependency-horizons.sh` that has something true to say.

Branch: `phase-29-research`. Never commit to main.
</objective>
