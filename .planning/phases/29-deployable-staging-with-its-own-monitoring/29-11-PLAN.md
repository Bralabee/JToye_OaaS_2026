<objective>
The first deploy, and the criterion the whole phase exists for: **a real Keycloak vendor login
through the ingress to a rendered dashboard, on a resolvable public hostname, with real seeded
rows.** Not localhost. Not a port-forward.

Phase 26-08's L7 proof is the template — one verbatim URL carrying `client_id` and an encoded
`redirect_uri`, landing on a rendered dashboard — now against staging rather than minikube.

Two things make this harder than "deploy and click":

**There is no staging seed path anywhere in the repo.** Compose seeds via the dev realm and local
fixtures. DPLY-01 says "real seeded rows", and a dashboard that renders an empty state is not the
criterion. So this plan builds one: a one-shot Job, gated so it cannot run twice, asserted by a row
count — not by "the page rendered".

**Three separate things can each make a green-looking login false.** The security headers are set
via `configuration-snippet`, which the controller only honours if `allow-snippet-annotations` is
true (plan 29-05) — a default install serves every page WITHOUT them while the Ingress object shows
them and every HTTP check returns 200. The CSP must name `auth-staging.olajay.co.uk`, and a CSP
source WITH A PATH matches exactly unless it ends in `/` — the recorded trap that once blocked
customer sign-in while the realm looked listed. And `check-runtime-freshness.sh` cannot see a k8s
runtime at all, so the delivered-runtime doctrine needs a different instrument here.

Purpose: this is DPLY-01.
Output: a running staging environment and a dated evidence file whose red arm was run first.

Branch: `phase-29-research`. Never commit to main.
</objective>

  ONE verbatim URL of the form

  recorded in full, followed by a rendered dashboard carrying rows that came from the seed.

The RED arm (research Blocker A): point keycloak.client-id at a deliberately absent client
(`does-not-exist`), re-apply, and confirm the login proof goes RED. If it does not, the proof is not
testing the login. Run this arm and restore before recording the green.

Served-response proofs (NOT manifest reads):
  curl -sI https://app-staging.olajay.co.uk | grep -i strict-transport-security     -> must hit
  curl -sI https://app-staging.olajay.co.uk | grep -io "form-action[^;]*"           -> must name the IdP origin
  curl -sI https://app-staging.olajay.co.uk | grep -i x-robots-tag                  -> must read noindex
  ⚠ trap_csp_realm_path_matching: a CSP source WITH A PATH matches exactly unless it ends in `/`.
    Assert the exact served string, not that the hostname appears somewhere in it.

Runtime parity, k8s analogue (research Open Question 3): `scripts/check-runtime-freshness.sh` compares
Docker `.Metadata.LastTagTime` and can ONLY VOID against a cluster — it is NOT the instrument here,

digest comparison: read the running pods' image digests and assert they equal the digests pushed for
the deployed commit. Wiring that into CI is plan 29-15's; running it by hand is this plan's.

Existing E2E asset: frontend/e2e/dashboard-mobile.spec.ts carries a real-Keycloak login helper —
that helper is the reusable part. It has never been run against a public host.

Pitfall 10: `NoOrdersCreated` is blind after every restart — the series behind it is a request
counter that does not survive a JVM restart. `scripts/seed-order-metric.sh` is the committed fix and
must run against the INGRESS hostname, not localhost. Do not diagnose it; run it. (That belongs to
plan 29-12, but the restart happens here.)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet -> ingress -> frontend/api/Keycloak/Grafana | Four public hostnames, TLS-terminated at the edge |
| browser -> Keycloak | An unauthenticated OIDC authorize request |
| seed Job -> managed Postgres | A privileged write path into the platform database |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-11-01 | Information Disclosure | Security headers declared but never served | mitigate | Verified in the SERVED response by `curl -sI`, with a fail arm proving the grep can return empty. The manifest is explicitly not accepted as proof |
| T-29-11-02 | Spoofing | A CSP whose IdP source does not match, refusing the sign-in redirect | mitigate | The exact served source string is asserted, and the trailing-slash path-matching question is answered explicitly rather than assumed |
| T-29-11-03 | Information Disclosure | The staging OpenAPI surface unauthenticated (#549) | mitigate | Regression check in Task 2 against the real hostname; the Phase 28 fix must not silently regress |
| T-29-11-04 | Tampering | A deployed runtime older than the branch | mitigate | Running pod image digests compared against the pushed digests for the deployed commit; `check-runtime-freshness.sh` explicitly named as NOT the instrument, so its VOID cannot be recorded as a pass |
