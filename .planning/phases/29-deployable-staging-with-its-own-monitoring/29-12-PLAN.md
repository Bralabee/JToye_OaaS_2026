<objective>
Tracer slice, secrets layer of the DPLY-01 path: Key Vault → Secrets Store CSI → synced Secret → the secretKeyRef names the
manifests already use (D-23, closes #100 for deployed environments and #300 by supersession). Workload Identity is the
authentication, as Phase 36 already uses for Blob.

Two measured mechanics shape the design. (1) The CSI driver syncs a Kubernetes Secret ONLY while a pod mounts the
SecretProviderClass, and deletes it when the last consuming pod goes — so every consumer mounts its own SPC, and the RabbitMQ
operator (which reads the default-user Secret before any broker pod exists) is served by a tiny always-on secret-sync pod
(RESEARCH Pattern 4 / Pitfall 11; A7 measured live in plan 29-14). (2) The staging golden shows postgres-credentials read by
both core-java and pg-backup, and keycloak-credentials read by both core-java and frontend; two SPCs producing one Secret name
would overwrite each other's keys. "Each identity reads only its own secrets" therefore means: second consumers read a
Secret of their own name, mapped to the same Key Vault object — one value, two least-privilege paths.

The derived-name chain is secretKeyRef → SPC secretObjects → objectName → Key Vault, checked by a new gate; plan 29-13's
write-once writer and deploy preflight consume `keyvault-chain.py objects` so no name list is ever hand-written.
Output: base renames, the azure-keyvault component, the chain gate, INV-10 widened, regenerated goldens, #100 reopened.
</objective>
