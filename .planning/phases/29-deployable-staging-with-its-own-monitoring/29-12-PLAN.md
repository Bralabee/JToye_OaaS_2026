<objective>
DPLY-03's literal criterion: **`check-alert-liveness.sh` and `check-alert-metrics.sh` exit 0 against
the staging target.** Both scripts' headers already require the exit code and an ISO-8601 timestamp
to appear in the phase SUMMARY, so this plan's output shape is prescribed.

Two things this plan must refuse to do.

**It must not read exit 2 as "environment not ready".** VOID is never clean — that is the scripts'
own doctrine, and a SUMMARY recording exit 2 as an environment issue would be recording the
criterion failing. Plan 29-03 made the k8s path exist; if it still VOIDs, that is a defect to fix.

**It must not diagnose `NoOrdersCreated`.** The series behind it is a request counter that does not
survive a JVM restart, so `check-alert-metrics.sh` M-1 goes red on any freshly deployed core-java
until an order is placed. The committed fix is `scripts/seed-order-metric.sh`, and on staging it runs
against the INGRESS hostname, not localhost. Run it; do not investigate it.

And one thing it must expect. Phase 27's finding F-3c was that `HighMemoryUsage` and
`FrequentGarbageCollection` had unqualified `jvm_*` selectors and bound to **Keycloak's** JVM while
carrying `service: core-java`. Phase 27 fixed it by deleting the static `service:` label so the
series' own label wins. In staging, Keycloak is in-cluster and scraped **for the first time**, so
both JVMs are present again. L-2b (subject correctness) exists to catch exactly this. Expect it to
have opinions and read them.

Purpose: this is DPLY-03, and #98's first two acceptance criteria with it.
Output: two green gates against a real cluster, and an alert email in a real inbox.

Branch: `phase-29-research`. Never commit to main.
</objective>

Exit-code contract (both scripts): 0 clean · 1 a live detection defect · 2 VOID. "Found nothing" is
NEVER "clean". Both headers require the exit code and an ISO-8601 timestamp in the phase SUMMARY.

Expected scrape targets UP (the eight jobs from plan 29-06): prometheus, core-java, edge-go,
postgres, keycloak, redis, rabbitmq, rabbitmq-queues. The `keycloak` job is UP in k8s for the FIRST

DORMANT_RULES is the ONLY sanctioned way to park a rule that genuinely cannot apply

infra/monitoring/prometheus/alerts.yml is forbidden — and check-alert-corpus-parity.sh (plan 29-06)
would catch a one-sided edit anyway.

Also forbidden: adding an EXPECT_EMPTY-style allowlist entry to get a gate green. Both gates have
STALE arms that fail when an exemption outlives its reason; the entry is the wrong fix and the gate
is designed to say so.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Alertmanager -> Gmail relay | Alert content and an SMTP credential leave the cluster |
| operator laptop -> cluster (port-forward) | Temporary privileged access to cluster-internal services |
| alert content -> a third-party mailbox | Alert bodies may carry hostnames, service names and metric values |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-12-01 | Information Disclosure | Alert bodies carrying internal detail to an external mailbox | accept | Staging alert bodies carry hostnames, service names and metric values, no customer data. Recorded rather than assumed; staging's seeded data contains no real PII by design |
| T-29-12-02 | Repudiation | Recording a VOID (exit 2) as a pass | mitigate | Both gates' VOID paths exercised deliberately; the plan states in advance that exit 2 is a task failure, not an environment caveat |
| T-29-12-03 | Denial of Service | An alert that never dispatches because of group_interval | mitigate | The constant-alertname grouping trap is named in advance and must be ruled out before any other diagnosis |
| T-29-12-04 | Tampering | A rule silently edited to make a gate green | mitigate | `check-alert-corpus-parity.sh` asserts the two copies stay byte-identical; DORMANT_RULES with a wake-trigger is the only sanctioned parking mechanism; allowlist entries are explicitly rejected |
| T-29-12-05 | Spoofing | An alert whose subject label points at the wrong workload | mitigate | L-2b subject correctness read rather than skimmed, with Keycloak's JVM now in the scrape set — the exact Phase 27 F-3c shape |
| T-29-12-06 | Information Disclosure | The Gmail app password | mitigate | Consumed only by Alertmanager from a Secret; the fail arm uses a deliberately wrong credential rather than printing the real one |
| T-29-12-SC | Tampering | npm/pip/cargo installs | mitigate | None in this plan |
</threat_model>
