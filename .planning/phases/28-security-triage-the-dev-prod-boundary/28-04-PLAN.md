<objective>
Close #281 per D-09/D-10: re-check the subscriber's grant before EVERY emit, so a revoked user's
still-open SSE connection delivers nothing even though the socket may linger to `SSE_TIMEOUT`.

Purpose: `subscribe()` snapshots the caller's `ShopScope` once, at connection time. Its own javadoc
says so — "a grant revoked mid-stream takes effect on the next reconnect (<= 5-min emitter
timeout)". That snapshot has no temporal dimension, and #281 is exactly the window it leaves open.

**The dominant risk in this plan is not the security arm — it is the liveness arm.**
`broadcast()` runs on the `OrderSseFanoutListener` `@RabbitListener` thread, which carries no
`SecurityContext`, no `TenantContext` and no tenant GUC. A re-check written the obvious way queries
`shop_staff` under FORCE RLS with nothing pinned, resolves "no grants" for every subscriber, and
delivers nothing to anyone — a dead KDS that passes every security assertion in the change. The
revoked-user test passing on the first try with no GUC handling written is the tell, not the
reassurance.

Output: a per-emit re-check with both arms proven, and the revocation latency stated as a number.
</objective>
