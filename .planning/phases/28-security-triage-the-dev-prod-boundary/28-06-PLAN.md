<objective>
Close #283 and #284: replace the retained `auth == null` internal-caller bypass with an explicit
declaration, so trust is something a caller ASSERTS rather than something the absence of a principal
implies.

Purpose: `ShopAccessService.isInternalCaller()` at :622-623 returns true whenever the current thread
carries no `Authentication`. Its own javadoc already states the semantics precisely, and that is the
problem — the rule is correct only because no gated service is currently reached from a background
path. #284's premise has partly decayed: since Phase 24, `MediaProcessingWorker` (`@RabbitListener`)
reaches `MediaAssetService`, a class with three `shopAccessService.require(...)` calls (:118, :384,
:439). The specific entry point it uses, `placeAsset` (:297-312), does NOT gate — so the claim still
holds, but it now holds by one method in a class that gates three of its other entry points. That is
"one new call away" made concrete.

The same class already made exactly this move once, for machine clients: `isDeclaredMachineClient`
(:626-637) grants trust ONLY by explicit declaration and never infers it from an unparseable
subject. This plan applies that precedent to the internal-caller case.

**Budget the blast radius honestly.** #283 records 62 no-principal test files depending on the
current behaviour, and this project's memory records that new auth gates have silently broken
EXISTING integrationTests before. A targeted test run is not acceptable evidence here.

Output: the marker, the wrappers, every legitimate internal entry point declared, and a FULL
`:core-java:test :core-java:integrationTest` run green.
</objective>
