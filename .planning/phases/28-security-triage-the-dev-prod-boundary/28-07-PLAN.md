<objective>
Ship D-01/D-03's durable half: a non-owner runtime role, its grants, and every configuration
surface that has to name it.

Purpose — and get the framing right, because writing it up wrong would be a false security claim.
All 36 tenant tables are ENABLE + FORCE RLS today, so the owner role is ALREADY subject to RLS.
Measured live: as `jtoye_app` with no tenant GUC, `products` returns 0; under two tenant GUCs, 47
and 4; as superuser, 51. So **D-01 is a durability fix, not the closure of a live hole** — exactly
as D-01's own wording says: isolation stops depending on FORCE RLS being remembered on every future
table. #552's acceptance criterion, "a query that returns rows under a pinned tenant returns none
under a different one", is already satisfiable on today's role. The criterion that can actually fail
is the OWNERSHIP one, not the FILTERING one, and plan 28-08 is where it gets asserted.

**The trap that is already biting this repository.** `ALTER DEFAULT PRIVILEGES` without `FOR ROLE`
registers the defaults against the CURRENT role. Both existing bootstrap scripts run as the
superuser while Flyway creates tables as `jtoye_app`, so the defaults apply to nothing Flyway makes.
Measured live: `jtoye_backup` CANNOT `SELECT postcode_centroid`, the newest table — 40 of 41
readable, 1 missing. A `pg_dump` as the backup role does not capture what it claims to. Repeat that
mistake for the runtime role and the app boots fine today and dies on the first table a future
migration adds.

Output: the bootstrap SQL for both paths, the repaired backup grants, a sanitized issue for the live
defect, the Flyway credential decoupling, and the new key pair declared on every surface.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application connection -> PostgreSQL | today the app connects as the OWNER of every table it reads |
| migrator connection -> PostgreSQL | needs DDL; must not be the same credential the request path uses |
| committed config templates -> a future operator | a template naming the wrong role is how the previous misconfiguration shipped |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-30 | Information Disclosure | a future migration adding a table that forgets FORCE RLS, with the app connected as its owner | mitigate | non-owner `jtoye_runtime` role with an enumerated DML grant set; ownership can no longer be the thing standing between the app and every row |
