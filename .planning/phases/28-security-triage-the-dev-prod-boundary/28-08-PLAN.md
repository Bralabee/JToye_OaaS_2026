<objective>
Prove D-01's split holds, permanently and live — and make a future environment that reverts to the
owner role fail at boot instead of failing silently.

Purpose: D-04 asks for both a permanent regression-proof test and a one-off live measurement, both
directions recorded. The permanent half matters more than it looks, because the failure this split
guards against is invisible in the present tense: an `ALTER DEFAULT PRIVILEGES` registered against
the wrong role works today and breaks on the first table a future migration creates. RESEARCH names
the future-table grant test as **the highest-value new test in the phase** for exactly that reason —
a grant test that only checks EXISTING tables cannot fail for the reason that matters.

Two pitfalls this plan is shaped around. First, a CRUD-only integration test cannot catch the
non-DML gaps: `PostcodeCentroidImporter` is an `ApplicationRunner` that does `CREATE TEMP TABLE` and
`TRUNCATE` on every startup where the row count does not match the manifest, so the harness must
boot the WHOLE application as the runtime role, not merely run queries as it. Second, the obvious
live arm — "as the runtime role with no tenant pinned, every tenant table returns 0" — FAILS ON A
CORRECT TREE: `shops` returns 3, because `shops_public_read` is a permissive SELECT policy
`(published = true) OR (tenant_id = current_tenant_id())` serving the public storefront, and
permissive policies are OR-ed. Running that arm on `shops` and "fixing" the result would break the
storefront.

Output: the boot validator's ownership check, the future-table grant contract, the isolation suite
running as a non-owner, and the live stack repointed and measured with a control.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| runtime database role -> table ownership | the property this plan asserts; ownership is what would let the app read past a forgotten FORCE RLS |
| a future migration -> the runtime role's privileges | new objects must be covered without a manual grant, or the app dies on deploy |
| an operator's environment file -> the running application | a reverted `DB_USER` must fail loudly rather than quietly restoring owner access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-37 | Information Disclosure | an environment silently reverted to the owner role | mitigate | `validateNotTableOwner()` boot fail-fast with a named reason and the files to edit, proven by a break arm and by a profile arm showing the validator actually runs |
| T-28-38 | Denial of Service | a future migration's table unreadable by the runtime role | mitigate | `RuntimeRoleGrantContractTest`'s future-table assertion, with the `FOR ROLE`-omitted arm observed FALSE |
| T-28-39 | Denial of Service | `PostcodeCentroidImporter` failing on TRUNCATE or TEMPORARY at startup | mitigate | asserted in the grant contract AND observed on a real boot of the whole application, because a CRUD-only test cannot reach it |
