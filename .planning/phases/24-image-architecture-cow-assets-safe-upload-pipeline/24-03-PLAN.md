<objective>
Deliver the request-thread half of the safe pipeline (IMG-02 accept side): a reject-early oversize guard, a quarantine store + PENDING `media_asset`, an idempotent 202 accept, a dedicated `media_event_outbox` → `media.events` publish path — sidestepping the `outbox_flusher_dispatch_trap` entirely — and the RETIREMENT of the old synchronous `ProductController.uploadImage` handler so the new accept is the sole owner of `POST /api/v1/products/{id}/image` (no Ambiguous-mapping boot failure).

Purpose: A 2GB body must be refused at the request thread before buffering (a 2GB in-memory MultipartFile is itself a DoS). The accept must return immediately (202) with the asset id and hand normalization to an async worker. The upload endpoint is a mutating API surface, so it carries the uniform Idempotency-Key contract + RFC 7807 typed errors (D-06). Because the new controller lives in the un-prefixed `uk.jtoye.core.media` package and hard-mounts the same route the auto-prefixed `ProductController` already owns, the old handler MUST be retired in this same plan or the ApplicationContext will not refresh.

Output: `MediaEventOutbox` trio (dedicated table, cloned from the hardened `PaymentEventOutbox` set), the `media.events` RabbitMQ topology, `MediaUploadController.accept` (Content-Length 413 + Idempotency-Key + 202), the ProductController retirement of the colliding `uploadImage` handler, `MediaAssetService.acceptQuarantineAndQueue` (quarantine PUT + PENDING insert + outbox insert in one tx), the 413 handler, and the accept/idempotency Wave-0 tests.
</objective>

| Boundary | Description |
|----------|-------------|
| client → accept endpoint | Untrusted multipart body + headers cross into the request thread; must be size-gated before buffering |
| accept tx → outbox | The PENDING asset + outbox row must commit atomically or neither |
| external AI agent → mutating API | Idempotency-Key contract governs replay safety |
