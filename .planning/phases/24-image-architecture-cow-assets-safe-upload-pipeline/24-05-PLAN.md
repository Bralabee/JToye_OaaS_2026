<objective>
Expose the vendor-facing review/rejection queue as a backend surface (IMG-03 vendor-visible half + the data contract for IMG-04): a tenant-scoped GET listing FAILED (reason + re-upload) and flagged-ACTIVE (Keep/Replace) assets, a Keep action that dismisses the flag, the product/media DTO enrichment that carries `MediaAssetStatus` + `flagged` + `failureReason` so the UI can render processing/failed/flagged states, and — closing the IMG-01 delete surface — the wiring of the existing vendor image-delete paths (`removeImage` / `removeAdditionalImage`) to the `product_media` + ref-counted `releaseAsset` model.

Purpose: A FAILED asset must surface a vendor-visible rejection reason and a flagged-ACTIVE asset must land in a review queue with Keep (dismiss) or Replace (re-upload) — without a hard "block product on FAILED" gate (D-04b). Replace reuses the 24-03 accept endpoint; Keep is a new dismiss-flag action. The DTO is the seam the 24-06 frontend renders against. Separately, the one place a human triggers image deletion (the `DELETE /{id}/image` + `DELETE /{id}/images/{index}` endpoints) must remove the `product_media` row and call `releaseAsset` — otherwise a vendor deletion orphans the join row + `media_asset` and breaks IMG-01's "physical delete only at ref-count 0" guarantee.

Output: `MediaController` (review-queue GET + keep POST), `MediaAssetDto` (+ the `MediaAssetStatus` mapping into product DTOs), the vendor image-delete wiring in `ProductService`, and the three IMG-01/03/04 backend tests. Depends on 24-04 (worker produces FAILED/flagged) + 24-02 (model + dual-read + `releaseAsset`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vendor → review queue | A vendor may only see + act on their own tenant's assets |
| Keep/dismiss action | A mutating action must be tenant-scoped and typed |
| vendor → image delete | A delete must be tenant-scoped and must not leak/orphan cross-tenant assets |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-19 | Information Disclosure | cross-tenant review-queue read | mitigate | RLS (`current_tenant_id()`, request-thread GUC) scopes the FAILED/flagged selection; integration test asserts another tenant's rows are invisible |
| T-24-20 | Tampering | cross-tenant flag-dismiss | mitigate | `dismissFlag` is tenant-scoped; a foreign assetId returns 404 RFC 7807 (no oracle) |
| T-24-21 | Information Disclosure | failure_reason leaking internal detail | accept | `failure_reason` is a vendor-facing message (e.g. "unsupported format", "could not decode") set by the worker — not a stack trace; tenant-scoped so only the owner sees it |
| T-24-22 | Elevation of Privilege | unauthenticated queue/keep access | mitigate | `@PreAuthorize` catalog read/write scopes mirror ProductController |
| T-24-26 | Tampering / Information Disclosure | cross-tenant / orphaning image delete | mitigate | `removeImage`/`removeAdditionalImage` keep the existing `shopAccessService.require(SHOP_MANAGER)` + RLS scope; `releaseAsset` runs inside the tenant GUC and only ever deletes a `media_asset` at ref-count 0 (never a shared asset), closing the orphan/leak vector at the human-delete surface |
</threat_model>
