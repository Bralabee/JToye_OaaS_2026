# Phase 16.1 Plan 02: Per-tenant SSE Emitter Routing (AUDIT-W0-01) Summary

**Replaced OrderSseService's single shared CopyOnWriteArrayList with a per-tenant ConcurrentHashMap<UUID, Set<SseEmitter>>, filtered broadcast() by event.tenantId(), made subscribe() fail-closed when TenantContext is unset, and added a 4-test regression suite proving cross-tenant isolation.**

## Accomplishments

- Closed the highest-blast-radius pre-prod blocker from the 2026-04-27 council audit: every dashboard tab on every tenant previously received every other tenant's order state changes.
- subscribe() now captures TenantContext.get() at attach time and stores the emitter in a per-tenant bucket; broadcast() routes by event.tenantId() so only the matching tenant's bucket is iterated.
- subscribe() with no TenantContext fails closed with IllegalStateException (LOCKED decision) — no silent attachment to a shared/default bucket.
- Per-tenant memory hygiene: emitter completion (or timeout/error) removes the emitter from its bucket, and a now-empty bucket is evicted from the outer map via computeIfPresent.
- 11 OrderSseService* tests green (7 patched existing + 4 new isolation tests). The new broadcastIsTenantScoped test uses Mockito.spy and verifies tenant A's emitter received exactly one send while tenant B's received zero.
- Confirmed during planning + execution: OrderController.streamOrderEvents() and OrderStateChangeListener did NOT need to change — they remain pass-through callers, and OrderStateChangeEvent.tenantId() already exists at field 2 of the record.

## Decisions Made

- **Fail-closed at subscribe()** — chose `throw new IllegalStateException(...)` over `AccessDeniedException` or HTTP 401: this is a security tripwire for a misconfigured request pipeline (TenantContext not populated by JwtTenantFilter), not an authorization failure of the user. Routing through GlobalExceptionHandler to a 500 is acceptable second-order behaviour. (LOCKED in 16.1-CONTEXT.md Item 1.)
- **Throw via explicit if-block instead of `Optional.orElseThrow(...)`** — both are semantically equivalent fail-closed patterns. The explicit form was chosen because the plan's grep-based acceptance criteria literally check for `throw new IllegalStateException`.
- **Inner set chosen as `Collections.newSetFromMap(new ConcurrentHashMap<>())`** rather than `CopyOnWriteArraySet`. Broadcast iteration is read-mostly, but `bucket.remove(emitter)` inside the IOException catch + the cleanup callback both run during iteration — CHM-backed set tolerates concurrent modification without snapshotting on each write.
- **Reflection-based completionCallback invocation in cleanupRemovesEmptyBucket test** — `SseEmitter#complete()` does NOT dispatch onCompletion callbacks in unit tests because Spring wires the dispatch Handler from the response writer. Reaching into `ResponseBodyEmitter#completionCallback` (a Runnable bundling all registered delegates) is the same callback Spring would invoke once the response is fully flushed in production, so the test exercises the exact production cleanup path.

## Deviations from Plan

None - plan executed exactly as written.

The two grep-based acceptance criteria (`throw new IllegalStateException` count = 1; `CopyOnWriteArrayList` count = 0) shaped two minor implementation-form choices in Task 1 — using an explicit `if (tenantId == null) throw ...` block (instead of `Optional.orElseThrow(...)` lambda) and scrubbing the literal `CopyOnWriteArrayList` token from a Javadoc reference. Both are equivalent in semantics; this is honoring the plan's literal grep contract, not deviating from its intent.

## Issues Encountered

- **Initial `cleanupRemovesEmptyBucket` test failure** — the first iteration of the test relied on `emitter.complete()` to dispatch onCompletion callbacks. In Spring 6.2, `ResponseBodyEmitter#complete()` only invokes the completion callback when a response Handler has been initialized (production path); in plain JUnit it is a no-op. Resolved by inspecting Spring's compiled bytecode (`javap` on `ResponseBodyEmitter.class`) to confirm the field name `completionCallback` and that `DefaultCallback implements Runnable`, then invoking it directly via reflection. The plan's `<action>` notes for Task 2 explicitly anticipated this with the "if `replaceEmitterInBucket` fails on a `cleanupRemovesEmptyBucket`-shaped flake, accept the alternative …" escape-hatch — used it.
