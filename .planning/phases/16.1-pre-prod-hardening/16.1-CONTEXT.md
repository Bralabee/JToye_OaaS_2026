# Phase 16.1: Pre-prod Hardening (Wave 0 Council Audit Fixes) - Context

**Gathered:** 2026-04-27
**Status:** Ready for planning
**Source:** Council audit (`docs/audit/COUNCIL-AUDIT-2026-04-27.md`) + 8 specialist remediation docs (`docs/audit/remediation/`). Findings re-verified against live code on 2026-04-27 — all 5 issues reproduce exactly as described.

<domain>
## Phase Boundary

Close the 5 confirmed pre-prod blockers from the 2026-04-27 council audit:

1. `OrderSseService` cross-tenant data leak (every SSE subscriber sees every tenant's order events)
2. `/public/orders` IDOR (verify parameter is optional → enumeration via email alone)
3. Stripe webhook idempotency (`handleWebhookEvent` has no de-dup → duplicate `financial_transactions` rows on retry)
4. `reviews_tenant_write` RLS policy uses wrong setting name (`app.tenant_id` vs canonical `app.current_tenant_id`) AND has an OR-clause that lets anyone setting `app.customer_email` insert spam reviews
5. 9 tables (`reviews`, `shop_promotions`, `shop_announcements`, 6 `_aud` audit tables) lack `FORCE ROW LEVEL SECURITY` → table owner / superuser bypass defeats tenant isolation in the same DB role used by some Flyway migrations and Envers writes

In-scope: Java code changes + a single Flyway V35 migration + regression tests (incl. `RlsContractTest` from `docs/audit/remediation/03-database-remediation.md` F11).

Out of scope (deferred to other phases):
- `charge.refunded` webhook handler — Phase 17 will add this as part of vendor refund flow.
- The other 7 remediation pairs from the council audit (devops/MDC, prod actuator exposure, edge-go absorb, frontend redesign, etc.) — Wave 1+ work, separate phases.

</domain>

<decisions>
## Implementation Decisions

### Migration strategy
- **LOCKED**: Single Flyway migration `V35__rls_idempotency_force_rls.sql` covers items 3, 4, and 5 (one migration, three concerns) so deployment is atomic. Items 1 and 2 are pure Java — no migration impact.
- **LOCKED**: New table `processed_stripe_events(event_id TEXT PRIMARY KEY, processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW())`. No tenant_id (Stripe events are global). Not RLS-enabled — service writes happen outside tenant context.
- **LOCKED**: Migration is forward-only. No rollback path needed for the RLS tightening — looser policies are unsafe to keep around as fallback.

### Item 1 — `OrderSseService` cross-tenant filter
- **LOCKED**: Capture `TenantContext.get()` at `subscribe()` and store it alongside the `SseEmitter`. Filter `broadcast()` by event tenant.
- **LOCKED**: Replace the bare `CopyOnWriteArrayList<SseEmitter>` with `CopyOnWriteArrayList<TenantSseSubscription>` (record holding `UUID tenantId`, `SseEmitter emitter`).
- **LOCKED**: `OrderStateChangeEvent` must carry tenant identity. If it doesn't already, add `UUID tenantId()` accessor and populate from `TenantContext.get()` at the call site (`OrderStateMachineService` — verify during planning).
- **LOCKED**: If `TenantContext.get()` is null at subscribe, throw `IllegalStateException` rather than silently broadcasting cross-tenant — fail-closed.
- **LOCKED**: Regression test `OrderSseServiceTenantIsolationTest`: two subscriptions with different captured tenants; broadcast for tenant A; assert tenant B's emitter received zero events.

### Item 2 — Customer-orders IDOR
- **LOCKED**: Make `verify` parameter mandatory at the controller level. Reject with HTTP 400 (not 401/403) when missing or blank — this is a request-shape error, not auth.
- **LOCKED**: Change `@RequestParam(name = "verify", required = false) String verifyOrderNumber` → `@RequestParam(name = "verify") String verifyOrderNumber` plus a `@NotBlank` style guard.
- **LOCKED**: Always call `storefrontService.trackOrder(verifyOrderNumber, email)` before `getCustomerOrders(email)` — current code only verifies when verify is present. After the fix, the `if` guard is dead and must be removed (the trackOrder call becomes unconditional).
- **LOCKED**: Regression test `PublicStorefrontControllerIdorTest`: GET `/public/orders?email=victim@example.com` → 400; GET with valid `verify` → 200 with that customer's orders only.

### Item 3 — Stripe webhook idempotency
- **LOCKED**: Insert into `processed_stripe_events` with `INSERT ... ON CONFLICT DO NOTHING RETURNING event_id` at the very top of `handleWebhookEvent`, immediately after signature verification and before the type switch. If 0 rows returned (already processed), log at INFO and return.
- **LOCKED**: Use `JdbcTemplate.queryForObject` (or `JdbcClient`) to capture the RETURNING — this is TOCTOU-safe (atomic in Postgres) per `docs/audit/remediation/01-backend-remediation.md` F2.
- **LOCKED**: Wrap the duplicate-event short-circuit so it sits *outside* the existing `@Transactional` boundary on `handleWebhookEvent` — or use REQUIRES_NEW for the dedup row insert — so a downstream transaction rollback does not reset the dedup record. Decision deferred to planner; both shapes work.
- **LOCKED**: Regression test `StripeWebhookIdempotencyIntegrationTest` against Testcontainers Postgres: post the same `event.id` payload twice; assert exactly one `financial_transactions` row.

### Item 4 — `reviews_tenant_write` rewrite
- **LOCKED**: V35 drops the existing `reviews_tenant_write` policy and recreates with:
  - `tenant_id = current_setting('app.current_tenant_id', true)::UUID` (canonical setting name)
  - **AND** `EXISTS (SELECT 1 FROM orders WHERE id = order_id AND customer_email = current_setting('app.customer_email', true))` (proves the writer owns an order matching the claimed email)
  - The previous OR-clause is removed entirely.
- **LOCKED**: Confirm during planning that the storefront review-submit path sets `app.customer_email` on the connection before INSERT; if not, that wiring is part of this phase.
- **LOCKED**: Regression test `ReviewsRlsPolicyIntegrationTest` (Testcontainers): attempt to insert a review with arbitrary `tenant_id` + arbitrary `customer_email` (no matching order) → INSERT blocked; valid path (matching order + customer_email) → INSERT succeeds.

### Item 5 — `FORCE ROW LEVEL SECURITY` on 9 tables
- **LOCKED**: V35 issues `ALTER TABLE <name> FORCE ROW LEVEL SECURITY` for: `reviews`, `shop_promotions`, `shop_announcements`, `customers_aud`, `shops_aud`, `products_aud`, `financial_transactions_aud`, `orders_aud`, `order_items_aud`.
- **LOCKED**: Regression: assert `SELECT relforcerowsecurity FROM pg_class WHERE relname IN (…) AND relkind='r'` returns true for all 9. Likely folded into `RlsContractTest`.
- **LOCKED**: Verify (during planning, before migration write) that the application DB role is *not* the table owner — `FORCE RLS` would block migration scripts running as that role from bypassing RLS. If it IS the owner, planner must split: keep migration role as owner, add policies for the migration role, OR add a separate `app_user` role used by the running service. Per `docs/audit/remediation/03-database-remediation.md` F2 the existing setup should already separate these, but verify.

### Cross-cutting: `RlsContractTest`
- **LOCKED**: Implement `RlsContractTest` per `docs/audit/remediation/03-database-remediation.md` F11 — a single Testcontainers test that exhaustively walks every table in `pg_tables` (in `public` schema, excluding `flyway_schema_history`) and asserts both `relrowsecurity = true` AND `relforcerowsecurity = true`. This catches future drift on any table.
- **LOCKED**: Test runs in CI as part of the existing Testcontainers suite — no new Docker plumbing.

### Claude's Discretion
- Exact split of plans (single bundled plan vs one plan per item) — recommend one V35 migration plan + per-fix Java plans + the RlsContractTest as the closing gate, but the planner agent decides.
- Whether to add a feature flag — recommended NO. These are bug fixes, not toggles. Old behaviour was insecure.
- Method-level annotations on `subscribe()` (e.g., `@PreAuthorize`) — Claude's discretion; current code is filter-driven, keep that pattern.
- Whether to add a `processed_stripe_events.processed_at` index — yes if we'll prune; defer pruning to a separate housekeeping phase.

</decisions>

<specifics>
## Specific Ideas

- The `INSERT ... ON CONFLICT DO NOTHING RETURNING event_id` pattern returns 0 rows on conflict — that's the duplicate signal. Some teams use a separate `SELECT` first; the audit explicitly chose the atomic INSERT path (TOCTOU-safe under concurrent webhook delivery from Stripe's edge).
- Don't try to attach tenant filter at the SSE controller level via `@PreAuthorize` — that runs after the request enters Spring but the broadcast happens off-request on a worker thread where SecurityContext isn't propagated. Filtering inside `OrderSseService` is correct.
- The `_aud` tables are written by Hibernate Envers automatically — don't try to add INSERT policies that require app context, just FORCE existing ones. Envers writes happen inside the same transaction as the parent entity write, so RLS context is already set.
- `current_setting('app.customer_email', true)` returns NULL when unset — the new `EXISTS` clause in `reviews_tenant_write` short-circuits to false in that case, which is the desired behaviour (storefront-only path).

</specifics>
