# Phase 16.1 Plan 04: Stripe Webhook Idempotency (AUDIT-W0-03) Summary

**TOCTOU-safe `INSERT ... ON CONFLICT DO NOTHING` guard at the top of `PaymentService.handleWebhookEvent` ensures Stripe webhook retries fire side effects exactly once. Backed by V35's `processed_stripe_events` table and a Testcontainers regression that proves duplicate `event.id` delivery yields exactly one `financial_transactions` row, one `publishStateChange` call, and one `publishSucceeded` call.**

## Accomplishments

- AUDIT-W0-03 closed at the application layer. Today every retry of `payment_intent.succeeded` re-runs `handlePaymentIntentSucceeded`, which double-writes `financial_transactions`, double-publishes the order state-change event, and double-fires the payment-succeeded event. Stripe retries successful webhooks if our handler is slow or returns 5xx, and retries failed webhooks for up to 72h, so this was a routine production-path data-integrity bug. The guard now short-circuits duplicates at the top of the method.
- TOCTOU-safe path chosen over the JPA `existsByEventId` + `saveAndFlush` pattern proposed in `docs/audit/remediation/01-backend-remediation.md` Finding 2. A single `INSERT ... ON CONFLICT DO NOTHING` statement is atomic in Postgres so concurrent webhook deliveries from Stripe's edge cannot both think they are "first" — the SELECT-then-INSERT JPA pattern has a race window between the existence check and the save.
- `JdbcTemplate` is constructor-injected (canonical pattern at `DatabaseConfigurationValidator.java:35,44`); no new entity / repository class introduced, matching the LOCKED CONTEXT decision (16.1-CONTEXT.md `<decisions>` Item 3).
- 3-test Testcontainers regression covering: load-bearing duplicate (proves exactly-once semantics), single-delivery sanity (proves the guard runs and inserts on first delivery), and distinct-event-id negative control (proves the guard is keyed on `event.id` and does not over-block).
- All 7 existing `PaymentServiceTest` unit tests continue to pass after the constructor change. Total payment-package test count after this plan: **24 tests, 24 passing** (7 PaymentServiceTest + 4 PaymentControllerTest + 3 PaymentEventPublisherTest + 4 PaymentEventOutboxFlusherTest + 3 StripePropertiesRedactionTest + **3 new StripeWebhookIdempotencyIntegrationTest**).

## Decisions Made

- **Transaction shape: in-transaction, NOT REQUIRES_NEW.** 16.1-CONTEXT.md Item 3 LOCKED both shapes as acceptable. The in-transaction shape gives the desired retry semantic: if downstream processing throws, the dedup row rolls back and Stripe's next retry will succeed cleanly. The REQUIRES_NEW alternative would keep the dedup row on rollback (so we always return 2xx to Stripe), but that requires a separate reconciliation path for events whose downstream processing failed — out of scope for Wave 0. Documented in code comment at PaymentService.java line ~135.
- **JdbcTemplate, not a new JPA entity/repo.** LOCKED CONTEXT path. The remediation doc proposed a `ProcessedStripeEvent` entity + repository with `existsByEventId` + `saveAndFlush`; we deviated to keep the guard a single atomic SQL statement (TOCTOU-safe under concurrent delivery) and to avoid JPA second-level cache surprises.
- **Existing PaymentServiceTest reconciled with `Mockito.lenient()`.** The unit tests don't run against Postgres, so the new `JdbcTemplate` dependency must be mocked. Using `lenient()` with broad matchers (`anyString()`, `any()`) returning `1` lets every existing test model the "first delivery, proceed" path without per-test stub setup. Strict-mode behaviour assertions on the `update(...)` call are deferred to the integration test where the real DB does the work.

**1. [Rule 3 - Blocking] H2 default in src/test/resources/application-test.yml**
- **Found during:** Task 2 first integration-test run
- **Issue:** Initial `@DynamicPropertySource` only set `spring.datasource.{url,username,password}` and `spring.flyway.enabled=true`, intending to use Postgres. But `src/test/resources/application-test.yml` (which I had not realised existed — distinct from `src/main/resources/application-test.yml`) hard-sets `driver-class-name: org.h2.Driver` and `database-platform: org.hibernate.dialect.H2Dialect`. Result: Spring booted Hikari with the H2 driver pointing at the postgres URL — `Driver org.h2.Driver claims to not accept jdbcUrl, jdbc:postgresql://...`.
- **Fix:** Added explicit overrides for `spring.datasource.driver-class-name`, `spring.jpa.database-platform`, `spring.jpa.properties.hibernate.dialect`, plus RabbitMQ stubs. Mirrors the working pattern from `CrossTenantSpoofIntegrationTest`.
- **Files modified:** `core-java/src/test/java/uk/jtoye/core/payment/StripeWebhookIdempotencyIntegrationTest.java`
- **Commit:** `5967a40`

## Deferred Issues

**Schema drift: order_items_aud missing product_name column**
- **Symptom:** `Schema-validation: missing column [product_name] in table [order_items_aud]` when running any `@SpringBootTest` with `spring.jpa.hibernate.ddl-auto=validate` against Testcontainers Postgres.
- **Cause:** V30 (`V30__order_item_product_name.sql`) added `product_name` to `order_items` but did NOT add the matching column to `order_items_aud`. Hibernate Envers expects the audit table to mirror the entity's audited columns.
- **Why deferred:** Out of scope for Plan 16.1-04 (AUDIT-W0-03 scope). This is a pre-existing latent issue in the migration history. Tests that use `ddl-auto: create-drop` (the project default in test profile) do not surface it because Hibernate rebuilds the schema from the JPA model on boot.
- **Recommended next action:** Add a small Flyway migration (V36 or later) that runs `ALTER TABLE order_items_aud ADD COLUMN IF NOT EXISTS product_name VARCHAR(255)`. Should ship in a follow-up `/gsd-quick` or be folded into Phase 17's prep.
