# Backend / Distributed Systems Audit
**Auditor persona**: Senior backend engineer, 15y multi-tenant SaaS
**Date**: 2026-04-27
**Verdict score**: 6.5/10 — solid bones, several real distributed-systems bugs that will bite under load

The team clearly knows the tropes — they have RLS, JWT-derived tenancy, a transactional outbox, optimistic locking, an SSE/STOMP split, Resilience4j, Bucket4j on Redis. The execution is uneven. The two showstoppers are the unscoped order SSE broadcast (real cross-tenant data leak in production) and the missing Stripe webhook idempotency (real money/state bugs on Stripe retries). Neither is hypothetical — both will fire the first time a second tenant subscribes or Stripe retries a successful payment.

## Top 5 Strengths
1. **Stock decrement is genuinely well thought out** — `core-java/src/main/java/uk/jtoye/core/order/StockService.java:68-110` uses `@Retryable` on `ObjectOptimisticLockingFailureException` with `Propagation.REQUIRES_NEW`, and the comments at lines 75-83 correctly explain *why* the new transaction boundary is required for the AOP retry to see the commit-time exception. That's a senior-engineer trap caught proactively.
2. **Transactional outbox for payment events** — `payment/PaymentEventPublisher.java:64-88` + `PaymentEventOutboxFlusher.java:69-93` survives a RabbitMQ outage by writing to `payment_event_outbox` in the webhook transaction, with per-tenant flush iteration to keep RLS satisfied (V31 + V33). This is the right pattern; many teams skip it.
3. **Optimistic locking on Order** — `order/Order.java:113-115` (`@Version`) plus the in-memory mutate-then-save ordering in `OrderService.transitionOrder` (lines 309-340) means concurrent state transitions collide cleanly instead of last-writer-wins.
4. **Tenant-aware cache key generator fails closed** — `config/TenantAwareCacheKeyGenerator.java:36-38` throws on missing TenantContext rather than collapsing to a shared "no-tenant" key. The comment block at 23-29 explicitly calls out the cross-tenant cache hit it prevents. Correct decision.
5. **STOMP channel interceptor enforces tenant on subscribe** — `websocket/TenantChannelInterceptor.java:110-140` parses the destination, requires a tenant segment, and rejects cross-tenant subscriptions with `MessageDeliveryException`. Combined with `afterMessageHandled` clearing TenantContext on the same thread (line 67-71, `ExecutorChannelInterceptor` contract), this is a model implementation.

## Top 5 Concerns (severity-classified)

1. **[CRITICAL] OrderSseService broadcasts every order state change to every connected SSE client across all tenants** — evidence: `core-java/src/main/java/uk/jtoye/core/order/OrderSseService.java:17,29-40`; `OrderController.java:43-47` (subscribe is unfiltered). The `emitters` list is a single global `CopyOnWriteArrayList<SseEmitter>`, and `broadcast()` writes the event (which contains `tenantId`, `orderNumber`, `previousStatus`, `newStatus`) to **every** emitter. — why it matters: This is a live multi-tenant data leak. Tenant B's dashboard subscribed to `/orders/stream` will receive Tenant A's order state changes, leaking order numbers, IDs, and tenant IDs. The STOMP path (`OrderStateChangeListener.java:51-58`) was correctly tenant-segmented to `/topic/kitchen/{tenantId}/{shopId}` — the SSE path was not. — fix sketch: replace the single list with `Map<UUID, List<SseEmitter>>` keyed by `TenantContext.get()` captured at subscribe time; in `broadcast(event)`, iterate only `emitters.get(event.tenantId())`. Add a regression test that subscribes from two tenants and asserts isolation.

2. **[CRITICAL] Stripe webhook handler has no idempotency guard** — evidence: `payment/PaymentService.java:113-132` (`handleWebhookEvent`) processes every Stripe `Event` it receives without recording `event.getId()` or checking it against a processed-events table; the only idempotency in the system is `Order.idempotencyKey` (V24) which guards the *customer's* guest-order POST, not the webhook. `handlePaymentIntentSucceeded` (lines 134-199) unconditionally sets order status, calls `eventPublisher.publishStateChange`, calls `paymentEventPublisher.publishSucceeded`, and **calls `financialTransactionService.createTransaction`** — every one of these will be re-executed when Stripe retries the webhook (Stripe retries successful webhooks if the response is slow or 5xx, and retries up to 72h on failure). — why it matters: Duplicate `financial_transactions` rows = wrong VAT, wrong revenue reporting, customer double-charged in the books even though only one capture happened. Duplicate `OrderStateChangeEvent` published = duplicate emails to the customer, double-decrement on any future workflow step. — fix sketch: add a `stripe_processed_events(event_id PRIMARY KEY, processed_at, ...)` table, and at the top of `handleWebhookEvent` do `INSERT ... ON CONFLICT DO NOTHING RETURNING id` — if no row returned, log and exit. Or use `event.getIdempotencyKey()` against an outbox-style processed-events table.

3. **[HIGH] `@Async` email path runs on the unbounded SimpleAsyncTaskExecutor and has no TenantContext propagation** — evidence: `CoreApplication.java:12` enables `@EnableAsync` but no `AsyncConfigurer` or custom `TaskExecutor` bean exists anywhere (`grep -rn "TaskExecutor\|ThreadPoolTaskExecutor"` returns nothing in main). All six `@Async` methods in `notification/EmailNotificationService.java:35,49,63,77,91,105` therefore run on `SimpleAsyncTaskExecutor` which spawns a new thread per call with no upper bound. Additionally, no `TaskDecorator` propagates `TenantContext` (`grep -rn "TaskDecorator"` returns nothing) so any `@Async` method that touched a tenant-scoped repository would silently bypass RLS. — why it matters: Under email burst (cancellation storm, daily summary blast), JVM thread count goes unbounded → OOM. The only thing saving you today is that `EmailNotificationService` doesn't touch the DB; the moment someone adds a repo call to an `@Async` method, you have a stealth tenant-leak. — fix sketch: register `@Bean public TaskExecutor taskExecutor()` returning a bounded `ThreadPoolTaskExecutor` (core=4, max=16, queue=200, rejection=CALLER_RUNS) and wire a `TaskDecorator` that snapshots `TenantContext.get()` and re-applies + clears around each task.

4. **[HIGH] Two filters racing to clear TenantContext, one runs *before* authentication** — evidence: `security/TenantFilter.java:13` is registered as `@Component` (so Boot auto-registers it as a global servlet filter), but `SecurityConfig.java:96` *also* injects it into the security chain via `addFilterBefore(tenantFilter, UsernamePasswordAuthenticationFilter.class)`. Both registrations apply. `TenantFilter`'s `finally { TenantContext.clear(); }` (line 33) thus fires twice per request, and the first invocation runs *before* `JwtTenantFilter` (which runs `@Order(200)` after Spring Security). Add `TenantContextCleanupFilter` (`Ordered.HIGHEST_PRECEDENCE`) which also clears in finally — that's three clears per request. — why it matters: It works today by accident: `TenantContext.clear()` on an already-clear ThreadLocal is a no-op, and JWT-derived tenants get set late enough that the early `TenantFilter.clear()` doesn't see them. But a future maintainer adding any logic that reads TenantContext between `TenantFilter` and `JwtTenantFilter` will see an unexpected null. The filter ordering is fragile and undocumented. — fix sketch: pick one — either remove `@Component` from `TenantFilter` and rely solely on the explicit `addFilterBefore`, or stop adding it explicitly and let Spring Boot auto-registration handle it. Delete the redundant `clear()` in `TenantFilter.finally` since `TenantContextCleanupFilter` (HIGHEST_PRECEDENCE = outermost = last to finally) already owns cleanup.

5. **[HIGH] OrderStateMachineService spins up a new StateMachine per call with `Mono.block()` everywhere on a servlet thread** — evidence: `order/OrderStateMachineService.java:45-90`. Every state transition: `stateMachineFactory.getStateMachine(UUID.randomUUID())` (line 49 — random ID, no caching), `stopReactively().block()` (×2), `resetStateMachineReactively().block()`, `startReactively().block()`, `sendEvent(...).blockLast()`. That's five reactor blocks on Tomcat threads per transition. Plus the state machine is stateless by design (state lives in `Order.status`) so the entire dance produces the same answer as a static `EnumMap<OrderStatus, EnumSet<OrderEvent>>` table lookup would. — why it matters: Spring StateMachine is heavy — each `getStateMachine()` allocates a full reactor pipeline. Under transition load (KDS clicking through orders rapidly) you'll see GC pressure, thread starvation, and unexplained latency. You're paying the cost of a stateful framework while not using its statefulness. — fix sketch: replace with a hand-rolled transition table (`Map<OrderStatus, Map<OrderEvent, OrderStatus>>`) populated once at startup. ~30 lines, no reactor, no AOP, fully testable. Keep `InvalidStateTransitionException` contract identical so callers don't change.

## Detailed findings by area

### Architecture
Package layout is feature-sliced (`order/`, `shop/`, `payment/`, `storefront/`) which is the right call for a domain like this — easier than the layered-by-tech alternative. Service classes are mostly the right size: `OrderService` is 412 lines but reads cleanly; `PublicStorefrontService` (637 lines) is starting to bloat — `getShopConfig`, `getCustomerOrders`, `trackOrder`, `createGuestOrder` all live in one class and `createGuestOrder` alone is 170 lines. Controllers correctly delegate (`OrderController` is pure routing). Domain model is anemic in the Fowler sense — entities like `Order` are JPA bags of getters/setters with one helper (`calculateTotal()` line 133) — but for a CRUD-heavy SaaS this is pragmatic. Avoid the urge to "fix" it.

`PublicStorefrontService.resolvePublicShopForSlug` and `ReviewService.resolvePublicShopForSlug` are duplicated (the latter's javadoc at lines 105-119 explicitly says so and defers consolidation to "third consumer"). Fine for now, but the third consumer is coming — promotions and announcements public endpoints already exist.

### Multi-tenancy
The three-layer defense (RLS → `JwtTenantFilter` → `TenantContext`) is the right architecture. `TenantSetLocalAspect.java:27-55` correctly uses `set_config('app.current_tenant_id', ?, true)` (transaction-scoped) via `PreparedStatement` — defense-in-depth against SQL injection on a value that's already validated. The `@Before` advice on `Repository+` methods (line 43) catches the case where TenantContext is set inside a `@Transactional` method body after the transaction has already begun.

Background paths handle TenantContext correctly per-iteration: `ScheduledCleanupService.java:58-71` and `PaymentEventOutboxFlusher.java:77-92` both `set` then `clear` in a try/finally inside the per-tenant loop. `OrderStateChangeListener.java:64-77` does the same for the RabbitMQ consumer side.

The major gap is async paths (see HIGH #3 above) — `@Async` methods don't propagate TenantContext via TaskDecorator. Today only email runs async and email doesn't query the DB, so it's accidentally safe. This is a one-PR landmine.

### State machine
Works correctly for happy path (verified via `OrderStateMachineConfig.java:38-114`). Cancel transitions explicitly enumerated from every non-terminal state — good, no implicit "any" wildcard. End states (COMPLETED, CANCELLED) are marked `.end()` so the machine refuses further transitions.

Concurrency safety on transitions relies entirely on `@Version` (`Order.java:113-115`). Two operators clicking "Confirm" at the same millisecond → second one gets `ObjectOptimisticLockingFailureException` from `orderRepository.save(order)` at `OrderService.java:340`. There's no `@Recover` for this on `transitionOrder` (only on `StockService.decrementForOrder`), so the second operator gets a 500 from `GlobalExceptionHandler.handleGenericException` rather than a clean 409. Recommend: catch `ObjectOptimisticLockingFailureException` in `transitionOrder`, map to 409 Conflict with a "retry" body. The implementation cost of `StateMachineService` itself is real (HIGH #5) — but functional correctness is OK.

### API design
RFC 7807 ProblemDetail is in use (`common/GlobalExceptionHandler.java:31-133`) — every handler builds a `ProblemDetail` with title, type URI, and status. This is the modern Spring 6 idiom and well done.

**No API versioning at all.** Every `@RequestMapping` (verified: `/orders`, `/shops`, `/products`, `/customers`, `/payments`, etc.) is unversioned. The CLAUDE.md mentions "API versioning" as a Milestone 2 deliverable; the code doesn't reflect it. When you have to break the order DTO shape (e.g., to add multi-currency), you'll have no path forward except big-bang.

Idempotency: only the guest order POST has it (`PublicStorefrontService.java:326-348`, `Order.idempotencyKey` field). The Stripe webhook does not (CRITICAL #2). `POST /orders` (the authenticated path in `OrderController.createOrder`) does not — duplicate browser POSTs from a slow network create duplicate orders.

### Concurrency
- `@EnableAsync` declared with no executor bean → unbounded SimpleAsyncTaskExecutor (HIGH #3).
- `@EnableScheduling` is fine; only two scheduled jobs and they're correctly transactional + per-tenant.
- SSE: `OrderSseService` uses `CopyOnWriteArrayList` for thread safety on the emitter list, which is correct for read-heavy / rare-write — but writes happen on every state change, and on every subscribe/unsubscribe. Under heavy load, CopyOnWrite gets expensive (full array copy per mutation). Use a `ConcurrentHashMap<UUID, Set<SseEmitter>>` (one CHM per tenant) when you fix CRITICAL #1.
- No back-pressure on SSE: `broadcast()` (line 31) iterates synchronously on the event-publisher thread (the RabbitMQ consumer thread, since it's called from `OrderStateChangeListener`). One slow client (network stalled) blocks the consumer for that emitter's send timeout. Wrap each `emitter.send(...)` in a per-emitter executor or use `ResponseBodyEmitter` async dispatch.

### Caching
The team **already lived through** the cross-tenant cache leak — comments in `ShopService.java:42-44`, `ProductService.java:51-55`, and `TenantCacheEvictor.java:18-21` all reference past `@CacheEvict(allEntries=true)` incidents. `TenantCacheEvictor` is a clean fix.

But `BulkImportService.java:55,110` and `SyncService.java:41-44` **still use `@CacheEvict(allEntries=true)`** — these are exactly the methods the rest of the codebase abandoned. A bulk CSV import by Tenant A invalidates Tenant B's product cache. Same bug, just hiding in the bulk-import surface area. Fix: replace with `cacheEvictor.evictAllForMethod("products", "getProductById")` once that method is implemented, or just iterate and evict each created entity's key.

TTLs are set (10min products, 15min shops in `CacheConfig.java:59-62`). `disableCachingNullValues()` is set (line 53) — good, prevents negative-cache poisoning. `@Cacheable(unless = "#result == null")` is consistent with that.

### Resilience
`@CircuitBreaker(name = "stripe")` on `PaymentService.createPaymentIntent` (line 84) — but **no `fallbackMethod`** declared. When the breaker opens, the call throws `CallNotPermittedException` which falls through to the generic 500 handler. The user-facing error message becomes "An unexpected error occurred". For a payment intent failure you want to return a 503 with a "try again in 30 seconds" message. AI service does this correctly: `ai/ImageAnalysisService.java:128-129` declares both `@CircuitBreaker(fallbackMethod="analyzeFallback")` and `@Retry(name = "ai")`. Mirror that pattern for Stripe.

No retry on Stripe failure — the breaker config in `application.yml:181-201` lists `email` and `ai` retry instances but no `stripe` instance. Stripe's API is generally reliable but transient 5xx happen; one retry with 1s backoff would be a cheap win.

RabbitMQ retry/DLQ topology is correct (`RabbitMQConfig.java:61-129`): topic exchange + DLX + 3 retries via `RetryOperationsInterceptor`, `defaultRequeueRejected=false` so failed messages route to DLQ instead of looping. JWT decoder timeouts are explicitly set (`SecurityConfig.java:34-50`) at 5s connect / 5s read — many teams forget this and hang on Keycloak slowness.

### Code quality
- **Lombok usage is minimal** — only `SyncController`, `SyncService`, and the two sync DTOs use `@RequiredArgsConstructor` / `@Builder` (4 files total). No `@Data` abuse anywhere. Most entities have hand-written getters/setters which is verbose but explicit. Fine.
- **`@Transactional` coverage is appropriate.** Services without `@Transactional` are correctly so: `OrderSseService`, `OrderStateMachineService`, `ImageAnalysisService`, `EmailNotificationService`, `BusinessMetricsService`, `StorageService` — none of these touch JPA in a way that needs transactional boundaries.
- **One swallowed exception worth flagging**: `BulkImportService.java:197-199` catches `Exception` in `parseCsv` and only logs — a malformed CSV silently produces an empty result. The caller (`importFromCsv` line 63) treats empty rows as "OK no work to do" and returns success. A user uploading a corrupt CSV gets a 200 with `totalRows: 0`. Should propagate as a 400.
- **`OrderEventPublisher.java:38-41`** swallows AMQP exceptions on `convertAndSend`. Fine for the order-events path because the operational impact is "no email" (low blast radius), but inconsistent with the payment side which moved to the outbox pattern. Either move order events to an outbox too, or document why the asymmetry is acceptable.
- **One nitpick:** `OrderService.java:399-410` and `PublicStorefrontService.java:526-531` duplicate `generateOrderNumber`. Pull into a small `OrderNumberGenerator` component.

## Concrete recommendations (prioritized)
1. **Fix the SSE tenant leak** (CRITICAL #1) — top of the list. Two-line data structure change + a regression test. Estimated 1 hour. Until this is fixed, do not market the dashboard as multi-tenant safe.
2. **Add Stripe webhook idempotency** (CRITICAL #2) — `stripe_processed_events` table + `INSERT ... ON CONFLICT DO NOTHING` guard at the top of `handleWebhookEvent`. Estimated 2 hours including a test that double-delivers an event and asserts single side-effects.
3. **Configure a bounded `TaskExecutor` + `TaskDecorator`** for `@EnableAsync` (HIGH #3). Estimated 2 hours. Add at least one `@Async` integration test that asserts TenantContext propagation.
4. **De-duplicate filter registration** (HIGH #4) — remove `@Component` from `TenantFilter` since it's explicitly added in `SecurityConfig`. 5 minutes.
5. **Replace Spring StateMachine with a transition map** (HIGH #5) — eliminates 5 `Mono.block()` calls per transition. ~2 hours including porting tests.
6. **Add `fallbackMethod` to `@CircuitBreaker(name="stripe")`** + define the `stripe` retry instance in `application.yml`. 30 minutes.
7. **Fix the `@CacheEvict(allEntries=true)` regressions** in `BulkImportService` and `SyncService`. 30 minutes.
8. **Add API versioning** (`/v1/...` URI prefix is the cheapest option). Without it, your first breaking-change is a customer outage. 4 hours including updating frontend + edge.
9. **Map `ObjectOptimisticLockingFailureException` to 409** in `GlobalExceptionHandler` so optimistic-lock collisions on order transitions return a clean retry signal instead of 500.
10. **Add idempotency to authenticated `POST /orders`** (mirror the guest path). Customers double-clicking "place order" should not create duplicate orders.

## What I would do first if I owned this codebase
Fix the two CRITICAL items the same afternoon and ship them — both are small diffs with high blast radius. Then I'd write one E2E test that opens two SSE streams as two tenants, transitions an order in tenant A, and asserts tenant B sees nothing — and a second test that double-delivers a `payment_intent.succeeded` webhook and asserts exactly one financial transaction row. Those two tests pin the worst behaviors permanently. Then in the same week I'd configure the bounded TaskExecutor + TaskDecorator before someone adds a tenant-scoped repository call to an `@Async` method. Everything else is improvement; those four items are "stop the bleed".
